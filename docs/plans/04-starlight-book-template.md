# 4. 학습 콘텐츠 품질 정비와 Starlight 템플릿 분리

상태: 진행 중
지금 위치: M01~M05 완료 · 원본 품질 조건 충족 · 다음 M06 이관표 확정 후 M07 독립 저장소 생성
실행 범위: 전체 완료. M01~M10을 의존 순서대로 수행하고 주요 마일스톤에서 로컬 커밋한다.
푸시·원격 저장소 생성·배포는 하지 않는다. 템플릿 생성은 M05 충족 뒤에만 진행한다.

[계획 관리 규칙](README.md)을 따른다. 후속 실행 시 최신 사용자 요청에 맞춰 실행 범위를 갱신한다.

## 목표와 완료 조건

동료가 `../starlight-book-template`을 출발점으로 자신의 학습 자료를 축적하고, AI에 작성을 맡겨도
개념을 이해하고 적용하는 데 도움이 되는 덱을 얻도록 한다. 원본의 작성 지침과 `coding-agents`·
`starlight` 덱을 먼저 정비하고, 그 결과가 검증된 다음 독립된 로컬 템플릿 저장소를 만든다.

- [x] `AGENTS.md`는 작업 진입점과 핵심 행동 규칙을 안내하고, 상세 학습 품질 기준은 작성 지침에 있다.
- [x] 두 덱의 모든 페이지를 정확성·설명·예제·구조·이식성 관점에서 검토하고 수정 근거를 기록했다.
- [x] 두 덱의 제목·파일명·URL·구성도는 번호 없는 개념·작업 이름을 사용하고, 원본의 옛 URL·주요 절 링크를 보존한다.
- [ ] 원본에서 M05의 품질 완료 조건을 충족한 뒤에만 템플릿 폴더를 만든다.
- [ ] 새 저장소는 기본 학습 덱 두 개와 공용 기반만 포함하며, 원본 폴더·Git 이력·개인 설정 없이 동작한다.
- [ ] 동료가 README만으로 환경 준비 → 실행 → 개인화 → 첫 덱 작성 → 검증을 진행할 수 있다.
- [ ] 새 환경에서 설치·검사가 통과하고, AI로 작은 덱을 만드는 대표 작업에서 품질 기준을 적용한 결과가 있다.
- [ ] 두 저장소의 결과·검증·제한·영구 문서 위치가 기록되어 있다. 원격 공개는 별도 범위다.

## 범위와 입력

### 작업 범위

원본에서는 공통 지침, 두 덱, 이름 변경에 따른 참조·호환 경로를 정비한다. 다른 덱은 두 덱으로
들어오는 링크 수정처럼 이번 변경에 필요한 부분만 고친다. 원본의 도메인·배포 대상은 유지한다.

템플릿에서는 사이트 기반과 검토된 두 덱을 복사하고, 개인화·시작 안내·검증 체계를 정리한다.
원본에서 모든 개인 사례를 지우거나 전체 사이트를 범용 프레임워크로 만드는 작업은 하지 않는다.
템플릿용 차이는 이관표에 남기고, 추출 뒤 두 덱을 템플릿의 실제 파일·설정과 다시 대조한다.

이번 계획에 포함하지 않는 것은 다른 덱 전면 개편, 전체 의존성 업그레이드, UI 재설계, 범용 덱 생성기,
자동 동기화 도구, 다국어화, 실제 호스팅 배포다. 커밋·푸시·원격 저장소 생성·GitHub Template 설정은
사용자가 요청한 때 수행한다. 후속 전체 구현 요청은 로컬 폴더 생성과 `git init -b main`까지 포함한다.

## 학습 품질 기준

목표는 컴포넌트와 체크리스트가 채워진 문서가 아니라, 독자가 **왜 필요한지 설명하고 작은 문제에
적용할 수 있는 문서**다. 다음 기준을 M02에서 영구 지침에 반영하고 두 덱의 리뷰에 실제로 사용한다.

| 관점 | 읽는 사람이 얻어야 할 것 | 검토 근거 |
|---|---|---|
| 독자·범위 | 필요한 사전 지식과 읽은 뒤 할 수 있는 일을 안다 | baseline·index에 독자, 선행 지식, 학습 결과, 범위 밖 주제가 맞물린다 |
| 개념 설명 | 문제·원리·해결 방법을 자기 말로 연결한다 | 결론만 선언하지 않고 왜 그렇게 동작하는지 예제나 흐름으로 설명한다 |
| 인지 부담 | 필요한 용어를 필요한 시점에 배운다 | 한 페이지의 중심 질문이 명확하고, 핵심 이해를 선택 심화에 의존시키지 않는다 |
| 적용 | 설명을 따라 작은 작업을 하고 결과를 판단한다 | 필요한 입력·파일·명령과 예상 결과가 있다. 바꾸는 실습에는 복구 방법도 있다 |
| 구분과 오해 | 비슷한 개념의 차이와 적용 조건을 안다 | 자주 생기는 오해를 구체적 사례로 바로잡고, 권장안을 제품의 보장으로 단정하지 않는다 |
| 시각 자료 | 관계·순서·경계를 더 쉽게 이해한다 | 본문과 그림의 용어가 일치하고 독자가 볼 지점을 짚는다. 장식용 그림을 요구하지 않는다 |
| 정확성과 현재성 | 사실·운영 선택·예시·미검증을 구분한다 | 핵심 주장 가까이에 공식 근거가 있고, 명령·코드·경로는 해당 버전과 실물에 맞는다 |
| 재방문 | 검색으로 도착해도 문맥과 다음 행동을 안다 | 제목·description·선행 개념 링크가 유효하고, 요약이 판단 기준을 남긴다 |
| 이해 확인 | 외운 문장 없이 개념을 설명하거나 적용한다 | 적합한 학습 페이지에 짧은 질문·변형 과제와 답의 근거 또는 관찰 기준이 있다 |

모든 페이지에 같은 절 개수·분량·퀴즈를 강요하지 않는다. 개념 설명, 따라 하는 실습, 비교·참조 페이지는
필요한 구성이 다르다. `<Thesis>`·`<TermIntro>`의 존재와 `pnpm check` 통과는 형식·기술 검증이며,
설명의 정확성이나 학습 효과를 대신하지 않는다. 실제 학습 효과가 입증됐다고 과장하지 않는다.

리뷰 기록은 이 계획에 페이지별로 `중심 질문 / 문제 / 수정 또는 유지 이유 / 근거·실행 결과 / 남은 제한`을
남긴다. 분할하면 이전 페이지와 새 페이지의 대응을 기록한다. 단순히 “리뷰 완료”나 점수만 적지 않는다.
핵심 설명의 오류, 빠진 선행 개념, 따라 할 수 없는 주요 예제는 완료 전에 해결한다.

### M01 — 전체 리뷰 목록과 학습 경로 설계

두 덱의 index·본문·baseline·`_deck.mjs`를 전부 읽고 현재 페이지별 검토 행을 만든다.
사전 조사에서 읽은 일부 본문과 제목 목록을 전체 리뷰로 취급하지 않는다.

1. 독자를 “Git과 기본 명령 실행은 가능하지만 이 사이트 구조는 처음인 동료”로 잡는다.
   기본 독자 가정이 맞지 않는 요구가 들어오면 필요한 준비 안내만 조정한다.
2. Starlight는 실행·첫 페이지·새 덱·품질 검토로 이어지는 읽기 경로와 구조·확장의 참조 경로를 정한다.
   Coding Agents는 단일 저장소의 지침·요청·검증·재개부터 설명하고 monorepo 등은 심화로 둔다.
3. 분할 후보를 질문 단위로 정한다. Coding Agents의 지침 설계, 도구별 탐색, 작업 계획,
   실행·검증·재개를 각각 독립해서 읽을 필요가 있는지 판단한다. 목표 페이지 수는 먼저 고정하지 않는다.
4. 번호 없는 새 slug, 옛 URL·앵커, 들어오는 본문·지침·계획 링크를 대응시킨다.
   특히 이 저장소의 `docs/plans/README.md`가 Coding Agents 본문을 참조한다는 점을 포함한다.
5. 핵심 사실의 공식 확인 대상과 직접 실행할 예제를 고른다. 접근할 수 없는 자료는 미확인으로 기록한다.

### M02 — AI가 따를 작성·리뷰 계약 정비

`AGENTS.md`에는 독자 우선, 수정 전 정본 확인, 근거 확인, 작성 후 의미 검토, 필요한 검증과 종료 조건처럼
매 작업에 필요한 행동만 둔다. 긴 품질 표·예시·작성 순서는 `docs/content-authoring.md`가 소유한다.
`CLAUDE.md`는 공유 정본을 가져오는 얇은 어댑터를 유지한다.

- 작성 흐름을 독자·질문·범위 확인 → 근거와 예제 확인 → 학습 순서 구성 → 작성 → 의미 리뷰 → 기술 검증으로 정리한다.
- 새 덱의 baseline에는 기준 버전 외에 독자·선행 지식·학습 결과·범위를 짧게 담도록 한다.
  기존 모든 덱에 새 필드를 일괄 강제하는 스키마 변경은 하지 않는다.
- 개념·실습·참조 문서의 좋은 예를 짧게 제시하고, 문장만 매끄럽게 다듬는 리뷰와 내용 검토를 구분한다.
- 질문과 답의 연결, 최소 예제의 예상 결과, 흔한 오해, 불필요한 전문 용어와 반복 제거를 리뷰 행동으로 쓴다.
- 실제로 확인한 주장에만 검토 날짜를 반영한다. 검증 명령을 적은 것과 실행한 것을 구분한다.
- 분량·표·D2 개수로 품질을 점수화하거나 매번 외부 심사·재승인을 요구하지 않는다.
  자동 검사는 기존 도구를 우선하고, 새 규칙은 반복되는 객관적 오류를 잡을 필요가 있을 때만 추가한다.

컨텍스트와 재개, 권한·검증, 계획 문서 관련 주장은 제품별로 확인한다. 도구 접근이 없어 실행하지
못한 항목을 실측했다고 쓰지 않는다. 핵심 경로는 독자가 사용할 수 있을 만큼 근거가 있어야 한다.

  원본 개발 프로세스 설명에서 학습 자료 작성에도 적용되는 원리가 드러나게 한다.

6. 템플릿에서 설치와 `pnpm check`를 실행한다. 이식을 위해 원본 검사의 강도를 낮추지 않는다.

### M09 — 새 환경과 대표 학습 작업 검증

원본 `node_modules`·캐시·개인 설정을 물려받지 않은 템플릿에서 README 순서대로
`pnpm install --frozen-lockfile`과 `pnpm check`를 확인한다. 실제 사용한 OS·아키텍처·버전을 기록하며
로컬 성공을 다른 OS나 원격 CI의 실행 성공으로 확대하지 않는다.

최종 지침으로 작은 임시 덱을 하나 작성하는 시나리오를 수행한다. 공통 파일, 두 덱의 예시와
“독자·주제·학습 결과” 요청만으로 baseline·metadata·index·개념/적용 본문을 만들고 다음을 확인한다.

- 작성자가 별도의 구두 설명 없이 필요한 정본·구조·명령을 찾을 수 있는가.
- 핵심 질문에 답하는 설명, 실행 가능한 예제와 예상 결과, 적절한 이해 확인이 있는가.
- 자동 등록·검사와 작성 지침이 실제 작업을 지원하며 불필요한 반복이나 중단을 만들지 않는가.

이것은 작성 흐름의 표본 검증이며 독립 학습자 실험으로 보고하지 않는다. 문제를 발견하면 지침이나
예제를 수정하고 영향을 받은 부분만 재확인한다. 임시 덱은 최종 배포본에서 제거하고, 기본 덱이 정확히
두 개인 최종 상태에서 `pnpm check`를 실행한다. 제거가 결과를 바꾸므로 이 최종 검사는 생략하지 않는다.

## 검증 범위

- 최초 조사·계획 작성에서는 diff·참조 경로만 확인했다. 현재 전체 실행에서는 아래 변경별 검증을 수행한다.
- 지침 문서만 바꾸는 M02는 같은 기준을 쓴다. 의미 리뷰는 바뀐 규칙과 예제를 대조해 수행한다.
- 콘텐츠·코드·설정 변경은 한 실행 묶음을 마칠 때 해당 저장소에서 `pnpm check`를 한 번 실행한다.
  앞선 결과에 영향을 주는 변경이 없다면 마감용으로 반복하지 않는다.
- 새 D2·변경한 배치는 정적 렌더로 확인한다. 클라이언트 리다이렉트나 UI 동작을 바꿨을 때만
  구체적 확인 항목을 정해 대표 페이지 1~2개에서 브라우저로 확인한다. 두 덱 전체를 순회하지 않는다.
- 새 저장소에서는 Git 이력 없음, 다른 덱 링크·미사용 tag, 개인 도메인·계정·경로 잔류를 확인한다.
  원저작자 출처처럼 의도적으로 남긴 참조와 실수로 남긴 배포·운영 설정을 구분한다.

  관련 완료 조건을 충족했다고 표시하지 않는다.

### 이름과 호환 경로

Starlight는 `00-intro→intro`, `01-landscape→landscape`, `02-astro→astro`,
`03-starlight→structure`, `04-mdx→mdx`, `05-components→components`, `06-custom→custom`,
`07-writing→writing`, `08-pipeline→pipeline`, `09-wrapup→wrapup`으로 옮긴다.
Coding Agents는 `00-project-instructions→project-instructions`,
`01-development-process→work-plans`가 기본 진입이며, 분할된 절은 위 새 페이지로 이동한다.

기존 heading을 추출해 이전 URL+anchor를 새 URL+anchor로 대응한다. 번호 요약은 `요약`으로,
삭제·통합 절은 그 질문을 이어받는 절로 보낸다. 원본의 기존 legacy route 패턴을 확인해
호환 페이지를 두고 검색에서 제외한다. M05에서 모든 대응 목적지와 대표 브라우저 이동을 확인한다.
템플릿에는 호환 페이지를 이관하지 않는다.

들어오는 파일 참조는 `docs/plans/README.md`, `docs/plans/01-cka-udemy-rework.md`,
`docs/deploy.md`, 두 덱 MDX·metadata에서 발견했다. 파일 이동 때 다시 전역 검색한다.
기존 완료 계획의 실행 내용은 유지하고 깨지는 파일 참조만 갱신한다.

### M02 의미 리뷰

작성 정본은 독자·질문·범위 → 근거·예제 → 학습 순서 → 작성 → 의미 리뷰 → 기술 검증 순서다.
AGENTS에는 매번 수행할 행동과 정본 링크만 추가하고 세부 표·예시는 작성 지침에 둔다.
새 baseline에 독자·선행 지식·학습 결과·범위를 요구하되 기존 덱 스키마는 바꾸지 않는다.
검토 날짜는 사실 확인 범위에 한정하고, 필수 컴포넌트·검사 통과를 학습 효과로 간주하지 않는다.
CLAUDE는 기존 `@AGENTS.md` 한 줄을 유지한다. 재승인·외부 심사·분량 할당은 추가하지 않았다.
`git diff --check` 통과, 변경한 네 문서의 로컬 참조 45개 존재 확인 통과.
빌드에 포함되지 않는 지침·계획만 바뀌어 `pnpm check`는 실행하지 않았다.

## M03 근거 확인 중간 기록 (2026-09-18)

OpenAI Docs 스킬로 공식 문서를 검색하고 원문을 열었다. 현재 근거는 문서 확인이며
Codex·Claude Code 별도 세션을 실행한 실측이 아니다.

- [OpenAI AGENTS](https://learn.chatgpt.com/docs/agent-configuration/agents-md): 시작 시 루트→cwd,
  폴더별 override/AGENTS/fallback 하나, 가까운 지침 우선, 기본 32 KiB를 확인했다.
- [Anthropic memory](https://code.claude.com/docs/en/memory): cwd와 상위 지침을 시작 시 결합하고
  하위 지침은 파일을 읽을 때 로드한다. import는 참조 파일 기준 상대 경로이며 내용을 컨텍스트에
  펼친다. `/context`로 목록 확인을 안내한다. 기존의 “Claude는 AGENTS를 읽지 않는다”는 문장은
  **자동 탐색 대상이 아니다**로 좁혀 직접 읽기·import와 구분할 것.
- [ExecPlan](https://developers.openai.com/cookbook/articles/codex_exec_plans): 현재 페이지에
  **archived** 표시가 있다. 현행 공식 필수 표준으로 소개하지 않고 자기완결 계획의 과거 공식 사례로
  명시할 것. 자기완결·진행 중 갱신·다음 milestone 지속은 원문에서 확인했다.
- [Claude best practices](https://code.claude.com/docs/en/best-practices)와
  [OpenAI best practices](https://learn.chatgpt.com/guides/best-practices)를 열었다.
  전자의 실행 가능한 검증 신호를 확인했다. 후자는 필요한 본문을 추가 확인할 것.

다음 실행: 기존 `dist/coding-agents/*/index.html`과 원본 heading을 대조해 옛 anchor를 보존하고,
M01의 5개 본문으로 개편한다. 호환 구현 참고는 `src/pages/keycloak/[legacy].astro`와
`src/data/keycloak-legacy-routes.json`이다. hash는 브라우저에서 대응하므로 대표 이동 확인이 필요하다.
관련 레거시 코드를 읽었으나 새 호환 파일은 아직 만들지 않았다.

요청·검토 예제 평가: “JSON을 자세히”는 독자·범위·판정 신호가 없어 길이로 성공을 대체할 수 있다.
개선 요청은 JS 기초 독자, JSON과 객체 표기의 차이, 파싱 오류 수정, 제외 범위, 예제 실행,
의미 리뷰와 사이트 검사까지 관찰할 항목을 지정한다. 리뷰 요청은 문장 교정에 한정하지 않고
전제·근거·실행 가능성·이해 확인의 연결을 검사한다. 재개 요청은 계획뿐 아니라 현재 diff를 대조한다.
이 평가는 요청의 충분성 검토이며 아직 임시 덱을 생성·실행한 결과는 아니다.
