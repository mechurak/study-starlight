# 콘텐츠 작성 규칙

페이지는 전부 `.mdx`로 만든다. 독자가 세부 용어를 만나기 전에 **전체에서 지금 어디를 보는지**부터
알 수 있어야 한다. 표·D2·Mermaid·공식 구조도·실제 화면처럼 이해를 앞당기는 시각 자료를 적극적으로 쓴다.
그림을 넣더라도 원래 있던 사실을 지우지 않는다.

## 설명 순서와 제목

- 각 장 맨 위에는 `<Thesis>`로 "결론부터" 핵심 요약 한 줄을 둔다. 본문을 읽지 않아도
  이 장이 무엇을 주장하는지 알 수 있어야 하고, 요약이 한 줄로 안 되면 장의 범위가 너무 넓은 것이다.
  굵기는 컴포넌트가 입히므로 안에서 `**`를 반복하지 않는다. 예전의 `> 결론부터 — **…**`
  인용 형식은 더 쓰지 않는다. 사용 예는 `src/components/docs/Thesis.astro` 머리 주석에 있다.
- 첫머리는 핵심 요약 다음에 **큰 그림 → 이 장이 답할 질문 → 세부 개념·도구** 순서로 연다.
  제품명·약어·설정값부터 나열하지 않는다.
- 큰 그림은 독자가 뒤의 세부 내용을 꽂을 수 있는 지도여야 한다. 전체 흐름, 구성 요소의 역할,
  앞뒤 장과의 관계 중 필요한 것을 짧은 문단·표·다이어그램 하나로 먼저 보여준다.
- 한꺼번에 소개하는 새 용어는 최소화한다. 첫머리의 `<TermIntro>`에는 큰 그림을 읽는 데 꼭 필요한
  말만 두고, 설치·질의·운영 용어는 실제로 쓰는 절 바로 앞으로 미룬다.
- 새 용어·약어는 처음 나올 때 풀 이름을 쓰고, 새 개념은 **없으면 무슨 문제가 생기는지 → 해법** 순서로 설명한다.
- 정착된 영어 용어를 억지로 한글로 번역하지 않는다. 제품·스펙의 고유 명칭(Declarative Agent,
  Agent Harness 등)은 영어 표기를 유지하고, 처음 나올 때 뜻을 풀어 설명한다. 일반 형용사로 쓰는
  말(선언형 관리 같은 것)까지 영어로 되돌릴 필요는 없다.
- **한 제목 아래에서는 한 가지 개념만 다룬다.** 한 절에서 두 번째 개념을 설명하기 시작하면
  제목을 나눈다. 요약 한 줄로 그 절을 설명할 수 없으면 개념이 섞여 있다는 신호다.
- 제목 계층으로 우측 목차를 조직한다. h2는 주제 묶음 5~9개, 상세 절은 h3로 내린다.
- h4는 목차에 잡히지 않으므로 쓰지 않는다. 제목을 바꾸면 앵커 slug도 바뀐다.
- 시험 포인트·핵심 원칙은 `:::tip[…]`, 함정·주의는 `:::caution[함정]`을 쓴다.

### 큰 그림을 먼저 보여주는 예

```text
나쁜 순서: 제품 A의 컴포넌트 이름 8개 → 설정 파일 → 이 제품이 푸는 문제
좋은 순서: 사용자가 겪는 문제 → 전체 흐름과 역할 → 제품이 맡는 자리 → 컴포넌트와 설정
```

첫 화면을 읽은 독자가 최소한 다음 두 질문에는 답할 수 있어야 한다.

- **이 장은 전체 중 어느 부분인가?**
- **이 장을 읽고 나면 어떤 질문에 답할 수 있는가?**

## 시각 자료와 외부 이미지

텍스트만으로 머릿속에 모양을 만들기 어려운 내용에는 시각 자료를 적극적으로 붙인다.
특히 다음은 그림의 효과가 크다.

- 시스템 전체 구조와 데이터 흐름
- 요청·이벤트의 시간 순서와 상태 변화
- 제품의 실제 화면, 트레이스 워터폴, 대시보드, 개발 도구 UI
- 저장 형식·계층·공간 배치처럼 위치 관계가 중요한 개념
- 둘 이상의 방식이나 전후 상태를 나란히 비교하는 경우

자료 형식은 목적에 맞춰 고른다.

| 보여줄 것 | 우선 수단 |
|---|---|
| 새로 그리는 다이어그램(관계·시퀀스·상태·아키텍처·흐름) | D2 |
| 기존 Mermaid가 있는 문서의 수정, D2 미지원 타입(timeline 등) | Mermaid |
| 실제 제품이 어떻게 보이는가 | **공식 문서의 스크린샷** |
| 복잡한 공식 아키텍처·데이터 형식 | **공식 구조도** |
| 반복 필드와 정확한 비교 | 표 |
| 코드로 직접 보여줄 수 없는 질감·현장·물체 | 출처가 분명한 외부 이미지 |

외부 이미지는 다음 원칙을 모두 지킨다.

1. **공식 문서·원 저작자 자료를 우선한다.** 검색 결과 썸네일이나 출처를 거슬러 올라갈 수 없는
   재업로드 이미지는 쓰지 않는다.
2. 원격 URL을 그대로 임베드하지 않고 `public/images/<덱>/`에 사본을 둔다. 원본 사이트의 장애·개편,
   핫링크 차단 때문에 문서가 깨지는 일을 막기 위해서다.
3. 이미지 아래에 **이 그림에서 어디를 봐야 하는지**를 한두 문장으로 적는다. 그림 안의 낯선
   용어를 다시 전부 설명하지 말고, 현재 문맥에 필요한 부분만 가리킨다.
4. **원본이 실린 페이지 링크와 출처 이름을 반드시 함께 둔다.** 이미지 파일만 링크하지 않고,
   저자가 제공한 설명과 최신 버전을 확인할 수 있는 원문 페이지로 연결한다.
5. `alt`에는 “그림”이 아니라 그림이 전달하는 핵심 관계를 쓴다. 장식 이미지는 넣지 않는다.
6. 원본 `width`·`height`를 지정해 지연 로딩 전에도 공간을 예약하고, 모바일에서 본문 전체가
   가로로 넘치지 않는지 확인한다.

외부 이미지는 공용 `<SourceFigure>`를 사용한다. 이미지를 누르면 전체 화면 확대 dialog가 열리고,
캡션의 출처 링크는 원문 페이지로 간다.

```mdx
import SourceFigure from '../../../components/docs/SourceFigure.astro';

<SourceFigure
  src="/images/<덱>/example.png"
  alt="요청이 수집기를 거쳐 세 저장소로 나뉘고 조회 화면에서 다시 합쳐지는 구조"
  width={1600}
  height={900}
  caption="지금은 가운데 수집기에서 세 저장소로 갈라지는 화살표만 본다."
  sourceHref="https://example.com/official-documentation/page"
  sourceLabel="제품 공식 문서 — Architecture"
/>
```

외부 이미지를 추가하거나 바꾸면 `pnpm check`에 더해 브라우저에서 **이미지 로드 · 출처 링크 ·
대체 텍스트 · 모바일 넘침 · 다크 모드 배경**을 확인한다.

## 프론트매터

기본은 `title`과 `description`이다. 사이드바 순서와 그룹은 `src/data/decks.mjs`에서 관리하므로
`sidebar` 계열 필드는 쓰지 않는다. 사이드바 라벨은 `title`에서 오므로 장 번호를 제목에 유지한다.

나중에 찾거나 현재성을 판단하는 데 필요할 때만 다음 필드를 추가한다.

```yaml
aliases: [옛 이름, 약어, 동의어]
reviewedAt: 2026-08-12
status: stable # stable | review | stale
```

`aliases`는 본문 앞에 표시되어 Pagefind 검색 대상이 된다. `reviewedAt`은 단순 수정일이 아니라
내용의 현재성을 실제로 확인한 날짜다. 확신 없이 오늘 날짜를 넣지 않는다.

## 근거와 참고 자료

사실·버전·수식·현재성 있는 주장처럼 나중에 근거를 재확인할 필요가 있는 내용에는
**공식 문서나 원 논문 중심의 참고 링크**를 둔다. 링크는 말미에 모으지 말고 **그 주장이 있는
문장에 바로 건다.** 페이지 말미의 `## 참고 자료`는 본문 흐름에 넣기 어려운 추가 읽을거리를
두는 보조 절로만 쓰고, 각 링크에서 무엇을 확인할 수 있는지 짧게 적는다.

도구 설치를 안내할 때는 **긴 설치 커맨드·스크립트를 본문에 복사하지 않는다.** 공식 설치
페이지가 정본이고 스크립트는 자주 바뀌므로, 공식 페이지 링크를 걸고 거기서 최신 스크립트를
확인해 설치하도록 안내한다. 본문에는 설치 확인 명령(`tool version` 같은 것)과 이 덱에서
실제로 쓰는 옵션·설정만 둔다.

모든 페이지에 억지로 넣지는 않는다. 단순한 내부 절차나 작성자의 정리처럼 별도 원문이 없는
내용은 생략하고, 링크가 본문의 어떤 주장과 연결되는지 알 수 없게 URL만 나열하지 않는다.

## 강조와 CommonMark 함정

- 닫는 `**` 앞에 따옴표·괄호·`%`·백틱을 두고 바로 뒤에 한글 조사를 붙이지 않는다.
  - `**"조회 → 해결"**의` → `"**조회 → 해결**"의`
  - `**커리큘럼의 25%**가` → `**커리큘럼의 25%가**`
  - `` **`get all`**이다 `` → `` `get all`이다 ``
- 한 문단이나 표 한 칸에 범위 표시 `~`를 두 번 쓰지 않는다. GFM이 그 사이를 취소선으로 해석할 수 있다.
- raw HTML을 본문에 인라인으로 쓰지 않는다. 한 번 쓸 강조는 `**`와 aside를 사용한다.

## 컴포넌트 위치

```text
src/components/
  layout/  Starlight override와 사이트 레이아웃
  docs/    여러 덱이 공유하는 문서 컴포넌트
  demos/   특정 개념을 보여주는 인터랙티브 데모
```

기존 컴포넌트를 먼저 확인한다. 새 컴포넌트의 스타일은 자체 `<style>`에 캡슐화하고,
다크 모드는 `[data-theme='dark']`로 대응한다. 사이트 전역 조정만 `src/styles/custom.css`에 둔다.

산문으로 길게 풀기 전에 내장 컴포넌트로 구조화할 수 있는지 먼저 본다. 순서 있는 절차는
`<Steps>`, 갈래 비교는 `<Tabs>`, 분류 개요는 `<CardGrid>`처럼 **모양이 정해진 정보는 그 모양의
컴포넌트**에 담고, 아래 표에서 쓸 자리를 고른다.

| 컴포넌트 | 쓸 자리 |
|---|---|
| `<Steps>` | 순서가 있는 절차 |
| `<Tabs>` | 차이만 보여주고 싶은 두 갈래 |
| `<CardGrid>` + `<Card>` | 층·분류의 개요 |
| `<FileTree>` | 디렉터리 구조 |
| `<LinkCard>` | 장 끝의 다음 장 안내 |
| `<LinkButton>` | 덱 index의 “첫 장부터 읽기” CTA — 덱마다 하나 |
| `<Badge>` | 성숙도·deprecated·기본값·시험 비중 같은 짧은 상태 |
| `<DeckMap>` | 덱 index의 “구성” 절 — 덱마다 하나 |
| `<Thesis>` | 장 첫머리의 “결론부터” 핵심 요약 — 장마다 하나 |
| `<SourceFigure>` | 공식 문서 등 외부 이미지 — 읽을 지점·대체 텍스트·원문 출처 포함 |
| `<ExternalLink>` | 새 탭에서 열어야 하는 외부 링크 — 기본은 일반 마크다운 링크 |
| D2 | 새 다이어그램의 기본값 — 관계도, 시퀀스, 상태, 아키텍처, 흐름 |
| Mermaid | 기존 Mermaid 다이어그램의 수정, D2 미지원 타입(timeline 등) |

한 페이지 안에서 OS별 커맨드를 여러 절에 걸쳐 반복해서 보여줄 때는 매번 `<Tabs>`를 따로
두지 말고 `<Tabs syncKey="operating-system">`로 동기화한다. 독자가 한 번 자기 OS를 고르면
페이지의(그리고 다른 페이지의) 모든 그룹이 함께 전환된다. 동기화되는 모든 그룹의 `<TabItem>`
label은 정확히 `macOS`, `Ubuntu`로 맞춘다 — label이 다르면 동기화가 깨진다.
실제 사용 예는 `src/content/docs/lab-environment/01-kind.mdx`에 있다.

`<FileTree>`는 `- 경로/` 뒤에 설명을 이어 쓰면 주석으로 표시된다. 중요한 파일은 `**굵게**` 한다.

## 덱 index

덱 index의 첫 화면에는 **이 덱이 왜 필요한가(배경)와 무엇을 다루는가(내용 요약)**가 드러나야
한다. 장 제목 나열은 요약이 아니다 — 어떤 문제의식에서 출발했고 읽고 나면 무엇을 알게 되는지를
짧은 문단으로 먼저 쓴다.

덱 index에는 `<LinkButton>`과 `<DeckMap>`을 각각 하나 둔다. 구성도에는 D2·Mermaid 같은
다이어그램 대신 `<DeckMap>`을 쓴다.
`DeckMap`의 props와 의미는 `src/components/docs/DeckMap.astro` 머리 주석에 있다.

## MDX에서 자주 깨지는 것

- JSX 안의 마크다운은 들여쓰기하지 않는다. `<Card>`·`<TabItem>` 태그와 내용을 0칸에 두고 빈 줄로 띄운다.
- `<Steps>` 안 번호 목록에 딸린 코드 블록만 3칸 들여쓴다.
- 제목에 `<Badge>`를 붙일 때 공백 없이 쓴다. 공백이 있으면 앵커 slug 끝에 `-`가 붙는다.
- `src/content/docs/`의 새 페이지는 manifest에 넣거나 topic plugin의 `exclude`에 추가한다.
- 코드 펜스 언어는 하이라이터가 지원하는 이름만 쓴다. 전용 문법이 없으면 `text`를 쓴다.

## D2

**새로 그리는 다이어그램은 D2가 기본값이다.** ```` ```d2 ```` 펜스는 빌드 때 SVG `<img>`로
바뀌고, 이미지를 누르면 starlight-image-zoom의 확대 dialog가 열린다 — Mermaid와 달리 전용
확대 컴포넌트가 필요 없다. 기존 Mermaid를 일괄 변환하지는 않고, 해당 문서를 손볼 때
자연스럽게 D2로 옮긴다.

````md
```d2 layout=elk pad=40 title="빌드 시 SVG가 생성되는 문서 흐름"
direction: right

source: D2 펜스
build: Astro 빌드
svg: SVG 이미지
browser: 브라우저

source -> build: 변환 {
  style.animated: true
}
build -> svg: 생성 {
  style.animated: true
}
svg -> browser: 표시 {
  style.animated: true
}
```
````

- **좌우로 너무 넓어지지 않게 그린다.** 본문 폭을 넘는 SVG는 축소되어 글자가 작아진다.
  `direction: right`에서 노드가 가로로 5개를 넘어가면 `direction: down`으로 바꾸거나,
  단계를 컨테이너로 묶어 세로로 쌓는 배치를 먼저 고려한다.
- 접근 가능한 대체 텍스트가 되도록 `title="…"`을 구체적으로 쓴다.
- 엣지의 `style.animated: true`는 방향이나 진행이 핵심일 때만 쓴다.
- 기본 `inline: false`를 유지한다. 외부 SVG `<img>`가 다크 모드와 이미지 확대에 가장 안정적이다.
- `layout=elk`, `pad`, `sketch`, `theme` 같은 펜스 속성은 그 그림에 필요한 것만 덮어쓴다.
- D2 `<img>`에는 Mermaid식 카드 프레임을 씌우지 않는다. starlight-image-zoom의 기본 표시를 그대로 둔다.
- D2 문법 오류는 빌드가 잡지만, SVG 로드·애니메이션·라이트/다크·확대는 브라우저에서 확인한다.

## Mermaid

Mermaid는 **기존 Mermaid 다이어그램을 수정할 때**와 D2가 지원하지 않는 타입(timeline 등)에만
쓴다. 빌드 성공은 클라이언트 렌더 성공을 보장하지 않으므로 변경 시 브라우저에서
라이트·다크 모드를 확인한다.

의미 팔레트는 다음 여섯 개로 통일한다.

```text
classDef ok   fill:#dcfce7,stroke:#16a34a,color:#14532d
classDef bad  fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
classDef warn fill:#fef3c7,stroke:#d97706,color:#78350f
classDef key  fill:#dbeafe,stroke:#2563eb,color:#1e3a8a
classDef mute fill:#f1f5f9,stroke:#94a3b8,color:#334155
classDef zone fill:#ede9fe,stroke:#7c3aed,color:#4c1d95
```

- `stateDiagram-v2`는 테마 기본값을 쓴다.
- 노드 라벨은 `["…"]`, 엣지 라벨은 `-->|"…"|`처럼 감싼다.
- 라벨의 `&`는 `&amp;`로 쓰고 `<`·`>`는 피한다. `<br/>`만 줄바꿈에 사용한다.
- 여러 subgraph는 `flowchart LR`과 내부 `direction`으로 정렬한다.
- `<Tabs>` 안 다이어그램을 검사할 때는 숨은 tabpanel을 먼저 연다.
- 모든 Mermaid에는 공통 카드와 확대 버튼이 자동으로 붙는다. SVG나 오른쪽 위 버튼을 누르면
  화면에 맞춰 커진 dialog가 열리고, ESC·닫기 버튼·바깥 영역 클릭으로 닫는다.
- 흐름을 구분해서 보여 줄 엣지는 `A -.-> B`처럼 점선으로 쓴다. 모든 선을 점선으로 만들지 않는다.
