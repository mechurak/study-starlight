## 이 덱은 누구를 위한 것인가

- **이 사이트를 고치거나 덱을 새로 만들** 사람 — 지금은 소유자 한 명이지만, 미래의 자신 포함
- 스터디 노트를 어디에 쌓을지 고민하며 **노션·위키·문서 사이트 사이에서** 저울질하는 사람
- 마크다운은 써 봤는데 **MDX·컴포넌트·빌드가 뭘 하는 물건인지** 감이 없는 사람

전제하는 것: 마크다운 기본 문법, git, 터미널에서 명령 실행.
전제하지 않는 것: Astro나 프론트엔드 프레임워크 경험, JavaScript 숙련도.

## 왜 노션이 아니라 문서 사이트인가

학습 노트는 쓰는 날보다 **다시 찾는 날이 훨씬 많다.** 그래서 요구사항이
"쓰기 편한가"가 아니라 "쌓이고, 검색되고, 참조되는가"로 바뀐다.
이 관점에서 도구를 보면 갈림길이 분명해진다.

| 판단할 것 | 서비스형 위키 | 이 사이트의 docs-as-code |
|---|---|---|
| 편집 경로 | 화면 편집과 협업 기능 중심 | MDX 파일과 Git diff 중심 |
| 이식·복구 | 내보내기 형식·이력 정책 확인 | 파일과 Git 이력을 직접 보관 |
| 검증 | 서비스가 제공하는 기능과 API 확인 | 자체 검사·빌드·링크 검사 조합 |
| 운영 부담 | 계정·서비스 정책에 의존 | 의존성·빌드·호스팅을 직접 관리 |

이 사이트는 파일 소유와 Git 기반 변경 검토를 우선해 문서 사이트를 택했다.
비개발자 여러 명의 동시 편집이 중요하면 다른 선택이 나을 수 있다.
서비스 전체를 이식 불가능하거나 AI로 다룰 수 없다고 일반화하지 않는다.


:::tip[핵심]
이 선택의 본질은 Starlight냐 다른 SSG냐가 아니라 **"본문을 파일로 소유하는가"** 다.
파일이면 git · grep · 에이전트 · 빌드 검증이 전부 따라오고, 도구는 나중에 갈아탈 수도 있다.
:::

## 미리 잡아두는 멘탈 모델 — 3층 분리

이 사이트에서 무언가를 고칠 때, 손대는 파일은 항상 셋 중 한 층에 있다.

```d2 title="콘텐츠·구조·표현 세 층이 각각 pnpm check를 거쳐 정적 산출물 dist/가 되는 흐름"
direction: right

      font-color: "#1e3a8a"
    }
  }
  mute: {
    style: {
      fill: "#f1f5f9"

  }
  ok: {
    style: {

}

content: "콘텐츠\nsrc/content/docs/\n마크다운 · MDX" { class: key }
structure: "구조\n_deck.mjs · src/data/ · astro.config.mjs\n덱 metadata · 사이트 설정" { class: mute }
presentation: "표현\nsrc/components/ · custom.css\n컴포넌트 · 스타일" { class: mute }
check: "검사 · 빌드\npnpm check" { class: ok }
dist: "dist/\n정적 HTML + 검색 인덱스" { class: ok }

content -> check
structure -> check
presentation -> check
check -> dist
```

- **콘텐츠** — 글을 쓰고 고치는 일의 거의 전부. 마크다운만 만지면 되고, [MDX](/starlight/mdx/)·[문서 작성](/starlight/writing/)에서 다룬다
- **구조** — 덱을 추가하거나 장 순서를 바꿀 때만 연다. [Starlight 구조](/starlight/structure/)에서 다룬다
- **표현** — 새 시각 패턴이 필요할 때만. [커스텀 컴포넌트](/starlight/custom/)에서 다룬다

층을 나누면 고칠 위치를 좁히기 쉽다. 다만 MDX import나 frontmatter 오류는 전체 빌드를
깨뜨릴 수 있으므로 분리가 검증을 대신하지는 않는다.

## 실행하고 첫 페이지를 만든다

저장소 루트에서 Node 24 이상과 `package.json`의 pnpm 11.20.0을 준비한다.
설치 방법은 [Node 공식 다운로드](https://nodejs.org/en/download)와
[pnpm 설치 안내](https://pnpm.io/installation)를 따른다.
D2 준비 스크립트는 macOS arm64/x64, Linux arm64/x64를 지원하며 첫 설정 로드에는
고정 바이너리를 내려받을 네트워크가 필요하다.

```bash
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm astro dev --background
pnpm astro dev status
```

출력된 로컬 주소에서 사이트를 연다. 종료는 `pnpm astro dev stop`, 로그는
`pnpm astro dev logs`다. 실행만 해 보는 데 원격 저장소·배포·AI 계정은 필요 없다.
준비됐다면 [첫 덱 작성](/starlight/first-deck/)의 최소 파일을 만들고 자동 등록을 확인한다.

## 이 덱의 기준

**Starlight 0.41.6 · Astro 7.1.6, 2026-09-18 확인** 기준이다. Starlight는 아직 1.0 전이라
마이너 버전에서도 동작이 바뀔 수 있다 — 업그레이드 전에
[docs/starlight-changes.md](https://github.com/mechurak/study-starlight/blob/main/docs/starlight-changes.md)를 본다.

그리고 다시 한번 — **예제는 전부 이 레포다.** 장마다 "이 레포에서는"이 나오는 이유이고,
이 덱이 공식 문서를 베낀 요약이 아니라 **선택과 운영의 기록**인 이유다.

## 요약

- 대상은 **이 사이트를 고치거나 비슷한 것을 만들려는 사람**, 예제는 이 레포 자체
- 노션 대신 문서 사이트인 이유는 **본문을 파일로 소유**하기 위해서다 — git · 검색 · 에이전트 협업이 따라온다
- 멘탈 모델은 3층 분리: **콘텐츠**(`src/content/docs/`) / **구조**(덱별 `_deck.mjs` · `src/data/` · `astro.config.mjs`) / **표현**(`src/components/`)
- 기준은 Starlight 0.41.6 · Astro 7.1.6 — 예제가 레포와 다르면 레포가 맞다
