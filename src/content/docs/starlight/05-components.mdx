## 원칙 — 컴포넌트는 정보 구조다

내장 컴포넌트를 "예쁘게 만드는 도구"로 잡으면 페이지마다 다른 장식이 쌓이고,
사이트는 오히려 산만해진다. 이 레포의 관점은 반대다 —
**정보의 모양이 먼저 있고, 그 모양에 맞는 컴포넌트가 따라온다.**
절차라서 `<Steps>`, 갈래라서 `<Tabs>`, 분류라서 `<CardGrid>`다.

문서가 "있어 보이는" 것은 페이지별 장식이 아니라 **덱 전체의 일관성**에서 나온다 —
같은 정보 모양에는 항상 같은 컴포넌트, 같은 결론 성격에는 항상 같은 색(아래 팔레트).
독자가 규칙을 학습하면, 모양만 보고도 정보의 성격을 읽는다.

## 본문에 넣는 것은 세 종류다

한 덩어리로 "컴포넌트"라고 부르게 되지만, 본문에 넣는 것들은 **출신이 다르고 그래서 고장 나는
방식도 다르다.** 이 구분을 먼저 잡아 두면 뭔가 안 나올 때 어느 문서를 뒤질지가 바로 좁혀진다.

| 종류 | 쓰는 법 | 어디서 오나 | 예 |
|---|---|---|---|
| **내장 컴포넌트** | import 후 태그로 | Starlight 패키지 | `<Steps>` · `<Tabs>` · `<Card>` · `<FileTree>` · `<Badge>` |
| **지시어 (aside)** | `:::tip[…]` 문법, import 없이 | Starlight의 마크다운 확장 | `:::note` · `:::tip` · `:::caution` · `:::danger` |
| **다이어그램 펜스** | 코드 펜스에 언어 이름으로 | **Astro integration** (2장) | `d2` |

:::caution[함정 — D2는 컴포넌트가 아니다]
D2는 import하지 않는다. 언어 이름을 `d2`로 준 **코드 펜스**를 `astro-d2` integration이 빌드 때
가로채 SVG로 바꾸는 것이고, 이건 Starlight가 아니라 **Astro 층에 꽂힌 서드파티**다(2장의 config).
그래서 Starlight 공식 문서에는 D2가 없고, 다이어그램이 회색 코드 블록으로 나올 때 확인할 곳도
`astro.config.mjs`의 integration 순서다.
:::

## 역할 표 — 무엇을 어디에

| 요소 | 쓸 자리 | 쓰지 말 자리 |
|---|---|---|
| `<Steps>` | 순서가 있는 절차 | 순서 없는 나열 (그냥 목록으로) |
| `<Tabs>` | **차이만 보여주고 싶은 두 갈래** | 전부 읽어야 하는 내용 (탭은 안 보이는 쪽이 생긴다) |
| `<CardGrid>` + `<Card>` | 층·분류의 개요, "해결책 넷 중 하나" | 본문 문단의 대체 |
| `<FileTree>` | 디렉터리 구조 | 파일 아닌 계층 (그건 D2) |
| `<LinkCard>` | 장 끝의 "다음 장으로" | 본문 중간 (흐름을 끊는다) |
| `<LinkButton>` | 덱 index의 시작 CTA — **덱마다 하나** | 본문 어디든 (`<LinkCard>`와 역할이 겹친다) |
| `<Badge>` | 표·제목 옆의 짧은 상태 라벨 | 문장 속 강조 (그건 `**`) |
| 아이콘 | `<Card icon>` · topics의 덱 icon — **prop으로만** | 본문 문장 속 인라인 (스캔을 방해한다) |
| aside | 시험 포인트·핵심은 tip, 함정은 caution | 본문 대체 — 상자가 본문보다 많으면 실패 |
| D2 펜스 | **다이어그램** — 결정 트리 · 관계 · 상태 · 시퀀스 · 아키텍처, "왜 그런가" | 훑어보기용 데이터 (그건 표) |

이 표에서 오른쪽 열이 왼쪽 열만큼 중요하다 — 컴포넌트 남용의 결과는
"전부 강조되어 아무것도 강조되지 않는" 페이지다.

## 절차 · 갈래 · 분류 — 큰 셋

### 절차는 Steps

번호 목록을 `<Steps>`로 감싸면 진행선이 붙은 스텝 UI가 된다. 순서를 바꾸면 안 되는
작업(복구 절차, 업그레이드, 진단 순서)에만 쓴다. 안에서는 마크다운 번호 목록 문법을
그대로 쓰므로, 목록 항목에 딸린 코드 블록은 3칸 들여쓴다(4장의 예외 그것).

```mdx
<Steps>

1. 번호 목록을 그냥 쓴다

2. 항목 사이는 빈 줄로 띄운다

3. 번호 원과 진행선은 컴포넌트가 그린다

</Steps>
```

위 소스가 이렇게 나온다 —

<Steps>

1. 번호 목록을 그냥 쓴다

2. 항목 사이는 빈 줄로 띄운다

3. 번호 원과 진행선은 컴포넌트가 그린다

</Steps>

### 갈래는 Tabs

<Tabs>
<TabItem label="쓸 때">
두 갈래가 **서로 배타적**이고, 독자는 자기 갈래 하나만 읽으면 될 때.
"느린 정책 / 빠른 정책", "macOS / Linux" — 이 페이지의 이 예시 자체가 그 예시다.
</TabItem>
<TabItem label="쓰지 말 때">
양쪽을 다 읽어야 이해되는 내용. 탭은 **한쪽을 숨기는 UI**다 — 숨겨도 되는 내용만 넣는다.
비활성 탭은 `hidden`이라 Playwright 검증에서도 안 잡힌다(8장).
</TabItem>
</Tabs>

### 분류는 CardGrid

장 첫머리의 "이 장은 이런 덩어리들이다", 또는 "다룬다/다루지 않는다" 같은
대칭 분류에 쓴다. 카드 자식 마크다운은 0칸 들여쓰기 — 4장의 규칙이 제일 자주 걸리는 곳이다.

<CardGrid>
<Card title="한 카드는 한 덩어리" icon="puzzle">
카드 안은 짧게 쓴다. 문단이 길어지면 그건 카드가 아니라 본문이다.
</Card>
<Card title="아이콘은 prop으로만" icon="star">
`icon`은 Starlight 아이콘 이름 중에서 고른다. 본문 문장 속 인라인 아이콘은 쓰지 않는다.
</Card>
</CardGrid>

0장의 "다룬다 / 다루지 않는다"가 이 컴포넌트의 실제 사용례다.

## 소소하지만 규칙이 있는 것들

- **`<FileTree>`** — `- 경로/` 뒤에 설명을 이어 쓰면 회색 주석이 되고, 파일명을
  `**굵게**` 하면 강조된다. 중요한 파일을 눈에 띄게 하는 공식 수단
- **`<Badge>` 를 제목에 달 때는 공백 없이 붙인다.** `### 집계 ClusterRole<Badge …/>` —
  띄우면 앵커 slug 끝에 `-`가 붙어 **링크가 조용히 바뀐다.** 빌드는 통과한다.
  간격은 `custom.css`의 `:is(h2, h3) > .sl-badge` 규칙이 알아서 준다
- **`<LinkCard>` 는 장 끝 전용** — 이 덱의 모든 장이 다음 장 안내로 끝나는 그 자리다.
  이 페이지 맨 아래의 "6. 커스텀 컴포넌트" 카드가 그것이고, `<LinkButton>`은 덱 index에 하나 있다

`<FileTree>`는 소스와 결과가 이렇게 대응한다 —

```mdx
<FileTree>
- src/components/
  - **docs/** 여러 덱이 공유하는 문서 컴포넌트
  - demos/ 특정 개념을 보여주는 인터랙티브 데모
</FileTree>
```

<FileTree>
- src/components/
  - **docs/** 여러 덱이 공유하는 문서 컴포넌트
  - demos/ 특정 개념을 보여주는 인터랙티브 데모
</FileTree>

`<Badge>`는 `variant`가 색을 정한다 — aside와 같은 색 체계라 의미가 사이트 전체에서 이어진다.

| 소스 | 결과 |
|---|---|
| `<Badge text="기본값" variant="note" />` | <Badge text="기본값" variant="note" /> |
| `<Badge text="deprecated" variant="caution" />` | <Badge text="deprecated" variant="caution" /> |

## aside — 네 가지 색의 약속

```mdx
:::tip[핵심]
시험 포인트 · 핵심 원칙 — "이것만 기억하면 된다"
:::

:::caution[함정 1 — 구체 라벨을 단다]
독자가 실제로 밟을 지뢰. 라벨에 무엇의 함정인지 쓴다.
:::
```

- `note`(파랑) 배경 정보 / `tip`(보라) 핵심·요령 / `caution`(노랑) 함정·주의 / `danger`(빨강) 되돌릴 수 없는 것
- 라벨은 구체적으로 — `[함정]`보다 `[함정 — 빌드는 통과한다]`가 검색과 스캔에 낫다
- **절제가 규칙이다.** aside는 본문의 밀도를 높이는 장치가 아니라 흐름 밖 정보의 자리다.
  한 절에 상자가 둘을 넘으면 본문 구조를 의심한다

렌더된 실물은 이 장에 이미 있다 — 위 "세 종류" 절의 `caution`이다.
여기에 예시용 상자를 더 만들지 않은 것도 규칙의 일부다. **보여주려고 늘리는 순간 절제가 깨진다.**

## 다이어그램 — 전부 D2다

표가 사실의 나열이라면, 다이어그램은 **관계와 인과**다 — 결정 트리, 층 구조, 상태 전이,
시퀀스. 원래 있던 사실을 지우면서 그림으로 대체하지 않고(7장에서 다시), 별도 이미지 파일도
만들지 않는다 — 다이어그램은 **전부 펜스 안 텍스트**라서 diff가 되고, 검색이 되고, 고치기 쉽다.

그리는 도구는 **D2 하나다.** D2 펜스는 빌드 때 SVG `<img>`로 만들어진다 —
이 한 문장에서 장점이 다 나온다.

- **문법 오류를 빌드가 잡는다.** 깨진 그림이 배포로 새어 나가지 않는다
- 이미지를 누르면 starlight-image-zoom의 전체 화면 확대 dialog가 그냥 붙는다 — 전용 확대 컴포넌트가 필요 없다
- 다이어그램 렌더용 JS를 브라우저에 보내지 않는다 — 2장의 섬 목록에 D2가 없는 이유

```d2 title="D2 펜스가 빌드 시 SVG로 생성되고 브라우저에서 확대되는 흐름"
direction: right

source: D2 펜스 {
  shape: document
}
build: Astro 빌드 {
  shape: hexagon
}
svg: SVG 이미지 {
  shape: rectangle
}
browser: 브라우저 {
  shape: rectangle
}

source -> build: 변환 {
  style.animated: true
}
build -> svg: 생성 {
  style.animated: true
}
svg -> browser: 표시·확대 {
  style.animated: true
}
```

이 레포의 D2 규칙 —

- 기본값은 config에 있다 — 레이아웃 `elk`, 여백 `40px`, 테마는 라이트 `0` · 다크 `200`.
  펜스 속성(`layout=` · `pad=` 등)으로는 그 그림에 필요한 것만 덮어쓴다
- `title="…"`을 구체적으로 쓴다 — 접근 가능한 대체 텍스트가 된다
- **좌우로 너무 넓히지 않는다.** 본문 폭을 넘는 SVG는 축소되어 글자가 작아진다 —
  `direction: right`에서 노드가 가로로 5개를 넘으면 `direction: down`을 먼저 고려한다
- 색이 필요하면 아래 **여섯 색 의미 팔레트**를 `classes:`로 선언해 쓴다 —
  색의 의미가 사이트 전체에서 이어진다 (이 덱의 0~1장 다이어그램이 실물 예다)
- `style.animated: true`는 방향이 핵심인 엣지에만 쓴다. 움직임이 많으면 오히려 읽기를 방해한다
- 기본 `inline: false`를 유지한다 — 외부 SVG `<img>`가 다크 모드와 확대에 가장 안정적이다.
  대신 노드 자체의 클릭 링크·툴팁은 쓰지 않는다
- 문법은 빌드가 잡지만 **색 전환 · 움직임 · 확대 dialog는 브라우저가 판정**한다(8장)

### 여섯 색 의미 팔레트

색의 의미는 사이트 전체가 여섯 개로 통일한다 — 다이어그램만이 아니라 `DeckMap`과 랜딩의
카테고리 식별색도 같은 값을 쓴다. 정본 표는
[docs/content-authoring.md의 "의미 팔레트" 절](https://github.com/mechurak/study-starlight/blob/main/docs/content-authoring.md)이다.

```text
ok   fill:#dcfce7  stroke:#16a34a  font-color:#14532d   /* 정상·성공 */
bad  fill:#fee2e2  stroke:#dc2626  font-color:#7f1d1d   /* 실패·원인 */
warn fill:#fef3c7  stroke:#d97706  font-color:#78350f   /* 주의·대기 */
key  fill:#dbeafe  stroke:#2563eb  font-color:#1e3a8a   /* 핵심 대상 */
mute fill:#f1f5f9  stroke:#94a3b8  font-color:#334155   /* 배경·경유 */
zone fill:#ede9fe  stroke:#7c3aed  font-color:#4c1d95   /* 층·구획 (의미 판정 아님) */
```

`font-color`까지 셋을 항상 같이 준다 — 배경색만 주면 다크 모드에서 밝은 배경 + 밝은 글자가
되는 함정을 Mermaid 시절에 밟았고, D2에서도 같은 원리가 적용된다.

### Mermaid에서 D2로 — 왜 갈아탔나

이 사이트의 다이어그램은 원래 Mermaid였다 — 한때 437개까지 있었다. 문제는 렌더 위치였다.
Mermaid는 **브라우저(클라이언트)에서** SVG를 그리는 섬이라(2장), 문법이 틀린 다이어그램도
빌드는 통과했다 — "빌드 성공 ≠ 렌더 성공". 다이어그램을 만질 때마다 브라우저에서 라이트·다크
두 모드를 확인해야 했고, 클릭 확대도 전용 컴포넌트(`MermaidZoom`)를 따로 만들어 얹어야 했다.

그래서 덱 단위 일괄 마이그레이션으로 전부 D2로 변환하고 **Mermaid 통합을 제거했다**
(2026-08, 이슈 #2). D2가 지원하지 않는 timeline 1개는 형태를 재설계해 옮겼다.
지금 ```` ```mermaid ```` 펜스를 쓰면 가로채는 integration이 없어 회색 코드 블록으로
렌더될 뿐이다 — 새 다이어그램은 D2로 그린다.

## 5장 요약

- 컴포넌트는 장식이 아니라 **정보 모양의 선언** — 절차는 Steps, 갈래는 Tabs, 분류는 CardGrid
- 본문에 넣는 것은 세 종류다 — **내장 컴포넌트**(import) · **지시어**(`:::`) · **다이어그램 펜스**(Astro integration).
  D2는 컴포넌트가 아니라서 Starlight 문서가 아니라 `astro.config.mjs`를 본다
- 역할 표의 오른쪽 열(쓰지 말 자리)이 일관성을 지킨다 — LinkButton은 덱당 하나, 아이콘은 prop으로만
- aside는 네 색의 약속 + **구체 라벨 + 절제** — 상자가 본문을 이기면 실패
- 다이어그램은 "왜"를 맡고 **전부 D2** — 빌드가 문법을 잡고, SVG `<img>`라 확대와 다크 모드가 공짜다.
  클라이언트 렌더라 "빌드 성공 ≠ 렌더 성공"이던 Mermaid는 전부 변환하고 통합을 제거했다
- 색은 **여섯 색 의미 팔레트 고정** — `fill`·`stroke`·`font-color` 셋을 항상 같이 준다
- Badge는 제목에 붙여 쓴다(slug!) · 다이어그램의 최종 모습은 **브라우저가 판정**한다
