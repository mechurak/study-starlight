## 덱을 관통한 한 문장

**콘텐츠 · 구조 · 표현은 다른 층이고, 층마다 판정자가 다르다.**

- 콘텐츠(`src/content/docs/`)는 마크다운/MDX — 문법은 빌드가, 렌더는 브라우저가 판정한다
- 구조(덱별 `_deck.mjs` · MDX frontmatter · `src/data/` · `astro.config.mjs`)는 가까운 원본과 파생 설정 — 어긋남은 `check:content`가 잡는다
- 표현(`src/components/` · `custom.css`)은 컴포넌트와 스타일 — 라이트/다크 두 모드가 판정한다

무언가 이상할 때 "어느 층의 문제인가"부터 물으면, 뒤질 파일과 문서가 바로 좁혀진다.

## 비슷한 학습 지식베이스를 만든다면

제품 매뉴얼은 제품 구조를 따라가지만, 개인·팀 학습 노트는 **나중에 다시 찾는 방식**을
따라가야 한다. 이 레포를 정리하면서 남은 판단을 통증과 해법으로 묶으면 다음과 같다.

| 커졌을 때 보이는 통증 | 도입할 구조 원칙 | 이 레포의 구현 |
|---|---|---|
| 사이드바·랜딩·장 수가 서로 다르다 | 같은 가까운 원본에서 모든 보기를 파생한다 | `_deck.mjs`와 MDX를 `load-decks.mjs`가 합성 |
| 중앙 manifest가 수백 줄의 콘텐츠 목록이 된다 | 정보 소유권을 덱·페이지 가까이 옮긴다 | 덱 정보는 `_deck.mjs`, 그룹·순서는 각 MDX |
| 컴포넌트를 어디서 고칠지 모르겠다 | 역할로 디렉터리를 나눈다 | `layout/` · `docs/` · `demos/` |
| 예전 이름이나 약어로 검색하면 안 나온다 | 검색용 동의어를 본문 HTML에 남긴다 | 페이지 frontmatter·덱 `_deck.mjs`의 `aliases`를 렌더 |
| 오래된 글인지 판단할 수 없다 | 수정일과 **내용 검토일**을 구분하고 미검토를 숨기지 않는다 | `reviewedAt` + `status` + `pnpm report:content` |
| 작업 규칙 파일이 길어 아무도 안 읽는다 | 루트 규칙은 **지도**, 세부는 목적별 문서로 둔다 | `AGENTS.md` → 작성·D2·검증·배포 문서 |
| 빌드는 되는데 페이지·anchor가 빠지거나 중복된다 | 프레임워크 밖의 프로젝트 불변식을 검사한다 | content → build → 렌더된 내부 링크를 `pnpm check`로 묶음 |
| 로컬에서는 고쳤는데 다음 변경에서 다시 깨진다 | 같은 검사를 CI에서도 반복한다 | push·pull request마다 `pnpm check` |

여기서 핵심은 특정 manifest가 아니라 **한 사실에 편집 지점을 하나만 두는 것**이다.
전역 어휘는 `catalog.mjs`, 덱 정보는 그 덱의 `_deck.mjs`, 페이지 소속·순서는 그 MDX가 소유한다.
같은 목록을 사이드바와 랜딩에 다시 적지 않고 파생하며, 파생할 수 없는 규칙만 한 문서를 원본으로 둔다.

### 페이지는 검색 결과 한 건의 크기로

덱은 학습 경로이고, 페이지는 **나중에 검색해서 착지할 단위**다. 한 덱을 거대한 페이지
하나로 만들면 처음 읽기는 편해도, 검색 결과가 늘 같은 페이지를 가리키고 링크도 절
앵커에 의존한다. 반대로 한 문단마다 페이지를 나누면 맥락이 사라진다.

이 레포의 기준은 "하나의 질문이나 판단을 제목·description·목차로 설명할 수 있는가"다.
가능하면 페이지 하나, 너무 크면 h2 묶음을 기준으로 나눈다. 덱의 `index.mdx`는 내용을
복제하지 않고 **왜 읽는지와 어떤 순서로 읽는지**만 안내한다.

### 처음부터 전부 만들지 않는다

아래 장치는 필요해진 순서대로 추가한다.

1. Starlight 기본 라우팅·사이드바·검색으로 글부터 쓴다
2. 서로 무관한 주제가 늘어날 때 topic으로 사이드바를 나눈다
3. 같은 목록을 두 군데 이상 편집하게 될 때 가까운 원본 하나를 정하고 나머지를 파생한다
4. 실제 검색 실패가 쌓일 때 `aliases`, 현재성 판단이 어려울 때 `reviewedAt`·`status`를 넣는다
5. 같은 표현을 세 번째 복붙할 때 문서 컴포넌트로 뽑는다
6. 사람이 반복해서 놓치는 불변식만 검사 스크립트와 CI로 고정한다

:::tip[도입 기준]
좋은 구조는 파일이 많은 구조가 아니라 **같은 실수를 두 번 하지 않게 만든 구조**다.
기본 Starlight로 해결되는 동안은 기본값을 쓰고, 실제로 반복된 통증에만 새 계층을 둔다.
특히 override는 업그레이드 때 다시 확인할 부채이므로 마지막 수단이다(6장).
:::

## 새 덱을 추가하는 절차

이 레포에서 가장 자주 반복될 작업이라 절차로 박아 둔다.

<Steps>

1. `src/content/docs/<덱이름>/`을 만들고 `_deck.mjs`를 둔다

   가까운 성격의 덱 설정을 복사해 `navOrder` · `catalogOrder` · metadata · `category` · `tags` ·
   `termIntro` · `groups` · `map`을 정한다. 이 파일이 있으면 loader가 덱을 자동 발견한다.

2. 같은 폴더에 `_baseline.md`와 `index.mdx`를 만든다

   baseline에는 기준 버전 · 서술 규칙 · 범위 경계를 둔다. index에는 `<LinkButton>` 하나와
   `<DeckMap deck="<덱이름>" />` 하나를 둔다. map 단계는 `_deck.mjs`만 고친다.

3. 본문 페이지를 넣는다

   장 파일명은 `00-intro.mdx`부터 번호로 두고 처음부터 `.mdx`로 만든다. 각 페이지에
   `deckGroup`과 겹치지 않는 `sidebar.order`를 적으면 사이드바와 장 수에 자동 반영된다.
   새 장은 `<Thesis>`를 두고, 개념 학습 덱이면 규칙에 맞춰 `<TermIntro>`도 둔다.

4. `pnpm check`로 설정·본문·빌드·내부 링크를 판정하고, 실제 사이드바와 DeckMap을 확인한다

</Steps>

## 치트시트

### 명령

| 하려는 것 | 명령 |
|---|---|
| dev 서버 (백그라운드) | `pnpm astro dev --background` → `pnpm astro dev stop` / `status` / `logs` |
| 전 페이지 판정 | `pnpm check` |
| 덱별 검토·Thesis 이관 현황 | `pnpm report:content` |
| 배포와 같은 산출물 확인 | `pnpm preview` |
| 깨진 굵게 찾기 | `grep -rho '\*\*[^<*]\{0,45\}' dist --include=index.html \| sort -u` |
| 제목 고치기 전 앵커 참조 확인 | `grep -rn '#앵커-slug' src/content/docs/` |
| 배포 | `main` 푸시 (요청받았을 때만) — 브랜치 푸시는 preview |

### 빌드가 통과해도 깨져 있는 것들

여덟 장에서 반복해 나온, **조용히 깨지는** 지점만 모으면 —

| 증상 | 원인 | 장 |
|---|---|---|
| D2가 코드 블록이거나 빌드 실패 | `astroD2()`가 `starlight()` 뒤, 또는 D2 문법 오류 | 2·5 |
| 다이어그램이 다크 모드에서 안 읽힘 | 팔레트의 `font-color` 누락 | 5 |
| D2를 눌러도 확대되지 않음 | `inline: true`로 SVG를 HTML에 직접 넣음 | 5 |
| 화면에 `**` 가 그대로 보임 | 닫는 `**` 앞 문장부호 + 뒤 조사 | 4 |
| 컴포넌트 안 내용이 코드 블록으로 | JSX 자식 마크다운 들여쓰기 | 4 |
| 외부 참고 링크가 조용히 죽음 | 상대 사이트의 이전·삭제 — 기본 내부 링크 검사 범위 밖 | 7 |
| 제목 옆 Badge 후 링크 변경 | `<Badge>` 앞에 공백 — slug 끝에 `-` | 5 |
| 검색에 새 글이 안 나옴 (배포) | 인덱스는 빌드 산출물 — 배포가 안 된 것 | 8 |
| 하위 경로 배포에서 본문 링크만 깨짐 | 본문 절대 경로 링크에 base 미적용 | 8 |

## 이 덱이 스스로에게 거는 검증

이 덱의 예제는 전부 이 레포다(0장). 그래서 레포가 바뀌면 이 덱도 낡는다 —
컴포넌트 목록(6장), 배포 설정(8장), 덱 추가 절차(이 장)를 고쳤다면
`starlight` 덱의 해당 대목도 같이 고친다. 기준은 덱 폴더의 `_baseline.md`에 있다.
