## 문서를 두는 곳은 세 부류다

"문서 어디에 쓰지"의 선택지는 많아 보이지만, **본문이 어디에 사는가**로 가르면 세 부류로 정리된다.

<CardGrid>
<Card title="SaaS 위키" icon="document">
**Notion · Confluence · Slite**

본문이 그 서비스의 DB에 산다. 편집은 가장 편하고 협업 기능이 강하다.
대가는 이식성 — 내보내기는 되지만 서식·구조가 뭉개지고, 외부 공개·커스터마이즈가 제한된다.
</Card>
<Card title="문서 호스팅 서비스" icon="cloud-download">
**GitBook · ReadMe · Mintlify**

git 연동은 되지만 렌더링·검색·테마를 서비스가 쥔다.
"docs-as-code의 편집 + SaaS의 운영"이라는 절충. 팀 요금제가 붙고, 커스터마이즈는 서비스가 허용한 만큼만.
</Card>
<Card title="docs-as-code SSG" icon="seti:git">
**Starlight · Docusaurus · VitePress · MkDocs**

본문이 내 레포의 마크다운이고, 빌드도 배포도 내가 쥔다.
자유도와 소유권이 최대인 대신 **초기 설정과 운영이 내 몫**이다. 이 레포의 선택.
</Card>
</CardGrid>

0장에서 봤듯 이 레포의 요구는 축적·검색·참조 + 파일 소유였으므로 세 번째 부류로 좁혀졌다.
남은 것은 그 안에서 어느 SSG인가다.

## docs-as-code 진영의 후보들

2026년 기준, 문서 특화 SSG의 주전급은 이렇다.

| 도구 | 기반 | 만든 곳 | 특징 한 줄 |
|---|---|---|---|
| **Starlight** | Astro | Astro 팀 | 기본 zero-JS · 검색/i18n/다크모드 내장 · 프레임워크 무관 컴포넌트 |
| Docusaurus | React | Meta | 가장 큰 생태계 · **문서 버전 관리**(v1/v2 병행 문서) · 블로그 내장 |
| VitePress | Vue | Vue 팀 | 가볍고 빠름 · Vue 생태계 표준 · 커스터마이즈는 Vue로 |
| MkDocs Material | Python | 커뮤니티 (오픈소스 + 스폰서) | Python 생태계 표준 · 플러그인 성숙 · 마크다운 확장 문법이 독자적 |
| Nextra / Fumadocs | Next.js | 커뮤니티 | Next.js 앱에 문서를 **끼워 넣을 때** — 문서가 앱의 일부인 경우 |
| Sphinx | Python | Python 프로젝트 | docstring에서 **API 문서 자동 생성** — 라이브러리 레퍼런스용 |
| mdBook | Rust | Rust 프로젝트 | 책 형태 문서 — 단순하고 빠르지만 확장성이 좁다 |

전부 마크다운 + git + 정적 빌드라는 뼈대는 같다. 갈리는 지점은
**① 무엇이 내장인가**(검색·i18n·다크모드를 조립해야 하나) 와
**② 커스터마이즈할 때 어떤 기술을 요구하는가**(React냐 Vue냐 Python이냐) 다.

특정 프레임워크에 묶일 이유가 없었다.

## 왜 Starlight였나

결승에 남는 것은 보통 Starlight와 Docusaurus다. 이 레포가 Starlight를 고른 이유 —

### 처음부터 있던 요구 — 덱 여러 개를 한 사이트에

이 레포는 덱이 하나뿐이던 첫 커밋에 이미 덱별 사이드바 플러그인을 넣었고, 같은 날 두 번째 덱이
붙었다. 지금은 23개다. 서로 무관한 주제를 한 사이드바에 늘어놓지 않는 것이 나중에 생긴 고민이
아니라 **출발 조건**이었다는 뜻이다(구조는 [3장](/starlight/03-starlight/)).

그런데 이 요구만으로는 후보가 갈리지 않는다. Docusaurus는 문서 묶음을 여러 인스턴스로 두는
기능이 있고, VitePress는 경로별 사이드바가 기본이다. "네이티브로 되는가"만 따지면 오히려
Starlight가 진다 — 이 레포의 덱별 사이드바는 코어 기능이 아니라 커뮤니티 플러그인
(`starlight-sidebar-topics`)이다.

갈린 것은 되느냐가 아니라 **얼마를 내느냐**였다. 덱 23개에서 Docusaurus는
[문서 묶음마다 docs 플러그인 인스턴스](https://docusaurus.io/docs/docs-multi-instance)를
설정에 세우고 사이드바 파일도 인스턴스별로 두지만, 이 레포는 manifest 배열에 항목 하나를
더하면 사이드바와 랜딩 카드가 같이 나온다. 다만 공정하게 보면 Docusaurus 설정도 JS라 배열을
돌려 인스턴스를 생성하는 glue를 직접 짤 수 있고, 지금의 덱 드롭다운 사이드바 같은 UI는
어느 쪽이든 기본이 아니라 override가 필요하다 — Starlight는 컴포넌트 override(6장),
Docusaurus는 테마 컴포넌트를 꺼내 고치는 swizzling. 차이는 가능/불가능이 아니라
**직접 유지할 glue의 양**이다.

:::tip[요구사항과 결정 근거는 다르다]
요구사항이 후보 전부를 통과하면 그건 **결정 근거가 아니라 전제**다. 거기서 멈추지 말고
"그래서 각자 얼마를 내는가"로 한 칸 더 들어가야 선택의 이유가 나온다.
:::

### 검색이 내장이다 — Docusaurus와 실제로 갈리는 지점

Starlight는 정적 검색 엔진 [Pagefind가 내장](https://starlight.astro.build/ko/guides/site-search/)이라
설정 없이, 외부 서비스 없이, 한국어 본문까지 첫 빌드부터 검색된다(8장).
[Docusaurus는 검색이 코어에 없다](https://docusaurus.io/docs/search) — 공식 경로인 Algolia
DocSearch는 무료지만 **공개 사이트 + 신청·승인이 필요한 외부 SaaS**고, 아니면 커뮤니티 로컬
검색 플러그인을 골라 한국어 토크나이징까지 직접 챙겨야 한다. 목적이 "축적·검색·참조"인
개인 노트에서 검색이 외부 의존이 되는 것 — 일상에서 가장 크게 갈리는 차이는 사실 이거다.

### 기본값이 문서에 맞다

Docusaurus는 React 앱이다 — 문서 페이지에도 React 런타임이 실리고 하이드레이션이 돈다.
Starlight는 Astro의 **zero-JS 기본값**(2장) 위에 있어서 문서 페이지가 거의 순수 HTML로 나간다.
읽는 게 전부인 사이트에서 저 JS는 얻는 것 없이 내는 비용이다.

다만 크기를 정직하게 재면 이건 **결정타가 아니라 안 낼 이유가 없는 세금**이다. Docusaurus
사이트도 충분히 빠르고, 독자가 사실상 본인 혼자인 개인 노트에서 체감 차이는 제한적이다.
"공짜로 낼 이유가 없다"까지가 이 논거의 정확한 크기다.

### 조립할 게 없다

검색(Pagefind) · 다크모드 · 목차 · i18n · 접근성 · SEO(canonical·sitemap)가 **전부 내장**이다.
MkDocs나 VitePress에서 플러그인을 골라 조립해야 하는 것들이 첫 빌드부터 그냥 있다.
혼자 운영하는 사이트에서는 "고를 자유"보다 **"고르지 않아도 되는 기본값"** 이 크다.

공정하게 덧붙이면 이 논거가 겨냥하는 것은 **MkDocs·VitePress**다. Docusaurus도 다크모드 ·
목차 · i18n · 블로그까지 내장인 batteries-included 진영이라, Docusaurus 상대로 유효한
내장 차이는 위의 검색 하나다.

### 컴포넌트가 프레임워크에 묶이지 않는다

본문 확장이 필요하면 Astro 컴포넌트를 만들면 되고(6장), 정말 필요하면
React든 Vue든 섞어 넣을 수도 있다. 이 레포의 `TermIntro`·`DeckMap` 같은 컴포넌트는
전부 순수 Astro라 **클라이언트 JS를 하나도 만들지 않는다.**

### 필요한 만큼만 손댈 수 있다

frontmatter 한 줄 → 내장 컴포넌트 → 커스텀 컴포넌트 → 컴포넌트 override(사이드바 교체 같은
UI 수술)까지, 개입의 사다리가 촘촘하다. 이 레포는 사다리를 실제로 끝까지 썼다 —
덱 드롭다운 사이드바가 override의 산물이다(6장).

### 갈림길이 아니었던 것들

공정한 비교를 위해 **Docusaurus의 감점 요인이 아닌 것**도 적어 둔다.

- **React를 알아야 한다** — 개발자 1인 레포에서 커스터마이즈 기술이 React냐 Astro냐는
  단점이 아니다. 위 zero-JS 논거는 "작성자가 React를 배워야 해서"가 아니라 **"독자 페이지에
  런타임이 실려서"** 다 — 작성자 비용과 독자 비용을 섞으면 비교가 흐려진다.
- **빌드가 느리다** — 이 악명은 webpack 기반이던 시절 수천 페이지 사이트 얘기다.
  [v3.6의 Docusaurus Faster](https://docusaurus.io/blog/releases/3.6)(Rspack 전환)로 크게
  해소됐고, 이 레포 규모(페이지 ~340장)면 어느 쪽이든 몇 분 안이다. 게다가 D2 SVG 생성(8장)
  같은 다이어그램 빌드 비용은 프레임워크와 무관해서 갈아타도 그대로다.

:::caution[함정 — 정직한 단점]
Starlight는 **아직 0.x다.** 마이너 업그레이드가 breaking일 수 있고, 이 레포처럼
override를 쓰면 업그레이드 때 맞춰 고칠 각오가 필요하다. 커뮤니티 플러그인 수도
Docusaurus보다 적다. "가장 안전한 선택"이 아니라 **"이 요구에 가장 맞는 선택"** 이었다.
:::

## AI가 작성자일 때

이 레포의 실제 작성 주체는 사람이 아니라 **Claude Code·Codex 같은 코딩 에이전트**다 —
사람은 정리할 주제를 요구하고 디테일 수정을 지시하는 편집장 역할이다. 위 비교는 사람
작성자를 전제로 했는데, 작성자가 AI로 바뀌면 축이 두 개 더 들어온다 — **검증 루프**와
**모델 지식**이다. (MDX의 까다로움은 후보 양쪽이 같이 쓰므로 축이 되지 못한다 — 함정인
동시에, 빌드가 문법을 잡아준다는 뜻이기도 하다.)

### 부류 선택은 더 굳어진다

AI 작성자에게 필요한 것은 세 가지다 — 산출물이 **diff 가능한 텍스트 파일**일 것,
**빌드라는 결정적 판정자**가 있을 것, git으로 리뷰·롤백이 될 것. SaaS 위키는 셋 다 없다 —
API로 블록을 조작해야 하고, 판정자가 없고, 되돌리기가 서비스 히스토리에 갇힌다.
사람에게 "이식성 대 편의"였던 첫 갈림이 AI 작성자에게는 **작동 대 불능**에 가깝다.

### 검증 루프 — Starlight가 유리해지는 축

정적 HTML은 **빌드 통과 + 산출물 grep**으로 눈 없이 검증된다. 하이드레이션이 도는 페이지는
"빌드는 통과했는데 브라우저에서만 깨지는" 실패 부류가 추가되는데, 브라우저 확인은 AI에게
가장 비싼 검증이다. 빌드가 못 잡는 목록(8장)이 짧을수록 AI가 혼자 끝내는 작업의 비율이 높아진다.

그리고 앞에서 "갈림길이 아니다"라고 했던 **빌드 시간이 여기서 되돌아온다** — CI 문제가
아니라 루프 지연으로. AI는 한 세션에 `pnpm check`를 수십 번 돌리므로, 이 레포의
339페이지 14초 빌드와 페이지마다 React SSR을 도는 빌드의 차이가 반복 횟수만큼 곱해진다.
사람에게 무시할 차이가 AI에게는 아니게 되는 지점이다.

### 모델 지식 — Docusaurus가 유리해지는 축

학습 코퍼스가 크고 v3 API가 안정된 Docusaurus는 AI가 설정·컴포넌트 코드를 쓸 때 정확도가
높다. **Starlight는 0.x라 모델의 사전 지식이 낡은 버전을 가리키는 일이 실제로 생긴다.**
이 레포의 대응은 규칙 파일이다 — `_baseline.md`가 기준 버전(Starlight 0.41 · Astro 7)을
못 박고 "레포 실물이 정본"을 선언하며, `docs/content-authoring.md`가 MDX·Mermaid 함정을
목록화한다. AI의 낡은 사전 지식은 더 좋은 모델이 아니라 **레포 안의 규칙 파일로 덮는다.**

:::tip[규칙은 대화가 아니라 파일에 둔다]
AI 작성자는 세션마다 기억이 리셋되고 사전 지식은 낡는다. "저번에 말했잖아"는 통하지 않는다 —
지켜야 할 것은 전부 `AGENTS.md`·`_baseline.md`·`docs/`의 규칙 파일에 두고, 세션이 그걸 읽고
시작하게 한다. 이 장 자체도 그 체계 위에서 AI가 썼다.
:::

## 선택이 달라지는 경우

같은 비교를 다른 상황에 대입하면 결론이 바뀐다 — 이 표가 이 장의 재사용 가치다.

| 상황 | 추천 | 이유 |
|---|---|---|
| 편집자가 비개발자 여럿 | Notion · GitBook | git이 진입 장벽이다 — 도구가 아니라 사람에 맞춘다 |
| 제품 문서 + 버전별 문서 병행 | Docusaurus | v1/v2 문서 버전 관리가 내장 · 생태계 최대 |
| Vue 프로젝트의 공식 문서 | VitePress | 생태계 관례 — 기여자가 이미 아는 도구 |
| Python 라이브러리 레퍼런스 | Sphinx · MkDocs | docstring 자동 추출이 본체 |
| Next.js 서비스 안의 /docs | Nextra · Fumadocs | 앱과 문서가 한 배포 단위 |
| **무관한 주제 여러 개를 담는 개인·소규모 학습 노트** | **Starlight** | 검색까지 내장 + zero-JS + manifest 한 벌에서 덱마다 사이드바 |

### 이미 고른 뒤에 오는 추천 — 갈아타기는 다른 문제다

위 표는 전부 "처음 고를 때" 기준이다. 운영 중인 사이트에 새 도구를 추천받으면
— 실제로 Fumadocs를 추천받은 적이 있다 — 판정에 **전환 비용**이 추가된다.

Fumadocs로 그 판정을 해 보면: Starlight가 "설정하면 완성된 문서 사이트"라면
Fumadocs는 "문서 사이트를 조립하는 부품 세트"에 가깝다. React 컴포넌트를 본문에
자유롭게 심고 문서를 Next.js 앱의 일부로 넣을 때 강한데, **그 강점이 여기서는 살 데가 없다** —
이 사이트는 독립 정적 사이트이고 React 런타임이 필요한 지점이 없다.
반면 전환 비용은 전방위다:

- **본문이 Starlight 문법에 물려 있다** — `:::tip` aside, `<Steps>`·`<Tabs>` 내장 컴포넌트를 전 페이지가 쓴다
- **커스텀 컴포넌트 전부 재작성** — `TermIntro`·`DeckMap`·사이드바 override는 Astro 컴포넌트라 React로 다시 써야 한다
- **파이프라인 재구축** — D2·Mermaid 다이어그램 통합, topics 기반 덱 구조, Pagefind 검색(대체제인 Orama는 한국어 토크나이징을 따로 설정해야 한다)

:::tip[재사용할 판정 절차]
새 도구 추천은 두 단계로 판정한다 — ① 위 갈림길 트리에 다시 넣어 **처음부터라도 그걸
골랐을지** 보고, ② 아니라면 끝, 맞더라도 **전환 비용이 새 강점을 넘는지** 계산한다.
"더 좋은 도구인가"가 아니라 "**갈아탈 만큼** 좋은가"가 질문이다.
:::

## 1장 요약

- 문서 도구는 **본문이 어디에 사는가**로 세 부류다 — SaaS 위키 / 호스팅 서비스 / docs-as-code SSG
- docs-as-code 후보들의 차이는 **내장 범위**와 **커스터마이즈에 요구되는 기술**이다
- Starlight를 고른 이유: **검색 내장**(Docusaurus는 외부 의존 — 일상에서 가장 크게 갈리는 차이), 문서에 맞는 zero-JS 기본값, 프레임워크 무관 컴포넌트, 촘촘한 개입 사다리
- **덱 여러 개**는 출발 조건이었지만 후보 전부가 해내므로 결정 근거가 아니다 — 갈린 것은 직접 유지할 glue의 양이다 (manifest 한 줄 대 인스턴스별 설정 + swizzling)
- 갈림길이 아닌 것도 있다 — React 지식 요구, 빌드 시간(v3.6 Rspack 이후). zero-JS 차이도 결정타가 아니라 **안 낼 이유가 없는 세금**이다
- 이 레포의 실제 작성자는 **AI**다 — 검증 루프(빌드=판정자 · 14초 루프)는 Starlight 편, 모델 지식(0.x라 사전 지식이 낡음)은 Docusaurus 편이고, 후자는 `_baseline.md` 같은 규칙 파일로 덮는다
- 단점도 있다 — 0.x의 불안정성, 상대적으로 작은 생태계. 상황이 다르면 선택도 달라진다
- 운영 중에 받은 도구 추천(Fumadocs 등)은 **갈아타기 판정**이다 — 트리 재통과에 더해 전환 비용까지 계산한다
