## 왜 Astro부터 아는가

Starlight만 배우고 Astro를 건너뛰면, 이런 순간마다 막힌다 —

- 빌드 에러가 `astro build` 층에서 난다 (Starlight 문서에는 없는 메시지)
- 컴포넌트를 만들려는데 `.astro` 파일 문법을 모른다 (6장의 전제)
- `astro.config.mjs`를 여는데 어디까지가 Astro고 어디부터가 Starlight인지 모른다

반대로 Astro의 개념 네 개 — zero-JS 기본값, 아일랜드, `.astro` 컴포넌트, 콘텐츠 컬렉션 —
만 잡으면 Starlight는 "그 위에 얹힌 잘 만든 테마"로 단순해진다. 이 장이 그 네 개다.

### 흔한 혼동 — "React 같은 UI 라이브러리인가?"

아니다 — **층위가 다르다.** React는 화면 조각(컴포넌트)을 그리는 UI 라이브러리이고,
Astro는 라우팅·빌드·페이지 생성까지 담당하는 **사이트 프레임워크**다.
비교 상대는 React가 아니라 Next.js 쪽이다.

| | 층위 | 브라우저 JS |
|---|---|---|
| React | 화면 조각을 그리는 **UI 라이브러리** | 런타임이 항상 실린다 |
| Next.js | React 기반 **앱 프레임워크** — 라우팅·빌드까지 | React 런타임 포함 |
| Astro | **콘텐츠 중심 사이트 프레임워크** | 기본 0 — 섬(아래 절)만 |

게다가 Astro는 React의 경쟁자라기보다 **React를 부품으로 끼울 수도 있는 상위 틀**이다 —
상호작용이 필요한 자리에만 React·Vue·Svelte 컴포넌트를 섬으로 심을 수 있다.
층으로 쌓으면 이 사이트는 **Astro(틀) → Starlight(문서 테마) → 덱(콘텐츠)** 세 겹이다.

## 기본값이 반대다 — zero-JS

일반적인 SPA 프레임워크(React·Vue 기반)와 Astro는 출발점이 반대다.

| | SPA 프레임워크 (Next.js 등) | Astro |
|---|---|---|
| 기본 산출물 | JS 앱 — HTML은 그 결과물 | **HTML — JS는 예외적 추가물** |
| 브라우저가 받는 것 | HTML + 프레임워크 런타임 + 앱 코드 | HTML + (필요한 섬의 JS만) |
| 상호작용 | 어디서나 공짜 | 섬으로 선언한 곳만 |
| 맞는 물건 | 앱 — 상태와 상호작용이 본체 | **콘텐츠 — 읽는 것이 본체** |

문서 사이트에서 상호작용은 검색·테마 전환·탭 정도가 전부다. 나머지 99%는 읽기다.
"전부 JS로 만들고 문서라서 덜 쓴다"보다 **"전부 HTML로 만들고 필요한 곳만 JS를 얹는다"** 가
문서의 본성에 맞는다 — 1장에서 Starlight를 고른 첫 번째 이유가 이 기본값이었다.

## 아일랜드 — 필요한 곳만 살아 있다

JS가 필요한 컴포넌트는 `client:*` 지시자로 섬임을 선언한다.

```astro
<SearchBox client:load />     <!-- 페이지 로드 즉시 하이드레이션 -->
<Chart client:visible />      <!-- 화면에 보일 때 비로소 JS 로드 -->
<Widget client:idle />        <!-- 브라우저가 한가할 때 -->
```

지시자가 없는 컴포넌트는 **빌드 때 HTML로 굳고 브라우저에서는 그냥 마크업**이다.
이 사이트에서 실제로 살아 있는 섬은 몇 개 안 된다 — 검색 모달, 테마 전환,
`<Tabs>` 전환, 이미지 확대 dialog. 다이어그램(D2)은 이 목록에 없다. SVG를 빌드 때 만들기
때문이다. 한때 클라이언트에서 SVG를 그리는 mermaid 렌더러도 섬이었지만, 문법 오류가 빌드를
통과하는 비용 때문에 전부 D2로 옮기고 제거했다.
`TermIntro`·`DeckMap` 같은 이 레포의 컴포넌트는 전부 지시자 없이 쓰므로 JS 비용이 0이다.

:::tip[핵심]
"컴포넌트를 쓰면 무거워지지 않나"라는 걱정은 Astro에서는 방향이 다르다 —
**컴포넌트는 기본적으로 빌드 시점 템플릿**이고, 무거워지는 건 `client:*`를 붙인 순간부터다.
:::

## .astro 컴포넌트 — 빌드 때 실행되는 템플릿

`.astro` 파일은 두 부분이다. 위쪽 코드 펜스(`---` 사이)는 **빌드 시점에 서버에서 실행**되는
JavaScript(TypeScript)이고, 아래쪽은 그 결과를 채워 넣는 HTML 템플릿이다.

```astro
---
// 빌드 시점 코드 — 브라우저에는 절대 안 간다
interface Props { title: string; }
const { title } = Astro.props;
const built = new Date().toISOString();
---
<section>
  <h2>{title}</h2>
  <p>이 HTML은 {built} 에 만들어졌다</p>
</section>

<style>
  /* 이 컴포넌트에만 적용된다 — 6장에서 상세히 */
  section { border: 1px solid gray; }
</style>
```

JSX와 닮았지만 결정적으로 다르다 — **클라이언트 상태가 없다.** `useState`도 이벤트 핸들러도
없고, 렌더는 빌드 때 단 한 번이다. 상호작용이 필요하면 `<script>` 태그(브라우저로 감)나
프레임워크 섬을 쓴다. 이 구분이 6장(커스텀 컴포넌트)의 전제라서 여기서 못 박아 둔다.

## 콘텐츠 컬렉션 — 프론트매터에 타입이 붙는다

`src/content/docs/` 아래의 파일들은 그냥 폴더가 아니라 **`docs` 컬렉션**이다.
Starlight가 이 컬렉션의 스키마(어떤 프론트매터 필드가 있고 각각 무슨 타입인지)를 정의해 두었고,
빌드가 모든 파일을 스키마로 검증한다.

- `title`을 빼먹으면 → 빌드 실패 (조용히 깨진 페이지가 생기지 않는다)
- `description:`에 오타로 `descripton:`을 쓰면 → 알 수 없는 필드로 잡힌다
- 파일명이 `_`로 시작하면 → **컬렉션에서 제외** — 빌드·검색·사이드바 어디에도 안 잡힌다. 덱별 `_baseline.md`가 본문 옆에 살아도 안전한 이유다

"마크다운 폴더인데 빌드가 검증해 준다"가 콘텐츠 컬렉션의 가치 전부이고,
docs-as-code에서 SSG가 위키보다 나은 지점 — **깨짐이 배포 전에 잡힌다** — 의 실체다.

## 이 레포에서 Astro가 하는 일

`astro.config.mjs`에서 Astro 층은 `site`와 다이어그램 integration들이다 — 나머지는 전부
`starlight()` 안(3장)이다.

```js
import path from 'node:path';
import { prepareD2 } from './scripts/prepare-d2.mjs';

const d2BinDirectory = await prepareD2(); // 공식 native D2 v0.8.2를 검증·캐시
const currentPath = process.env.PATH?.split(path.delimiter).filter(Boolean) ?? [];
process.env.PATH = [d2BinDirectory, ...currentPath.filter((entry) => entry !== d2BinDirectory)]
  .join(path.delimiter);

export default defineConfig({
  site: 'https://study.upggu.com',   // canonical · sitemap의 기준 주소 (8장)
  markdown: { processor: unified() }, // 이미지 확대 플러그인의 Astro 7 임시 호환 설정
  integrations: [
    astroD2({                       // ```d2를 빌드 시 SVG로 만드는 integration
      layout: 'elk',
    }),
    starlight({ /* 사이트의 나머지 전부 */ }),
  ],
});
```

`prepareD2()`는 시스템 전역 설치 대신 실행 플랫폼의 공식 archive와 고정 SHA-256을 사용한다.
검증된 바이너리는 `node_modules/.astro/d2/v0.8.2/`에 캐시하므로 Cloudflare Pages에서 build
cache 기능을 켠 경우 다음 빌드에 보존할 수 있고, 캐시가 없어도 같은 설정 로드 과정에서 다시 준비된다.

:::caution[함정]
**`astroD2()`가 `starlight()`보다 먼저 와야 한다.** integration은 배열
순서대로 마크다운 파이프라인에 끼어드는데, 순서가 바뀌면 D2 펜스가 Starlight의
코드 블록 처리에 먼저 잡혀 **그냥 회색 코드 블록으로 렌더될 수 있다.**
:::

빌드 흐름으로 보면 이 장의 개념들이 한 줄에 꿰인다 —

```d2 title="MDX 파일이 remark·rehype 변환과 .astro 템플릿 렌더를 거쳐 정적 HTML과 최소한의 JS 번들이 되는 빌드 흐름"
direction: down

classes: {
  key: {
    style: {
      fill: "#dbeafe"
      stroke: "#2563eb"
      font-color: "#1e3a8a"
    }
  }
  mute: {
    style: {
      fill: "#f1f5f9"
      stroke: "#94a3b8"
      font-color: "#334155"
    }
  }
  ok: {
    style: {
      fill: "#dcfce7"
      stroke: "#16a34a"
      font-color: "#14532d"
    }
  }
}

mdx: "*.mdx\n콘텐츠 컬렉션이 검증" { class: key }
transform: "remark · rehype 변환\nD2가 여기 끼어든다" { class: mute }
render: ".astro 템플릿 렌더\n빌드 시점 · 서버" { class: mute }
html: "정적 HTML" { class: ok }
js: "필요한 JS만 번들\n검색 · 탭 · 확대" { class: ok }

mdx -> transform
transform -> render
render -> html
render -> js
```

## 2장 요약

- Astro는 UI 라이브러리가 아니라 **사이트 프레임워크**다 — 비교 상대는 React가 아니라 Next.js이고, React는 오히려 섬으로 끼우는 부품이다
- Astro의 기본값은 **JS를 보내지 않는 것** — 문서처럼 읽기가 본체인 사이트에 맞는 출발점
- 상호작용이 필요한 컴포넌트만 `client:*` 지시자로 **아일랜드**가 되어 JS를 받는다
- `.astro` 컴포넌트 = 빌드 시점 코드(`---` 펜스) + HTML 템플릿. **클라이언트 상태가 없다**
- `src/content/docs/`는 **콘텐츠 컬렉션** — 프론트매터를 빌드가 검증하고, `_` 파일은 제외된다
- 이 레포의 Astro 층은 `site` + 다이어그램 integration이고, **D2가 starlight보다 먼저**여야 한다
