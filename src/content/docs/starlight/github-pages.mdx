## 주소 형태부터 정한다

GitHub Pages는 저장소 이름에 따라 주소가 달라지고, 그 차이가 설정 방법을 가른다.

| 형태 | 주소 | 조건 | 이 사이트에서 |
|---|---|---|---|
| 사용자 사이트 | `https://<계정>.github.io/` | 저장소 이름이 `<계정>.github.io` | 그대로 가능 |
| 커스텀 도메인 | `https://notes.example.com/` | 도메인 DNS와 `public/CNAME` | 그대로 가능 |
| 프로젝트 사이트 | `https://<계정>.github.io/<저장소>/` | 저장소 이름 자유 | **별도 작업 필요** |

이 사이트의 본문 링크는 `/starlight/intro/`처럼 루트 기준이다. 프로젝트 사이트는 Astro `base`를
설정해야 하는데, base는 Astro가 만드는 자산 경로에는 붙지만 **본문에 직접 쓴 절대 경로 링크까지
바꿔 주지 않는다.** [빌드와 검증](/starlight/pipeline/#cloudflare-pages가-아니라면)에서 설명한 제한이다.
처음 배포한다면 사용자 사이트나 커스텀 도메인을 고른다. 이 페이지의 나머지는 그 두 경우를 다룬다.

## site를 실제 주소로 바꾼다

`astro.config.mjs`의 `site`는 canonical 링크와 sitemap의 기준 주소다. 배포 주소와 다르면
검색엔진이 엉뚱한 주소를 대표로 삼는다.

```js title="astro.config.mjs — 사용자 사이트 예"
export default defineConfig({
  site: 'https://<계정>.github.io',
  // base는 두지 않는다. 루트 배포이기 때문이다.
});
```

`<계정>`은 실제 GitHub 계정 이름으로 바꾼다. 커스텀 도메인이면 그 도메인을 넣는다.

## 워크플로 파일을 추가한다

[Astro 공식 GitHub Pages 안내](https://docs.astro.build/en/guides/deploy/github/)의 워크플로에
이 저장소에 필요한 값을 더한 것이다. 기존 `check.yml`은 검사용이므로 그대로 두고 파일을 하나 더 만든다.

```yaml title=".github/workflows/deploy.yml"
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          # 랜딩 카드의 "마지막 수정"이 git log에서 나오므로 전체 이력을 받는다.
          fetch-depth: 0
      - uses: withastro/action@v6
        with:
          package-manager: pnpm@11.20.0
          build-cmd: pnpm build
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v5
```

각 줄이 맡는 일은 다음과 같다.

| 부분 | 왜 필요한가 |
|---|---|
| `fetch-depth: 0` | 기본값 1이면 모든 문서가 같은 날짜로 보인다. 저장소의 `prepare-git-history.mjs`는 Cloudflare Pages에서만 동작하므로 여기서는 checkout이 직접 전체 이력을 받아야 한다 |
| `withastro/action@v6` | lockfile로 패키지 관리자를 감지해 설치·빌드하고 산출물을 Pages 아티팩트로 올린다. Node 기본값은 24다 |
| `package-manager: pnpm@11.20.0` | `pnpm-workspace.yaml`의 `allowBuilds`는 pnpm 10.26 이상 문법이라 버전을 명시한다. `package.json`의 `packageManager`와 같은 값으로 맞춘다 |
| `build-cmd: pnpm build` | `package.json`의 build 스크립트를 그대로 쓴다. D2 바이너리는 이 안에서 GitHub release에서 내려받는다 |
| `deploy-pages@v5` | 빌드 job이 올린 아티팩트를 Pages에 게시한다 |

## Pages의 게시 원본을 Actions로 바꾼다

<Steps>

1. 저장소 **Settings → Pages**로 간다.

2. **Build and deployment → Source**에서 **GitHub Actions**를 고른다. 브랜치 게시 방식은 쓰지 않는다.

3. 워크플로 파일을 `main`에 푸시한다. Actions 탭에서 `Deploy to GitHub Pages`가 실행된다.

4. 두 job이 초록색이 되면 Settings → Pages 상단에 게시된 주소가 보인다.

</Steps>

예상 결과는 `https://<계정>.github.io/starlight/intro/`가 열리고, 아래 명령의 canonical이
`site`에 넣은 주소로 시작하는 것이다.

```bash
curl -s https://<계정>.github.io/starlight/intro/ | grep -o '<link rel="canonical"[^>]*>'
```

첫 실행이 실패하면 로그에서 pnpm 버전과 D2 다운로드 줄부터 본다. 로컬에서 `pnpm check`가
통과하는데 Actions에서만 실패한다면 대개 이 둘 중 하나다.

## 커스텀 도메인을 붙일 때

<Steps>

1. `public/CNAME` 파일에 도메인 한 줄을 넣는다. 빌드 때 `dist/`로 복사된다.

   ```text title="public/CNAME"
   notes.example.com
   ```

2. DNS에서 그 도메인을 GitHub Pages로 향하게 한다. 레코드 종류와 값은
   [GitHub 문서](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site)를 따른다.

3. `astro.config.mjs`의 `site`를 도메인으로 바꾸고 푸시한다.

</Steps>

Settings → Pages의 Custom domain 칸에도 같은 값을 넣어야 HTTPS 인증서가 발급된다.

## 확인할 제한

- **비공개 저장소여도 사이트는 공개다.** GitHub 문서가 명시하는 동작이며, 요금제에 따라 비공개
  저장소의 Pages 자체가 막힐 수 있다.
- 빌드는 GitHub이 제공하는 러너에서 돌며 외부 다운로드가 가능하다. D2 바이너리 다운로드가 여기 의존한다.
- 브랜치별 미리보기는 없다. 다른 브랜치를 미리 보려면 로컬 `pnpm preview`를 쓴다.
- 위 워크플로는 2026-09-18 공식 문서와 이 저장소의 스크립트를 대조해 작성했고, 실제 GitHub Pages
  배포로 실측한 것은 아니다. `package-manager` 입력이 pnpm 11을 받는지는 첫 실행 로그로 확인한다.

## 이해 확인

저장소 이름을 `study-notes`로 두고 그대로 배포하면 무엇이 깨질까? 주소가
`<계정>.github.io/study-notes/`가 되는데 본문 링크는 `/starlight/…`로 루트를 가리키므로
사이드바와 본문 링크가 404가 된다. 저장소 이름을 `<계정>.github.io`로 바꾸거나 커스텀 도메인을 붙인다.
