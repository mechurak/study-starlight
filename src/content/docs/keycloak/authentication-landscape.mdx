<Thesis>AD·LDAP·Keycloak·OAuth·OIDC·SAML은 같은 종류의 기술이 아니며, 저장소·제품·프로토콜·흐름·보호 장치·로그인 경험으로 나눠야 관계가 보인다.</Thesis>

사내 앱이 사용자 비밀번호를 직접 검증하게 두면 앱마다 비밀번호 처리, 로그인 정책, 감사 지점이
늘어난다. 대신 앱은 사용자를 Identity Provider(IdP)로 보내고, IdP가 돌려준 인증 결과를 검증한다.
디렉터리는 계정과 그룹의 원본으로 남고, IdP가 앱 앞에서 로그인과 세션을 맡는다.

## 이 장에서 답할 질문

- AD·LDAP·IdP·OIDC·SAML은 각각 제품인가, 프로토콜인가?
- Authorization Code와 PKCE는 OIDC 로그인 안에서 어떻게 이어지는가?
- Keycloak이 AD를 직접 읽는 경로와 AD FS에 인증을 맡기는 경로는 무엇이 다른가?

## 먼저 종류를 나눈다

이름이 함께 등장한다고 같은 층의 대안은 아니다. 예를 들어 LDAP 대신 OIDC를 고르는 것이 아니라,
디렉터리와 IdP 사이에는 LDAP를 쓰고 IdP와 앱 사이에는 OIDC를 쓸 수 있다.

| 개념 | 종류 | 이 구조에서 하는 일 |
|---|---|---|
| [AD / AD DS](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/virtual-dc/active-directory-domain-services-overview) | 디렉터리 제품·서비스 | 사용자·그룹 같은 디렉터리 객체를 계층 구조로 보관한다. 여기서 AD는 Active Directory Domain Services(AD DS)를 뜻한다. |
| LDAP / LDAPS | 디렉터리 접근 프로토콜 | 디렉터리 entry를 조회하고 bind로 자격 증명을 확인한다. LDAPS는 이 통신을 TLS로 보호한다. |
| [Keycloak](https://www.keycloak.org/docs/26.7.0/server_admin/#core-concepts-and-terms) · [AD FS](https://learn.microsoft.com/en-us/windows-server/identity/ad-fs/ad-fs-overview) | IdP 제품·구성요소 | 사용자를 인증하고 federation 관계를 중계하며 앱에 인증 결과를 제공한다. AD FS는 AD DS와 다른 역할이다. |
| [OAuth 2.0](https://www.rfc-editor.org/rfc/rfc6749.html) | 접근 권한 위임 프레임워크 | 앱이 제한된 API 접근 권한을 access token으로 받게 한다. 그 자체가 사용자 로그인 프로토콜은 아니다. |
| [OpenID Connect(OIDC)](https://openid.net/specs/openid-connect-core-1_0-18.html) | OAuth 2.0 위의 사용자 인증 프로토콜 | OAuth 2.0 흐름에 ID token과 표준 claim을 더해 앱이 로그인한 사용자를 확인하게 한다. |
| [SAML 2.0](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-tech-overview-2.0.html) | 별도 계열의 federation 로그인 프로토콜 | IdP와 앱이 브라우저를 거쳐 XML assertion을 주고받아 로그인한다. OIDC 위에서 동작하는 기술이 아니다. |
| [Authorization Code](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1) | OAuth 2.0의 흐름 | 브라우저에는 access token 대신 짧게 쓰는 일회성 code를 전달하고, 앱이 그 code를 token으로 교환한다. |
| [PKCE](https://www.rfc-editor.org/rfc/rfc7636.html) | Authorization Code의 보호 장치 | 처음 보낸 `code_challenge`와 교환 때의 `code_verifier`를 묶어, code를 훔친 다른 주체의 token 교환을 막는다. |
| SSO | 로그인 경험 | 프로토콜 이름이 아니라 같은 IdP 세션을 여러 앱의 로그인 요청이 재사용해 비밀번호 재입력을 줄인 결과다. |

browser: 사용자 · 브라우저 { class: mute }

앱 A와 앱 B는 서로의 cookie를 공유하지 않는다. 두 앱이 각각 Keycloak 또는 AD FS로 로그인 요청을
보냈을 때 **같은 IdP 세션을 다시 쓰는 지점**이 SSO다. OIDC를 선택했다면 Authorization Code 안에서
`code_challenge`와 `code_verifier`를 확인하는 부분에 PKCE가 붙는다. SAML은 code나 PKCE 없이 별도의
assertion 흐름을 쓴다. 앱이 API를 호출할 때는 OAuth access token을 보내고, API가 그 token과 권한을
검증한다.

## 혼동하기 쉬운 경계를 지킨다

:::caution[이름보다 종류를 먼저 묻는다]
- AD FS·Keycloak은 제품 또는 서버 구성요소이고, OIDC·SAML은 그 사이에서 쓰는 프로토콜이다.
- LDAP는 디렉터리 조회·bind 프로토콜이지 브라우저 SSO 프로토콜이 아니다.
- OAuth 2.0 자체를 로그인 프로토콜이라고 설명하지 않는다. 사용자 인증에는 OIDC 같은 계층이 필요하다.
- PKCE는 OIDC의 대안이 아니라 Authorization Code 흐름에 붙는 code 보호 장치다.
- 인증 성공은 사용자를 확인했다는 뜻이다. 그 사용자가 API 작업을 해도 되는지는 별도의 인가 판단이다.
:::

## 회사 환경에서는 두 연결을 구분한다

회사에 AD와 AD FS가 모두 있어도 Keycloak을 연결하는 경로는 하나로 고정되지 않는다. 자격 증명을
검증하는 주체와 브라우저가 이동하는 위치를 보면 두 경로를 가를 수 있다.

| 경로 | 실제 연결 | 인증하는 곳 | 브라우저 이동 | 선택 결과 |
|---|---|---|---|---|
| Keycloak User Federation | Keycloak → AD/AD DS | Keycloak이 LDAP/LDAPS로 사용자를 찾고 사용자 bind를 요청 | Keycloak 로그인 경로 안에 머묾 | 디렉터리 계정이 Keycloak 사용자 모델로 연결됨 |
| Keycloak Identity Brokering | Keycloak → AD FS | AD FS가 사용자를 인증하고 OIDC 또는 SAML 결과를 Keycloak에 반환 | Keycloak에서 AD FS 로그인 화면으로 이동 | 외부 IdP 신원이 Keycloak realm 사용자와 연결됨 |

[AD FS의 OIDC/OAuth 흐름](https://learn.microsoft.com/en-us/windows-server/identity/ad-fs/overview/ad-fs-openid-connect-oauth-flows-scenarios)과
[SAML 지원](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adfsod/fdd5e60d-6ede-4392-938c-81dbe12a73e6)은
Microsoft 공식 문서에서 확인할 수 있다.
[Keycloak의 external storage 설명](https://www.keycloak.org/docs/26.7.0/server_admin/#using-external-storage)은
LDAP·AD의 사용자와 자격 증명을 공통 사용자 모델로 연결하는 첫 번째 경로를 다룬다.
[Identity Brokering 설명](https://www.keycloak.org/docs/26.7.0/server_admin/#integrating-identity-providers)은
외부 OIDC·SAML IdP가 인증한 결과를 받아 내부 앱으로 중계하는 두 번째 경로를 다룬다. 즉 AD DS와
AD FS를 같은 제품처럼 부르거나, AD가 있다는 이유만으로 연결 방식을 단정하면 안 된다.

## 요약

- AD/AD DS는 디렉터리이고 LDAP/LDAPS는 그 디렉터리에 접근하는 프로토콜이다.
- Keycloak과 AD FS는 IdP가 될 수 있고, 앱과는 OIDC나 SAML로 연결한다.
- OAuth 2.0 access token은 API 권한 위임에 쓰며 OIDC가 사용자 인증을 더한다.
- Authorization Code 흐름의 일회성 code를 PKCE가 보호하고, 공통 IdP 세션 재사용이 SSO 경험을 만든다.
