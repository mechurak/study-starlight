## 문제 — 앱마다 AD에 직접 붙으면

IdP 없이도 사내 인증은 만들 수 있다. 앱마다 LDAP 라이브러리를 넣고
AD에 bind해서 비밀번호를 검증하면 된다. 실제로 오래된 사내 시스템이 대부분 이 구조였고,
앱이 서너 개를 넘는 순간부터 다음이 전부 아프기 시작한다.

```d2 layout=elk pad=40 title="IdP가 없던 시절 그룹웨어·포털·위키·새 앱이 저마다 AD에 직접 연동하던 모습"
direction: right

classes: {
  bad: {
    style: {
      fill: "#fee2e2"
      stroke: "#dc2626"
      font-color: "#7f1d1d"
    }
  }
  mute: {
    style: {
      fill: "#f1f5f9"
      stroke: "#94a3b8"
      font-color: "#334155"
    }
  }
}

before: IdP가 없던 시절 — 앱 N개 × AD 직접 연동 {
  a1: 그룹웨어 { class: bad }
  a2: 사내 포털 { class: bad }
  a3: 위키 { class: bad }
  a4: 새 앱… { class: bad }
  ad1: AD { class: mute }

  a1 -> ad1
  a2 -> ad1
  a3 -> ad1
  a4 -> ad1
}
```

| 통증 | 왜 아픈가 |
|---|---|
| **비밀번호가 모든 앱을 지나간다** | 앱마다 로그인 폼이 있고, 사용자의 AD 비밀번호가 앱 코드·로그·메모리를 통과한다. **앱 하나가 뚫리면 사내 계정이 통째로 새는** 구조다 |
| 로그인이 앱마다 따로 | 아침에 앱 5개를 열면 5번 로그인한다 |
| MFA·정책이 제각각 | MFA를 붙이려면 앱마다 붙여야 하고, 실제로는 아무 데도 안 붙는다 |
| 감사 기록이 흩어진다 | "누가 언제 어디 로그인했나"를 앱 N개의 로그를 모아야 안다 |
| 권한 회수가 안 보인다 | 퇴사 처리는 AD 계정 비활성화로 끝나야 하는데, 앱마다 세션·캐시가 남는다 |
| 웹 밖으로 못 나간다 | LDAP은 사내망 프로토콜이다. 브라우저·모바일·외부 SaaS는 LDAP으로 인증할 수 없다 |

## 해법 — 인증을 한 곳으로 모은다

로그인이라는 일을 **앱에서 떼어내 전담 서버(IdP)에 몰아주는** 것이 SSO의 본질이다.
앱은 로그인 화면을 없애고, 사용자를 IdP로 보낸 뒤, **"누가 로그인했는지"가 적힌 토큰**만 받는다.

```d2 layout=elk pad=40 title="IdP를 세운 뒤 앱 넷이 Keycloak만 바라보고 AD로 가는 LDAP bind는 Keycloak 한 곳뿐인 모습"
direction: down

classes: {
  ok: {
    style: {
      fill: "#dcfce7"
      stroke: "#16a34a"
      font-color: "#14532d"
    }
  }
  key: {
    style: {
      fill: "#dbeafe"
      stroke: "#2563eb"
      font-color: "#1e3a8a"
    }
  }
  mute: {
    style: {
      fill: "#f1f5f9"
      stroke: "#94a3b8"
      font-color: "#334155"
    }
  }
}

after: IdP를 세운 뒤 — 비밀번호는 한 길로만 {
  b1: 그룹웨어 { class: ok }
  b2: 사내 포털 { class: ok }
  b3: 위키 { class: ok }
  b4: 쿠버네티스 { class: ok }
  kc: "Keycloak (IdP)" { class: key }
  ad2: AD { class: mute }

  b1 -> kc
  b2 -> kc
  b3 -> kc
  b4 -> kc
  kc -> ad2: "LDAP bind (여기만)"
}
```

| 통증 | IdP가 이렇게 푼다 |
|---|---|
| 비밀번호 노출 | 사용자는 Keycloak 로그인 화면에만 비밀번호를 내고, Keycloak만 AD bind에 쓴다. 업무 앱은 서명된 토큰만 본다 |
| 반복 로그인 | Keycloak에 세션이 하나 생기고, 같은 realm의 모든 앱이 그 세션을 탄다 |
| MFA·정책 | Keycloak **한 곳에** 걸면 모든 앱에 적용된다 |
| 감사 | 로그인 이벤트가 Keycloak 한 곳에 쌓인다 ([9장](/keycloak/09-ops/)) |
| 회수 | AD 비활성화가 다음 로그인부터 전 앱에 적용되고, 세션도 한 곳에서 끊는다 ([5장](/keycloak/05-sessions/)) |
| 웹 밖 | 앱과는 **웹 표준**(OIDC)으로 대화하므로 브라우저·CLI·모바일 전부 커버한다 ([2장](/keycloak/02-oauth-oidc/)) |

:::tip[핵심]
**AD는 없어지지 않는다.** 계정·그룹·비밀번호의 원본은 그대로 AD다.
Keycloak은 AD를 대체하는 것이 아니라, AD 앞에서 **웹 세계로 통역**해 주는 층이다.
"사용자 저장소(AD)"와 "IdP(Keycloak)"는 서로 다른 층의 물건이다.
:::

## Keycloak은 무엇인가

- **오픈소스 IdP다.** Red Hat이 시작했고 2023년부터 CNCF(Cloud Native Computing Foundation)
  인큐베이팅 프로젝트다. 상용 지원판은 Red Hat build of Keycloak이라는 이름으로 따로 있다
- 17부터 런타임이 WildFly에서 **Quarkus로 바뀌었다** — 옛 문서와 설정 방식이 다른 이유다 ([0장](/keycloak/00-intro/))
- OIDC와 SAML을 모두 말하고, LDAP/AD 페더레이션과 타 IdP 브로커링을 지원한다 —
  즉 **사내 인증 허브**에 필요한 부품이 한 상자에 들어 있다

### 같은 층의 다른 물건들

비교는 같은 층 안에서만 성립한다 — IdP끼리 비교하고, AD와는 비교하지 않는다.

| 층 | 물건 | 비고 |
|---|---|---|
| 사용자 저장소 | **AD**, OpenLDAP | 계정·그룹의 원본. IdP가 아니다 |
| IdP (자체 운영) | **Keycloak**, ADFS, authentik | ADFS는 윈도우 서버에 묶인 마이크로소프트제 IdP |
| IdP (SaaS) | Entra ID, Okta | 관리형. 온프렘 제약이 있으면 선택지에서 빠진다 |
| 경량 브로커 | Dex | 저장소 없이 프로토콜 변환만 하는 얇은 층. k8s 커뮤니티에서 자주 보인다 |

## 사내 구성의 전체 그림 — 3개 경계, 2번의 매핑

이 덱 전체의 지도다. AD와 앱은 서로 직접 모르고, 가운데 Keycloak이 잇는다.
**경계마다 매핑(mapper) 이 한 번씩** 일어난다.

```d2 layout=elk pad=40 title="AD의 사용자 원본이 Keycloak의 User Federation·모델·Protocol Mapper를 거쳐 앱이 보는 토큰 claim으로 옮겨 가는 경로"
direction: down

classes: {
  key: {
    style: {
      fill: "#dbeafe"
      stroke: "#2563eb"
      font-color: "#1e3a8a"
    }
  }
  ok: {
    style: {
      fill: "#dcfce7"
      stroke: "#16a34a"
      font-color: "#14532d"
    }
  }
  mute: {
    style: {
      fill: "#f1f5f9"
      stroke: "#94a3b8"
      font-color: "#334155"
    }
  }
}

ad: "① AD (사용자 원본)" {
  u: "사용자\nsAMAccountName · mail\nmemberOf = 그룹" { class: mute }
}

kc: "② Keycloak realm (IdP)" {
  fed: "User Federation\n(LDAP 매퍼)" { class: key }
  model: 사용자 · 그룹 · 롤 모델 { class: ok }
  pm: Protocol Mapper { class: key }

  fed -> model
  model -> pm
}

app: "③ 앱 · 쿠버네티스 (client)" {
  token: "토큰의 claim만 본다\npreferred_username · email · groups" { class: mute }
}

ad.u -> kc.fed: LDAPS bind + 속성 변환
kc.pm -> app.token: OIDC 토큰 발급
```

| 경계 | 무슨 변환이 일어나나 | 어디서 설정 | 다루는 장 |
|---|---|---|---|
| **① AD → Keycloak** | AD 속성·그룹 → Keycloak 사용자·그룹·롤 | User Federation의 **LDAP 매퍼** | [4장](/keycloak/04-ad-federation/) |
| **② Keycloak → 앱** | Keycloak 모델 → **토큰 claim** | client의 **Protocol Mapper** | [3장](/keycloak/03-structure/) |

그래서 "AD 그룹이 앱까지 어떻게 오나"의 전체 사슬은 —
**AD `memberOf` → (LDAP group 매퍼) → Keycloak 그룹 → (protocol mapper) → 토큰의 `groups` claim → 앱이 인가에 사용.**

:::caution[함정]
두 매핑은 **따로 설정하고 따로 고장난다.** Keycloak 콘솔에 그룹이 보여도
protocol mapper가 없으면 토큰에 안 실리고, 매퍼가 있어도 LDAP 쪽이 끊겼으면
그룹 자체가 안 들어온다. "안 보인다" 문의를 받으면 **어느 경계인지부터** 가른다.
:::

## 1장 요약

- 앱마다 AD 직접 연동은 **비밀번호가 모든 앱을 지나가는** 구조다 — 이게 IdP가 푸는 1번 통증
- SSO의 본질은 "로그인 상태 공유"가 아니라 **"로그인이라는 일을 IdP에 몰아준 것"**
- AD는 사용자 저장소로 남고, Keycloak은 그 앞의 **통역 층**이다 — 서로 다른 층
- 전체 그림은 **3개 경계, 2번의 매핑** — AD→Keycloak(4장), Keycloak→앱(3장)
