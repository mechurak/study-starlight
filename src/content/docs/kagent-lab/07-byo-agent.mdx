## 책임이 어떻게 달라지나

| 항목 | Declarative Agent | BYO Agent |
|---|---|---|
| Agent logic | `systemMessage`와 resource 조합 | application code와 framework |
| runtime | kagent가 표준 runtime 구성 | image 안에 포함 |
| protocol | kagent runtime이 제공 | image가 A2A server 계약 구현 |
| dependency | kagent release가 주로 고정 | project lockfile·image가 고정 |
| 공급망 | CR·prompt·tool reference 검토 | code·dependency·base image·SBOM까지 검토 |

이번 장의 필수 범위는 **project 생성 → image build → 로컬 실행**이다. cluster 배포는 registry와 Secret을
준비한 뒤에만 선택한다. `localhost` image를 kind node가 자동으로 볼 수 있다고 가정하지 않는다.

## project 만들기

cluster와 별개인 작업 디렉터리에서 실행한다. 생성물에는 별도 Git 저장소를 만들 필요가 없다.

```bash
mkdir -p /tmp/kagent-lab-byo
cd /tmp/kagent-lab-byo
kagent init adk python labbyo \
  --model-provider OpenAI \
  --model-name gpt-4.1-mini
cd labbyo
```

`/tmp`의 생성물은 임시 학습 파일이다. 필요한 code는 직접 검토한 뒤 별도 project로 옮기고, API key나 `.env`
파일은 옮기지 않는다.

```text
labbyo/
├── labbyo/              # Agent code와 Agent Card
├── kagent.yaml          # build·run·deploy metadata
├── pyproject.toml       # Python dependency
├── docker-compose.yaml  # local runtime
└── README.md
```

실제 생성 결과가 이 목록과 다르면 설치된 CLI version의 README를 원본으로 삼는다.

### 사내 LiteLLM을 쓰면 generated code도 바꾼다

Declarative Agent의 `ModelConfig`는 BYO image 안의 model client에 자동 적용되지 않는다. v0.9.9의 OpenAI template은
`LiteLlm(model="openai/<이름>")`과 `OPENAI_API_KEY`만 생성하므로 그대로 실행하면 public OpenAI endpoint를
향한다. OpenAI API를 직접 쓸 수 없다면 `labbyo/agent.py`의 `create_model()`을 명시적으로 바꾼다.

```python
import os

from google.adk.models.lite_llm import LiteLlm


def create_model():
    return LiteLlm(
        model=f"openai/{os.environ['LITELLM_MODEL']}",
        api_base=os.environ["LITELLM_BASE_URL"],
        api_key=os.environ["LITELLM_API_KEY"],
    )
```

generated `docker-compose.yaml`의 Agent service에도 세 변수를 전달한다.

```yaml
environment:
  - LITELLM_MODEL=${LITELLM_MODEL}
  - LITELLM_BASE_URL=${LITELLM_BASE_URL}
  - LITELLM_API_KEY=${LITELLM_API_KEY}
```

이 변경은 `ModelConfig` 재사용이 아니라 BYO application code의 model client 설정이다. build 전에 diff를 읽고,
LiteLLM alias가 tool calling을 지원하는지도 다시 확인한다.

## build와 local run

<Steps>

1. **선택한 model credential이 현재 shell에 있는지 확인한다**

   ```bash
   if test -n "$OPENAI_API_KEY" || test -n "$LITELLM_API_KEY"; then
     echo "model API key is set"
   fi
   ```

2. **project image를 만든다**

   ```bash
   kagent build
   ```

3. **로컬 terminal UI에서 실행한다**

   ```bash
   kagent run
   ```

4. generated Agent의 기본 tool을 한 번 호출하고 응답을 본다. 종료는 `Ctrl+C`다.

5. code나 instructions 한 줄을 바꾼 뒤 다시 `kagent build`, `kagent run`해 image build가 변경 경계임을 확인한다.

</Steps>

로컬 성공은 code와 model 연결을 빠르게 검증한다. Kubernetes scheduling, registry pull, ServiceAccount,
NetworkPolicy, Secret reference, A2A route까지 검증한 것은 아니다.

## cluster 배포 전 gate

다음 질문에 모두 답할 수 있을 때만 cluster deploy로 넘어간다.

- image 이름이 kind node가 pull할 registry를 가리키는가?
- mutable `latest`가 아니라 digest나 immutable tag를 기록했는가?
- `.env.production`이 Git에서 제외되고 최소 key만 가지는가?
- generated `kagent.yaml`의 Agent 이름·namespace·port·A2A 설정을 검토했는가?
- image를 non-root와 제한된 filesystem·resource로 실행할 수 있는가?

공식 local development 흐름은 registry 준비 뒤 다음 형태로 build/push와 deploy를 연결한다.

```bash
kagent build --push
kagent deploy --env-file .env.production
```

이 두 명령은 **registry와 production env file을 사용하도록 project를 먼저 설정한 경우에만** 실행한다.
이 입문 덱은 특정 registry credential을 가정하지 않으므로 cluster 배포를 필수 완료 조건으로 두지 않는다.

## BYO resource에서 볼 계약

cluster에 배포된 BYO Agent는 개념상 다음 필드를 갖는다. placeholder image를 그대로 적용하지 않는다.

```yaml
apiVersion: kagent.dev/v1alpha2
kind: Agent
metadata:
  name: lab-byo
  namespace: kagent
spec:
  type: BYO
  byo:
    deployment:
      image: registry.example/lab-byo@sha256:<digest>
      env:
        - name: LITELLM_MODEL
          value: company-model-alias
        - name: LITELLM_BASE_URL
          value: https://litellm.company.example/v1
        - name: LITELLM_API_KEY
          valueFrom:
            secretKeyRef:
              name: lab-byo-model
              key: LITELLM_API_KEY
```

kagent가 image를 실행해 주더라도 Agent logic·dependency·secret 사용·A2A implementation은 image 제작자의
책임이다. 이것이 Declarative에서 BYO로 넘어갈 때 넓어지는 신뢰 경계다.

## 안 될 때 먼저 볼 것

| 증상 | 확인 |
|---|---|
| `kagent init`이 실패 | CLI version과 지원 framework·language — `kagent init --help` |
| `kagent build`가 실패 | Docker daemon 실행 여부, base image pull과 프록시·registry 접근 |
| `kagent run`이 바로 종료 | container log — model key 환경 변수 누락, 로컬 포트 충돌 |
| LiteLLM인데 요청이 public OpenAI로 나감 | `create_model()`의 `api_base`와 compose의 환경 변수 전달 |
| LiteLLM 호출이 `400` | model alias 뒤 upstream의 function/tool calling 지원 |

## 완료 체크

- generated project의 code·`kagent.yaml`·compose 역할을 구분한다.
- `kagent build`와 `kagent run`으로 local loop를 한 번 돌았다.
- LiteLLM을 선택했다면 BYO code와 runtime에 model·`api_base`·credential을 별도로 전달했다.
- 로컬 성공과 cluster 배포 성공이 다른 검증이라는 것을 설명한다.
- registry와 Secret이 준비되지 않았다면 deploy 명령을 실행하지 않았다.
