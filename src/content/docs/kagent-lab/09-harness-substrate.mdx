이 장은 cluster가 필요 없는 개념 장이다. 8장에서 cleanup을 마친 뒤, 이 실습이 다루지 않은 두 실행 형태가
무엇을 풀고 어떤 인프라 준비를 요구하는지 지도만 그린다.

## 왜 실행 기반이 따로 필요한가

2~7장의 Agent는 `Declarative`든 `BYO`든 배포하면 A2A 요청을 기다리는 **상주 Deployment**가 됐다.
이 모델은 Agent가 몇 개일 때는 단순하고 좋지만, 두 방향에서 한계가 온다.

- **idle 낭비** — Agent가 수십·수백 개 등록되면 대부분은 호출을 기다리며 놀고 있는데도 pod마다
  memory·CPU를 계속 점유한다. Agent 수만큼 pod를 늘리는 구조는 밀도가 나쁘다.
- **오래 사는 작업 환경** — coding agent는 반대로 filesystem과 process 상태를 세션 너머로
  유지해야 한다. 요청-응답만 처리하는 kagent 기본 runtime에 이 상태를 욱여넣을 수 없다.

kagent는 이 두 요구를 `Agent.spec.type`에 값을 추가하는 대신 **별도 Kubernetes kind와 별도 runtime**으로
푼다. 그 runtime이 [Agent Substrate](https://kagent.dev/docs/kagent/concepts/agent-substrate)다.

## 세 실행 형태 나란히 보기

| | `Agent` (이 실습 2~7장) | `SandboxAgent` | `AgentHarness` |
|---|---|---|---|
| 실행 위치 | Deployment pod | Agent Substrate actor | Agent Substrate actor |
| 상주 방식 | 항상 떠 있음 | idle이면 snapshot으로 내려감 | 장기 세션 유지 |
| 안의 내용 | kagent runtime 또는 BYO image | Declarative 선언과 비슷한 Go agent | OpenClaw·Hermes 같은 외부 coding agent |
| 푸는 문제 | 항상 호출 가능한 Agent | idle compute 회수 | coding agent sandbox의 lifecycle 관리 |

`SandboxAgent`는 Job처럼 매번 사라지는 방식이 아니다. 논리적 Agent는 그대로 있고, idle일 때 상태를
snapshot으로 내렸다가 다음 요청에서 이어지는 **suspendable** 방식이다.

## Agent Substrate — worker pool과 snapshot

Agent Substrate는 Agent 수명주기를 pod에서 분리한다. 미리 데워 둔 소수의 worker pod pool 위에
actor(실행 중인 Agent 인스턴스)를 다중화하고, idle actor의 상태는 압축해 object storage로 내린다.

인프라 관점에서 달라지는 것은 네 가지다.

| 관심사 | 상주 Deployment | Agent Substrate |
|---|---|---|
| 밀도 | Agent 수 = pod 수 | 다수 Agent가 소수 worker를 공유 |
| 시작 시간 | cold boot | snapshot 복원 |
| 격리 | 컨테이너 격리 | gVisor sandbox |
| 새 의존성 | 없음 | snapshot용 object storage(S3·GCS) |

## AgentHarness — coding agent의 원격 sandbox

[AgentHarness](https://kagent.dev/docs/kagent/concepts/agent-harness/)는 OpenClaw·Hermes 같은
**외부 coding agent를 담는 원격 sandbox의 lifecycle 관리** resource다. kagent가 agent runtime을
workload 안에 패키징하는 대신, 이미 존재하는 coding agent를 Substrate actor 안에서 돌리고
UI·messaging channel로 연결한다.

- `spec.substrate`가 실행 기반을 정한다 — `workerPoolRef`(어느 WorkerPool에서 돌릴지),
  `snapshotsConfig`(actor 상태 snapshot을 어디에 둘지), `workloadImage`(sandbox image 교체).
- controller는 harness마다 `ActorTemplate`을 생성하고, 여러 chat 세션을 하나의 공유 actor에 다중화한다.
- coding agent의 stdio ACP server는 sandbox 안의 `acp-shim`이 WebSocket으로 바꿔 controller와
  UI·API에 노출한다.

7장의 BYO Agent가 "A2A 계약을 구현한 image를 가져오는" 방식이었다면, AgentHarness는 A2A를 구현하지 않은
coding agent를 ACP 계약 그대로 받아들이는 자리다. 신뢰 경계는 BYO보다 더 넓다 — sandbox 안에서
filesystem과 process를 가진 code가 장시간 실행된다.

## kind 실습 밖에 있는 이유와 준비물

이 덱이 두 형태를 hands-on으로 다루지 않는 이유는 개념이 어려워서가 아니라 **전제 인프라** 때문이다.
Agent Substrate는 gVisor로 격리된 worker pod와 snapshot을 받아 줄 object storage를 요구한다.
단일 kind 입문 실습의 범위를 넘고, 활성화 절차는
[공식 설치 문서](https://kagent.dev/docs/kagent/introduction/installation)에서 확인한다.

사내에서 검토가 필요해지는 신호는 이렇다.

- 등록된 Agent 수가 동시에 활성인 수를 크게 웃돌아 idle pod 비용이 눈에 띈다.
- 사내 사용자에게 OpenClaw 같은 coding agent 세션을 제공하려 한다.
- Agent가 실행하는 code를 컨테이너 격리보다 강하게 가두라는 보안 요구가 있다.

이때 인프라 파트가 준비할 것은 gVisor를 지원하는 node pool과 object storage다. 온프렘이라면
snapshot 저장소로 [MinIO](/onprem/06-minio/) 같은 S3-compatible storage가 후보가 된다.

## 완료 체크

- `SandboxAgent`·`AgentHarness`가 `Agent.spec.type`의 값이 아니라 별도 kind라고 말할 수 있다.
- Agent Substrate가 무엇을 아끼고(idle compute) 무엇을 새로 요구하는지(gVisor·object storage) 설명할 수 있다.
- MCP·A2A에 이어 ACP가 어느 자리의 계약인지 — coding agent 구동 — 구분할 수 있다.
- 상주 Deployment로 충분한 경우와 Substrate 검토가 필요한 신호를 구분할 수 있다.
