## 먼저 남길 것 확인

다음 질문에 따라 한 경로만 고른다.

| 다음 행동 | 정리 방법 |
|---|---|
| 2~7장을 다시 반복한다 | custom resource만 삭제 |
| 다른 kagent 기능을 더 탐색한다 | custom resource만 삭제하고 demo profile 유지 |
| 실습을 끝낸다 | `kagent-lab` kind cluster 전체 삭제 |

port-forward와 dashboard terminal은 각각 `Ctrl+C`로 종료한다. 로컬 tunnel을 끄는 것은 cluster resource를
지우는 작업이 아니다.

## 선택 A — 만든 resource만 지우기

<Steps>

1. **정확한 대상이 있는지 확인한다**

   ```bash
   kubectl -n kagent get \
     agent/lab-reader agent/simple-fetch-agent mcpserver/mcp-website-fetcher
   ```

2. **이 덱에서 만든 셋만 지운다**

   ```bash
   kubectl -n kagent delete \
     agent/lab-reader agent/simple-fetch-agent mcpserver/mcp-website-fetcher
   ```

3. **sample과 control plane이 남았는지 확인한다**

   ```bash
   kubectl -n kagent get agents
   kubectl -n kagent get pods
   ```

</Steps>

`broken-model-agent`는 6장에서 이미 지웠다. 남아 있다면 이름을 확인하고 별도로 삭제한다.

## 선택 B — 전용 cluster 전체 지우기

실습 종료의 기본 경로다. cluster 안의 kagent resource, Secret, session, DB 상태는 함께 사라지고 복구할 수 없다.

<Steps>

1. **kind cluster 이름을 확인한다**

   ```bash
   kind get clusters
   ```

2. **정확히 `kagent-lab`만 삭제한다**

   ```bash
   kind delete cluster --name kagent-lab
   ```

3. **목록과 context에서 사라졌는지 확인한다**

   ```bash
   kind get clusters
   kubectl config get-contexts
   ```

4. **현재 shell의 API key를 해제한다**

   ```bash
   unset OPENAI_API_KEY LITELLM_API_KEY LITELLM_BASE_URL LITELLM_MODEL
   ```

</Steps>

kind node image와 container는 cluster 삭제로 정리되지만 host의 kagent·kind·kubectl CLI와 Docker cache는
남는다. 이들은 다른 실습에서도 재사용하므로 자동으로 삭제하지 않는다.

## 왜 `kagent uninstall`을 기본으로 쓰지 않나

공식 uninstall은 cluster 전체의 kagent resource를 제거하며 되돌릴 수 없다. 공유 cluster에서는 다른 사용자의
Agent와 tool까지 포함할 수 있다. 이 덱은 애초에 전용 kind cluster를 만들었으므로 cluster 이름으로 통째로 지우는
쪽이 cleanup 경계가 더 분명하다.

설치만 제거하고 cluster를 재사용하려는 별도 상황이라면 공식 순서와 경고를 다시 읽고 실행한다.

## 이번 실습에서 얻은 판단 기준

1. dashboard 화면보다 `Agent` spec과 condition이 먼저다.
2. model, prompt, tool allowlist는 서로 다른 변경·권한 경계다.
3. MCP는 Agent가 tool을 부르는 안쪽 계약이고 A2A는 client가 Agent를 부르는 바깥쪽 계약이다.
4. `Accepted`, `Ready`, invoke 성공은 각각 다른 checkpoint다.
5. BYO는 자유도가 커지는 만큼 image·dependency·protocol·secret 책임도 넓어진다.
6. production에서는 catalog·ACL·승인·감사·격리를 kagent 바깥에 더 설계해야 한다.
