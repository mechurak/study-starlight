<Thesis>회사가 빌드한 Paseo 사내 빌드가 카탈로그의 로컬 프런트엔드가 되고, 사용자별 허용 범위는 사내 백엔드가 결정한다</Thesis>

임직원이 각자 쓰는 Paseo 안에서 회사의 skill·dashboard·prompt·tool을 찾고 실행하게 만들고 싶다.
새 포털을 하나 더 만드는 대신 Paseo sidebar에 회사 카탈로그를 넣으면 코딩 agent를 쓰던 문맥을
떠나지 않아도 된다. 하지만 PC의 화면만으로는 AD 로그인, 부서별 권한, 회수와 감사가 해결되지 않는다.

배포 형태는 plugin 개별 설치가 아니라 **사내 빌드**다. upstream Paseo(AGPLv3) 릴리스 태그에
최소 패치를 얹어 회사가 빌드·서명하고, 카탈로그 plugin·사내 CA·프록시 기본값을 동봉해 인스톨러
하나로 배포한다. 비개발자 사용자에게 Node·npm·plugin 설치를 요구하지 않기 위해서다.

이 덱은 개인 PC의 사내 빌드와 온프렘 Kubernetes의 Catalog API 사이에 경계를 긋는다. 동봉
plugin은 화면과 로컬 BFF를 맡고, Keycloak은 AD 사용자를 인증하며, oauth2-proxy는 브라우저
cookie와 API Bearer token을 검증한다. Catalog API는 `sub`와 조직 entitlement를 기준으로 허용된
항목만 반환한다.

**2026년 8월 24일 기준** Paseo 저장소·라이선스와 Paseo·Keycloak·oauth2-proxy 공식 문서를
확인했다. 모두 현재성이 있는 영역이므로 upstream 버전을 올리거나 배포하기 전에 사용 중인
태그의 config schema와 plugin declaration을 다시 확인한다.

```d2 layout=elk pad=40 title="개인 PC의 Paseo 사내 빌드에서 Keycloak 인증을 거쳐 권한이 필터링된 사내 카탈로그를 받는 구조"
direction: right

  handler: "catalog handler\nlocal BFF"
  store: "OS credential store"

  paseo -> handler: "typed RPC"
  handler -> store: "refresh token"
}

idp: "Keycloak + AD\n사용자 인증"
proxy: "oauth2-proxy\nJWT 검증"
api: "Catalog API\nentitlement 필터"
items: "skill · dashboard\nprompt · tool"

pc.handler -> idp: "Device Flow" {
  style.animated: true
}

  style.animated: true
}
proxy -> api: "검증된 요청" {
  style.animated: true
}
api -> items: "허용된 항목만" {
  style.animated: true
}
```

여기서 사내 빌드는 사용자를 직접 판정하지 않는다. 토큰을 얻고 전달하며 결과를 그릴 뿐이다.
최종 권한은 Catalog API가 서버 쪽에서 계산한다. PC에 내려간 artifact는 복사될 수 있으므로,
민감한 tool과 dashboard는 실제 실행 요청에서도 다시 인증·인가한다.
