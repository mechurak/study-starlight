> 결론부터 — **Paseo plugin은 카탈로그의 로컬 프런트엔드가 되고, 사용자별 허용 범위는 사내 백엔드가 결정한다**

임직원이 각자 쓰는 Paseo 안에서 회사의 skill·dashboard·prompt·tool을 찾고 실행하게 만들고 싶다.
새 포털을 하나 더 만드는 대신 Paseo sidebar에 회사 카탈로그를 넣으면 코딩 agent를 쓰던 문맥을
떠나지 않아도 된다. 하지만 PC의 plugin만으로는 AD 로그인, 부서별 권한, 회수와 감사가 해결되지 않는다.

이 덱은 개인 PC의 Paseo와 온프렘 Kubernetes의 Catalog API 사이에 경계를 긋는다. Paseo plugin은
화면과 로컬 BFF를 맡고, Keycloak은 AD 사용자를 인증하며, oauth2-proxy는 브라우저 cookie와 API
Bearer token을 검증한다. Catalog API는 `sub`와 조직 entitlement를 기준으로 허용된 항목만 반환한다.

**2026년 8월 21일 기준** Paseo·Keycloak·oauth2-proxy 공식 문서를 확인했다. 세 제품 모두 현재성이
있는 영역이므로 배포 전에는 사용 중인 버전의 option과 plugin declaration을 다시 확인한다.

## 한 장으로 보는 결론

```d2 layout=elk pad=40 title="개인 PC의 Paseo에서 Keycloak 인증을 거쳐 권한이 필터링된 사내 카탈로그를 받는 구조"
direction: right

pc: "임직원 PC" {
  paseo: "Paseo app\nplugin surface"
  handler: "plugin handler\nlocal BFF"
  store: "OS credential store"

  paseo -> handler: "typed RPC"
  handler -> store: "refresh token"
}

idp: "Keycloak + AD\n사용자 인증"
proxy: "oauth2-proxy\nJWT 검증"
api: "Catalog API\nentitlement 필터"
items: "skill · dashboard\nprompt · tool"

pc.handler -> idp: "Device Flow" {
  style.animated: true
}
pc.handler -> proxy: "Bearer access token" {
  style.animated: true
}
proxy -> api: "검증된 요청" {
  style.animated: true
}
api -> items: "허용된 항목만" {
  style.animated: true
}
```

여기서 plugin은 사용자를 직접 판정하지 않는다. 토큰을 얻고 전달하며 결과를 그릴 뿐이다.
최종 권한은 Catalog API가 서버 쪽에서 계산한다. PC에 내려간 artifact는 복사될 수 있으므로,
민감한 tool과 dashboard는 실제 실행 요청에서도 다시 인증·인가한다.
