## 바뀌지 않는 결정

- 배포 단위는 회사가 빌드·서명한 **Paseo 사내 빌드 인스톨러 하나**다. 사용자 PC에
  Node·npm·plugin 설치를 요구하지 않는다.
- 지원 환경은 native Windows 11 24H2+의 x64와 ARM64다. Software Center에는 설치 항목 하나를
  보여 주되 배포 규칙이 아키텍처별 서명 package를 선택한다.
- AGPLv3 컴플라이언스 검토가 선결 조건이고, 배포 범위는 법인 내부로 한정한다.
- upstream 릴리스 태그에 버전을 고정하고 회사 변경은 최소 패치 세트로 관리한다.
  config로 끌 수 있는 것은 패치하지 않는다.
- 카탈로그 구현은 사내 빌드에 동봉한 plugin이다 — plugin API를 써서 코어 패치를 얇게 유지하고,
  동봉 plugin 외의 plugin 로드는 allowlist 패치로 차단한다.
- relay·모바일 페어링·원격 데몬 접속·bundled web UI는 끄거나 제거하고, 업데이트는 사내 채널로만 받는다.
- Paseo가 실제로 쓸 **선택된 provider CLI만** 인스톨러가 설치한다. Claude Code·Codex·Gemini CLI
  셋을 모두 설치할 의무는 없다.
- Catalog Keycloak 로그인과 provider 로그인은 별도 흐름이다. 관리 설정은 회사 조직·workspace를
  강제하지만 인증 자체를 없애지는 않으며, 브라우저의 IdP session이 남아 있으면 입력이 줄어들 뿐이다.
- 비개발자에게 폴더를 고르게 하지 않는다 — 기본 project와 작업 단위 workspace를 자동 생성한다.
- oauth2-proxy용 `catalog-web`과 Paseo용 `paseo-catalog` Keycloak client를 분리한다.
- Paseo는 client secret 없는 Device Authorization Grant를 기본으로 한다.
- oauth2-proxy의 callback은 사내 HTTPS `/oauth2/callback`이며 localhost가 아니다.
- PKCE loopback 대안을 쓸 때만 `http://127.0.0.1`을 `paseo-catalog`에 등록한다.
- oauth2-proxy는 browser cookie와 검증된 JWT Bearer 요청을 모두 처리한다.
- Catalog API가 `iss + sub`와 entitlement로 item row와 action을 필터링한다.
- local artifact 존재와 현재 실행 권한을 분리한다.
- 민감한 dashboard·tool server는 실행 요청마다 다시 인가한다.

## 세 단계로 도입한다

<Steps>
1. **PoC — 인증과 읽기**

   Device Flow 로그인, `/v1/me`, 허용된 prompt 목록과 401·403 상태까지만 구현한다.

2. **Pilot — Paseo 동작 연결**

   prompt resolve와 현재 workspace의 agent 생성을 연결하고, pilot 부서의 entitlement와 audit을 검증한다.

3. **Production — 설치와 runtime 권한**

   서명 artifact, provider별 skill adapter, session MCP, tool server 재인가, MDM rollout과 rollback을 추가한다.
</Steps>

한 단계의 완료 조건이 충족되기 전에 다음 단계의 code execution 범위를 열지 않는다.

## production 보안 점검

- [ ] AGPLv3 컴플라이언스 검토 결과와 허용된 배포 범위가 문서화되어 있다.
- [ ] 배포 빌드에서 relay·bundled web UI·원격 접속이 꺼져 있고 daemon이 `127.0.0.1`에만 listen한다.
- [ ] 동봉 plugin 외의 plugin 로드가 allowlist 패치로 차단된다.
- [ ] Windows 11 24H2 x64와 ARM64에서 설치·업데이트·rollback·제거 smoke test가 각각 통과한다.
- [ ] 설치된 Paseo와 provider CLI가 host 아키텍처용 native artifact이며 x64 emulation에 기대지 않는다.
- [ ] agent CLI 로그인이 관리 설정으로 회사 조직에 고정되어 개인 계정·개인 API key 우회가 차단된다.
- [ ] Catalog Keycloak과 각 provider의 최초 로그인·만료·재로그인을 서로 다른 상태로 안내한다.
- [ ] oauth2-proxy client secret이 Kubernetes Secret 밖과 직원 PC에 존재하지 않는다.
- [ ] refresh token은 지원 OS의 credential store에 저장되고 logout·회수된다.
- [ ] token과 device code가 plugin·proxy·backend log에 남지 않는다.
- [ ] audience mapper와 proxy/backend의 expected audience가 같다.
- [ ] backend Service는 oauth2-proxy·정해진 ingress 경로에서만 접근 가능하다.
- [ ] 외부 `X-Forwarded-*` identity header는 제거되고 검증된 값만 생성된다.
- [ ] artifact는 immutable version·hash·signature와 publisher를 가진다.
- [ ] installer가 path traversal·기존 파일 충돌·부분 실패를 처리한다.
- [ ] tool과 dashboard backend가 실행 시점에 사용자 권한을 다시 확인한다.
- [ ] 사내 빌드의 canary·rollback과 최소 지원 version 정책이 있고, upstream 보안 릴리스를 추적하는 담당이 있다.

## 마지막 판단 카드

| 질문 | 답 |
|---|---|
| Paseo를 사내 catalog frontend처럼 쓸 수 있는가 | 가능하다. surface와 RPC가 이 역할에 맞는다. |
| plugin을 사용자에게 따로 설치시키는가 | 아니다. 사내 빌드에 동봉해 인스톨러 하나로 배포한다. |
| Claude Code·Codex·Gemini CLI를 모두 설치해야 하는가 | 아니다. Paseo는 agent를 내장하지 않으므로 사용할 provider가 하나 이상 필요할 뿐, 회사가 승인한 provider만 배포하면 된다. |
| 사용자 PC에서 npm으로 provider를 설치하는가 | 아니다. CI에서 version을 고정해 payload를 만들고, native binary 또는 app-local Node runtime과 Gemini bundle을 설치한다. |
| Windows ARM64를 x64 emulation으로 지원해도 되는가 | 기본 지원 경로로 두지 않는다. host 아키텍처용 artifact를 배포하고 emulation은 장애 진단용 fallback으로만 본다. |
| 카탈로그 UI를 코어에 직접 구현하는가 | 아니다. 동봉 plugin으로 격리해 코어 패치를 얇게 유지한다. |
| upstream과 끊어진 포크인가 | 아니다. 릴리스 태그 위 최소 패치로 upstream을 추적한다. |
| Keycloak 로그인 정보를 권한에 쓸 수 있는가 | 가능하다. token identity와 backend entitlement를 결합한다. |
| oauth2-proxy callback을 localhost로 바꾸는가 | 아니다. 기존 HTTPS callback을 유지한다. |
| Paseo에서 localhost callback이 꼭 필요한가 | 아니다. Device Flow에는 callback이 없다. |
| oauth2-proxy만으로 항목별 권한이 끝나는가 | 아니다. Catalog API가 최종 action을 판정한다. |
| 목록에서 숨기면 설치된 skill도 회수되는가 | 아니다. local artifact와 runtime permission을 따로 관리한다. |
