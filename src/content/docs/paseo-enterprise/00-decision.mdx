## 먼저 풀려는 문제

직원은 이미 Paseo에서 repository를 고르고 coding agent에게 prompt를 보낸다. 회사 표준 prompt나
승인된 MCP tool을 쓰기 위해 별도 포털을 열고 내용을 복사해야 한다면 문맥이 끊기고, 최신 버전인지도
확신하기 어렵다. 필요한 것은 거대한 사내 포털이 아니라 **현재 agent 작업에 붙는 작은 카탈로그**다.

```text
찾기 → 설명과 권한 확인 → 현재 작업에 붙이기 → 실행 결과를 Paseo에서 계속 보기
```

이 흐름의 첫 세 단계를 Paseo sidebar 안에 둘 수 있다. 다만 PC의 화면만으로는 AD 로그인,
부서별 권한, 회수와 감사가 해결되지 않는다 — 그 몫은 사내 백엔드가 가진다.

## 결정 1 — 별도 포털이 아니라 Paseo 안의 카탈로그

MCP tool을 현재 agent 설정에 추가한다.

작은 운영 dashboard를 agent 작업 옆에서 확인한다.

대형 table과 복잡한 입력 form이 화면의 중심이다.

결재선·알림·실시간 협업이 독립 제품 수준이다.

웹 전용 component library와 browser API가 필수다.

카탈로그 화면이 import할 수 있는 runtime module은 React, React Native, TanStack Query, Zod와
plugin API 등으로 제한된다. 따라서 기존 웹 dashboard를 그대로 embed할 수 있다고 가정하지
않는다. 작은 dashboard는 surface로 그리고, 복잡한 기존 화면은 SSO가 적용된 URL을 기본 browser로 연다.

## 결정 2 — plugin 개별 배포가 아니라 사내 빌드

처음 검토한 구조는 upstream Paseo를 그대로 쓰고 회사 카탈로그 plugin을 따로 배포하는 것이었다.
비개발자 사용자를 기준으로 두 배포 형태의 설치 부담을 비교하면 차이가 크다.

| 사용자가 해야 하는 일 | plugin 개별 배포 | 사내 빌드 |
|---|---|---|
| Paseo 설치 | 직접 다운로드·설치 | 인스톨러 하나에 포함 |
| Node.js·npm 설치 | 필요 (plugin이 로컬 `npm install` 기반) | 불필요 |
| 사내 npm registry 세팅 | 프록시·인증서 포함 직접 설정 | 불필요 |
| 카탈로그 plugin 설치 | 경로 지정 후 설치·활성화 | 동봉·기본 활성화 |
| 사내 CA·프록시 설정 | 안내 문서 따라 직접 | 빌드·인스톨러가 프로비저닝 |

이 차이는 우연이 아니다. [Paseo plugin 공식 문서](https://paseo.sh/docs/plugins)는 plugin이
**아직 배포용으로 설계되지 않았다고 명시한다** ("experimental", "not designed for
distribution yet") — 개인이 자기 PC에서
로컬 코드를 돌리는 용도로 설계되었고, 조직 단위 배포 채널이 아직 없다. 반면 Paseo 데스크톱 앱은
데몬을 번들해 "별도로 설치할 것이 없다"고 안내한다. 배포 단위를 **회사가 빌드한 앱 하나**로
바꾸면 이 성질을 그대로 물려받는다.

사내 빌드가 배포 시점에 해결하는 것은 설치 부담만이 아니다.

- **보안 환경 프로비저닝** — 사설 CA 신뢰, 사내 프록시 기본값, Catalog API 주소,
  Keycloak client 설정을 사용자 손을 거치지 않고 굽는다.
- **쓰지 않을 표면 제거** — relay 페어링·모바일 접속·원격 데몬 접속·bundled web UI는
  지원하지 않기로 했다. config로 끌 수 있는 것은 config로 끄고, 페어링 안내처럼
  화면에 남는 표면만 패치로 제거한다.
- **버전 통제** — upstream 자동 업데이트 대신 사내 업데이트 채널로 검증된 버전만 배포한다.

여기서 버린 것은 plugin의 **배포 형식**이지 plugin API 자체가 아니다. 카탈로그 구현을 어디에
두는지는 다음 결정에서 따로 본다.

:::caution[선결 조건 — AGPLv3]
Paseo는 [AGPLv3](https://github.com/getpaseo/paseo/blob/main/LICENSE)로 배포된다. 같은 법인
임직원 PC에 배포하는 내부 사용이라도, 소스를 수정해 배포하는 이상 사내 오픈소스 컴플라이언스
검토를 먼저 통과해야 한다. 계열사·협력사로 배포 범위를 넓히는 것은 별도 재검토 대상이다.
이 덱은 기술 구조만 다루고 라이선스 해석은 컴플라이언스 조직의 판단을 따른다.
:::

## 결정 3 — 코어 직접 통합이 아니라 동봉 plugin

사내 빌드로 가면 코어 소스를 마음대로 고칠 수 있으므로, plugin 기능을 아예 쓰지 않고 카탈로그
UI를 코어에 직접 구현하는 안도 검토했다. 채택하지 않았다 — 이 구조의 유지비는 패치 세트의
크기인데, 두 안의 패치 두께가 다르기 때문이다.

| | 동봉 plugin (채택) | 코어 직접 통합 |
|---|---|---|
| 코어와의 접점 | plugin API 계약 하나 | upstream이 활발히 고치는 앱 소스 곳곳 |
| upstream rebase | 계약 접점만 재확인 | 우리 UI와 upstream 변경이 같은 파일에서 충돌 |
| plugin API 파손 | 등록·RPC 접점 몇 곳만 수정 | 해당 없음 — 대신 모든 코어 변경이 잠재 충돌 |
| 확장 지점 배선 | sidebar·surface·RPC·attachment 제공됨 | 직접 깔고 유지 |

plugin API가 experimental이라는 사실이 이 결정을 뒤집지는 못한다. 버전을 릴리스 태그에
고정하므로 API 변경은 rebase 시점에만 만나고, 그때 고칠 범위는 계약 접점 몇 곳으로 좁다.
코어 곳곳에 흩어진 UI 패치를 매번 충돌 해결하는 것보다 싸다.

**전환 기준** — surface 하나를 얹는 범위를 넘는 요구가 생기면 그 부분만 코어 패치로 내린다.
앱 첫 화면 자체를 사내용으로 교체, 로그인 전 앱 전체 잠금, Paseo 기본 UI 요소의 대규모 제거가
그런 신호다. 그 전까지는 plugin API 경계 안에 머문다.

:::caution[함께 열리는 문]
동봉 plugin을 돌리려면 plugin 기능 스위치를 켜야 하는데, 그대로 배포하면 사용자가 임의
plugin — sandbox 없이 daemon 머신 권한으로 실행되는 코드 — 을 설치할 수 있는 문도 함께 열린다.
동봉 plugin 외의 로드를 거부하는 allowlist 패치를 최소 패치 세트에 포함한다
([1장](/paseo-enterprise/01-internal-build/)).
:::

## 책임을 다섯 곳에 나눈다

| 구성 요소 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| 카탈로그 surface (동봉 plugin) | 탐색 UI, loading·error·재로그인 상태 | 최종 권한 판정, 장기 token |
| catalog handler (동봉 plugin) | OIDC 흐름, token 갱신, Catalog API 호출 | 조직정보의 정본, 전사 배포 정책 |
| Keycloak | 사용자 인증, AD identity·group claim | catalog 항목별 정책 |
| oauth2-proxy | cookie/JWT 검증, 서비스 1차 진입 통제 | 개인·부서별 항목 조합 |
| Catalog API | entitlement 계산, 허용된 metadata·artifact | PC의 agent 실행 생명주기 |

:::tip[핵심 원칙]
사내 빌드는 권한을 **표현**하지만 권한의 정본은 아니다. 화면에서 버튼을 숨기는 것과
API 요청을 거부하는 것은 다른 통제다.
:::

## 도입 전에 답할 질문

- 사내 빌드의 owner, 빌드 파이프라인과 업데이트 채널은 누가 운영하는가
- AGPLv3 수정·사내 배포에 대한 컴플라이언스 검토는 통과했는가
- 지원할 agent CLI는 무엇이고, 좌석·SSO 로그인 정책은 무엇으로 강제하는가
- 사용자 identity는 Keycloak의 어떤 realm과 client에서 발급되는가
- 개인·부서·직무 권한은 Keycloak role인가, 별도 entitlement DB인가
- skill과 prompt를 내려받은 뒤 권한이 회수되면 무엇을 할 수 있어야 하는가
- tool 실행은 어느 서버가 매번 재인가하는가
- Windows 11 24H2 x64·ARM64에서 provider별 native 실행·credential store·sandbox를 어떻게 검증하는가

이 질문에 답하지 않은 채 UI부터 만들면 catalog는 보여도 통제 가능한 사내 제품은 되지 않는다.
