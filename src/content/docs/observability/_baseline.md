# observability 덱의 기준

`observability` 덱을 고치기 전에 읽는다. 다른 덱에는 해당하지 않는다.

## 이 덱의 축

**"뭐가 문제냐"에서 원인까지 가는 시간을 줄이는 것**이 덱 전체의 뼈대다. 대시보드가 아니다.
1장의 세 신호 표(메트릭 · 로그 · 트레이스 ↔ 답하는 질문 ↔ 장 번호)가 곧 목차이고,
2~5장은 그 신호를 하나씩 맡는다.

두 번째 축은 **셋을 잇는 장치 셋** — 로그에 실린 `trace_id`, 메트릭에 매달린 exemplar,
트레이스에서 로그로 가는 링크다. 각 장은 자기 신호를 설명하고 끝나는 게 아니라
**옆 신호로 어떻게 건너가는지**를 반드시 밝힌다. 5장이 그 셋을 실제로 연결한다.

세 번째 축은 **카디널리티**다. 관측 스택을 죽이는 1번 원인이고,
1 · 2 · 3장에서 각각 다른 얼굴로 다시 나온다 — 라벨 원칙을 장마다 반복해서 확인한다.

## 온프렘 덱과의 경계

이 덱은 [onprem 덱](/onprem/)의 **옛** 8~12장(분리 전 번호)이 커져서 2026-08-11에 독립한 것이다.
그래서 경계를 명시해 둔다.

- **온프렘 덱 8장이 "온프렘에서 관측이 무엇에 걸리나"** 를 맡는다 — 인프라 노드 배치,
  저장소를 클러스터 밖에 두는 이유, 유한한 용량, 알림 경로의 독립. 그쪽은 **판단**만 쓰고
  도구 사용법은 이 덱으로 넘긴다.
- **이 덱은 도구 넷을 맡는다** — 설치·설정·질의·운영·점검. 온프렘 고유의 제약이 걸리는
  자리(S3 엔드포인트, 사내 CA, egress 프록시)에서는 **온프렘 덱의 해당 장을 링크**하고
  여기서 다시 설명하지 않는다.
- 오브젝트 스토리지 자체는 [온프렘 덱 6장](/onprem/06-minio/), Postgres는
  [7장](/onprem/07-cnpg/), SSO는 [5장](/onprem/05-identity/)과 [keycloak 덱](/keycloak/)이 맡는다.
- 쿠버네티스 기초는 [cka 덱](/cka/), 리눅스 운영은 [server 덱](/server/)이 맡는다.

**한쪽을 고치면 다른 쪽 경계를 확인한다** — 같은 이야기가 양쪽에 자라면 분리한 의미가 없다.

## 따라 하기 실습의 경계

8~10장은 개념 장과 분리된 **hands-on 경로**다. 사용자가 직접 명령을 실행하고, 문서는
`실행 → 🔎 관찰 포인트 → 해석 → 스스로 해볼 과제 → cleanup` 순서로 안내한다.

- 공식 LGTM 설치를 감싸는 Makefile·스크립트·매니페스트·example app 복사본은 레포에 두지 않는다.
  8~10장은 Grafana 공식 저장소를 직접 checkout해 Kubernetes 예제, Java `rolldice`, traffic script를 쓴다.
- Docker·kind·kubectl의 운영체제별 준비와 정리는 [실습 환경 덱](/lab-environment/)이 맡는다.
  이 덱에는 관측 실습만의 자원·버전·명령만 남긴다.
- 첫 실습은 kind의 Kubernetes **v1.35.5**를 고정하고, Grafana `docker-otel-lgtm`
  **v0.30.2 공식 저장소**의 Kubernetes 예제와 Java example을 수정 없이 사용한다.
- 공식 v0.30.2 예제도 `grafana/otel-lgtm:latest`를 사용한다. 재현 가능한 고정 버전 실습으로 오해하지 않고,
  문서의 `kubectl ... jsonpath` 명령으로 실제 image digest와 실행 날짜를 검증 기록에 남긴다.
- LGTM 이미지는 **개발·데모 전용**이다. 단일 Pod · `emptyDir` · 로컬 admin을 운영 설치법처럼
  서술하지 않는다. 각 실습 장 첫부분에 운영 구성과의 차이를 밝힌다.
- 실습은 새로 만든 `kind-observability-lab` context의 `default` namespace만 사용한다. 공식 예제가 namespace를
  지정하지 않기 때문이다. 모든 문서 명령은 context를 명시하고, 다른 cluster의 `default`를 건드리지 않는다.
- Java example은 host에서 실행하고 공식 port-forward의 OTLP 4317·4318을 통해 kind 안의 Collector로 보낸다.
  공식 앱의 임의 지연과 약 30% 오류를 쓰므로 고정된 정상 → 장애 → 회복 구간을 약속하지 않는다.
- cleanup은 `kind delete cluster --name observability-lab`으로 전용 kind 클러스터만 삭제한다.
  다른 클러스터·이미지·볼륨은 건드리지 않는다.
- 온프렘 운영 실습은 이 단일 Pod 샘플을 확장하지 않는다. 제품별 공식 Helm 차트를 쓰는 별도 경로로
  분리하고, 레포에는 공식 차트의 렌더 결과가 아니라 환경별 values와 검증 절차만 둔다.
- 질의와 UI 절차는 추측으로 쓰지 않는다. 공식 example을 실행해 실제 메트릭 이름·Loki 필드·Tempo 스팬과
  상관 링크를 확인한 뒤 갱신한다.
- Explore에서 query와 신호 이동을 먼저 검증하고, 반복해서 볼 질문만 대시보드 패널로 옮긴다.
  대시보드를 조사보다 먼저 만들거나 모든 로그를 자동 새로고침하는 넓은 LogQL을 넣지 않는다.

## 서술 규칙

각 장 첫머리의 `<TermIntro>` 상자가 의무다 — 규칙은 AGENTS.md "덱" 절.

- **첫머리에는 그 장의 질문을 이해하는 데 필요한 말만 1~3개 둔다.** 설치·질의·운영처럼
  뒤 절에서 처음 쓰는 용어는 그 절 바로 앞의 두 번째 `<TermIntro>`로 미룬다. 용어 사전을
  장 입구에 한꺼번에 쏟지 않는다.
- 큰 그림은 **질문 → 신호 → 도구** 순서로 읽혀야 한다. 제품명부터 시작하지 않는다.
- 외부 그림은 공식 문서의 구조도·실제 화면처럼 텍스트를 대체할 때만 쓴다. 원본이 사라져도
  문서가 깨지지 않게 `public/images/observability/`에 사본을 두고, `<SourceFigure>`로
  **그림에서 볼 곳 + 원문 링크**를 함께 적는다.

- **2~5장은 네 단계 순서를 지킨다** — ① 데이터가 어떻게 생겼나(메트릭 한 줄 · 스트림 · 스팬의
  실제 모양) → ② 어떻게 묻나(PromQL · LogQL · TraceQL) → ③ 어떻게 세우나(Helm · CRD · 에이전트)
  → ④ 점검. 0장의 "각 장을 읽는 방식" 절이 이 약속을 독자에게 밝혀 두었으니,
  **장을 늘리거나 고칠 때 순서를 깨면 그 절도 같이 고쳐야 한다.**
  설정(③)부터 쓰는 서술로 돌아가지 않는다 — 이 덱이 한 번 그렇게 쓰였다가 다시 쓴 이유다.
- **질의 언어 셋은 경험을 전제하지 않는다.** 0장이 "PromQL·LogQL·TraceQL 경험을
  전제하지 않는다"고 못 박았으므로, 새 질의를 본문에 넣을 때 그 장에서 아직 안 나온
  문법이면 한 줄이라도 설명을 붙인다. 문법 요약표는 6장 각 절 끝에 있다.
- **카디널리티 규칙은 신호마다 다르다** — 메트릭·로그 라벨에는 유한한 것만,
  **트레이스 속성에는 고유 값을 넣어도 된다**(4장). 이 대비를 흐리지 않는다.
- **버전 번호는 위 표에 있는 것만 쓴다.** 표에 없는 도구(Alloy · OTel Collector · Thanos ·
  Mimir · Grafana Operator)는 버전을 적지 말고 성질만 쓴다 —
  확인 안 한 숫자를 적으면 이 덱의 신뢰가 통째로 깎인다.
- **"설정하는 법"보다 "안 될 때 어디를 보나"** 를 쓴다. 각 장 끝의 `점검` 절 —
  명령어 블록 + 증상·원인·확인 표 — 이 이 덱에서 제일 자주 열리는 자리다. 장을 늘릴 때도 이 형식을 유지한다.
- 온프렘 전제(인터넷 직접 연결 없음 · 사내 CA · 오토스케일 없음 · 유한한 디스크)는
  깔고 가되, **그 제약 자체를 설명하지 않는다** — 온프렘 덱을 링크한다.
