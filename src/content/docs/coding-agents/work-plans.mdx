## 언제 계획 문서를 만드는가

먼저 작업의 불확실성과 인계 필요를 본다. 파일 수만으로 판단하지 않는다.

| 작업 상황 | 필요한 준비와 기록 |
|---|---|
| 수정 범위와 결과가 분명한 작은 변경 | 대화에서 범위 확인 후 구현·검증. 별도 문서가 없어도 됨 |
| 접근법이나 요구사항이 불명확함 | 관련 코드 조사·작은 실험으로 가정을 확인하고 결정할 질문을 정리 |
| 여러 세션·도구가 이어받을 큰 작업 | 목표·완료 조건·결정·현재 상태를 공유 가능한 계획에 유지 |
| 기존 이슈·명세가 작업의 정본임 | 정본을 링크하고 부족한 실행·인계 정보만 보완 |

[Claude Code best practices](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code)는
불확실한 변경에는 탐색과 계획을 권하지만 작은 수정은 바로 수행할 수 있다고 설명한다.
OpenAI의 [ExecPlan 안내](https://developers.openai.com/cookbook/articles/codex_exec_plans)도
AGENTS에 “복잡한 기능이나 큰 리팩터링이면 ExecPlan을 쓴다”처럼 크기 조건을 적는 예를 보여 준다.

이는 **언제 계획이 유용한가**에 대한 기준이다. 누가 파일 생성을 결정하는지는 레포 정책으로 정한다.
예를 들어 사용자가 요청할 때만 만들거나, 미리 합의한 큰 작업 조건에서 만들게 할 수 있다.
이 저장소는 전자를 택했다. “여러 페이지를 수정해 줘”만으로 새 계획 파일을 만들지 않으며,
기존 계획의 실행·재개를 요청받으면 해당 문서를 갱신한다.

## Plan Mode와 저장소 계획은 역할이 다르다

| 구분 | 해결하는 문제 | 다른 도구에 넘길 때 |
|---|---|---|
| Plan Mode | 구현 전에 탐색하고 접근법을 검토 | 합의한 결과를 공유 문서에 반영 |
| 저장소의 작업 계획 | 목표·결정·진행 상태를 지속적으로 관리 | 같은 파일과 관련 정본을 읽음 |
| 같은 도구의 세션 재개 | 저장된 대화를 이어 감 | 다른 도구도 그 대화를 읽는다고 가정하지 않음 |

Codex의 [장기 작업 안내](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)는
Plan Mode와 지속적인 프로젝트 문서를 함께 소개한다. Claude Code도
[계획 모드와 대화 재개](https://code.claude.com/docs/en/common-workflows)를 별도 기능으로 설명한다.
Plan Mode를 켰다는 사실만으로 공유 계획의 위치나 갱신 규칙까지 정해지는 것은 아니다.

## 요구를 정하는 스펙과 순서를 정하는 계획은 나눌 수 있다

스펙은 **무엇을 왜 만들고 어떻게 완료를 판정하는가**를, 계획은 **어떤 순서와 의존 관계로 만들
것인가**를 답한다. 아래 CSV 예시처럼 한 작업 안에서 요구가 닫혀 있으면 한 파일의 두 절로 충분하다.
다음 조건이면 스펙을 별도 문서로 분리하는 편이 낫다.

| 조건 | 분리했을 때 얻는 것 |
|---|---|
| 같은 요구를 여러 계획·여러 도구가 참조함 | 요구를 한 곳에서 고치고 계획은 순서만 바꾼다 |
| 요구 확정에 긴 대화가 필요함 | 확정된 스펙만 남기고 구현은 새 세션의 깨끗한 컨텍스트에서 시작한다 |
| 구현 중 요구 변경을 구분해야 함 | 스펙의 변경과 계획의 조정을 따로 기록해 완료 조건이 조용히 낮아지는 일을 막는다 |

Claude Code의 [best practices](https://code.claude.com/docs/en/best-practices#let-claude-interview-you)는
큰 기능이면 먼저 인터뷰로 스펙을 파일에 쓰고, 새 세션에서 그 스펙만 보고 구현하도록 권한다.
좋은 스펙은 관련 파일·인터페이스·제외 범위·끝단 검증 절차를 자기완결적으로 담는다.
Codex의 [장기 작업 안내](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)도
목표·제약·완료 기준을 담은 명세와 마일스톤 계획을 별도 파일로 두었다.
기존 이슈나 명세가 이미 스펙 역할을 하면 그 문서를 링크하고 새로 쓰지 않는다.

## 계획 문서는 실행 가능한 계약이다

예시는 **가상 업무 서비스의 CSV 내보내기**다. 사용자가 아래 요구와 계획 작성에 동의했다고 가정한다.
경로는 설명용이며 실제 작성 시 조사한 원본 경로와 실행 가능한 검증 명령으로 채운다.

```md
# 업무 목록 CSV 내보내기

상태: 계획
지금 위치: 요구사항 합의 · 구현 미착수 · 다음 M1
실행 범위: 로컬 구현·검증·실패 수정까지 전체 완료. 커밋·푸시·배포 제외.

## 목표와 완료 조건

사용자는 현재 필터·정렬에 맞는 업무 목록 전체를 CSV로 받는다.

- [ ] 기존 조회 권한을 적용하고 페이지네이션 뒤의 항목도 포함한다.
- [ ] 열은 ID·제목·상태이며 쉼표·따옴표·줄바꿈이 있는 제목도 보존한다.
- [ ] 0건은 헤더만 반환하고, 1,000건 초과는 일부만 내보내지 않고 제한을 안내한다.
- [ ] UI에서 다운로드·실패 안내가 동작하고 기존 목록 조회가 유지된다.

## 범위와 근거

포함: 내보내기 API·버튼·관련 테스트·사용 안내.
제외: 비동기 대량 작업·예약 전송·새 권한 체계.
근거: 기존 목록 조회·권한 검사·CSV 처리 코드와 관련 지침의 실제 경로.

## 작업

| ID | 입력·의존성 | 결과 | 완료 판단 |
|---|---|---|---|
| M1 | 기존 조회·권한 코드 | 내보내기 API | 권한·필터·전체 건수·CSV 형식의 테스트 |
| M2 | M1의 응답·오류 계약 | 버튼·실패 안내 | 다운로드와 0건·초과 상황의 UI 동작 |
| M3 | M1·M2 | 통합 검증·사용 안내 | 실제 사용자 흐름과 기존 조회의 회귀 확인 |

## 결정과 현재 상태

합의: 첫 버전은 동기 처리·최대 1,000건. 대량 처리는 별도 요구로 남긴다.
미확인: 기존 조회 코드를 재사용할 때 권한·필터가 유지되는지 M1에서 확인한다.
검증: 아직 실행하지 않음. 구현 전 실제 검사 명령과 환경을 확인한다.
다음 행동: M1의 조회·권한 경로 확인 후 구현.
```

이 문서는 준비 단계의 예시이며 실행 성공을 주장하지 않는다. 실제 계획에서는 각 검증의
실행 명령·작업 위치·예상 관찰을 식별할 수 있어야 한다. 사용자 입력이 스프레드시트 수식으로
해석되는 문제처럼 기존 CSV 정책과 관련된 제약도 조사해 반영한다. 완성된 CSV 설계서는 아니다.

### 작업은 결과를 검증할 수 있게 나눈다

“백엔드 전부, 프런트 전부”보다 “권한을 유지한 API, 그 계약을 사용하는 UI”처럼 입력과 결과를
나누면 실패 위치를 알 수 있다. M2는 M1의 응답 계약에 의존하므로 계약이 바뀌면 함께 조정한다.
설정·문서 수정이 한 결과를 완성하는 데 필요하면 같은 작업에 포함한다.

멀리 있는 작업의 함수명과 모든 명령 순서까지 미리 확정할 필요는 없다. 확인이 필요한 가정에는
확인 방법을 붙이고 가까운 작업부터 구체화한다. 이는 과도한 레시피를 재검토하라는
[OpenAI 지침](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)을
계획 작성에 적용한 운영 제안이다.

## 계획의 크기와 실행 권한을 따로 정한다

| 요청 | 수행할 범위 |
|---|---|
| 계획 문서 작성만 | 근거·접근법·완료 조건을 작성하고 구현 전 종료 |
| 기존 계획의 M1만 수행 | M1의 구현·검증과 계획 갱신까지 |
| 기존 계획 전체 완료 | 허용된 다음 마일스톤을 이어서 완료 |

마일스톤은 결과를 확인하는 지점이다. 전체 완료를 맡겼다면 매번 재승인을 요구할 이유는 없다.
루틴한 구현 선택은 수행하되, 새 제품 요구나 허용되지 않은 외부 행동은 구분한다.
계획을 검토했다는 사실만으로 푸시·배포까지 허용됐다고 보지 않는다.
실행 중 질문이 필요해지는 경우와 병렬 작업의 경계는
[실행과 재개](/coding-agents/execution-and-resume/#권한과-병렬-작업의-경계)에서 다룬다.

## 발견한 사실에 맞춰 계획을 고친다

기존 목록 함수가 한 페이지만 반환한다면 재사용 가정이 틀린 것이다. 같은 권한·필터를 적용하는
조회 경로로 구현안을 바꾸고 이유·영향·필요한 검증을 계획에 기록한다.
이를 해결하려고 “현재 페이지의 항목만 내보낸다”로 완료 조건을 조용히 낮추면 안 된다.

구현 방식의 조정은 요청 범위 안에서 진행한다. 동기 API로는 요구를 만족할 수 없어 비동기 처리와
새 UX가 필요해졌다면 그 변경이 필요한 근거와 선택지를 제시하고 요구 범위를 다시 정한다.
차단된 작업에는 필요한 입력과 재개 조건을 쓰고, 독립적으로 가능한 작업은 이어 간다.

## 저장소 문서는 서로 다른 시간을 기억한다

| 정보 | 정본의 예 | 유지 방법 |
|---|---|---|
| 현재 제품 요구와 사용법 | 이슈·명세·README | 현재 동작에 맞춰 갱신 |
| 반복 작업 규칙 | AGENTS·검증 지침 | 여러 작업에 필요한 것만 유지 |
| 이번 작업의 결정·상태·실행 증거 | 작업 계획 또는 기존 이슈 | 실행하면서 갱신하고 완료 뒤 기록으로 보존 |
| 정확한 코드 변경 | Git commit과 미커밋 diff | 현재 상태와 계획의 기록을 대조 |

[OpenAI의 장기 작업 사례](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)는
명세·계획·실행 규칙·상태를 문서에 나누어 유지했다. 이 역할을 이해하되 같은 파일 네 개를
무조건 만들 필요는 없다. 기존 정본으로 충분하면 링크하고, 같은 상태를 이슈·계획·README에
중복해서 수동 관리하지 않는다.

## 파일명과 상태로 계획을 찾는다

파일명은 프로젝트가 선택한다. 날짜·이슈 번호·일련번호 중 어느 방식이든 현재 계획을 찾을 수
있으면 된다. 상태는 계획·진행 중·차단·완료·취소처럼 해석이 분명하게 두고 지금 위치를 함께 적는다.

OpenAI의 [Harness engineering](https://openai.com/index/harness-engineering/)은 약 100줄의
AGENTS를 문서 목차로 두고, 실행 계획을 `docs/exec-plans/`의 `active`·`completed` 폴더에 진행
기록과 함께 체크인했다고 소개한다. 상태를 파일 머리에 쓰는 대신 폴더 이동으로 표현하는 방식이다.
어느 쪽이든 **미완료 계획을 한 번의 명령이나 한 폴더에서 찾을 수 있는가**가 기준이다.

**이 스터디 저장소의 적용 예**는 `docs/plans/0001-csv-export.md` 같은 네 자리 번호다.
최대 번호 다음 값을 쓰고 재사용하지 않는다. README에는 공통 관리 규칙만 두며,
미완료 계획은 이 저장소 루트에서 다음으로 찾는다.

```bash
rg -n '^상태: (계획|진행 중|차단)' docs/plans/ -g '[0-9]*-*.md'
```

예상 결과는 파일 경로·줄 번호·상태다. 없으면 출력 없이 종료 코드 1이다.
다른 레포에 적용할 때는 그 레포의 경로·상태 표기에 맞춘다.

## ExecPlan과 계획 문서

[OpenAI Cookbook의 ExecPlan](https://developers.openai.com/cookbook/articles/codex_exec_plans)은
이전 대화 없이 구현할 수 있는 자기완결 계획의 사례다. Cookbook 목록에서 **archived**로 분류된
글이며 제품의 필수 형식이나 권한 규칙이 아니다.

이 덱에서는 저장소의 유지되는 정본을 링크하고, 이번 작업의 가정·결정·현재 상태를 계획에 적는다.
링크만 던져 두지 말고 그 문서가 무엇을 결정하는지 밝혀야 한다. 공유되지 않은 대화나 접근할 수
없는 문서에만 핵심 판단이 있으면 먼저 요지를 기록한다.

## 완료하면 필요한 지식을 제자리로 옮긴다

전체 조건과 실제 결과를 대조하고 필요한 검증이 끝났을 때 완료로 바꾼다.
미구현·미검증 조건을 남겨 둔 채 문서만 완료 처리하지 않는다. 합의해 제외한 항목은 변경 이유와
후속 위치를 기록한다. 사용법은 README, 기술 경계는 설계 문서, 반복 규칙은 해당 지침에 반영한다.
완료 계획은 당시 기록으로 보존하고 새 작업의 현재 지침으로 계속 덧붙이지 않는다.

## 이해 확인

API 테스트가 통과했지만 버튼은 아직 없다. 전체 완료일까? M1만 완료이며 사용자 흐름은 남아 있다.
실행 범위가 전체 완료라면 M2를 이어 간다.

이슈에 요구와 수용 기준이 이미 있다. 스펙 파일을 새로 써야 할까? 이슈를 스펙으로 링크하고
계획에는 순서·의존 관계·현재 상태만 적는다. 이슈에 없는 완료 조건이 있으면 그것만 보완한다.

계획의 재사용 가정이 틀렸다. 계획대로 밀어붙일까? 실제 코드로 가정을 수정하되 목표·권한·완료
조건을 유지한다. 요구 자체의 변경이 필요하다면 그 결정부터 분리한다.
