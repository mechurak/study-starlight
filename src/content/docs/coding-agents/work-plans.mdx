## 언제 계획 문서를 만드는가

오타 하나를 고치는 일은 요청·diff·필요한 검사로 마칠 수 있다. 여러 페이지를 나누고 옛 URL을
보존해야 한다면 순서와 완료 조건을 기록해야 한다. 다음 중 하나가 있으면 계획이 유용하다.

- 여러 단계나 세션에 걸쳐 끝내야 한다.
- 파일 이동·데이터 변경처럼 의존 순서와 호환 조건이 있다.
- 선택 이유나 미결 사항을 다음 작업에서도 알아야 한다.
- 일반 검사 외에 사용자 시나리오로 확인할 결과가 있다.

`docs/plans/`는 이 덱의 운영 선택이다. 두 제품의 필수 디렉터리 이름이 아니다.
이 저장소의 파일 번호·상태·목록 규칙은 `docs/plans/README.md`가 정한다.
학습 페이지 이름에는 순서 번호를 붙이지 않지만 작업 계획 번호는 식별자로 사용한다.

## 계획의 크기와 실행 권한을 따로 정한다

| 요청 | 수행할 범위 |
|---|---|
| 조사·계획만 | 근거·구조안·완료 조건까지, 구현 전 종료 |
| M1만 수행 | M1의 편집·검증·기록까지 |
| 전체 완료 | 허용된 다음 마일스톤을 이어서 완료 |

마일스톤을 작게 나눈 이유는 실패 위치와 검증 결과를 알기 위해서다. 전체 완료를 맡겼는데
매번 재승인을 요구하면 계획이 작업을 돕지 못한다. 반대로 로컬 편집 허가가 푸시·배포 허가는 아니다.
새 범위 결정이나 추가 권한이 필요한 행동은 구체적으로 구분한다.

## 저장소 문서는 서로 다른 시간을 기억한다

예를 들어 “두 페이지로 JSON 기초를 설명한다”는 작업이 끝난 뒤 새 세션을 시작한다고 하자.
다음 사람에게 필요한 것은 전체 채팅이 아니라 현재 학습 내용, 작성 규칙, 당시 검증 결과다.

| 정보 | 정본 | 완료 뒤 처리 |
|---|---|---|
| 현재 학습 내용 | 덱 본문·baseline | 새 사실에 맞춰 갱신 |
| 반복 작성·검증 규칙 | AGENTS·docs 지침 | 반복해서 필요한 것만 유지 |
| 이번 작업의 선택·상태·실행 증거 | 해당 계획 | 당시 기록으로 보존 |
| 정확한 변경 스냅샷 | Git commit | 요청받았을 때 커밋 |

제품 개발이라면 여러 작업이 공유하는 현재 사용자 요구를 PRD(Product Requirements Document)에,
장기 기술 경계를 architecture·spec에 둘 수 있다. 학습 노트 하나를 추가하려고 PRD·backlog·
changelog·decisions 파일을 모두 만들 필요는 없다. 기존 정본이 맡을 수 있으면 그곳에 둔다.
외부 이슈가 협업 정본이라면 같은 상태를 로컬 계획에 복제하지 않고 링크로 연결한다.

## 계획 문서는 실행 가능한 계약이다

다음은 가상 JSON 덱 작업의 시작 예시다. 실제 검증 결과가 아니라 **검증할 조건**이다.
파일 번호는 `docs/plans/README.md`에 따라 발급한다.

```md
# <번호>. JSON 기초 덱

상태: 계획
지금 위치: 독자·범위 확인 · 다음 M1
실행 범위: 전체 완료, 커밋·푸시·배포 제외

## 목표와 완료 조건

- [ ] JavaScript 기초 독자가 JSON과 JS 객체 표기의 차이를 설명한다.
- [ ] 유효한 JSON을 파싱하고 잘못된 쉼표를 고칠 수 있다.
- [ ] baseline·metadata·index·개념/적용 본문이 연결된다.
- [ ] 예제를 실행해 예상 결과와 대조하고 npm run check가 통과한다.

## 작업

- M1: 공식 근거·최소 예제·학습 순서 확인
- M2: 페이지 작성·의미 리뷰·예제 실행·사이트 검사

## 실행 기록

실제 결정·검증 명령·관찰·남은 제한을 수행 뒤 기록한다.

## 완료 기록

전체 수용 조건, 영구 문서 반영 위치, 미해결 사항을 대조한다.
```

“MDX 파일 두 개 생성”만으로는 위 학습 결과를 판정할 수 없다. 설명·예제·이해 확인이 목표와
연결돼야 한다. 검사 명령이 적혀 있다고 실행한 것은 아니므로 결과 칸을 미리 성공으로 채우지 않는다.

## ExecPlan과 계획 문서

[OpenAI Cookbook의 ExecPlan](https://developers.openai.com/cookbook/articles/codex_exec_plans)은
계획을 계속 갱신하며 작업을 이어 가는 공식 사례다. 현재 원문은 **archived**로 표시되어 있으며
현행 제품의 필수 형식이나 권한 규칙으로 취급하지 않는다.

| 비교 축 | 원문의 설계 | 이 덱의 선택 |
|---|---|---|
| 맥락 전달 | 계획 하나에 필요한 지식을 담아 자기완결 | 저장소 정본은 링크하고 대화에서 정한 결정은 계획에 기록 |
| 다음 단계 | 마일스톤을 이어서 진행 | 사용자가 맡긴 실행 범위와 추가 결정 지점을 따른다 |

우리 방식에서 링크가 유효하고 에이전트가 관련 정본을 읽어야 한다는 전제가 빠지면 자기완결성이
무너진다. 반대로 이미 있는 작성 규칙을 모든 계획에 복사하면 다음 개정부터 어긋난다.

## 완료하면 필요한 지식을 제자리로 옮긴다

전체 조건과 실제 결과를 대조한 뒤 상태·목록을 완료로 바꾼다. 새로 확인한 학습 내용은 본문,
버전·범위는 baseline, 공통 작성 규칙은 해당 지침으로 옮긴다. 계획은 당시 결정·검증 기록으로 남긴다.
확인하지 못한 항목은 완료로 표시하지 않고 이유와 재개 방법을 적는다.

## 이해 확인

M1 검사가 통과했다. 곧바로 M2를 실행해도 될까? 마일스톤 번호만으로는 답할 수 없다.
계획 머리의 사용자 실행 범위가 전체 완료이고 M2에 미결 결정·추가 권한이 없다면 이어 간다.
M1만 요청받았다면 기록까지 마치고 종료한다.
