이 페이지는 **자료 조사부터 작은 덱 작성, 결과 리뷰, 수정·검증, 재개까지 어떻게 연결하는가**를

## 요청은 결과와 경계를 드러낸다

아래는 요청 설계의 비교다. 두 모델을 실행해 성능을 비교한 실험 결과는 아니다.

| 요청 | 빠진 것 또는 판정 가능한 것 |
|---|---|
| JSON을 자세히 설명하는 덱을 만들어 줘 | 독자·적용 과제·범위·검증 기준이 없어 분량만 늘어날 수 있다 |
| JavaScript 기초 독자가 JSON을 파싱하고 쉼표 오류를 고치게 해 줘 | 필요한 설명과 예제를 결과에 맞춰 고를 수 있다 |

다음 요청은 이 사이트 구조에서 사용하도록 쓴 예시다.

```text
AGENTS.md와 작성 지침을 읽고 JSON 기초 덱을 만들어 줘.
독자: JavaScript 변수와 객체를 아는 입문자.
학습 결과: JSON과 JS 객체 표기를 구분하고, JSON.parse의 입력 오류를 고칠 수 있다.
범위: 객체·배열·문자열·숫자·불리언·null, 파싱과 직렬화의 최소 예제.
제외: 스키마 도구 비교, API 설계, 보안 일반론.

공식 근거와 예제를 먼저 확인한 뒤 baseline·metadata·index와 개념/적용 본문을 작성해 줘.
파일·URL에는 순서 번호를 넣지 마.
예제에는 실행 명령·예상 결과·실패 원인과 고치는 법을 써 줘.
의미 리뷰와 pnpm check까지 마치고, 실행한 검증과 남은 제한을 알려 줘.
커밋·푸시·배포는 하지 마.
```

[Claude Code best practices](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)는
에이전트가 실행해 판정할 수 있는 검증 신호를 주도록 권한다. 여기서는 파싱 결과와 사이트 검사가 그
신호이고, 설명이 독자의 질문에 답하는지는 작성 지침으로 따로 본다.

## 자료 조사와 작성의 연결을 확인한다

조사 결과가 링크 모음에서 끝나면 본문과 연결되지 않는다. 작성 전에 주장 → 근거 → 예제의 대응을 본다.
예를 들어 “JSON 문자열에는 큰따옴표를 쓴다”는 주장에는 공식 문법 근거와 유효/무효 입력 한 쌍을 둔다.
이 단계에서 실행 불가능한 주요 예제나 빠진 선행 개념을 발견하면 본문 분량을 늘리기 전에 고친다.

작업 중에는 한 번에 전체 덱을 계속 다시 쓰지 않는다. 중심 질문과 작은 예제를 먼저 맞추고,
그 결과를 목차·본문·이해 확인으로 확장한다. 작성 도중 범위가 API 인증까지 늘었다면 현재 독자의
학습 결과에 필요한지 판단한다. 요청에 없던 독립 주제라면 별도 작업 후보로 남긴다.

## 결과는 세 종류의 증거로 읽는다

| 증거 | 확인하는 질문 | 통과해도 남는 것 |
|---|---|---|
| diff·본문 | 요청한 범위와 설명 구조인가 | 예제의 실제 동작 |
| 예제 실행 | 입력이 예상 결과를 만드는가 | 독자가 원리를 이해하는가 |
| `pnpm check` | 구조·MDX·렌더된 내부 링크가 맞는가 | 사실 정확성·학습 효과 |

리뷰 요청도 문제를 구체화한다.

```text
생성한 덱을 독자와 학습 결과에 맞춰 리뷰해 줘.
페이지별로 중심 질문, 빠진 전제, 근거 없는 주장, 실행할 수 없는 예제를 찾아 고쳐 줘.
문장을 매끄럽게 바꾸는 데서 끝내지 말고 예제와 이해 확인의 답이 본문에서 도출되는지 확인해 줘.
실제 실행한 결과와 아직 확인하지 못한 항목을 구분해 기록해 줘.
```

독립 학습자가 이해했다는 관찰이 없다면 학습 효과를 입증했다고 쓰지 않는다.
이 과정은 작성 흐름과 예제의 표본 검증이다.

## 실패하면 원인을 좁히고 해당 결과를 다시 확인한다

`pnpm check`가 내부 앵커 오류로 실패했다면 링크 목적지와 렌더된 제목을 대조한다.
검사 코드를 약화하거나 문제 링크를 무작정 지우지 말고 독자가 도착해야 할 절을 연결한다.
내용상 잘못된 예제라면 예제와 설명을 함께 고친 뒤 다시 실행한다.

필수 검사가 통과한 뒤에는 새 변경·실패·미해결 문제가 없으면 반복하지 않는다.
화면 동작을 바꾸지 않은 페이지 작성만으로 브라우저 전수 검사를 추가하지 않는다.
이 저장소의 범위는 `docs/verification.md`가 정한다.

검증 기록에는 명령·결과·관찰을 둔다. 다음은 **기록 형식 예시**이며 실행 결과를 대신하지 않는다.

```md
- 예제: <실행 명령> → <관찰한 출력>, 본문의 예상 결과와 일치/불일치.
- 사이트 검사: pnpm check → <실제 종료 코드와 요약>.
- 의미 리뷰: <빠진 전제와 수정>, <남은 제한>.
```

## 새 세션은 현재 파일에서 재개한다

중단 전 계획 머리에 지금 위치, 마지막으로 실제 실행한 검사, 아직 확인하지 않은 항목과 다음 행동을
적는다. 채팅의 “거의 완료”보다 파일·diff·검사 결과를 기준으로 삼는다.

```text
AGENTS.md, docs/plans/README.md와 해당 계획의 현재 위치를 읽어 줘.
git status와 diff를 확인해 기록과 실제 파일이 맞는지 대조해 줘.
완료된 조건, 아직 검증되지 않은 조건, 다음 행동을 짧게 정리한 뒤
사용자가 지정한 실행 범위 안에서 미완료 작업을 이어 가 줘.
```

컨텍스트 요약이나 도구의 기억 기능을 저장소 정본의 대체물로 취급하지 않는다.
Claude Code의 [memory 설명](https://code.claude.com/docs/en/memory)은 지침과 자동 기억을 구분한다.
다른 도구도 알아야 할 결정은 로컬 개인 기억에만 두지 말고 계획·본문·공통 지침의 알맞은 곳에 남긴다.

## 권한과 병렬 작업의 경계

사용자가 정할 것은 목표·범위와 아직 허용하지 않은 외부 행동이다. 에이전트는 허용된 편집·검증·
실패 수정을 마친다. 질문이 필요하면 결정 대상, 현재까지 만든 결과, 선택의 영향을 구체적으로 알린다.
전체 완료 요청에 이미 허용된 다음 작업의 재승인을 끼워 넣지 않는다.

병렬 검토를 사용하는 환경이라면 서로 독립된 질문과 편집 경로를 나눠야 한다.
같은 파일의 연속 편집은 순서대로 처리한다. 위임 가능 여부와 실행 조건은 사용 중인 도구·세션 지침을
확인하며, 이 페이지가 모든 작업에서 subagent를 실행하라는 지시는 아니다.

## 이해 확인

사이트 검사가 통과했지만 실패 예제의 출력이 설명과 다르다. 완료로 보고할 수 있을까?
실행 결과와 학습 내용이 어긋났으므로 아직 아니다. 예제·설명을 고치고 영향을 받은 검증을 다시 한다.
반대로 모든 필수 조건이 충족됐는데 동일 검사를 다시 실행할 근거가 없다면 기록하고 마친다.
