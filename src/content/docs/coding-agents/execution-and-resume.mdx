## 요청은 결과와 경계를 드러낸다

공유 지침이 로드된 레포에서는 매번 모든 절차를 프롬프트에 복사하지 않는다.
목표·범위·완료 조건과 이번에 어디까지 맡기는지 쓴다. 다음은 계획 파일 작성도 명시적으로 요청한 예다.

```text
업무 목록에 CSV 내보내기를 추가해 줘.
현재 사용자의 조회 권한과 필터·정렬을 적용하고, 페이지 구분 없이 전체 결과를 포함해 줘.
열은 ID·제목·상태로 하고, 0건은 헤더만 반환해 줘.
최대 1,000건이며 초과하면 일부만 내려받지 않도록 제한을 안내해 줘.
비동기 대량 처리와 예약 전송은 이번 범위에서 제외해 줘.

먼저 기존 조회·권한·CSV 처리 경로와 검사 명령을 확인하고
레포의 규칙에 맞춰 작업 계획을 파일로 남겨 줘.
새 제품 결정이 필요하지 않으면 구현·동작 확인·실패 수정까지 끝내 줘.
계획의 현재 상태와 실제 검증 결과를 갱신해 줘. 커밋·푸시·배포는 제외해 줘.
```

계획만 논의하려면 마지막 실행 요청을 “계획 작성까지만 하고 구현은 시작하지 마”로 바꾼다.
OpenAI의 [Astra 지침](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)은
첫 구현에서 멈추지 않게 하려면 실행·확인·수정까지 완료 범위를 명확히 하라고 설명한다.
이 예시의 제한값은 합의한 요구이며 다른 프로젝트의 기본값이 아니다.

## 자료 조사와 구현의 연결을 확인한다

조사는 결정을 바꾸는 근거를 찾는 과정이다. CSV 사례라면 기존 조회 함수에 권한·필터가 어디서
적용되는지, 페이지네이션은 어디서 붙는지, 기존 CSV 라이브러리와 안전한 출력 규칙이 있는지 본다.
발견한 정본과 판단을 계획에 연결하고 관련 없는 서비스 전체를 먼저 읽지는 않는다.

M1의 API를 구현할 때에는 먼저 권한·필터·건수·출력 형식을 확인한다. M2는 확인한 API 계약을
사용해 버튼과 실패 안내를 연결한다. 실제 코드에서 계약이 바뀌면 계획과 의존 작업도 갱신한다.
모든 세션에 동일한 조사 순서를 강제할 필요는 없고, 다음 결과를 만들기에 충분한 근거가 있는지 본다.

## 결과는 세 종류의 증거로 읽는다

| 증거 | CSV 사례에서 확인할 것 | 통과해도 남는 것 |
|---|---|---|
| diff·요구사항 대조 | 조회 권한 재사용, 변경 범위, 빠진 조건 | 실제 실행 결과 |
| 자동 테스트·타입·빌드 | 다른 사용자 데이터 제외, 필터·전체 건수·CSV 형식, 기존 조회 | UI와 API의 실제 연결 |
| 사용자 흐름 확인 | 버튼에서 다운로드, 파일 내용, 초과·실패 안내 | 확인하지 않은 환경·입력 |

예를 들어 테스트 데이터에 필터 일치 25건과 다른 사용자 업무를 두고 목록은 10건씩 표시한다.
내보낸 파일의 데이터가 권한 있는 25건이면 페이지네이션 뒤까지 포함한 것이다. 10건이면
현재 페이지만 내보낸 것이므로 실패다. 쉼표·따옴표·줄바꿈이 있는 제목도 파싱 후 원래 값과 대조한다.
이는 **준비할 입력과 예상 관찰의 예시**이며 실제 통과 기록이 아니다.

[Claude Code best practices](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)는
에이전트가 결과를 판정할 수 있는 검증 신호를 주도록 권한다. 브라우저는 이 예시의 다운로드·실패
안내처럼 화면과 API의 연결을 확인해야 할 때 사용한다. 모든 문서 수정에 붙이는 기본 절차는 아니다.

## 실패하면 원인을 좁히고 해당 결과를 다시 확인한다

파일에 10건만 있다면 필터 전체 조회 대신 현재 페이지 응답을 사용했는지 좁힌다.
구현과 관련 테스트를 고치고 영향을 받은 검증을 다시 한다. 기대값을 10건으로 낮춰 통과시키지 않는다.
필수 검사가 통과한 뒤에는 새 변경·실패·미해결 문제가 없으면 반복하지 않는다.

기록에는 명령·작업 위치·검증한 코드 상태·결과·남은 제한을 필요한 만큼 적는다.
다음은 실제 결과로 채울 **기록 형식**이다.

```md
- 코드 상태: <브랜치·기준 커밋>, <검사 당시 미커밋 변경 범위>
- 자동 검사: <작업 위치와 실제 명령> → <종료 코드·관찰 요약>
- 사용자 흐름: <준비한 데이터·조작> → <파일 내용·화면에서 관찰한 결과>
- 미확인: <실행하지 못한 항목·이유·다음 확인 방법>
```

## 완료라고 말하기 전에 계획과 diff를 대조 리뷰한다

구현한 세션은 자기 diff를 관대하게 읽는다. 검사가 통과한 뒤에도 완료 조건 하나가 빠졌거나
요청 밖 파일이 바뀐 것은 새 컨텍스트가 더 잘 찾는다.
[Claude Code best practices](https://code.claude.com/docs/en/best-practices#add-an-adversarial-review-step)는
완료로 치기 전에 별도 컨텍스트의 리뷰어가 diff를 계획과 대조하도록 권한다.
Codex와 Claude Code를 함께 쓰는 레포라면 한 도구가 구현하고 다른 도구가 리뷰하는 배치가 자연스럽다.

리뷰어에게는 계획·diff·실제 검증 결과를 주고 무엇을 결함으로 볼지 정해 준다. 다음은 리뷰 도구에
줄 요청이며 경로는 실제 계획으로 바꾼다.

```text
docs/plans/<계획 파일>.md의 완료 조건과 현재 git diff를 대조해 줘.
완료 조건마다 구현·테스트가 있는지, 요청 범위 밖의 변경이 섞였는지,
계획에 적힌 검증 결과가 실제 코드 상태와 맞는지 확인해 줘.
정확성과 요구 누락만 보고하고 스타일 선호는 제외해 줘. 수정은 하지 마.
```

리뷰어는 결함을 찾으라는 요청을 받았으므로 문제없는 코드에서도 무언가 보고하기 쉽다.
완료 조건이나 정확성에 닿는 지적만 반영하고 나머지는 선택 사항으로 둔다.
리뷰 결과를 반영한 뒤에는 영향을 받은 검증만 다시 하고 계획의 검증 기록을 갱신한다.

## 도구를 바꾸기 전에 현재 상태를 남긴다

Anthropic의 [장기 에이전트 실험](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)은
진행 기록·기능 목록·Git 이력으로 다음 세션의 맥락을 복구한다. Agent SDK 기반 웹앱 실험이므로
같은 파일명·자동 커밋·매번 브라우저 검사를 모든 레포에 의무화하지 않는다.

Codex에서 M1을 마친 뒤 Claude Code로 바꾼다고 하자. 사용 중인 계획에 다음 정보를 갱신한다.
**가상 인계 예시**이며 대괄호 부분은 실제 값으로 채운다.

```md
지금 위치: M1 완료 · M2 UI 미착수
코드 위치: [작업 디렉터리·브랜치·기준 커밋]
미커밋 변경: [API와 테스트의 실제 경로]. 커밋은 요청받지 않아 하지 않음.
결정: 목록 쿼리의 권한·필터 부분을 재사용하고 페이지 제한만 분리함.
검증: [실제 명령·결과]. 권한·필터·전체 건수·형식은 확인, UI 연결은 미확인.
다음 행동: M2에서 [실제 API 경로]를 버튼에 연결하고 초과 안내를 확인.
차단 사항: [없음 또는 필요한 결정·재개 조건]
```

이 기록을 만들기 위해 별도 인계 파일을 항상 추가할 필요는 없다. 기존 계획이나 이슈의 현재 상태를
갱신한다. 이슈가 다른 도구에서 접근 불가능하다면 필요한 요지를 접근 가능한 문서나 요청에 제공한다.
다른 worktree·기기로 옮길 때에는 미커밋 변경도 전달해야 한다. 계획 경로만 넘겨서는 코드가 이동하지 않는다.

## 새 세션은 현재 파일에서 재개한다

같은 도구의 대화를 이어 갈 수 있어도 기록과 파일 상태가 일치하는지 확인한다.
Claude Code의 [대화 재개](https://code.claude.com/docs/en/common-workflows#resume-previous-conversations)와
공유 계획을 통한 도구 간 인계는 구분한다. 다음은 새 도구에 줄 요청이다. 경로를 실제 계획으로 바꾼다.

```text
이 레포의 docs/plans/<계획 파일>.md에서 미완료 작업을 끝까지 이어 가 줘.
계획의 목표·지금 위치·미결 사항과 관련 정본을 확인해 줘.
git status·diff·최근 이력을 대조해 계획과 실제 코드 상태가 맞는지 확인해 줘.
차이가 있으면 실제 상태를 근거로 기록을 바로잡고, 완료한 작업은 반복하지 마.
남은 구현·필요한 검증·이번 변경의 실패 수정과 계획 갱신까지 수행해 줘.
커밋·푸시·배포는 제외해 줘.
```

<Steps>

1. **목표와 현재 작업을 찾는다.** 계획과 현재 작업에 필요한 지침·원본부터 읽는다.
2. **기록을 실제 상태와 대조한다.** 브랜치·커밋·미커밋 diff를 보고 인계 이후의 변경을 확인한다.
3. **검증의 유효 범위를 판단한다.** 코드·환경이 바뀌었거나 결과가 의심되는 부분은 필요한 검사로 확인한다.
4. **미완료 작업을 수행한다.** 결정·검증·다음 행동을 갱신하고 전체 수용 조건까지 대조한다.

</Steps>

계획에 “테스트 통과”라고 있어도 이후 API가 바뀌었다면 그 결과가 현재 상태를 증명하지 않는다.
반대로 같은 상태에서 유효한 검사를 새 세션이라는 이유만으로 모두 반복할 필요도 없다.
이미 로드된 AGENTS를 다시 읽으라는 문구를 매번 붙이지 않는다.

## 권한과 병렬 작업의 경계

실행 범위와 재승인의 원칙은 [작업 계획](/coding-agents/work-plans/#계획의-크기와-실행-권한을-따로-정한다)에서
정했다. 실행 중 질문이 필요하면 현재까지 확인한 근거, 선택지, 그 결정에 의존하는 작업을 함께 제시해
사용자가 한 번에 판단할 수 있게 한다. 답을 기다리는 동안 그 결정에 의존하지 않는 작업은 이어 간다.

두 도구를 동시에 편집자로 쓸 때에는 독립된 범위와 작업 사본을 배정하고 공유 파일의 변경을 조정한다.
같은 체크아웃에서 연속으로 바꿔야 하는 파일은 순서대로 처리한다. 구현과 리뷰를 나누는 배치는
[대조 리뷰](#완료라고-말하기-전에-계획과-diff를-대조-리뷰한다)에서 설명했다.

Anthropic의 [후속 장기 작업 실험](https://www.anthropic.com/engineering/harness-design-long-running-apps)은
모델이 개선되면서 일부 분할·초기화·평가 절차를 줄였다고 설명한다. 여러 에이전트나 강제 세션
초기화를 기본으로 넣지 말고, 실제 어려움과 검증 효과에 맞춰 선택한다.

## 이해 확인

새 세션의 계획에는 M1 완료라고 적혔는데 해당 코드가 없다. 바로 M2로 갈까?
다른 브랜치·worktree에 있는지, 미커밋 변경이 전달되지 않았는지 확인해 상태부터 맞춘다.

API 검사만 통과한 상태에서 전체 완료라고 보고할 수 있을까? 버튼·다운로드·실패 안내가 남았다.
허용된 범위에서 확인과 수정을 마치고, 실제로 검증하지 못한 조건은 구분해 보고한다.
