## 먼저 기존 레포의 사실을 확인한다

템플릿부터 복사하면 실제로 없는 명령과 문서를 지침에 넣기 쉽다. README, 빌드 설정, CI,
기존 AGENTS·CLAUDE·기여 지침을 대조해 다음을 찾는다.

| 확인할 것 | 지침에 남길 내용 |
|---|---|
| 설치·실행·검사 명령과 실행 위치 | 실제로 쓸 명령, 환경 조건, 변경에 따른 검사 범위 |
| 구조와 변경 경계 | 주요 진입점, 생성 파일, 유지해야 할 의존 방향 |
| 기존 문서와 이슈 | 요구사항·설계·검증·현재 작업의 정본 위치 |
| 외부 상태를 바꾸는 작업 | 이미 허용한 로컬 작업과 별도 판단이 필요한 행동 |

예를 들어 CI가 `pnpm test`를 실행하는 레포에 익숙하다는 이유로 `npm test`를 넣지 않는다.
명령을 실행할 환경이 없다면 미확인이라고 남긴다. 지침 개선을 위해 관련 없는 코드를 고칠 필요도 없다.

## 같은 규칙을 두 파일에 복사하면 어긋난다

검사 명령을 바꿀 때 CLAUDE만 수정하면 어느 도구로 시작했느냐에 따라 다른 검사를 실행한다.
공유 규칙은 한 곳에 두고 제품별 입력을 연결하면 수정 지점이 분명해진다.

| 역할 | 이 덱의 기본 구성 | 맡는 일 |
|---|---|---|
| 공유 행동 규칙 | `AGENTS.md` | 프로젝트 제약, 문서 읽기 조건, 검증 범위와 허용된 작업의 설명 |
| 도구별 연결 | `CLAUDE.md`의 `@AGENTS.md` | 공유 규칙을 가져오고 필요한 도구별 차이만 추가 |
| 실행 결과 판정 | 검사 스크립트·CI | 테스트·타입·빌드 등 기계가 확인할 조건 |
| 반드시 막을 행동 | 도구별 hook·권한·sandbox 설정 | 지침과 무관하게 차단해야 하는 파일·명령·네트워크 |

[tldraw의 실제 구성](/coding-agents/public-repositories/#tldraw-공유-지침과-이슈-중심-작업)도 이 방식이다.
Claude Code의 조건부 AGENTS 직접 로딩을 쓰는 구성도 가능하므로 어댑터가 항상 필수인 것은 아니다.
기존 import를 유지할 수 있다는 설명과 적용 조건은
[공식 memory 문서](https://code.claude.com/docs/en/memory#agents-md)에서 확인한다.

## 루트 파일은 지도와 공통 계약이다

다음은 **가상 서비스 레포의 예시**다. 아래 문서가 실제로 있는 프로젝트를 가정한다.
기존 지침에 병합할 때 경로·검사 명령·권한 정책을 그 레포에 맞춘다.

```md title="AGENTS.md — 가상 예시"
# 작업 규칙

- 서비스 경계를 바꾸면 docs/design-docs/architecture.md를, DB 스키마를 바꾸면 docs/design-docs/database.md를 읽는다.
- 제품 요구는 docs/product-specs/가 정본이다. 요구가 바뀌면 그 문서를 함께 고친다.
- 수정 대상 경로에 아직 읽지 않은 하위 AGENTS.md가 있으면 수정 전에 확인한다.
- 사용자 변경을 보존하고 요청 범위의 구현·검증·이번 변경으로 생긴 오류 수정까지 마친다.
- 검증 명령과 환경 조건은 docs/verification.md를 따른다.
- 계획이 필요하면 docs/exec-plans/README.md의 생성 기준을 따른다. 진행 중인 계획은 active/에 있고 진행에 맞춰 갱신한다.
- 필수 검사가 통과하면 마친다. 새 변경·실패·미해결 문제가 있을 때 영향을 받은 검사를 다시 한다.
- 커밋·푸시·배포는 이 프로젝트에서 사용자가 허용한 범위에 따라 수행한다.
```

검증 문서에는 “테스트를 잘 실행” 같은 말 대신 실제 명령·작업 위치·대상 범위를 적는다.
어댑터를 쓰기로 했다면 같은 폴더에 다음을 둔다.

```md title="CLAUDE.md"
@AGENTS.md
```

import는 파일 내용도 컨텍스트에 넣는다. 파일이 한 줄이라고 컨텍스트 사용량이 줄지는 않는다.
OpenAI의 [Harness engineering](https://openai.com/index/harness-engineering/)도 짧은 AGENTS를
문서의 진입점으로 쓰고, 상세 지식은 저장소 안에서 관리하는 구성을 소개한다.

## 지침에는 행동만, 설명은 연결만 둔다

“항상 아키텍처·DB·배포 문서를 전부 읽어라”는 오타 수정에도 불필요한 맥락을 더한다.
“서비스 경계 변경이면 아키텍처 문서를 읽어라”처럼 **읽을 조건과 경로를 함께** 둔다.

| 정보 | 둘 곳 |
|---|---|
| 생성 파일을 직접 고치지 않는다는 규칙 | 공유 지침 |
| 생성 과정의 상세 설계 | 관련 README·설계 문서 |
| 이번 내보내기에 1,000건 제한을 선택한 이유 | 현재 작업 계획·요구사항 |
| 출력 형식과 권한이 맞는다는 증거 | 테스트·실제 검증 결과 |

반복 절차를 skill로 옮길 때도 적용 범위를 좁힌다. “DB 관련 작업이면 사용”보다
“마이그레이션을 추가·수정하거나 배포 순서를 검토할 때 사용”이 필요한 문서를 고르기 쉽다.
이 조건부 읽기와 skill 범위 설계는 OpenAI의
[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)에 근거한다.

## 지침은 권고이고 강제는 설정이 맡는다

AGENTS와 CLAUDE에 적은 문장은 모델이 읽고 따르는 맥락이다. Claude Code의
[memory 문서](https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)는 이를 “enforced
configuration이 아닌 context”라고 설명하고, 모델의 판단과 무관하게 막아야 하는 행동에는 hook을 쓰라고 안내한다.
“`.env`를 수정하지 마라”를 지침에만 두면 어긋날 때 알 수 없지만, 도구 설정에 두면 실행 전에 차단된다.

| 목적 | 지침에 쓸 것 | 설정으로 강제할 것 |
|---|---|---|
| 배포·마이그레이션 파일 보호 | 왜 건드리지 않는지와 예외 절차 | Claude Code의 PreToolUse hook, Codex의 sandbox 쓰기 범위 |
| 외부 네트워크·배포 명령 | 허용된 범위와 확인이 필요한 경우 | 권한 allowlist·승인 정책 |
| 검사 통과 전 종료 금지 | 어떤 검사가 완료 조건인지 | Stop hook 또는 CI |

Claude Code는 [hooks 가이드](https://code.claude.com/docs/en/hooks-guide)와 권한 설정으로,
Codex는 [sandbox 모드](https://learn.chatgpt.com/docs/sandboxing)와
[승인 정책](https://learn.chatgpt.com/docs/agent-approvals-security)으로 강제 경계를 둔다.
두 도구의 설정 형식은 다르므로 각자 설정하고, 공유 지침에는 그 경계가 있다는 사실과 예외 절차만 적는다.
설정 항목 전체는 이 덱의 범위 밖이며 공식 문서에서 현재 값을 확인한다.

## 작은 작업으로 지침 변경을 비교한다

모델의 과거 실수를 막으려고 넣은 단계가 현재도 필요한지 확인한다.
위 공식 글은 과도한 레시피·반복 검사·넓은 승인 문구를 재검토하고 완료 범위를 명확히 하라고 권한다.
이는 Astra에 대한 안내이므로 Claude Code를 포함한 모든 환경의 행동을 보장한다고 읽지 않는다.

예를 들어 안전한 로컬 테스트에서도 매번 멈춘다면 “모든 명령은 사전 승인”이라는 문구를 살핀다.
실제로 격리된 테스트라는 확인이 있을 때 그 범위의 실행·실패 수정·재검사를 허용한다고 구체화한다.
실제 권한·데이터·배포 제약은 유지한다.

지침 수정 전후를 비교하려면 오타 수정·작은 기능 변경·기존 계획 재개 중 필요한 표본을 고른다.
같은 시작 상태의 별도 작업 사본에서 각 도구가 **요구를 놓쳤는지, 불필요하게 멈췄는지,
관련 없는 문서를 읽거나 검사를 반복했는지** 본다. 짧아진 줄 수만으로 개선이라 판단하지 않는다.

## 다른 프로젝트에서 요청하기

다음 요청은 대상 레포에서 사용할 수 있다. 요청한 산출물은 기존 지침의 개선이며 새 계획 작성은 별개다.

```text
이 레포에서 Codex와 Claude Code를 함께 쓰기 좋게 작업 지침을 개선해 줘.
README·빌드 설정·CI·기존 에이전트 지침을 대조해 실제 명령과 문서 정본을 확인해 줘.
중복·충돌·없는 경로·지나친 읽기와 승인 절차를 찾아 관련 지침을 수정해 줘.
프로젝트 제약은 보존하고, 검증 범위와 큰 작업의 계획 생성·인계 기준을 명확히 해 줘.
실제로 확인한 근거와 확인하지 못한 환경 조건을 구분해 보고해 줘.
```

## 이해 확인

검사 명령이 바뀌면 어디를 고칠까? 실제 스크립트와 지침이 가리키는 검증 문서를 함께 맞춘다.
CLAUDE 어댑터에 명령을 다시 복제하지 않는다. 두 도구가 같은 문서를 읽는지도 확인한다.

“항상 테스트”를 삭제했으니 개선일까? 필수 검증까지 빠졌다면 아니다. 필요한 명령·완료 조건을
유지하면서 근거 없는 반복이 줄었는지 실제 작업으로 판단한다.

“마이그레이션 폴더는 수정 금지”를 AGENTS에 적었으니 충분할까? 모델이 읽고 따를 가능성이 높아질
뿐이다. 어긋나면 안 되는 경계라면 각 도구의 hook·sandbox 설정으로도 막고, 지침에는 예외 절차를 남긴다.
