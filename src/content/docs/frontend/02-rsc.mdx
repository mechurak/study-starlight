> `use client`는 스위치가 아니라 경계다

## Next.js를 한 문장으로

React 컴포넌트를 **서버에서도 실행할 수 있게** 만들고,
그에 필요한 라우팅·번들링·캐싱·배포를 한 덩어리로 묶은 것.

"서버에서도"가 핵심이고 나머지는 부속이다.
이 전환이 App Router(Next.js 13)에서 시작해 지금(16.x)까지 다듬어지고 있다.
Pages Router는 여전히 동작하지만, 새 프로젝트의 기본은 App Router다.

## 서버가 기본값, 클라이언트는 명시

App Router에서는 **아무 표시가 없으면 서버 컴포넌트**다.

```tsx
// app/posts/page.tsx — 표시 없음 = 서버 컴포넌트
import { db } from '@/lib/db'

export default async function PostsPage() {
  // 이 쿼리는 서버에서만 실행된다. 브라우저는 이 코드를 본 적도 없다.
  const posts = await db.post.findMany({ orderBy: { createdAt: 'desc' } })

  return (
    <ul>
      {posts.map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  )
}
```

`async` 컴포넌트가 자연스럽게 동작한다. 이건 **서버 컴포넌트만의 특권**이다.

브라우저가 필요한 것을 쓰려면 파일 맨 위에 지시자를 붙인다.

```tsx
'use client'   // ← 이 파일부터는 브라우저로 간다

import { useState } from 'react'
import { Button } from '@/components/ui/button'

export function Counter() {
  const [n, setN] = useState(0)
  return <Button onClick={() => setN(n + 1)}>눌린 횟수: {n}</Button>
}
```

`useState`, `useEffect`, `onClick`, `window`, `localStorage` —
**브라우저가 필요한 것을 쓰면 `use client`가 필요하다.**

### 양쪽에서 못 하는 것

| | 서버 컴포넌트 | 클라이언트 컴포넌트 |
|---|---|---|
| 훅 (`useState`, `useEffect`…) | ❌ | ✅ |
| 이벤트 핸들러 (`onClick`) | ❌ | ✅ |
| `window` · `localStorage` | ❌ | ✅ |
| Context **제공** (`<Provider>`) | ❌ | ✅ |
| `async` 컴포넌트 | ✅ | ❌ |
| DB · 파일시스템 직접 접근 | ✅ | ❌ |
| 비밀 환경변수 | ✅ | ❌ |
| Node.js 전용 모듈 | ✅ | ❌ |

## `use client`는 스위치가 아니라 경계다

가장 흔한 오해다. `use client`는 그 파일 하나가 아니라 **거기서부터 아래 전부**를
클라이언트로 만든다.

```d2 layout=elk pad=40 title="'use client' 경계 아래로는 전부 클라이언트가 되는 컴포넌트 트리"
direction: down

classes: {
  ok: { style: { fill: "#dcfce7"; stroke: "#16a34a"; font-color: "#14532d" } }
  warn: { style: { fill: "#fef3c7"; stroke: "#d97706"; font-color: "#78350f" } }
  bad: { style: { fill: "#fee2e2"; stroke: "#dc2626"; font-color: "#7f1d1d" } }
}

p: "app/page.tsx — 서버" { class: ok }
h: "Header — 서버" { class: ok }
s: "SearchBox — 'use client' ← 경계" { class: warn }
l: "PostList — 서버" { class: ok }
sg: "Suggestions — 표시 없어도 클라이언트" { class: bad }
hl: "Highlight — 역시 클라이언트" { class: bad }

p -> h
p -> s
p -> l
s -> sg
sg -> hl
```

:::caution[함정]
그래서 `use client`를 **트리 위쪽에 두면 앱 대부분이 클라이언트가 된다.**
레이아웃 최상단에 무심코 붙이는 것이 이 스택에서 가장 흔한 사고다 —
`children`에 들어오는 모든 것이 딸려간다.
:::

### 경계를 잎사귀로 밀어라

<Tabs>
<TabItem label="나쁜 배치">

```tsx
'use client'
export default function Layout({ children }) {
  const [open, setOpen] = useState(false)
  return (
    <div>
      <Sidebar open={open} />
      <button onClick={() => setOpen(!open)}>메뉴</button>
```

`children` 안의 모든 것이 클라이언트로 딸려간다.
차트 라이브러리, 에디터, 날짜 피커가 그 아래에 있으면 번들이 폭발한다.

## 클라이언트가 서버를 감쌀 수 있다

반대 방향이 되는지가 헷갈리는 지점이다. 정답: **`children`으로 넘기면 된다.**

```tsx
// ❌ 클라이언트 컴포넌트가 서버 컴포넌트를 직접 import — 불가능
'use client'
import { ServerPostList } from './post-list'  // 서버 컴포넌트

export function Panel() {
  return <div><ServerPostList /></div>   // 클라이언트로 끌려들어간다
}
```

```tsx
// ✅ children으로 받으면 된다
'use client'
export function Panel({ children }) {
  const [open, setOpen] = useState(true)
  return <div>{open && children}</div>
}

// 서버 컴포넌트(page.tsx)에서 조립
<Panel>
  <ServerPostList />   {/* 서버에서 렌더된 결과가 들어간다 */}
</Panel>
```

:::tip[핵심]
금지된 것은 **import**지 **감싸는 것**이 아니다.
import는 번들러가 정적으로 따라가지만, `children`으로 넘긴 JSX는 **이미 렌더된 결과**라서
서버에 남을 수 있다. 4장의 도넛 패턴이 전부 이 원리 위에 서 있다.
:::

### 경계를 넘는 props는 직렬화되어야 한다

| 넘길 수 있다 | 넘길 수 없다 |
|---|---|
| 문자열, 숫자, 불리언, `null` | 함수 (`onClick={handleClick}`) |
| 배열, 평범한 객체 | 클래스 인스턴스 (ORM 모델 객체 등) |
| `Date`, `Map`, `Set` | `Symbol` |
| Promise (React가 처리해 준다) | 클로저를 가진 무엇이든 |
| JSX (`children` 포함) | |
| Server Function 참조 | |

:::caution[함정]
ORM이 돌려준 객체를 그대로 넘기다 터지는 일이 흔하다.
Prisma의 모델 객체에는 메서드가 붙어 있어 직렬화되지 않는다.
`select`로 필요한 필드만 뽑거나 평범한 객체로 변환해서 넘긴다.
:::

## 서버에서 클라이언트로 가는 것의 정체

서버 컴포넌트의 렌더 결과는 HTML만이 아니다. **RSC 페이로드**라는 별도 형식도 함께 간다.

```d2 layout=elk pad=40 title="RSC 페이로드가 첫 방문 HTML과 클라이언트 이동 시 트리 merge로 갈라지는 흐름"
direction: down

classes: {
  key: { style: { fill: "#dbeafe"; stroke: "#2563eb"; font-color: "#1e3a8a" } }
  ok: { style: { fill: "#dcfce7"; stroke: "#16a34a"; font-color: "#14532d" } }
  mute: { style: { fill: "#f1f5f9"; stroke: "#94a3b8"; font-color: "#334155" } }
}

a: 서버 컴포넌트\n렌더 { class: mute }
b: RSC 페이로드\n직렬화된 트리 { class: key }
c: HTML\n첫 방문용 { class: mute }
d: 클라이언트 이동 시\n이 페이로드만 전송 { class: mute }
e: React 가 기존 트리에 merge\n클라이언트 상태 유지 { class: ok }

a -> b
b -> c
b -> d
d -> e
```

- 첫 방문 → HTML을 받아 즉시 보인다
- 링크 클릭 → 전체 페이지가 아니라 **RSC 페이로드만** 받는다
- 그래서 클라이언트 상태(스크롤, 입력값, 열린 모달)가 **유지된 채** 화면이 바뀐다

### 하이드레이션

1. 서버가 HTML을 보낸다 → 사용자에게 **보인다.** 하지만 버튼을 눌러도 반응이 없다
2. 클라이언트 컴포넌트의 JS가 도착한다
3. React가 그 HTML에 이벤트 핸들러를 붙인다 → **이제 동작한다**

2~3단계 사이의 간극이 짧을수록 좋은 앱이다.
**서버 컴포넌트를 많이 쓸수록 하이드레이션할 대상이 줄어든다.**

:::caution[함정]
서버와 클라이언트의 첫 렌더 결과가 다르면 "hydration mismatch" 에러가 난다.
`new Date()`, `Math.random()`, `typeof window` 분기가 단골 원인이다.
값이 요청마다 달라야 한다면 6장의 `connection()`을 쓴다.
:::

## 파일 구조의 감각

<FileTree>

- app/
  - layout.tsx 서버
  - providers.tsx 'use client' — **Provider 껍데기만**
  - page.tsx 서버 — 데이터 조회
  - \_components/ 밑줄 = 라우팅에서 제외
    - revenue.tsx 서버
    - filter.tsx 'use client'
- components/
  - ui/ shadcn/ui가 관리하는 영역
  - shared/ 여러 라우트가 쓰는 우리 컴포넌트
- lib/
  - db.ts **서버 전용** — 'server-only'
  - utils.ts 양쪽 다 쓰는 순수 함수

</FileTree>

`_components`처럼 **밑줄로 시작하는 폴더는 라우팅에서 제외**된다.
라우트 전용 조각을 페이지 옆에 두는 데 쓴다.

## 2장 요약

- Next.js의 본질은 **React를 서버에서 실행하는 것**이다
- App Router에서 **서버 컴포넌트가 기본값**, 클라이언트는 `use client`로 명시
- `use client`는 스위치가 아니라 **경계**다 — 아래 전부가 클라이언트가 된다
- 경계를 **잎사귀로 밀수록** 번들이 작아진다
- 클라이언트가 서버 컴포넌트를 쓰려면 **`children`으로 받는다** (import는 안 된다)
- 경계를 넘는 props는 **직렬화 가능**해야 한다 — 함수와 ORM 객체가 단골 사고
