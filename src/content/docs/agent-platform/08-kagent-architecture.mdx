kagent는 `Agent`를 Kubernetes resource로 표현하고 model과 MCP tool 연결을 함께 관리한다. GitOps·namespace·
ServiceAccount·NetworkPolicy 같은 기존 Kubernetes 운영 모델과 가까운 것이 장점이다.

그림에서 dashboard가 점선인 이유는 중요하다. dashboard는 **Kubernetes API의 같은 resource를 보는 또 하나의
클라이언트**일 뿐 별도 진실을 갖지 않는다. 사내 포털을 따로 만들면 dashboard는 최종 사용자 화면이 아니라
플랫폼 팀의 운영 콘솔로 남는다. 이 경계는 [10장](/agent-platform/10-kagent-integration/)에서 다시 다룬다.

## 구성 요소

| 구성 요소 | 하는 일 | 사내 플랫폼에서의 취급 |
|---|---|---|
| controller | CRD를 watch해 Deployment·Service를 만들고 status를 되돌려 쓴다 | adapter가 대화하는 유일한 control plane |
| engine (app) | Agent의 대화 loop를 실행한다. model 호출, tool 호출, session 관리 | Agent Pod 안에서 돈다. 직접 조작하지 않는다 |
| dashboard | 웹 UI. Agent 생성·대화·상태 확인 | 운영자 콘솔. 최종 사용자에게 열지 않는다 |
| CLI | `kagent install`, `kagent invoke` 등 또 하나의 입구 | 설치·진단용. 서버 코드에서 shell로 부르지 않는다 |
| kmcp | MCP server 개발·배포용 하위 프로젝트. 기본 설치에 포함 | 사용자 MCP 배포 경로 후보 |

[공식 architecture 문서](https://kagent.dev/docs/kagent/concepts/architecture)는 controller를 Go로 쓰인
Kubernetes controller로, engine을 "Agent의 대화 loop를 실행하는 핵심 구성 요소"로 설명한다.

:::caution[함정]
"kagent를 붙인다"를 dashboard가 쓰는 내부 HTTP API에 붙이는 것으로 오해하기 쉽다. 공식 문서가 외부
클라이언트용으로 문서화하고 version을 약속하는 것은 **CRD schema**다(2026년 8월 21일 확인).
통합 지점 선택은 [10장](/agent-platform/10-kagent-integration/#통합-지점을-무엇으로-잡을-것인가)에서 정한다.
:::

## 두 engine runtime

Declarative Agent는 `runtime` 필드로 engine 구현을 고른다. 차이는 기능이 아니라 **시작 시간과 자원**이다.

| runtime | 시작 시간 | 특징 |
|---|---|---|
| Python ADK (기본) | 약 15초 | LangGraph·CrewAI·OpenAI 통합을 함께 쓸 수 있다 |
| Go ADK | 약 2초 | 자원 사용이 적다. `SandboxAgent`는 이 runtime만 쓴다 |

Agent 수가 많아지면 이 15초가 그대로 비용이 된다. 사내에서 Agent를 수백 개 등록받을 계획이라면
runtime 기본값을 무엇으로 강제할지가 platform policy 항목이 된다.

## 세 가지 실행 형태

`Agent.spec.type`의 `Declarative`·`BYO`는 **logic과 runtime을 누가 공급하는지**를 구분한다.
한편 실행이 상주하는 방식은 `Agent`·`SandboxAgent`·`AgentHarness`라는 **서로 다른 Kubernetes kind**로 갈린다.
이 둘은 다른 축이다.

| | `Agent` | `SandboxAgent` | `AgentHarness` |
|---|---|---|---|
| 실행 위치 | Deployment Pod | Agent Substrate actor | Agent Substrate actor |
| 상주 방식 | 항상 떠 있음 | idle이면 snapshot으로 내려감 | 장기 세션 유지 |
| 안의 내용 | kagent engine 또는 BYO image | Go ADK 기반 선언형 Agent | OpenClaw·Hermes 같은 외부 coding agent |
| 푸는 문제 | 항상 호출 가능한 Agent | idle compute 회수 | coding agent workspace lifecycle |
| 전제 인프라 | 없음 | gVisor node·object storage | gVisor node·object storage |

:::tip[`type`은 수명주기가 아니다]
`Agent.spec.type`의 `Declarative`·`BYO`는 logic과 runtime을 누가 공급하는지 구분한다. 한 번 실행 후 종료,
주기 실행, 항상 상주 같은 호출·process 수명주기 분류가 아니다.
:::

Agent Substrate의 worker pool·snapshot 구조는 [kagent 실습 덱 9장](/kagent-lab/09-harness-substrate/)에
인프라 관점으로 정리해 두었다. 이 덱에서는 "언제 검토 대상이 되는가"만 기억하면 된다 — 등록된 Agent 수가
동시 활성 수를 크게 웃돌 때, 또는 사용자에게 coding agent 세션을 제공할 때다.

## 실행 수명주기는 다른 resource와 trigger로 표현한다

플랫폼이 받는 요구("매일 아침 실행", "한 번만 실행")를 kagent에 그대로 옮길 수 있는 필드는 없다.
아래처럼 다른 resource와 외부 trigger로 번역한다.

| 원하는 실행 성격 | kagent에서의 대응 | process와 state |
|---|---|---|
| 항상 호출 가능한 일반 Agent | `Agent`의 `Declarative` 또는 `BYO` | Deployment replica가 A2A 요청을 기다림 |
| idle compute를 회수하는 Declarative Agent | `SandboxAgent` + Agent Substrate | idle actor를 snapshot하고 요청 때 복원 |
| 장기 coding 환경 | `AgentHarness` + Agent Substrate | filesystem·process를 가진 원격 sandbox를 ACP로 연결 |
| 한 번의 task | `kagent invoke` 또는 A2A task | task만 끝나며 일반 Agent Deployment는 남음 |
| 일정·event 기반 실행 | 외부 scheduler·event consumer가 A2A invoke | core `Agent` spec에는 schedule이 없음 |

`SandboxAgent`는 일반 `Agent`와 비슷한 선언을 Agent Substrate actor로 실행해 idle 자원을 줄인다. 논리적 Agent가
매번 사라지는 Job은 아니며 snapshot에서 다시 이어지는 suspendable 방식이다. `AgentHarness`는 OpenClaw·Hermes
같은 coding agent의 장기 workspace를 관리하며 일반 Agent와도 다르다.

주기 작업은 platform의 `Trigger`를 Kubernetes `CronJob`, Argo Workflows 같은 scheduler에 매핑하고, 실행 시
승인된 Agent의 A2A endpoint를 호출하는 구성이 기본이다. 정말 process까지 매번 종료해야 한다면 Job 안에서
Agent code를 직접 실행할 수 있지만, 이때는 kagent `Agent`의 Ready endpoint·session 관리 모델을 재사용하지
못한다. 이 차이를 capability로 드러내는 방법은
[11장](/agent-platform/11-kagent-adapter/#capability-profile)에 있다.

제품 중립 분류는 [Agent 종류의 여섯 축](/agent-platform/02-agent-types/#여섯-개의-분류-축)에서,
trigger 계약은 [제품 밖의 domain model](/agent-platform/03-domain-model/#trigger는-agent-process가-아니다)에서 정의한다.

## 8장 요약

- kagent의 진실은 Kubernetes API의 resource이고 dashboard·CLI는 그것을 보는 입구다.
- controller는 resource를 조정하고 engine은 Agent Pod 안에서 대화 loop를 돌린다.
- engine runtime은 Python ADK(기본, 약 15초)와 Go ADK(약 2초) 중에서 고른다.
- `Declarative`/`BYO`는 공급 주체 축, `Agent`/`SandboxAgent`/`AgentHarness`는 상주 방식 축이다.
- 일정·event 실행은 kagent 밖의 scheduler가 A2A로 invoke하는 형태로 번역한다.
