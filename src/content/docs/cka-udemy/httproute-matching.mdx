<Thesis>HTTPRoute는 경로와 헤더의 일치 조건으로 백엔드를 고르며, 더 구체적인 match가 기본 경로보다 우선한다.</Thesis>

`/auto`에 들어온 요청 중 `User-Agent: mobile`만 모바일 서비스로 보내고 나머지는 데스크톱으로
보내는 작업이다. 라우트를 저장한 뒤에는 헤더가 맞는 요청과 맞지 않는 요청을 모두 보내야 한다.
개념은 [CKA Ingress와 Gateway API](/cka/ingress-gateway/), 설치·attachment 진단은
[Gateway와 HTTPRoute](/cka-udemy/gateway/)를 먼저 확인한다.

## 기존 Gateway와 Service 확인

아래는 `routing-lab` namespace에 HTTP listener `http`를 가진 `web-gateway`, 포트 80의
`web-mobile`·`web-desktop` Service와 정상 EndpointSlice가 이미 있는 경우다.
이름·namespace·listener는 실제 조회값으로 바꾼다.

```bash
kubectl -n routing-lab get gateway web-gateway -o yaml
kubectl -n routing-lab get svc web-mobile web-desktop
kubectl -n routing-lab get endpointslices
kubectl explain httproute.spec.rules.matches --recursive
```

Ingress를 옮기는 문제라면 기존 host·path·Service·port도 기록한다. Ingress는 기본 제공 API이고
Gateway API 리소스는 CRD다. 전환 확인 전 기존 Ingress를 지우지 않는다.

## path와 headers를 같은 match에 둔다

다음은 새 `device-route.yaml` 전체다. 같은 match의 path·headers는 AND, `matches`의
서로 다른 항목은 OR다. 구조는 [HTTP routing 가이드](https://gateway-api.sigs.k8s.io/guides/user-guides/http-routing/)에서
`matches`를 찾아 가져온다.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: device-route
  namespace: routing-lab
spec:
  parentRefs:
    - name: web-gateway
      sectionName: http
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /auto
          headers:
            - name: User-Agent
              type: Exact
              value: mobile
      backendRefs:
        - name: web-mobile
          port: 80
    - matches:
        - path:
            type: PathPrefix
            value: /auto
      backendRefs:
        - name: web-desktop
          port: 80
```

`Exact: mobile`은 값 전체가 `mobile`일 때만 맞는다. 일반 모바일 브라우저의 긴 User-Agent에
`mobile`이라는 단어가 포함된 것만으로는 일치하지 않는다. `backendRefs.port`는 Service의 포트다.

### 규칙의 위치보다 구체성이 먼저다

두 규칙의 경로가 같을 때 헤더 조건까지 일치한 규칙이 우선한다. 따라서 위 두 규칙의 순서를
바꾸어도 `User-Agent: mobile`은 모바일로 가야 한다. 같은 HTTPRoute에서 경로·method·헤더 수·
query parameter 수 등의 우선순위가 모두 같을 때에야 먼저 적힌 규칙으로 결정한다.
[HTTPRouteRule API 명세](https://gateway-api.sigs.k8s.io/reference/api-spec/1.4/spec/#httprouterule)의
`matches` 설명에서 precedence를 확인한다.

## attachment와 실제 응답 확인

```bash
kubectl apply -f device-route.yaml
kubectl -n routing-lab describe httproute device-route
kubectl -n routing-lab get httproute device-route -o yaml
```

해당 parent의 `Accepted=True`, `ResolvedRefs=True`를 보고 condition의 `observedGeneration`이
현재 `metadata.generation`을 반영했는지 확인한다. 이후 접근 가능한 Gateway 주소를 넣는다.
아래 주소는 예시이며 hostnames를 지정한 환경에서는 그 Host 헤더도 함께 보낸다.

```bash
GATEWAY_URL=http://gateway.example.test:30080
curl --max-time 5 -H 'User-Agent: mobile' "$GATEWAY_URL/auto"
curl --max-time 5 -H 'User-Agent: desktop' "$GATEWAY_URL/auto"
curl --max-time 5 -H 'User-Agent:' "$GATEWAY_URL/auto"
```

첫 요청만 모바일 응답이고 뒤의 두 요청은 데스크톱 응답이어야 한다. 상태가 True인데도
응답이 틀리면 같은 host/path를 쓰는 다른 HTTPRoute, 실제 전송한 헤더, Service EndpointSlice를 본다.
Ingress 전환이라면 원래 경로의 응답까지 확인한 뒤 요구된 Ingress만 제거한다.

## 되돌리기와 변형 과제

기존 Route 수정 전에는 원본 YAML을 보관하고, 실패하면 바꾼 `spec.rules`를 원래 값으로 돌려
재검증한다. 이 예제처럼 새로 추가한 Route만 되돌릴 때는
`kubectl -n routing-lab delete httproute device-route`를 사용한다.

`path`와 `headers`를 별도의 `matches` 항목으로 나누면 어떤 요청이 추가로 매칭될까?
OR가 되므로 `/auto`의 모든 요청뿐 아니라 다른 경로의 `User-Agent: mobile`도 후보가 된다.
두 조건을 모두 요구하려면 하나의 match 안에 유지한다.
