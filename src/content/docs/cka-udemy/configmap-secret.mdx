<Thesis>요구한 주입 방식에 맞는 참조 필드를 고르고 API 값과 컨테이너가 실제 읽는 값을 따로 확인한다</Thesis>

ConfigMap이나 Secret이 존재해도 Pod이 올바른 이름·키·주입 방식으로 참조하지 않으면 앱에는
값이 전달되지 않는다. 이 페이지에서는 **설정 생성 → 참조 연결 → 컨테이너 내부 값 확인**을
연습하고, 변경 뒤 기존 Pod에 반영되는 범위도 구분한다.
전체 주입 지도는 [CKA 설정과 리소스](/cka/config/)에서 복습한다.

기존 Pod을 바꿔야 하면 [소유자·재생성 판단](/cka-udemy/pod-config/)을 먼저 적용한다.
환경 변수는 기존 프로세스에 자동 반영되지 않고, volume은 동기화 지연과 `subPath` 예외가 있다.

## 환경 변수와 ConfigMap — Practice Test: Env Variables

원본 풀이: [09-Practice-Test-Env-Variables.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/09-Practice-Test-Env-Variables.md)

```bash
# "Create a new ConfigMap for the 'webapp-color' POD. Use the spec given on the right."
kubectl create configmap webapp-config-map --from-literal=APP_COLOR=darkblue
```

주입 두 방식 — 개별 지정(`env`)과 통째로(`envFrom`) —

```yaml
    env:              # — "Set the environment option to APP_COLOR - green."
    - name: APP_COLOR
      value: green
    envFrom:          # — "Set the environment option to envFrom and use configMapRef webapp-config-map."
    - configMapRef:
        name: webapp-config-map
```

세 가지 주입 방식(env/envFrom/volume)의 전체 지도는 [CKA 설정과 리소스](/cka/config/)에 있다.
시험 중 YAML 뼈대는 공식 문서
[Configure a Pod to Use a ConfigMap](https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/)에서
복사하는 게 빠르다.

### ConfigMap 변경 반영을 판정하는 루프

ConfigMap을 고친 뒤 API 오브젝트만 보고 끝내면 안 된다. **같은 Pod의 환경 변수**, **마운트 파일**,
**교체된 Pod의 환경 변수**를 분리해 확인한다.

```bash
# 1) API 서버에는 새 값이 저장됐는가
kubectl get cm app-config -o jsonpath='{.data.APP_COLOR}{"\n"}'

# 2) 기존 Pod의 env는 옛 값, 디렉터리 마운트 파일은 동기화 뒤 새 값이어야 한다
kubectl exec <pod> -- printenv APP_COLOR
kubectl exec <pod> -- cat /etc/config/APP_COLOR

# 3) env를 바꾸려면 Pod을 교체하고 새 Pod에서 다시 읽는다
kubectl rollout restart deploy/<name>
kubectl rollout status deploy/<name>
kubectl exec deploy/<name> -- printenv APP_COLOR
```

볼륨 반영은 kubelet 동기화 때문에 즉시 보이지 않을 수 있다. 그래도 계속 옛 값이면 `subPath` 마운트인지
먼저 확인한다. `subPath`와 환경 변수는 자동 갱신되지 않는다. 단독 Pod은 재생성해야 하고,
Deployment도 rollout하지 않은 채 scale만 바꾸면 옛 값 Pod과 새 값 Pod이 섞일 수 있다. 공식
[Updating Configuration via a ConfigMap](https://v1-35.docs.kubernetes.io/docs/tutorials/configuration/updating-configuration-via-a-configmap/)이
이 차이를 실행 흐름으로 보여 준다.

## Secret — Practice Test: Secrets

원본 풀이: [11.Practice-Test-Secrets.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/11.Practice-Test-Secrets.md)

```bash
# "Run command kubectl create secret generic db-secret --from-literal=DB_Host=sql01 --from-literal=DBUser=root --from-literal=DB_Password=password123"
# generic = 임의 키-값 타입 — docker-registry·tls 타입과 구분하는 서브커맨드다
kubectl create secret generic db-secret \
  --from-literal=DB_Host=sql01 \
  --from-literal=DB_User=root \
  --from-literal=DB_Password=password123
```

Pod에 통째로 주입할 때는 ConfigMap과 대칭으로 공식 문서의
[`envFrom.secretRef`](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#configure-all-key-value-pairs-in-a-secret-as-container-environment-variables)를 쓴다 —

```yaml
    envFrom:
    - secretRef:
        name: db-secret
```

:::tip[조회 습관]
`k get secrets`의 **DATA 열**이 키 개수다 — *Run the command 'kubectl get secrets' and look at the DATA field*.
값 확인은 `k describe secret`이 아니라
`k get secret <name> -o jsonpath='{.data.<key>}' | base64 -d` — describe는 값을 안 보여준다.
:::

### 기존 Secret을 읽기 전용 파일로 마운트 — secret-1401

`admin1401`의 기존 `dotfile-secret`을 사용한다. 먼저 Pod 초안을 만들고 컨테이너 이름과
볼륨을 고친다. 공식 [Secret 볼륨 예제](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#create-a-pod-that-has-access-to-the-secret-data-through-a-volume)에서
`volumes`·`volumeMounts` 블록을 가져온다.

```bash
kubectl run secret-1401 -n admin1401 --image=busybox \
  --dry-run=client -o yaml --command -- sleep 4800 > admin.yaml
```

완성한 `admin.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-1401
  namespace: admin1401
spec:
  containers:
    - name: secret-admin
      image: busybox
      command: ["sleep", "4800"]
      volumeMounts:
        - name: secret-volume
          mountPath: /etc/secret-volume
          readOnly: true
  volumes:
    - name: secret-volume
      secret:
        secretName: dotfile-secret
```

`volumes.name`과 `volumeMounts.name`을 맞추고, `secretName`에는 **같은 네임스페이스의
기존 Secret 이름**을 넣는다. Pod 이름과 컨테이너 이름이 다르다는 조건도 놓치지 않는다.

```bash
kubectl apply -f admin.yaml
kubectl -n admin1401 wait --for=condition=Ready pod/secret-1401 --timeout=120s
kubectl -n admin1401 describe pod secret-1401
kubectl -n admin1401 exec secret-1401 -c secret-admin -- ls -la /etc/secret-volume
```

`describe`의 마운트가 `(ro)`인지 확인한다. 점으로 시작하는 숨김 파일도 보려면 `ls -la`를 쓴다.

## 공식 문서에서 찾을 것

문제에서 한 키만 주입하면 [Configure a Pod to Use a ConfigMap](https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/)의
`env.valueFrom`, 전체 키면 `envFrom.configMapRef`, 파일이면 `volumes` 예제를 찾는다.
Secret은 [Distribute Credentials Securely Using Secrets](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/)에서
같은 세 갈래와 `readOnly` 마운트를 찾고 이름·키·namespace를 바꾼다.
변경 반영은 [Updating Configuration via a ConfigMap](https://kubernetes.io/docs/tutorials/configuration/updating-configuration-via-a-configmap/)에서
volume과 환경 변수 절을 비교한다.

## 완료 판정

API 오브젝트의 값만 보지 않는다. 환경 변수는 교체된 Pod에서 `printenv`, volume은 컨테이너의
실제 파일 내용으로 확인한다. Secret 파일 문제는 마운트가 읽기 전용인지와 숨김 파일까지 확인한다.
참조 오류면 Pod Events에서 ConfigMap·Secret·키 이름과 namespace를 대조한다.
Secret의 base64 디코딩 성공은 저장 암호화를 증명하지 않는다.
