<Thesis>대상 namespace와 생성 명령을 먼저 고르고, 도움말로 YAML 뼈대를 만든 뒤 실제 생성 여부를 확인한다</Thesis>

실습의 기본 조작은 명령을 많이 외우는 일이 아니라 **대상 범위와 생성 방식을 틀리지 않는 일**이다.
이 페이지에서는 namespace를 명시해 리소스를 조회·생성하고, 한 줄로 부족하면 도움말과
client dry-run으로 YAML 뼈대를 만든다. 조회와 선언형 작업의 원리는
[cka 3장 — kubectl](/cka/03-kubectl/)에서 복습한다.

`k`는 시험 환경의 `kubectl` 별칭이다. 여기서는 전체 명령을 익히기 위해 `kubectl`을 주로 쓴다.
Pod 자체의 생성·상태 판정은 [3장 — Pod 생성과 상태 확인](/cka-udemy/pods/),
출력 파일 문제는 [2장 — JSONPath 추출과 정렬](/cka-udemy/jsonpath/)로 분리한다.

## 네임스페이스 — Practice Test: Namespaces

원본 풀이: [19-Practice-Test-Namespaces.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/19-Practice-Test-Namespaces.md)

| 과제 | 명령 |
|---|---|
| 네임스페이스 목록 — *How many Namespaces exist on the system?* | `k get ns` |
| 특정 ns의 Pod — *How many pods exist in the research namespace?* | `k get pods -n research` |
| 전체 ns에서 찾기 — *Which namespace has the blue pod in it?* | `k get pods -A \| grep blue` |
| ns 지정해 생성 — *Create a POD in the finance namespace.* | `k run redis --image=redis -n finance` |

DNS 이름 규칙이 이 랩의 진짜 출제 포인트다 —

- **같은 네임스페이스**의 Service: 호스트 이름만 — `db-service`
  — *What DNS name should the Blue application use to access the database db-service in its own namespace - marketing?*
- **다른 네임스페이스**(dev)의 Service: `db-service.dev` 또는
  풀 네임 `db-service.dev.svc.cluster.local`
  — *What DNS name should the Blue application use to access the database db-service in the dev namespace?*

원리는 [cka 10장 이름 규칙](/cka/10-dns/)에 있다.

## 명령형 커맨드 — Practice Test: Imperative Commands

원본 풀이: [24-Practice-Test-Imperative-Commands.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/24-Practice-Test-Imperative-Commands.md)

YAML을 열지 않고 한 줄로 끝내는 연습이다. 전부 손에 붙여둘 것 —

```bash
# "Deploy a pod named nginx-pod using the nginx:alpine image."
kubectl run nginx-pod --image=nginx:alpine
# "Deploy a redis pod using the redis:alpine image with the labels set to tier=db."
kubectl run redis --image=redis:alpine -l tier=db          # 라벨 지정
# "Create a new pod called custom-nginx using the nginx image and expose it on container port 8080."
kubectl run custom-nginx --image=nginx --port=8080          # containerPort 지정
# "Create a service redis-service to expose the redis application within the cluster on port 6379."
kubectl expose pod redis --port=6379 --name redis-service   # ClusterIP Service. 여기의 --port는 Service 포트 — run의 --port(containerPort)와 다른 뜻
# "Create a new namespace called dev-ns."
kubectl create ns dev-ns
# "Create a deployment named webapp using the image kodekloud/webapp-color with 3 replicas."
kubectl create deployment webapp --image=kodekloud/webapp-color --replicas=3
# "Create a new deployment called redis-deploy in the dev-ns namespace with the redis image. It should have 2 replicas."
kubectl create deployment redis-deploy -n dev-ns --image=redis --replicas=2
```

:::tip[Pod + Service 한 줄]
"Pod을 만들고 같은 이름의 ClusterIP Service로 노출하라"는 문제는
`--expose`가 한 줄로 끝낸다 —

```bash
# "Create a pod called httpd using the image httpd:alpine in the default namespace. Next, create a service of type ClusterIP by the same name (httpd). The target port for the service should be 80."
kubectl run httpd --image=httpd:alpine --expose --port 80
```
:::

### 도움말 → YAML 뼈대 → 필요한 필드만 수정

옵션은 `-h`, YAML의 필드 위치는 `explain`으로 찾는다. `create -h`에서 리소스를 고른 뒤
하위 명령의 Examples까지 내려가면 문제의 이름·이미지·복제본 수를 바로 넣을 수 있다.

```bash
kubectl create -h
kubectl create deployment -h
kubectl create deployment logging-deployment -n logging-ns \
  --image=busybox --image=busybox --replicas=1 \
  --dry-run=client -o yaml > logging-deployment.yaml

kubectl explain deployment.spec.template.spec.volumes
kubectl explain deployment.spec.template.spec.containers.volumeMounts
kubectl explain deployment.spec.template.spec.initContainers
```

[`--image`는 반복해서 지정할 수 있다](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_deployment/).
위 명령은 컨테이너 두 개를 **모두 `containers` 아래에** 만든다. 생성된 이름을 요구한 이름으로
고치고, 컨테이너별 명령·마운트를 추가한다. 네이티브 사이드카라면 해당 컨테이너 블록을
`initContainers`로 옮겨 `restartPolicy: Always`를 넣는다.
[logging-deployment 완성 예제](/cka-udemy/03-pod-config/#logging-deployment--네이티브-로그-사이드카)에서 이어서 연습한다.

`--dry-run=client -o yaml`은 리소스를 생성하지 않고 YAML을 출력한다. 실제 생성·변경은
`kubectl apply -f logging-deployment.yaml`로 수행한다. 명령 뒤의 `--`는 kubectl 옵션의 끝을 뜻하며,
그 뒤에는 컨테이너 실행 명령을 넣을 수 있다. 컨테이너마다 명령이 다르면 YAML에서 각각 작성한다.

StorageClass·CSR처럼 전용 `create` 하위 명령이 없는 리소스는 공식 YAML 예제에서 시작한다.
옵션으로 모든 필드를 표현하려고 오래 찾기보다 생성기가 만드는 부분과 직접 채울 부분을 구분한다.
공식 명령을 복사해 수정할 편집 공간은 [시험용 VSCodium 메모](/cka/19-exam-strategy/#vscodium에서-공식-명령을-수정하기)를 참고한다.


## 시험장에서 공식 문서 찾기

검색창에는 아래 영문을 그대로 넣는다. 문서를 처음부터 읽지 말고 예제 명령이나
`--dry-run=client -o yaml` 부분으로 바로 이동한다.

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| 네임스페이스 | `Namespaces` | [Namespaces](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/)의 `--namespace` 사용법. YAML이면 `metadata.namespace`만 대상 리소스에 추가 |
| 명령형 커맨드 | `imperative commands` | [Managing Kubernetes Objects Using Imperative Commands](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/imperative-command/)의 `run`·`expose`·`create`와 `--dry-run=client -o yaml` 조합 |

:::tip[문서와 explain의 역할]
공식 문서에서는 **완성 예시의 구조**를 찾고, 현재 클러스터의 정확한 필드 경로는
`kubectl explain pod.spec.containers --recursive`로 확인한다. 둘을 함께 쓰면 버전 차이와 들여쓰기
실수를 가장 빨리 줄일 수 있다.
:::

### 시험 중 찾을 곳과 학습용 링크 구분

완성 명령보다 **어디서 찾는지**를 익힌다. 옵션은 `kubectl expose --help` 같은 하위 명령의
Examples에서, YAML 필드는 `kubectl explain service.spec.ports`에서, 전체 골격은 공식 문서에서 찾는다.
생성기가 있는 리소스는 `--dry-run=client -o yaml > 파일.yaml`로 시작하고, 제공된 파일이 있으면
그 파일부터 연다. 짧은 조회 결과는 Vim에 옮겨도 된다. 제출 형식을 충족하면 복잡한 출력식은 필수가 아니다.

2026-09-11 확인한 [Linux Foundation 허용 자료 안내](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)에
따르면 CKA는 Kubernetes docs·blog, Helm docs, Gateway API docs와 문제의 **Quick Reference에 제공된 문서**를
시험 VM 브라우저에서 볼 수 있다. 배포판에 설치된 문서와 터미널 도움말도 활용한다.
이 덱의 KodeKloud GitHub 풀이·cri-dockerd 사이트 등 학습용 링크가 자동으로 시험 허용 자료가 되는 것은 아니다.
Kubernetes 문서 검색에서도 외부 결과는 열지 않는다. 시험 직전에는 위 정본에서 허용 범위를 다시 확인한다.

```bash
kubectl create deployment --help
kubectl explain pod.spec.containers --recursive
systemctl -h
man systemctl
helm upgrade --help
```

`man`에서는 `/--now`처럼 검색하고 `n`으로 다음 결과, `q`로 종료한다.
브라우저에서는 문서 제목을 검색한 뒤 `Ctrl+F`로 필드 이름을 찾는다.

### Vim으로 YAML을 고치는 짧은 연습

초기 설정과 키 설명은 [CKA 1장 Vim 최소 세트](/cka/01-exam/#vim-최소-세트)가 정본이다.
연습 전에 Vim에서 `:setlocal expandtab tabstop=2 softtabstop=2 shiftwidth=2 autoindent number`를
실행한다. 아래 파일은 편집 연습용이며, 클러스터에 리소스를 만들지 않는다.

```bash
kubectl run vim-practice --image=nginx --dry-run=client -o yaml > vim-practice.yaml
vim vim-practice.yaml
```

1. `Esc` → `/image:` → `Enter`로 이미지 필드를 찾는다. `n`은 다음 검색 결과다.
2. `0`·`^`·`$`를 각각 눌러 줄 시작, 첫 글자, 마지막 문자의 차이를 확인한다.
3. `A`로 줄 끝에서 입력을 시작해 `:alpine`을 붙이고 `Esc`로 나온다. 값은 `nginx:alpine`이 된다.
4. 현재 줄에서 `>>`로 2칸 오른쪽 이동 후 `<<`로 원래 깊이로 돌아온다.
5. `V` → `j`로 두 줄을 선택하고 `>`로 이동한다. `gv` → `<`로 같은 두 줄을 원래 위치로 되돌린다.
6. `:wq`로 저장하고 다음 명령으로 YAML과 리소스 구조를 확인한다.

```bash
kubectl create --dry-run=client -f vim-practice.yaml -o yaml
```

출력에서 이미지 변경과 들여쓰기를 확인한다. client dry-run은 실제 Pod를 만들지 않으므로
스케줄링·이미지 다운로드·실행 성공을 검증하지는 않는다.

:::caution[함정 — 문서 YAML을 붙여넣은 뒤 들여쓰기가 밀린다]
터미널·Vim의 붙여넣기 처리에 따라 자동 들여쓰기가 중복 적용될 수 있다.
`Esc` → `u`로 잘못 붙인 부분을 되돌리고 `:set paste` → `i` → 터미널 붙여넣기 → `Esc` →
`:set nopaste` 순으로 다시 시도한다. 평소에는 `nopaste`로 편집한다.
복사해 온 블록의 깊이는 `V`로 줄들을 선택한 뒤 `>`·`<`로 맞춘다. 같은 계층의 필드가 정렬됐는지 확인한다.
:::


## 완료 판정

- 조회 문제는 namespace와 대상 이름이 맞는지 원문 요구와 다시 대조한다.
- 명령형 생성은 `kubectl get <type> <name> -n <namespace>`로 실제 오브젝트 생성을 확인한다.
- YAML 뼈대는 `kubectl create --dry-run=client -f <file> -o yaml`로 구문과 리소스 구조만 확인한다.
  client dry-run은 스케줄링·이미지 다운로드·앱 동작을 증명하지 않는다.
- 잘못 만든 리소스를 무조건 삭제하기 전에 `kubectl get -o yaml`로 수정 가능한 필드와
  소유 controller를 확인한다.
