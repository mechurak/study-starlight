> 짝이 되는 개념 장: [CKA Helm — 패키지 설치와 릴리스 관리](/cka/helm/)

원본 레포에는 이 랩의 풀이 문서가 없다 — 2025년 시험 개편으로 커리큘럼에
**"Use Helm and Kustomize to install cluster components"** 항목이 들어오며 추가된 랩이다.
Chart·Values·Release가 무엇인지는 [CKA Helm — 패키지 설치와 릴리스 관리](/cka/helm/)이 맡고,
이 장은 랩의 문제 순서를 따라 **명령 선택 → 실행 → 검증 → 실패 분기**만 본다.

## helm 설치 — 랩 전용 준비 단계

*Install the helm package on the controlplane node.* — 랩은 설치 스크립트 URL을 힌트로 주고,
정본은 [Helm 공식 설치 문서](https://helm.sh/docs/intro/install/)의 "From Script" 절이다.
스크립트 주소를 외울 필요는 없고 **설치 문서의 위치**만 기억한다. 받은 스크립트를 실행한 뒤에는
출력 메시지가 아니라 명령으로 확인한다.

```bash
helm version   # 바이너리가 PATH에 있고 버전이 찍히면 완료
```

이 문제는 뒤 문제들을 풀기 위한 환경 준비다. **실제 시험 터미널에는 helm이 이미 설치돼
있어서** helm 자체를 설치하라는 문제가 나올 가능성은 낮다 — 시험에서 테스트되는 건 이 장의
나머지, 즉 사용법 쪽이다.

:::tip[helm.sh/docs는 열 수 있다]
Helm이 커리큘럼에 들어오면서
[시험 열람 허용 목록](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)에
`helm.sh/docs`가 추가됐다. 플래그가 기억나지 않으면 문서를 열면 되고, 문서 탭까지 갈 것 없이
`helm repo --help`처럼 **`--help`가 1차 치트시트**다.
:::

## 차트 찾기 — hub와 repo, 그리고 두 버전 컬럼

*Search for a consul helm chart package from the Artifact Hub and identify the APP VERSION.*

```bash
helm search hub consul | grep -i hashicorp   # Artifact Hub 전체 — repo 등록 불필요
helm search repo wordpress                    # 내가 add한 저장소 안 — 등록이 선행 조건
helm search repo bitnami/wordpress            # 검색어의 접두사로 저장소를 한정
```

`repo`를 한정하는 별도 플래그가 있는 게 아니라 검색어 자체가 `저장소/차트` 접두사에
매칭된다. 결과에서 헷갈리기 쉬운 건 버전 컬럼 두 개다.

| 컬럼 | 뜻 |
|---|---|
| CHART VERSION | 차트(패키징 자체)의 버전 |
| APP VERSION | 그 차트가 배포하는 **애플리케이션**의 버전 |

문제가 "consul의 APP VERSION"을 물으면 세 번째 컬럼이다. `search hub`의 첫 컬럼은 차트
이름이 아니라 Artifact Hub **URL**이라, 공식 차트인지도 그 URL의 저장소 이름으로 가린다.

두 명령의 경계는 [CKA Helm — 패키지 설치와 릴리스 관리](/cka/helm/#helm-기본-명령)에 정리돼 있다 —
`hub`는 공개 카탈로그, `repo`는 내가 등록한 곳. 문제 문구에 "Artifact Hub"가 있으면 `hub`,
"newly added repository"가 있으면 `repo`로 그대로 갈린다.

## repo 등록 — add 뒤 update까지가 한 동작

*Add bitnami helm chart repository in the controlplane node.* — URL은 문제가 준다.

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update    # 인덱스 갱신 — add와 한 묶음으로 손에 붙인다
helm repo list      # 등록 확인
```

`helm repo` 서브커맨드는 `add <이름> <URL>` · `list` · `update` · `remove`가 사실상 전부고,
구조가 `git remote add`와 같아서 패턴 하나로 기억하면 된다.

:::caution[함정 — add만 하고 update를 안 하면]
`search repo`에 차트가 안 나오거나 오래된 버전이 잡힌다. add 직후엔 문제가 안 보여도,
랩 중간에 저장소 인덱스가 갱신된 경우 옛 목록으로 계속 검색하게 된다.
"등록했는데 검색이 안 된다"의 첫 용의자는 오타보다 update 누락이다.
:::

## 설치와 검증 — release 층과 워크로드 층

*Deploy the Apache application using the apache from the bitnami repository. Set the release
Name to: amaze-surf.*

```bash
helm install amaze-surf bitnami/apache
```

`search`와 달리 **install에서는 `저장소/차트` 전체 경로가 필수**다. 설치가 끝나면 두 층을
순서대로 본다 — release가 생겼는가, 그 release의 워크로드가 실제로 떴는가.

```bash
helm list                        # ① release 층 — STATUS: deployed
helm status amaze-surf           # 설치 결과 요약과 NOTES
kubectl get pods                 # ② 워크로드 층 — Running/Ready
```

이 랩의 채점은 ①만 봤다 — release가 존재하면 Pod이 Ready가 아니어도 통과했다.
하지만 시험·실무에서 "배포하라"는 지시는 ②까지가 완료 조건이라고 보고 둘 다 확인하는
습관을 남긴다. release는 `deployed`인데 Pod이 비정상이면 다음 절의 분기로 내려간다.

### 취약 이미지에서 release를 역추적해 제거한다

리소스 이름과 Helm release 이름이 같다고 추측하지 않는다. 가장 직접적인 방법은 모든 네임스페이스의
release를 열거하고, Helm이 각 release에 렌더한 manifest에서 정확한 이미지 문자열을 찾는 것이다.

```bash
helm list -A

helm list -A -o json \
  | jq -r '.[] | [.name, .namespace] | @tsv' \
  | while IFS=$'\t' read -r release namespace; do
      if helm get manifest "$release" -n "$namespace" \
        | grep -Fq 'kodekloud/webapp-color:v1'; then
        printf '%s\t%s\n' "$release" "$namespace"
      fi
    done
```

출력된 release와 namespace를 그대로 제거 명령에 넣는다. 제거 전 한 번 더 manifest를 열어 이미지와
대상을 확인하면 비슷한 이름의 release를 지우는 실수를 피할 수 있다.

```bash
helm get manifest <RELEASE> -n <NAMESPACE> \
  | grep -n -F 'kodekloud/webapp-color:v1'
helm uninstall <RELEASE> -n <NAMESPACE>
helm list -A
```

:::tip[현재 오브젝트와 Helm 기록을 구분한다]
`kubectl get deploy ... | jq`는 지금 실행 중인 Deployment의 이미지를 찾는 데 좋지만 StatefulSet,
DaemonSet, Job이나 init container를 빠뜨리기 쉽고 release 이름도 직접 알려 주지 않는다.
`helm get manifest`는 release → 렌더된 리소스 → 이미지의 연결을 한 번에 보존한다. 누군가 Helm 밖에서
이미지를 수정했을 가능성이 있으면 그때는 실제 워크로드도 함께 조회한다.
:::

## 차트 버전 업그레이드 — `--version`은 CHART VERSION

*Upgrade the nginx version to 1.27.x and use the Helm chart version 18.3.6 from the
Bitnami repository.* — 문제에서 먼저 분리할 값은 셋이다.

| 문제의 값 | Helm에서 뜻하는 것 | 이 문제의 값 |
|---|---|---|
| release | 클러스터에 설치된 인스턴스 이름 | `dazzling-web` |
| chart | 가져올 패키지 | `bitnami/nginx` |
| chart version | `--version`으로 고를 패키지 버전 | `18.3.6` |

`1.27.x`는 `--version`에 넣는 값이 아니다. 차트 메타데이터의 **APP VERSION**이고,
`18.3.6` 차트에서는 `1.27.4`다. 저장소 인덱스를 갱신하고 후보를 찾은 뒤, 정확한 차트를
직접 열어 두 버전의 대응을 확인한다.

```bash
helm list -A | grep dazzling-web                # release와 namespace 찾기
helm repo update bitnami                        # 로컬 저장소 인덱스 갱신
helm search repo bitnami/nginx --versions | grep '18.3.6'

helm show chart bitnami/nginx --version 18.3.6 \
  | grep -E '^(version|appVersion):'
# appVersion: 1.27.4
# version: 18.3.6
```

이 랩 환경에서는 `helm search repo bitnami/nginx --version 18.3.6`이 `No results found`를
출력해도 `helm show chart ... --version 18.3.6`은 성공할 수 있었다. `search repo`는 후보를
찾는 도구다. 정확한 버전의 `show chart`가 위 메타데이터를 출력하면 Helm이 그 차트를
resolve할 수 있으므로 업그레이드를 진행한다.

```bash
helm upgrade dazzling-web bitnami/nginx --version 18.3.6
```

release가 `default` 밖에 있으면 첫 명령에서 확인한 namespace를 `-n <namespace>`로 모든
Helm·kubectl 명령에 붙인다. 완료 뒤에는 Helm이 기록한 버전과 실제 워크로드를 모두 본다.

```bash
helm list | grep dazzling-web
helm status dazzling-web
kubectl get deploy,pods -l app.kubernetes.io/instance=dazzling-web
kubectl get deploy -l app.kubernetes.io/instance=dazzling-web \
  -o jsonpath='{.items[*].spec.template.spec.containers[*].image}{"\n"}'
```

`helm list`의 APP VERSION은 차트 메타데이터다. `image.tag`를 values로 따로 고정한 release라면
실제 이미지와 다를 수 있으므로 마지막 `kubectl` 출력의 이미지 태그까지 확인한다.

### kk-mock1 — podinfo 차트 6.11.2로 업그레이드

릴리스 이름 `kk-mock1`, 네임스페이스 `kk-ns`는 주어졌지만 **저장소 별칭은 조회해서 확인**한다.
릴리스와 저장소가 우연히 같은 이름일 수 있어도 같다고 가정하지 않는다.

```bash
helm list -n kk-ns
helm repo list
helm repo update
helm search repo podinfo --versions
```

검색 결과 NAME이 `podinfo/podinfo`이고 CHART VERSION에 `6.11.2`가 있다면 다음처럼 실행한다.
NAME이 `kk-mock1/podinfo`라면 두 번째 인자를 그 값으로 바꾼다.

```bash
helm upgrade kk-mock1 podinfo/podinfo -n kk-ns --version 6.11.2
helm list -n kk-ns
helm status kk-mock1 -n kk-ns
kubectl get deploy,pods -n kk-ns -l app.kubernetes.io/instance=kk-mock1
```

CHART가 `podinfo-6.11.2`, 상태가 `deployed`인지 확인하고 워크로드 Ready 상태도 본다.
`helm repo update`는 로컬 저장소 인덱스 갱신이므로 namespace를 지정할 필요가 없다.
특정 저장소만 갱신하려면 `helm repo update <저장소별칭>`이다. 기존 values 변경은 문제에서 요구하지
않으면 추가하지 않는다. 실패하면 `helm status`·Pod Events로 원인을 좁히고 아래 history 절에서
정상 리비전을 확인한다.

```bash
helm repo update --help
helm search repo --help
helm upgrade --help
```

도움말의 Usage에서 `upgrade RELEASE CHART`, 옵션에서 `--version`을 찾는다.
[공식 repo update](https://helm.sh/docs/helm/helm_repo_update/)와
[upgrade](https://helm.sh/docs/helm/helm_upgrade/) 문서도 같은 구조다.
차트 버전은 APP VERSION과 구분하고, `head`로 출력 일부만 잘라 목표 버전을 놓치지 않는다.

## 리비전 확인과 롤백 — history에서 정상 번호를 고른다

install·upgrade할 때마다 release에는 revision이 하나씩 쌓인다. 업그레이드 결과가 잘못됐다면
무작정 "직전"으로 돌리지 않고 `history`에서 마지막 정상 revision을 고른다.

```bash
helm history dazzling-web
# REVISION  STATUS      CHART          APP VERSION  DESCRIPTION
# 1         superseded  nginx-...      ...          Install complete
# 2         deployed    nginx-18.3.6   1.27.4       Upgrade complete

helm rollback dazzling-web 1 --wait --timeout 5m
```

rollback의 `1`은 **chart version이 아니라 release revision**이다. rollback도 과거 기록을
지우거나 revision 번호를 되감지 않는다. revision 1의 값과 매니페스트를 사용한 새 revision을
하나 더 만들므로, 끝난 뒤 history와 두 상태 층을 다시 확인한다.

```bash
helm history dazzling-web
helm status dazzling-web
kubectl get deploy,pods -l app.kubernetes.io/instance=dazzling-web
```

원래 문제가 성공한 업그레이드만 요구한다면 rollback을 실행하지 않는다. rollback은 업그레이드
검증이 실패했거나 문제에서 명시적으로 이전 revision 복구를 요구할 때의 후속 동작이다.
개념과 값 처리 옵션은 [CKA Helm — 패키지 설치와 릴리스 관리](/cka/helm/#업그레이드와-롤백)에
정리돼 있다.

## 이미지 이전 실패 — 랩 환경 보충

`helm status`는 deployed인데 Pod이 `ImagePullBackOff`면 release 생성과 image pull을
구분한다. `kubectl describe pod`의 Events에서 429, manifest 없음, init container 실패 중
어느 경우인지 확인하고 `helm show values`로 해당 이미지 값의 키를 찾는다.

이 랩에서는 Bitnami 이미지 배포 정책 변경
([bitnami/containers 공지](https://github.com/bitnami/containers/issues/83267)) 때문에
legacy 저장소 override가 필요했던 사례가 있었다. 이는 일반 Helm 절차가 아니라 당시 랩 환경의
보충 사례다. release를 지웠다 다시 만들기보다 요구된 값을 `helm upgrade --set`으로 수정하고,
revision 증가와 실제 Pod Ready를 다시 확인한다.

```bash
kubectl describe pod <pod>
helm show values bitnami/apache | less
helm upgrade amaze-surf bitnami/apache --set image.repository=<문제에서-확인한-저장소>
helm status amaze-surf
kubectl get pods
```

## 완료 기준

- `helm repo update` 뒤 목표 chart와 CHART VERSION·APP VERSION을 구분해 선택한다.
- install·upgrade 뒤 release가 deployed이고 해당 workload가 Ready다.
- `helm history`에서 선택한 정상 revision으로 rollback한 뒤 새 revision과 workload를 확인한다.
- release가 정상인데 Pod이 실패하면 Events로 Kubernetes 층의 원인을 확정한 뒤 values만 최소 수정한다.

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 확인할 것 |
|---|---|---|
| helm 설치 | `helm install script` | [Installing Helm](https://helm.sh/docs/intro/install/)의 From Script 절 — 최신 스크립트 주소 |
| 기본 워크플로 | `helm quickstart` | [Quickstart Guide](https://helm.sh/docs/intro/quickstart/)의 repo add → search → install → list → uninstall 순서 |
| install 플래그 | `helm install` | [helm install 레퍼런스](https://helm.sh/docs/helm/helm_install/)의 `--set` · `-f` · `--namespace` · `--create-namespace` |
| chart 버전 업그레이드 | `helm upgrade version` | [helm upgrade 레퍼런스](https://helm.sh/docs/v3/helm/helm_upgrade/)의 인자 순서 `RELEASE CHART`와 `--version` |
| revision 확인·복구 | `helm history` · `helm rollback` | [helm history](https://helm.sh/docs/v3/helm/helm_history/)에서 정상 revision을 찾고 [helm rollback](https://helm.sh/docs/v3/helm/helm_rollback/)의 두 번째 인자로 지정 |
| 값 이름 찾기 | `helm show values` | [helm show 레퍼런스](https://helm.sh/docs/helm/helm_show_values/) — override할 키 이름은 문서가 아니라 이 명령 출력에서 찾는다 |

## 이 장에서 남길 것

- 손에 붙일 명령은 `helm repo add/update` · `helm search repo` · `helm install/upgrade/rollback/uninstall` · `helm list`까지다. 설치 스크립트나 세부 플래그는 helm.sh/docs를 연다
- search는 저장소 접두사가 선택이지만 **install은 `저장소/차트` 전체 경로가 필수**다
- CHART VERSION은 패키징, **APP VERSION이 애플리케이션 버전**이다
- `repo add` 뒤 `repo update`까지가 한 동작 — 검색이 안 되면 update 누락부터 의심한다
- `helm upgrade RELEASE CHART --version CHART_VERSION` — `--version`은 APP VERSION이 아니다
- `helm history RELEASE`에서 정상 revision 확인 → `helm rollback RELEASE REVISION` → 두 상태 층 재검증
- 검증은 두 층: `helm list`(release) → `kubectl get pods`(워크로드). 랩 채점은 release만 볼 수 있지만 완료 조건은 둘 다로 잡는다
- 이미지 풀 실패는 Helm이 아니라 `kubectl describe`의 Events로 진단하고, 수정은 재설치가 아니라 `helm upgrade --set`이다
