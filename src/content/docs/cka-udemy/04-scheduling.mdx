> 짝이 되는 개념 장: [cka 7. 스케줄링](/cka/07-scheduling/)

실습이 일곱 벌로 가장 많은 장이다. 축은 두 방향이다 —
**affinity는 Pod이 노드를 고르고, taint는 노드가 Pod을 밀어낸다.**

## 수동 배치 — Practice Test: Manual Scheduling

원본 풀이: [03-Practice-Test-Manual-Scheduling.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/03-Practice-Test-Manual-Scheduling.md)

스케줄러가 없는 클러스터(kube-system에 kube-scheduler Pod이 없다)에서
Pod이 Pending에 머무는 상황 — *Why is the POD in a pending state? Inspect the environment
for various kubernetes control plane components.* — `spec.nodeName`을 직접 채워 배치한다.

```yaml
spec:                  # — "Manually schedule the pod on node01."
  nodeName: node01     # 스케줄러를 거치지 않는 직접 지정
  containers:
  - image: nginx
    name: nginx
```

:::caution[함정 — nodeName은 나중에 못 붙인다]
실행 중인 Pod에 `nodeName`을 추가하는 건 불가능하다 —
**지우고 재생성**해야 한다 (`kubectl replace --force -f nginx.yaml`).
후속 문제도 같은 반복이다 — *Now schedule the same pod on the controlplane node.*
:::

## 라벨과 셀렉터 — Practice Test: Labels and Selectors

원본 풀이: [05-Practice-Test-Labels-and-Selectors.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/05-Practice-Test-Labels-and-Selectors.md)

```bash
# "We have deployed a number of PODs. They are labelled with tier, env and bu. How many PODs exist in the dev environment (env)?"
kubectl get pods --selector env=dev                          # 하나
# "Identify the POD which is part of the prod environment, the finance BU and of frontend tier?"
kubectl get all --selector env=prod,bu=finance,tier=frontend # AND 조건은 쉼표
kubectl get pods -l env=dev --no-headers | wc -l             # 개수 세기 콤보 — 헤더 줄이 세어지지 않게 뗀다
```

`--selector`와 `-l`은 같다. "PODs, ReplicaSets **포함 모든 오브젝트**"를 세라면
`get pods`가 아니라 `get all`이다 — *How many objects are in the prod environment
including PODs, ReplicaSets and any other objects?*

## taint와 toleration — Practice Test: Taints and Tolerations

원본 풀이: [07-Practice-Test-Taints-and-Tolerations.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/07-Practice-Test-Taints-and-Tolerations.md)

```bash
# "Do any taints exist on node01 node?"
kubectl describe node node01 | grep -i taints        # 확인
# "Create a taint on node01 with key of spray, value of mortein and effect of NoSchedule"
kubectl taint nodes node01 spray=mortein:NoSchedule  # 부여
# "Remove the taint on controlplane, which currently has the taint effect of NoSchedule."
kubectl taint nodes controlplane node-role.kubernetes.io/control-plane:NoSchedule-  # 제거는 끝에 -
```

(원본은 옛 `master` 키로 쓰여 있다 — 현 시험 환경의 컨트롤 플레인 taint 키는
`node-role.kubernetes.io/control-plane`이다.)

toleration은 **Pod 스펙 수준**(containers와 같은 들여쓰기)에 넣는다 — 필드 철자는
[Taints and Tolerations 문서](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)에서
복사하면 안전하다 —

```yaml
spec:                # — "Create another pod named bee with the nginx image, which has a toleration set to the taint mortein."
  tolerations:
  - key: spray
    operator: Equal
    value: mortein
    effect: NoSchedule
  containers:
  - image: nginx
    name: bee
```

:::caution[함정 — toleration은 "가게" 하지 않는다]
toleration을 줘도 그 노드로 **유도되지는 않는다** — 갈 수 있게 될 뿐이다.
컨트롤 플레인의 taint를 제거하면 일반 Pod도 그리로 갈 수 있게 된다는 것,
그 역방향도 이 랩의 출제 포인트다 — *Why do you think the pod is in a pending state?*
→ *Which node is the POD mosquito on now?*
:::

## nodeAffinity — Practice Test: Node Affinity

원본 풀이: [10-Practice-Test-Node-Affinity.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/10-Practice-Test-Node-Affinity.md)

```bash
# "How many Labels exist on node node01?"
kubectl get node node01 --show-labels
# "Apply a label color=blue to node node01"
kubectl label node node01 color=blue
```

affinity YAML은 시험장에서 외워 쓰기보다 공식 문서
[Assign Pods to Nodes using Node Affinity](https://kubernetes.io/docs/tasks/configure-pod-container/assign-pods-nodes-using-node-affinity/)에서
복사해 오는 게 정석이다. Deployment의 **Pod 템플릿 쪽**(`spec.template.spec`)에 붙인다 —

```yaml
      affinity:      # — "Set Node Affinity to the deployment to place the pods on node01 only."
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: color
                operator: In
                values:
                - blue
```

값 없이 라벨의 존재만 볼 때는 `operator: Exists` (컨트롤 플레인에 배치하는 문제에서
`key: node-role.kubernetes.io/control-plane`과 함께 쓴다) — *Create a new deployment named red
with the nginx image and 2 replicas, and ensure it gets placed on the controlplane node only.*

## 리소스 요청과 제한 — Practice Test: Resource Limits

원본 풀이: [13-Practice-Test-Resource-Limits.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/13-Practice-Test-Resource-Limits.md)

- `k describe pod rabbit` → Requests/Limits 확인 — *Run the command 'kubectl describe pod rabbit' and inspect requests.*
- STATUS `OOMKilled` = 메모리 limit 초과로 죽음 → limit을 올려서 재생성 — *The status 'OOMKilled' indicates that the pod ran out of memory. Identify the memory limit set on the POD.*

```yaml
    resources:       # — "Update the elephant.yaml pod definition with the resource memory limits to 20Mi"
      requests:
        memory: 15Mi
      limits:
        memory: 20Mi
```

Pod 수준 리소스 수정도 원칙은 재생성이지만, 요즘 시험 기준(v1.35)에는
**in-place resize**(`--subresource=resize`)가 GA다 — [cka 4장](/cka/04-pods/) 끝 절 참고.

## DaemonSet — Practice Test: DaemonSets

원본 풀이: [15-Practice-Test-DaemonSets.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/15-Practice-Test-DaemonSets.md)

```bash
# "Run the command kubectl get daemonsets --all-namespaces"
kubectl get ds -A                                        # kube-proxy가 대표 사례
# "Run the command kubectl describe daemonset kube-proxy --namespace=kube-system"
kubectl describe ds kube-proxy -n kube-system
```

DaemonSet은 명령형 생성 명령이 없다 — **Deployment YAML을 뽑아서 고치는 것**이 정석이다:

```bash
# "Create a daemonset"
kubectl create deployment elasticsearch -n kube-system \
  --image=registry.k8s.io/fluentd-elasticsearch:1.20 --dry-run=client -o yaml > ds.yaml
```

고칠 곳: `kind: DaemonSet`, `replicas`·`strategy`·`status` 삭제. `spec.selector`와
템플릿 라벨은 그대로 두면 짝이 맞는다.

## 스태틱 Pod — Practice Test: Static Pods

원본 풀이: [17-Practice-Test-StaticPods.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/17-Practice-Test-StaticPods.md)

| 과제 | 명령 |
|---|---|
| 스태틱 Pod 찾기 — *Run the command kubectl get pods --all-namespaces and look for those with -controlplane appended in the name* | 이름 끝에 노드명 접미사 (`etcd-controlplane`) — `-o wide`로 노드 확인 |
| 매니페스트 경로 찾기 — *Run the command ps -aux \| grep kubelet and identify the config file… Then checkin the config file for staticPdPath.* | `ps -aux \| grep kubelet` → `--config` 파일 → `grep staticPodPath /var/lib/kubelet/config.yaml` |
| 스태틱 Pod 만들기 — *Create a pod definition file in the manifests folder. Use command kubectl run --restart=Never --image=busybox static-busybox…* | 아래 한 줄 |
| 지우기 — *Identify which node the static pod is created on, ssh to the node and delete the pod definition file.…* | 해당 노드에 ssh → 매니페스트 파일 삭제 |

```bash
# --command: 뒤의 sleep 1000을 args가 아니라 command(ENTRYPOINT 대체)로 넣는다 — 없으면 args로 들어간다
kubectl run static-busybox --image=busybox --restart=Never \
  --dry-run=client -o yaml --command -- sleep 1000 > /etc/kubernetes/manifests/static-busybox.yaml
```

:::tip[--restart=Never는 옛 generator 관용구다]
1.17까지는 `kubectl run`의 `--restart` 값이 만들어지는 리소스 종류를 정했다 —
기본값 `Always`면 Deployment, `Never`여야 단독 Pod. 스태틱 Pod 매니페스트에는
`kind: Pod`이 필요하니 필수 플래그였다. 지금은 generator가 제거돼 `run`이 항상
Pod만 만들므로 **이 플래그 없이도 `kind: Pod`이 나온다**. 남는 효과는
`restartPolicy: Never` 지정 하나 — 계속 떠 있어야 하는 스태틱 Pod이라면
오히려 기본값 `Always`가 맞다. 원문 명령이라 그대로 두되, 몰라서 넣는 건 아니게.
:::

:::caution[함정 — 다른 노드의 스태틱 Pod]
`kubectl delete`로 지우면 kubelet이 다시 만든다. **파일이 원본**이다 —
어느 노드인지 확인하고(`kubectl get pods -o wide`), `ssh <node>`로 들어가
staticPodPath의 파일을 지워야 사라진다. 경로가 기본값(`/etc/kubernetes/manifests`)이
아닐 수 있으니 kubelet config에서 확인하는 습관을 들일 것.
:::

## 이 장에서 남길 것

- Pending 진단은 `describe pod`의 Events 한 줄로 끝나는 경우가 대부분
- taint 제거는 명령 끝에 `-`, 컨트롤 플레인 키는 `node-role.kubernetes.io/control-plane`
- toleration은 Pod 스펙 수준, affinity는 Deployment면 템플릿 쪽 — **넣는 위치**가 반은 먹는다
- DaemonSet은 Deployment YAML을 뽑아 kind만 바꾼다
- 스태틱 Pod은 파일이 원본 — 만들 때도 지울 때도 매니페스트 디렉터리
