## 로컬 런타임 패키지 설치 — cri-docker

주어진 `.deb`를 설치하고 서비스를 실행·자동 시작하라는 문제는 대상 노드의 OS에서 푼다.
`cri-dockerd`는 Docker Engine을 Kubernetes CRI에 연결하는 구성요소다. 패키지 설치는 실행 파일과
서비스 설정을 함께 배치한다. [공식 설치 안내](https://mirantis.github.io/cri-dockerd/usage/install/)는
학습용 참고이며, 시험에서는 Quick Reference에 제공된 경우에만 해당 외부 사이트를 이용한다.

### node01 접속과 패키지 설치

```bash
ssh bob@node01
# 문제에서 제공한 암호 입력
sudo -i
hostname
ls -l /root/cri-docker_0.3.16.3-0.debian.deb
dpkg -i /root/cri-docker_0.3.16.3-0.debian.deb
```

`hostname`이 node01인지 먼저 확인한다. 위 파일명은 문제에 주어진 값이다.
의존성 부족으로 설치가 미완료되면 `apt-get -f install`의 해결 계획을 확인해 진행한다.
이미 있는 패키지를 설치하는 과제이므로 최신 바이너리를 별도로 다운로드할 필요가 없다.

### 실행과 부팅 시 자동 시작은 별도 조건

```bash
systemctl daemon-reload
systemctl enable --now cri-docker.service
systemctl is-active cri-docker.service
systemctl is-enabled cri-docker.service
systemctl status cri-docker.service --no-pager
```

`active`, `enabled`, 상태의 `active (running)`을 확인한다. `enable`만으로는 현재 실행되지 않는다.
`--now`가 기억나지 않으면 `systemctl start cri-docker.service`와
`systemctl enable cri-docker.service`로 나누어 실행해도 된다.
`daemon-reload`는 유닛 설정을 다시 읽는다. 패키지 스크립트가 이미 수행했다면 중복이고,
유닛 파일을 직접 추가·수정했다면 필요하다.

```bash
systemctl -h | grep -E 'start|enable|--now|daemon-reload'
man systemctl
```

`man`에서 `/--now`·`/daemon-reload`로 검색한다. 온라인
[systemctl 매뉴얼](https://manpages.debian.org/bookworm/systemd/systemctl.1.en.html)은 학습용이며
시험에서는 로컬 `-h`·`man`으로 같은 의미를 찾는다. 공식 cri-dockerd 수동 설치 예제의
`enable --now cri-docker.socket`과 이번 문제의 **service 실행·활성화** 요구를 구분한다.

실패하면 재설치보다 서비스 로그를 먼저 확인한다.

```bash
journalctl -u cri-docker.service -n 50 --no-pager
systemctl status docker.service cri-docker.socket --no-pager
```

Docker 연결 오류, socket 상태, 실행 파일 경로 중 실제 오류를 고치고 같은 세 검증 명령을 반복한다.

## kubeadm 설치 — Practice Test: Deploy a Cluster using Kubeadm

원본 풀이: [05-Practice-Test-Deploy-Kubernetes-Cluster-using-Kubeadm.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/11-Install-Kubernetes-the-kubeadm-way/05-Practice-Test-Deploy-Kubernetes-Cluster-using-Kubeadm.md)

(원본의 버전 번호·apt 저장소는 낡았다 — 패턴만 가져가고, 저장소 주소와 버전은
시험 문제가 주는 값과 [kubernetes.io 설치 문서](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/)를 따른다.)

<Steps>

1. 두 노드 모두: swap을 끄고 커널 모듈·파라미터를 적용한다

   ```bash
   swapoff -a

   cat <<EOF | tee /etc/modules-load.d/k8s.conf
   overlay
   br_netfilter
   EOF
   modprobe overlay
   modprobe br_netfilter

   cat <<EOF | tee /etc/sysctl.d/k8s.conf
   net.bridge.bridge-nf-call-iptables = 1
   net.ipv4.ip_forward = 1
   EOF
   sysctl --system

   # 파일을 썼다는 사실보다 현재 커널 값이 중요하다
   swapon --show
   lsmod | grep -E 'overlay|br_netfilter'
   sysctl net.bridge.bridge-nf-call-iptables net.ipv4.ip_forward
   ```

   이 sysctl 블록은 힌트로 주어지는 install-kubeadm 페이지 본문에 **없다**. 그 페이지의
   "Installing a container runtime" 절이 링크하는
   [Container Runtimes → Network configuration](https://kubernetes.io/docs/setup/production-environment/container-runtimes/#network-configuration)에
   있다 — 시험에서는 링크를 타고 들어가거나 kubernetes.io 검색창에 `ip_forward`를 친다.

2. 두 노드 모두: containerd를 systemd cgroup 드라이버로 맞추고 재시작한다

   ```bash
   containerd config default | tee /etc/containerd/config.toml
   sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
   systemctl restart containerd

   systemctl is-active containerd
   containerd config dump | grep SystemdCgroup
   ```

   공식 [Container Runtimes](https://v1-35.docs.kubernetes.io/docs/setup/production-environment/container-runtimes/#cgroup-drivers)
   문서처럼 containerd와 kubelet의 cgroup 드라이버가 다르면 kubelet이 정상 동작하지 않는다.
   배포판 패키지의 `/etc/containerd/config.toml`에서 `disabled_plugins`에 `cri`가 들어 있다면
   제거한 뒤 containerd를 다시 시작한다.

3. 두 노드 모두: pkgs.k8s.io 저장소 등록 후 정확한 버전으로 설치·고정

   ```bash
   # "Install the kubeadm, kubelet and kubectl packages at exact version 1.24.0 on the controlplane and node01."
   apt-get install -y kubelet=<버전> kubeadm=<버전> kubectl=<버전>
   apt-mark hold kubelet kubeadm kubectl   # hold = apt 자동 업그레이드 금지 — 버전이 몰래 틀어지는 걸 막는다
   ```

4. 컨트롤 플레인에서 init — advertise 주소는 `eth0`의 IP(`ip a` 확인)

   ```bash
   # "Initialize Control Plane Node (Master Node)."
   # cert-extra-sans: API 서버 인증서 SAN에 이름 추가 — 그 이름으로 접속해도 TLS가 안 깨지게
   # advertise-address: 다른 노드에 알릴 API 서버 IP — NIC이 여럿인 실습 환경이라 명시한다
   # pod-network-cidr: Pod IP 대역 — 설치할 CNI(flannel)의 기본값과 맞춘다
   # service-cidr: Service ClusterIP 대역 (기본 10.96.0.0/12) — 문제가 지정할 때만 붙인다
   kubeadm init \
     --apiserver-cert-extra-sans=controlplane \
     --apiserver-advertise-address <eth0 IP> \
     --pod-network-cidr=10.244.0.0/16
   mkdir -p ~/.kube && cp /etc/kubernetes/admin.conf ~/.kube/config
   ```

   문제가 플래그 이름을 그대로 불러주므로 철자는 문서 대신 `kubeadm init --help`로 확인하는 게
   빠르다. CIDR 값은 문제가 준 값이 우선이고(pod-network-cidr을 바꿨으면 CNI 매니페스트도 그
   값으로 맞춘다), kubeconfig 세팅 명령은 외울 것 없이 **init 성공 출력이 그대로 찍어준다** —
   출력에서 복사한다.

5. init 출력의 `kubeadm join ...`을 복사해 워커에서 실행 (`ssh node01`) — *Join node01 to the cluster using the join token*

6. CNI 설치 전까지 노드가 `NotReady`인 것은 **정상** — 문제에서 준 네트워크
   플러그인 매니페스트를 apply하면 Ready가 된다 — *Install a Network Plugin*

   바로 apply하지 말고 **받아서 두 군데를 확인한 뒤** apply한다 (flannel 랩 기준):

   ```bash
   curl -LO https://<문제가 준 kube-flannel.yml URL>

   # ① kube-flannel-cfg ConfigMap의 net-conf.json — "Network"가
   #    init 때 준 --pod-network-cidr과 같아야 한다 (flannel 기본값은 10.244.0.0/16)
   # ② kube-flannel 컨테이너 args — NIC이 여럿이면 --iface=eth0 추가
   #    (flannel의 인터페이스 자동 선택이 엉뚱한 NIC을 잡는 걸 막는다.
   #     init의 --apiserver-advertise-address를 명시한 것과 같은 이유)
   kubectl apply -f kube-flannel.yml

   watch kubectl get pods -A   # kube-flannel DaemonSet이 노드 수만큼 Running
   kubectl get nodes           # NotReady → Ready
   ```

   CIDR이 안 맞으면 **Pod은 뜨는데 통신이 안 된다** — [cka 15장 CNI 절](/cka/15-cluster-lifecycle/)의
   함정 그대로다. 클러스터 쪽 값이 기억 안 나면 `kubectl cluster-info dump | grep -m1 cluster-cidr`.

   CNI 설치 절차는 kubernetes.io가 아니라 **각 프로젝트 문서 소관**이다. 시험 허용 문서에는
   flannel GitHub이 없지만, 그래서 CNI 문제는 매니페스트 URL과 수정 지시를 문제 안에 준다 —
   외울 것은 URL이 아니라 **"받아서 CIDR 일치부터 확인"하는 습관**이다.

</Steps>

:::tip[join 토큰을 잃어버렸으면]
`kubeadm token create --print-join-command`가 다시 만들어준다 — *Generate a kubeadm join token*
:::

## 설치 완료 증명 — Ready에서 외부 접근까지

`kubeadm join`이 성공했다는 출력만으로 설치가 끝난 것은 아니다. 아래 순서로 **노드 → 시스템 Pod →
샘플 앱 → Service 내부 경로 → NodePort 외부 경로**를 한 층씩 확인한다. 중간 단계가 실패하면
그보다 바깥 단계는 아직 조사하지 않는다.

<Steps>

1. 두 노드와 CNI·CoreDNS가 준비됐는지 확인한다

   ```bash
   kubectl wait --for=condition=Ready nodes --all --timeout=180s
   kubectl get nodes -o wide
   kubectl get pods -n kube-system -o wide

   # kubeadm이 만든 kubelet 설정도 런타임과 systemd로 일치해야 한다
   grep '^cgroupDriver:' /var/lib/kubelet/config.yaml
   ```

   공식 [Creating a cluster with kubeadm](https://v1-35.docs.kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/#pod-network)
   문서는 Pod 네트워크가 설치되기 전에는 CoreDNS가 시작하지 않으며, 설치 뒤 CoreDNS가
   `Running`인지 확인하라고 안내한다. 노드가 `NotReady`면 `kubectl describe node <노드>`의
   `Ready`·`NetworkReady` 조건과 `journalctl -u kubelet`부터 본다.

2. 샘플 앱을 만들고 실제 Pod이 준비됐는지 확인한다

   ```bash
   kubectl create deployment web-check --image=nginx:1.29-alpine
   kubectl rollout status deployment/web-check --timeout=120s
   kubectl get pods -l app=web-check -o wide
   ```

3. NodePort Service와 EndpointSlice의 연결을 확인한다

   ```bash
   kubectl expose deployment web-check --type=NodePort --port=80 --target-port=80
   kubectl get svc web-check
   kubectl get endpointslices -l kubernetes.io/service-name=web-check
   ```

   EndpointSlice에 Ready 주소가 없으면 NodePort나 방화벽으로 넘어가지 않는다. 먼저 Service의
   셀렉터, Pod 라벨, readiness를 고친다.

4. 클러스터 안에서 Service를 통과하는지 확인한다

   ```bash
   kubectl run web-check-client --image=busybox:1.36 --rm -it --restart=Never -- \
     wget -qO- http://web-check
   ```

5. 클러스터 밖의 터미널에서 노드 IP와 할당된 포트로 확인한다

   ```bash
   kubectl get nodes -o wide
   kubectl get svc web-check
   curl http://<외부에서-도달-가능한-노드-IP>:<표시된-NODE-PORT>
   ```

   공식 [Service 문서의 NodePort 절](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/service/#type-nodeport)대로
   기본값에서는 같은 NodePort가 모든 노드에서 Service로 전달된다. 내부 Service 호출은 되는데
   외부 `curl`만 실패하면 노드 주소의 라우팅 가능 여부, 호스트 방화벽·클라우드 보안 규칙,
   kube-proxy의 `nodePortAddresses`를 확인한다. `externalTrafficPolicy: Local`이라면 Pod이 있는
   노드로 요청했는지도 함께 확인한다.

</Steps>

```bash
# 확인을 마친 뒤 실습 자원 정리
kubectl delete deployment,service web-check
```

## 노드 비우기 — Practice Test: OS Upgrades

공식 문서: [Safely Drain a Node — Use `kubectl drain` to remove a node from service](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/#use-kubectl-drain-to-remove-a-node-from-service)

원본 풀이: [03-Practice-Test-OS-Upgrades.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/06-Cluster-Maintenance/03-Practice-Test-OS-Upgrades.md)

### 왜 `--ignore-daemonsets`가 필요한가

DaemonSet Pod은 CNI·로그 수집기처럼 **그 노드 자체에서 동작해야 하는 에이전트**다.
일반 Pod처럼 퇴거해도 DaemonSet 컨트롤러가 같은 노드에 다시 만들며, DaemonSet Pod은
노드의 unschedulable taint도 기본적으로 허용한다. 그래서 `kubectl drain`은 DaemonSet Pod을
퇴거하지 않고, 이런 Pod을 발견하면 실수로 남긴 것이 아닌지 확인하도록 기본 실행을 중단한다.

`--ignore-daemonsets`는 **DaemonSet Pod이 노드에 남는 것을 알고 있으니, 그 Pod은 건드리지 말고
나머지 Pod의 퇴거를 계속하라**는 뜻이다. “DaemonSet Pod을 강제로 삭제하라”는 옵션이 아니다.
drain이 성공해도 해당 Pod은 노드를 종료하기 전까지 계속 보일 수 있다.

### `cordon`과 `uncordon`은 무슨 뜻인가

명령 레퍼런스: [`kubectl cordon`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_cordon/) ·
[`kubectl uncordon`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_uncordon/)

영어 `cordon`은 출입을 막으려고 치는 **통제선**이고, `cordon off`는 통제선을 쳐서 구역을
막는다는 뜻이다. Kubernetes에서도 같은 그림으로 기억하면 된다.

- `cordon`: 노드 주위에 통제선을 친다 → **새 Pod을 스케줄하지 못하게** 한다. 기존 Pod은 그대로다.
- `drain`: 먼저 통제선을 치고(cordon) → 기존 일반 Pod도 안전하게 퇴거한다.
- `uncordon`: `un-`을 붙여 통제선을 걷는다 → 노드를 다시 **스케줄 가능**하게 만든다.

따라서 `kubectl uncordon node01`은 유지보수가 끝난 `node01`을 다시 후보지로 열어 주는 명령이다.
이미 다른 노드로 옮겨 간 Pod을 `node01`로 돌려보내지는 않는다.

```bash
# "Run the command kubectl drain node01 --ignore-daemonsets"
kubectl drain node01 --ignore-daemonsets   # cordon + 일반 Pod 퇴거. DaemonSet Pod은 남겨 두고 진행한다
# "Run the command kubectl uncordon node01"
kubectl uncordon node01                    # 다시 받게
# "Run the command kubectl cordon node03"
kubectl cordon node03                      # 새 Pod만 막기 (기존은 안 쫓아냄)
```

:::caution[함정 1 — drain이 거부될 때]
컨트롤러(ReplicaSet 등) 소속이 아닌 **단독 Pod이 있으면 drain이 거부**된다.
`--force`를 붙이면 진행되지만 **그 Pod은 영원히 사라진다** — 문제도 이걸 물어본다 —
*What would happen to hr-app if node02 is drained forcefully?*
:::

:::caution[함정 2 — uncordon해도 Pod은 안 돌아온다]
uncordon은 "다시 스케줄 가능"으로 돌릴 뿐이다. 기존 Pod이 재배치되지는 않는다 —
**새로 생성되는 Pod부터** 그 노드에 갈 수 있다 — *Why are there no pods on node01?*
:::

## 버전 업그레이드 — Practice Test: Cluster Upgrade Process

원본 풀이: [06-Practice-Test-Cluster-Upgrade-Process.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/06-Cluster-Maintenance/06-Practice-Test-Cluster-Upgrade-Process.md)

**공식 문서 두 개를 순서대로 따른다:**
[Package Repository 변경](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/change-package-repository/) →
[kubeadm 업그레이드](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/).
원본 풀이의 `1.18` 명령은 낡았다. 이번 문제는 **1.34.0 → 정확히 1.35.0**이므로
v1.35 문서를 보고, 예제의 최신 patch 대신 `1.35.0`을 지정한다.

**controlplane → node01 순서로 한 노드씩 완료한다.** 패키지·`kubeadm`·`systemctl` 명령은
업그레이드 대상 노드에서, `kubectl` 명령은 kubeconfig가 있는 controlplane에서 실행한다.

<Steps>

1. **controlplane 비우기:** `kubectl drain controlplane --ignore-daemonsets`.
   `kubectl get pods -o wide`로 gold-nginx가 node01에서 Ready인지 확인한다.

2. **controlplane 업그레이드:** 해당 노드의 패키지 저장소를 `v1.35`로 변경 →
   `apt-get update` → kubeadm을 `1.35.0`으로 설치 → `kubeadm upgrade plan` →
   `kubeadm upgrade apply v1.35.0`.
   kubelet·kubectl도 `1.35.0`으로 설치하고 `systemctl daemon-reload` → `systemctl restart kubelet`.
   패키지 설치 전후에는 공식 문서대로 `unhold` / `hold`한다.

3. **controlplane 복귀 후 node01 비우기:** controlplane의 `Ready`·`v1.35.0` 확인 →
   `kubectl uncordon controlplane` → `kubectl drain node01 --ignore-daemonsets`.
   **gold-nginx가 controlplane에서 Ready인지 확인한 뒤** node01 업그레이드를 시작한다.
   Pending이면 `kubectl describe pod <Pod명>`의 Events와 controlplane의 taint를 확인한다.
   실습에서 `node-role.kubernetes.io/control-plane:NoSchedule`이 배치를 막는다면
   `kubectl taint nodes controlplane node-role.kubernetes.io/control-plane:NoSchedule-`로 제거한다.

4. **node01 업그레이드:** `ssh node01` → 이 노드도 저장소를 `v1.35`로 변경 →
   `apt-get update` → kubeadm을 `1.35.0`으로 설치 → **`kubeadm upgrade node`** →
   kubelet(설치돼 있다면 kubectl도)을 `1.35.0`으로 설치 → daemon-reload·kubelet 재시작.
   controlplane 터미널로 돌아와 node01의 `Ready`·`v1.35.0` 확인 → `kubectl uncordon node01`.
   uncordon해도 gold-nginx는 controlplane에 그대로 남는다.

</Steps>

**controlplane이 하나여도 drain한다.** drain은 일반 Pod을 퇴거시키며 API 서버·etcd 같은
static Pod은 제거하지 않는다. 단, 업그레이드 중 구성 요소가 재시작되므로 API는 잠시 중단될 수 있다.
공식 문서는 `apply` 뒤, kubelet 업그레이드 전에 drain하지만, **이 문제는 업그레이드 전에 앱을
옮기라고 했으므로 먼저 drain**한다.

### APT에서 설치할 버전 찾기

저장소를 목표 마이너로 바꾼 다음에는 패키지 목록을 새로 받고, 현재 저장소에서 설치할 수 있는
`kubeadm` 버전을 확인한다.

```bash
sudo apt-get update
sudo apt-cache madison kubeadm
```

`apt-cache madison`은 네트워크를 직접 조회하는 명령이 아니라, `apt-get update`가 받아 둔
패키지 목록에서 **사용 가능한 버전과 그 버전을 제공하는 저장소**를 표로 보여준다.
[APT 명령 레퍼런스](https://manpages.debian.org/bookworm/apt/apt-cache.8.en.html#madison)에서
설명하는 출력 형식은 다음과 같다.

```text
kubeadm | 1.35.0-1.1 | https://pkgs.k8s.io/core:/stable:/v1.35/deb Packages
```

여기서 `1.35.0`은 Kubernetes 버전이고, 뒤의 `-1.1`은 APT 패키징 revision이다.
KodeKloud는 이 출력의 **정확한 전체 문자열**을 복사해 설치한다.

```bash
sudo apt-get install kubeadm=1.35.0-1.1
```

공식 문서의 `1.35.x-*`에서 `x`는 글자 그대로 입력하는 값이 아니다. 고른 patch 버전으로
바꿔 `1.35.0-*`처럼 쓰며, 마지막 `*`가 `-1.1` 같은 패키징 revision과 맞는다.

```bash
sudo apt-mark unhold kubeadm && \
sudo apt-get update && sudo apt-get install -y kubeadm='1.35.0-*' && \
sudo apt-mark hold kubeadm
```

`hold`는 일반 APT 업그레이드가 Kubernetes 패키지 버전을 뜻하지 않게 바꾸지 못하도록 막는다.
공식 절차는 잠시 `unhold`하고 설치한 뒤 다시 `hold`하는 운영용 전체 흐름이다. KodeKloud 풀이는
앞에서 이미 `apt-get update`와 정확한 버전 확인을 마쳤고 일회성 실습에 필요한 설치만 보여 준다.
설치 방법이 다른 것이 아니라 **버전 지정과 hold 관리 범위를 어디까지 명시했는지가 다르다.**

:::caution[함정 — `-y`는 실패도 조용히 지나간다]
`-y`를 붙인 `apt-get install`은 다운그레이드나 hold된 패키지를 만나면 **아무것도 바꾸지 않고
통째로 실패**한다 — 마지막 줄에 `E: Packages were downgraded and -y was used without
--allow-downgrades.` 또는 `E: Held packages were changed and -y was used without
--allow-change-held-packages.`가 찍히지만 저장소 갱신 로그에 묻혀 지나치기 쉽다.
명령이 프롬프트로 돌아왔다고 설치된 게 아니다. 잘못 깐 버전을 바로잡을 때는
unhold 후 `--allow-downgrades`를 붙이고, 설치 명령 뒤에는 반드시
`dpkg -l | grep kube`로 **실제 설치된 버전 문자열**을 확인한다 — 채점기가 보는 것도 이것이다.
:::

:::caution[함정 — 워커는 apply가 아니라 node]
`kubeadm upgrade apply`는 **첫 컨트롤 플레인에서 한 번**이다.
워커(및 추가 컨트롤 플레인)는 `kubeadm upgrade node`. 그리고 **kubelet 업그레이드를
빼먹으면 `kubectl get nodes`의 VERSION이 안 바뀐다** — 채점은 이걸 본다.
:::

### 업그레이드 완료 증명

마지막 `uncordon` 뒤에는 **Ready · kubelet 버전 · 스케줄 가능 상태**를 한 번에 확인한다.

```bash
kubectl wait --for=condition=Ready nodes --all --timeout=180s
kubectl get nodes
kubectl get nodes \
  -o custom-columns='NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion,UNSCHEDULABLE:.spec.unschedulable'
kubectl get pods -n kube-system -o wide
```

공식 v1.35 [kubeadm 업그레이드 문서](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/#verify-the-status-of-the-cluster)도
모든 노드의 `STATUS`가 `Ready`이고 버전이 갱신됐는지를 마지막에 확인한다. `Ready`인데 버전만
예전이면 대상 노드의 kubelet 패키지·재시작을, `UNSCHEDULABLE=true`면 빠뜨린 `uncordon`을 확인한다.
시스템 Pod이 비정상이면 다음 노드로 넘어가기 전에 해당 Pod의 Events와 로그를 본다.

## etcd 백업과 복구 — Practice Test: Backup and Restore Methods

원본 풀이: [09-Practice-Test-Backup-and-Restore-Methods.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/06-Cluster-Maintenance/09-Practice-Test-Backup-and-Restore-Methods.md)

### 문제 문구에서 읽어야 할 것

*ETCD cluster*는 한 개 이상의 etcd 멤버가 제공하는 **하나의 논리적 저장소**다. 이 실습처럼
멤버가 하나인 환경도 관례상 cluster라고 부른다. *At what address can you reach the ETCD cluster
from the controlplane node?*는 이 저장소의 **client endpoint URL**을 묻는 말이다.

```text
https://127.0.0.1:2379
```

- endpoint는 etcd Pod의 `--listen-client-urls`에서 확인한다
- `2379`는 API 서버와 `etcdctl`이 접속하는 client 포트다
- `2380`은 etcd 멤버 사이의 peer 포트라서 답이 아니다

IPv4는 `https://127.0.0.1:2379`처럼 대괄호 없이 쓴다. KodeKloud의 일부 옛 풀이에 있는
`https://[127.0.0.1]:2379`는 IPv4에 필요 없는 표기다. 대괄호는 `https://[::1]:2379`처럼
콜론이 포함된 IPv6 주소와 포트를 구분할 때 사용한다.

### 서버 매니페스트와 `etcdctl`의 인증서 플래그

[23장](/cka-udemy/08-security/)에서 확인한 인증서 경로를 역할별로 연결하면 다음과 같다.

| 실행 주체 | 플래그 | 의미 |
|---|---|---|
| etcd 서버 | `--cert-file` | etcd가 클라이언트에게 제시하는 서버 인증서 |
| etcd 서버 | `--key-file` | 서버 인증서에 대응하는 개인 키 |
| etcd 서버 | `--trusted-ca-file` | `--client-cert-auth=true`일 때 접속한 클라이언트 인증서를 검증할 CA |
| `etcdctl` | `--cacert` | `etcdctl`이 etcd 서버 인증서를 검증할 CA |
| `etcdctl` | `--cert` · `--key` | `etcdctl`이 etcd에 제시할 클라이언트 인증서와 개인 키 |

따라서 *Where is the ETCD server certificate file located?*는 `--cert-file`의 값을 묻는다.
`--trusted-ca-file`은 서버 인증서 자체가 아니라 **서버가 신뢰하는 CA 인증서**다. etcd의
[Transport security model](https://etcd.io/docs/v3.6/op-guide/security/)에서 같은 검증 방향을 확인할 수 있다.

### `ETCDCTL_API=3`이 필요한 버전

이 환경변수는 etcd 서버의 버전을 바꾸는 옵션이 아니라 `etcdctl`이 **v3 API 명령 체계**를
사용하도록 고르는 스위치다. etcdctl 3.3 이하는 v2가 기본이라 필요했지만, **3.4부터 v3가
기본**이므로 요즘 버전에서는 생략해도 된다. 공식 명령과 실습 답안에서는 버전이 달라도
`snapshot save`를 v3로 실행한다는 뜻을 분명히 하려고 계속 붙인다. 근거는 etcd 공식
[3.3에서 3.4 업그레이드 문서](https://etcd.io/docs/v3.6/upgrades/upgrade_3_4/#make-etcdctl_api3-etcdctl-default)다.

```bash
etcdctl version                   # 설치된 etcdctl·API 버전 확인
ETCDCTL_API=3 etcdctl version     # 이 실행 한 번에만 v3 지정
export ETCDCTL_API=3              # 현재 셸의 뒤이은 명령에도 적용
```

### 백업만 요구할 때 — 저장 노드·경로·파일 검증

`controlplane`의 `/opt/etcd-backup.db`로 백업하라는 문제는 **controlplane 호스트에서** 아래
명령의 저장 경로를 `/opt/etcd-backup.db`로 바꾸면 된다. 백업은 실행 중인 etcd에 접속하므로
**drain이나 API 서버 중지가 필요 없다.** 복구 절차와 혼동하지 않는다.

`etcdctl snapshot save --help` 또는 공식
[Snapshot using etcdctl options](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/#snapshot-using-etcdctl-options)에서
명령을 가져오고, `/etc/kubernetes/manifests/etcd.yaml`에서 endpoint와 인증서 경로를 확인한다.
이 실습 풀이의 `server.crt/key`를 아래에 사용한다. 인증서 파일명만 외워 다른 환경에 적용하지 말고
etcd가 신뢰하는 CA와 클라이언트 인증에 사용할 수 있는 인증서·키를 확인한다.

```bash
# 백업 — 인증서 세 개는 etcd 스태틱 Pod 매니페스트에서 확인
# 플래그가 기억 안 나면 공식 문서 "Operating etcd clusters for Kubernetes"에서 복사:
# https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/
# ETCDCTL_API=3: v3 API 명시 — etcdctl 3.4부터는 v3가 기본이라 생략 가능
# "Take a snapshot of the ETCD database using the built-in snapshot functionality. Store the backup file at location /opt/snapshot-pre-boot.db"
ETCDCTL_API=3 etcdctl snapshot save /opt/snapshot-pre-boot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# "saved" 출력만 믿지 않고 파일과 스냅샷 메타데이터를 함께 확인한다
sudo test -s /opt/snapshot-pre-boot.db
sudo etcdutl --write-out=table snapshot status /opt/snapshot-pre-boot.db
```

공식 v1.35 [etcd 운영 문서](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/#built-in-snapshot)는
`snapshot save` 뒤 `etcdutl snapshot status`로 hash·revision·key 수·크기를 확인한다.
`etcdctl snapshot status`는 etcd 3.5부터 deprecated이므로 `etcdutl`을 우선한다.

### 복구 절차 — 쓰기를 멈추고 새 data-dir로 전환

복구의 핵심은 **API 쓰기 중단 → 새 디렉터리로 복원 → etcd 전환 → 컨트롤 플레인 재동기화**다.
공식 v1.35 [etcd 복구 문서](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/#restoring-an-etcd-cluster)는
실행 중인 모든 API 서버를 먼저 멈추고, 모든 etcd 인스턴스를 복원한 다음 API 서버를 다시
시작하라고 한다. 아래 단일 control plane 실습에서는 kube-apiserver 매니페스트 하나를 옮겨 구현한다.

<Steps>

1. kube-apiserver를 내려 etcd로 들어오는 API 쓰기를 멈춘다

   kubeadm은 control plane 구성 요소를 `/etc/kubernetes/manifests/`의 스태틱 Pod으로 실행한다.
   kubelet은 이 디렉터리를 주기적으로 스캔해 파일이 사라지면 Pod을 내리고, 돌아오면 다시 만든다.
   공식 [스태틱 Pod 동적 추가·제거](https://v1-35.docs.kubernetes.io/docs/tasks/configure-pod-container/static-pod/#dynamic-addition-and-removal-of-static-pods)에도
   `mv` → 대기 → `crictl ps`로 확인하는 같은 예제가 있다.

   ```bash
   mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/
   sleep 20

   # 실행 중인 kube-apiserver가 나오지 않아야 중지 완료
   crictl ps | grep kube-apiserver
   ```

   HA control plane이면 한 노드만 내려서는 쓰기가 멈추지 않는다. 공식 문서의 **모든 API 서버**라는
   조건대로 각 control plane 노드의 인스턴스를 모두 멈춰야 한다.

2. 스냅샷을 현재 디렉터리와 다른 새 data-dir로 복원한다

   ```bash
   # "Luckily we took a backup. Restore the original state of the cluster using the backup file."
   etcdutl snapshot restore /opt/snapshot-pre-boot.db \
     --data-dir /var/lib/etcd-from-backup
   ```

   `etcdutl`은 로컬 스냅샷 파일을 새 data-dir로 푸는 도구다. `etcdctl snapshot restore`는
   etcd 3.5부터 deprecated이므로 복구에는 `etcdutl`을 우선한다.

3. etcd 스태틱 Pod이 새 data-dir을 보게 전환한다

   ```yaml
   # /etc/kubernetes/manifests/etcd.yaml — etcd-data 볼륨의 hostPath만 바꾼다
     - hostPath:
         path: /var/lib/etcd-from-backup
         type: DirectoryOrCreate
       name: etcd-data
   ```

   저장하면 kubelet이 변경을 감지해 etcd 스태틱 Pod을 재생성한다. 아직 API 서버가 내려가 있으므로
   `kubectl`이 아니라 노드의 CRI를 직접 본다.

   ```bash
   crictl ps | grep etcd
   # 비정상이면 종료된 컨테이너와 로그까지 확인
   crictl ps -a | grep etcd
   crictl logs <etcd-container-id>
   ```

4. kube-apiserver 매니페스트를 되돌려 API를 다시 연다

   ```bash
   mv /tmp/kube-apiserver.yaml /etc/kubernetes/manifests/
   sleep 20
   crictl ps | grep kube-apiserver
   ```

5. controller-manager·scheduler·kubelet을 재시작한다

   공식 etcd 복구 문서는 이 구성 요소들이 복구 전의 오래된 데이터를 계속 의존하지 않도록
   `kube-scheduler`, `kube-controller-manager`, `kubelet`도 재시작하라고 권고한다. 앞의 두 구성
   요소도 kubeadm 스태틱 Pod이므로 같은 매니페스트 이동 패턴을 쓴다.

   ```bash
   mv /etc/kubernetes/manifests/kube-controller-manager.yaml /tmp/
   sleep 20
   mv /tmp/kube-controller-manager.yaml /etc/kubernetes/manifests/

   mv /etc/kubernetes/manifests/kube-scheduler.yaml /tmp/
   sleep 20
   mv /tmp/kube-scheduler.yaml /etc/kubernetes/manifests/

   systemctl restart kubelet
   ```

6. 런타임 → API → 복구된 리소스 순으로 확인한다

   ```bash
   # 네 control plane 컨테이너가 모두 Running인지 먼저 확인
   crictl ps

   # API가 준비된 뒤 클러스터 상태와 스냅샷 당시 리소스를 확인
   kubectl get --raw='/readyz?verbose'
   kubectl get nodes
   kubectl get pods -n kube-system
   kubectl get deployments,services --all-namespaces
   ```

</Steps>

`sleep 20`은 kubelet의 다음 매니페스트 스캔을 기다리는 여유 시간이지 완료 판정 자체가 아니다.
시험에서는 시간이 지났다는 사실보다 `crictl ps`에서 컨테이너가 실제로 사라지고 다시 생겼는지를 본다.
또한 매니페스트 사본을 `kube-apiserver.yaml.backup`처럼 같은 디렉터리에 두면 kubelet이 그 파일도
읽을 수 있으므로, 임시 사본은 반드시 `/etc/kubernetes/manifests/` 밖에 둔다.

:::tip[백업엔 인증서 필수, 복원엔 불필요]
`snapshot save`는 살아 있는 etcd에 접속하므로 인증서가 필요하고,
`snapshot restore`는 파일을 푸는 작업이라 필요 없다. 헷갈리면 이 구분으로 기억.
:::

## 스택 vs 외부 etcd — Practice Test: Backup and Restore Methods 2

원본 풀이: [10-Practice-Test-Backup-and-Restore-Methods-2.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/06-Cluster-Maintenance/10-Practice-Test-Backup-and-Restore-Methods-2.md)

멀티 클러스터 환경 — 먼저 `kubectl config get-contexts` / `use-context`로 오간다 —
*Explore the student-node and the clusters it has access to.*

| 구분 | 스택(stacked) | 외부(external) |
|---|---|---|
| 판별 — *How is ETCD configured for cluster1?* | kube-system에 etcd Pod이 **있다** | 없다 — API 서버의 `--etcd-servers`가 외부 IP |
| 실행 형태 | 스태틱 Pod | 별도 서버의 **systemd 서비스** |
| 데이터 디렉터리 — *What is the default data directory used the for ETCD datastore used in cluster1?* | etcd Pod의 `etcd-data` hostPath | `systemctl cat etcd.service`의 `--data-dir` |
| 복구 후 전환 | 매니페스트의 hostPath 수정 | **서비스 유닛 파일** 수정 → `daemon-reload` + `restart` |

외부 etcd 복구에서 추가되는 두 가지 — *An ETCD backup for cluster2 is stored at /opt/cluster2.db.
Use this snapshot file to carry out a restore on cluster2 to a new path /var/lib/etcd-data-new.*

```bash
# "Move the backup to the etcd-server node"
scp /opt/cluster2.db etcd-server:~/                 # 스냅샷을 etcd 서버로
# "Set ownership on the restored directory"
chown -R etcd:etcd /var/lib/etcd-data-new           # 복원 디렉터리 소유권
```

:::caution[함정 — daemon-reload]
유닛 파일을 고쳤으면 `systemctl daemon-reload` 없이는 반영되지 않는다.
`restart etcd`만 하고 "왜 그대로지"에 빠지는 게 이 랩의 함정이다.
:::

## 시험장에서 공식 문서 찾기

이 장은 리소스 YAML보다 **버전별 명령 순서와 노드별 실행 위치**를 공식 문서에서 확인하는 비중이 크다.

| 이 장의 섹션 | 검색어 | 공식 문서에서 확인할 것 |
|---|---|---|
| kubeadm 설치 | `Installing kubeadm` | [Installing kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/)의 현재 패키지 저장소, swap·포트·런타임 사전 조건 |
| init·join·CNI | `Creating cluster kubeadm` | [Creating a cluster with kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)의 `kubeadm init`, kubeconfig 복사, Pod 네트워크, join 순서 |
| drain·uncordon | `Safely Drain a Node` | [Safely Drain a Node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)에서 DaemonSet·단독 Pod·`emptyDir` 때문에 필요한 플래그와 데이터 유실 조건 |
| 버전 업그레이드 | `Upgrading kubeadm clusters` | [Changing The Kubernetes Package Repository](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/change-package-repository/)에서 목표 마이너 저장소로 바꾸고, [Upgrading kubeadm clusters](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/)에서 control plane/worker 절차 확인 |
| etcd 백업·복구 | `Operating etcd clusters Kubernetes` · `Create static Pods dynamic removal` | [Operating etcd clusters for Kubernetes](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)에서 API 서버 중지·restore·구성 요소 재시작을, [Create static Pods](https://kubernetes.io/docs/tasks/configure-pod-container/static-pod/#dynamic-addition-and-removal-of-static-pods)에서 매니페스트를 디렉터리 밖으로 옮겨 중지·재기동하는 패턴을 확인. endpoint와 인증서 경로는 실제 etcd 매니페스트에서 가져오기 |

업그레이드 문서는 현재 최신 마이너를 기준으로 내용이 바뀐다. 시험 클러스터의 출발·목표 버전을 먼저
확인하고, 페이지 상단의 버전 선택기에서 그 버전 문서를 고른 뒤 패키지 문자열까지 그대로 따른다.

## 이 장에서 남길 것

- kubeadm: 커널 설정 → 패키지 고정 설치 → init → join → CNI. NotReady는 CNI 전까지 정상
- drain은 단독 Pod에서 멈춘다(`--force`는 유실 감수). uncordon은 재배치가 아니다
- 업그레이드: 컨트롤 플레인 `upgrade apply`, 워커 `upgrade node`, **모든 노드의 Ready·버전·schedulable까지 봐야 끝**
- etcd 백업은 파일 존재뿐 아니라 `etcdutl snapshot status`의 메타데이터까지 확인한다
- etcd 복구 = 새 디렉터리로 restore + etcd의 시선(hostPath 또는 --data-dir)을 그리로
- 외부 etcd면 systemd — scp·chown·daemon-reload가 추가된다
