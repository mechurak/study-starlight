<Thesis>
관측 작업은 `top`이나 `logs`를 무작정 실행하는 일이 아니라, 메트릭 파이프라인의 준비 상태와
Pod이 멈춘 단계를 먼저 확인한 뒤 읽을 증거를 고르는 일이다.

metrics-server가 값을 내는지 확인하고 CPU·메모리 단위를 정확히 읽는다. 장애 진단에서는
Pod의 NODE·Events로 실행 전후를 가른 뒤 현재 로그, 이전 로그, kubelet 로그로 필요한 만큼만 내려간다.

## metrics-server — Practice Test: Monitor Cluster Components

원본 풀이: [03-Practice-Test-Monitor-Cluster-Components.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/04-Logging-and-Monitoring/03-Practice-Test-Monitor-Cluster-Components.md)

`kubectl top`은 **metrics-server가 있어야** 동작한다 — 기본 설치가 아니다.

```bash
# "Let us deploy metrics-server to monitor the PODs and Nodes. Pull the git repository for the deployment files."
git clone https://github.com/kodekloudhub/kubernetes-metrics-server.git
# "Deploy the metrics-server by creating all the components downloaded."
kubectl create -f kubernetes-metrics-server/
# "Identify the node that consumes the most CPU(cores)."
kubectl top node                  # CPU(cores) / MEMORY(bytes) 열
# "Identify the POD that consumes the most Memory(bytes)."
kubectl top pod
```

### `kubectl top` 출력 읽기

```text
NAME                           CPU(cores)   MEMORY(bytes)
flask-app-4-5cfb5d78c4-p9l2m  1m           19Mi
flask-app-4-5cfb5d78c4-t229n  1m           19Mi
```

헤더가 `CPU(cores)`와 `MEMORY(bytes)`여도 실제 값에는 읽기 쉬운 접미사가 붙는다.

| 출력 | 읽는 법 |
|---|---|
| CPU `1m` | 0.001 CPU = 코어 하나의 0.1%에 해당하는 사용량 |
| CPU `500m` | 0.5 CPU |
| CPU `1000m` | 1 CPU |
| 메모리 `19Mi` | 19 mebibytes = `19 × 1024²` bytes, 약 19.9 MB |

CPU의 `m`은 millisecond가 아니라 **millicpu**다. [공식 리소스 단위 설명](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#resource-units-in-kubernetes)처럼
`1000m = 1 CPU`로 읽는다. 메모리의 `Mi`는 mebibyte라서 `1Mi = 1,048,576 bytes`이고,
10진 단위인 `1M = 1,000,000 bytes`와 다르다.

CPU 값은 실행 후의 누적 CPU 시간이 아니라 **최근 측정 구간의 평균 CPU 사용 속도**다.
예를 들어 15초 구간에 CPU 시간 7.5초를 소비했다면 `7.5 / 15 = 0.5 CPU = 500m`이다.
여기서 15초는 설명용 예시이며 실제 구간은 클러스터에 따라 다를 수 있다. Metrics API는
그 구간을 `window`로 돌려준다.

```bash
kubectl get --raw \
  '/apis/metrics.k8s.io/v1beta1/namespaces/<namespace>/pods/<pod>'
# 응답의 timestamp와 window 확인
```

[Metrics API의 `timestamp`와 `window`](https://kubernetes.io/docs/reference/external-api/metrics.v1beta1/)는
`timestamp - window`부터 `timestamp`까지 수집한 값이라는 뜻이다. 요청이 없던 frontend Pod의
CPU가 `1m`처럼 작은 것은 자연스럽다. probe나 런타임의 백그라운드 작업 때문에 꼭 `0m`은 아니며,
메모리는 시간당 사용량이 아니므로 앱 프로세스가 떠 있는 동안 일정량을 계속 차지할 수 있다.

- `kubectl top pod`은 현재 namespace만 본다. 전체 namespace는 `kubectl top pods -A`
- 짧은 CPU 급증은 평균값에 희석돼 peak 그대로 보이지 않을 수 있다. `top`은 현황 점검과 오토스케일링용이지
  장기 이력이나 정밀 분석용 모니터링 도구가 아니다

- 설치 직후에는 수집이 안 돼 있다 — **몇 분 기다렸다가** top이 값을 낼 때까지 재시도
  — *It takes a few minutes for the metrics server to start gathering data.*
- "가장 CPU를 많이 쓰는 노드/Pod" 유형은 전부 top 출력의 열 읽기다
- 정렬까지 시키면 `kubectl top pod --sort-by=memory`

메트릭이 어디서 와서 어디로 가는지(kubelet → metrics-server → HPA)는
[CKA 오토스케일링](/cka/autoscaling/)에 있다. 실제 CPU·메모리 목표 설정은
[HPA 설정과 검증](/cka-udemy/autoscaling/)에서 이어 간다.

## 메트릭 조회 명령을 스크립트로 제출

실행 결과가 아니라 **다시 실행할 명령 파일**을 요구하면 `top` 출력을 저장하지 않는다.
다음은 노드 전체와 전체 namespace의 컨테이너별 사용량을 보는 두 스크립트다.
지정 작업 호스트에서 쓰기 가능한 제출 경로로 파일명을 바꾼다.

```bash
cat > node-metrics.sh <<'EOF'
#!/bin/sh
kubectl top nodes
EOF
cat > container-metrics.sh <<'EOF'
#!/bin/sh
kubectl top pods -A --containers
EOF
chmod +x node-metrics.sh container-metrics.sh
./node-metrics.sh
./container-metrics.sh
```

`k` alias는 비대화형 셸에 없을 수 있어 전체 명령을 쓴다. 실행할 셸의 kubeconfig로 요청하므로
SSH 호스트와 context도 확인한다. 특정 namespace만 요구하면 `-A`를 해당 `-n`으로 바꾼다.
옵션은 [`kubectl top pod`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_top/kubectl_top_pod/)의
`--containers`에서 확인한다. metric 수집 실패를 빈 출력 파일로 숨기지 않는다.

## 애플리케이션 로그 — Practice Test: Managing Application Logs

원본 풀이: [06-Practice-Test-Managing-Application-Logs.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/04-Logging-and-Monitoring/06-Practice-Test-Managing-Application-Logs.md)

```bash
# "Inspect the logs of the POD"
kubectl logs webapp-1                  # 단일 컨테이너면 이걸로 끝
# "Inspect the logs of the webapp in the POD"
kubectl logs webapp-2 -c simple-webapp # 멀티 컨테이너면 -c 필수
kubectl logs webapp-1 -f               # 스트리밍
kubectl logs webapp-1 --previous       # 재시작 전 로그 — CrashLoopBackOff 진단의 핵심
```

:::tip[로그에서 답을 베끼는 유형]
"USER5의 로그인 실패 원인은?" 같은 문제는 로그 본문에서 답을 읽어 옮기는 것이다.
명령보다 **로그를 끝까지 읽는 침착함**이 채점 대상이다.
:::

## 증상에 맞는 로그 진입점을 고른다

`Pending`이라는 글자만 보고 로그부터 열지 않는다. 먼저 `spec.nodeName`과 Events로 **스케줄링 전**인지,
노드에 배치된 뒤 **컨테이너 생성·실행 중** 실패했는지를 가른다.

```bash
kubectl get pod <pod> -o wide       # STATUS / NODE 확인
kubectl describe pod <pod>
```

| 확인 결과 | 다음 증거 | 진입점 |
|---|---|---|
| `NODE`가 비었고 `Pending` | 스케줄러가 후보 노드를 모두 거른 이유 | `describe pod`의 Events |
| `NODE`가 있고 컨테이너가 재시작 | 현재·이전 컨테이너 출력 | `kubectl logs -c …`, `--previous` |
| 노드가 `NotReady`이거나 컨테이너 생성 자체가 실패 | 해당 노드의 kubelet·런타임 | `journalctl -u kubelet`, `crictl` |
| control plane Pod이 실패하고 API는 응답함 | `kube-system`의 컴포넌트 로그 | `kubectl -n kube-system logs …` |
| API 서버가 응답하지 않음 | control plane 노드의 스태틱 Pod 컨테이너 | `crictl ps -a`, `crictl logs` |

```bash
# 실행된 컨테이너가 있다 — 애플리케이션 출력부터 본다
kubectl logs <pod> -c <container> --previous

# 노드 조건·kubelet 문제다 — Pod이 배치된 노드로 들어간다
kubectl get pod <pod> -o wide
ssh <node>
sudo journalctl -u kubelet -n 100 --no-pager
sudo ls -l /var/log/containers/                 # /var/log/pods 쪽 로그의 링크

# kubeadm control plane에서 API 서버가 죽었다 — kubectl 대신 런타임으로 내려간다
sudo crictl ps -a --name kube-apiserver
sudo crictl logs <container-id>
```

Linux의 systemd 기반 노드에서는 kubelet과 컨테이너 런타임 로그를 journald에서 읽는다. 반면 kubeadm의
API 서버·스케줄러·컨트롤러 매니저는 보통 스태틱 Pod이므로, API가 살아 있으면 `kubectl logs`, 죽었으면
노드의 `crictl logs`가 같은 컨테이너 로그로 가는 두 경로다. 컨테이너 표준 출력의 기본 실체는
`/var/log/pods` 아래이고 `/var/log/containers`는 이를 찾기 쉬운 링크로 제공한다.

:::caution[실패 층이 바뀌면 도구도 바뀐다]
라벨·taint·리소스 때문에 스케줄링되지 않은 Pod에는 읽을 컨테이너 로그가 없다. 반대로 `nodeName`이
채워졌는데도 `journalctl -u kubelet`만 뒤지면 애플리케이션의 종료 원인을 놓친다. 먼저 Events로
경계를 정하고, 배치 뒤에는 컨테이너 → kubelet → control plane 순으로 필요한 층만 내려간다.
:::

공식 근거: [로깅 아키텍처](https://v1-35.docs.kubernetes.io/docs/concepts/cluster-administration/logging/),
[Pod 디버깅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-application/debug-pods/),
[클러스터 트러블슈팅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-cluster/),
[`crictl`로 노드 디버깅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-cluster/crictl/).

## Pod에서 런타임 컨테이너까지 추적

실행 노드의 container ID·runtimeType·로그를 요구하면 API의 Pod 이름을 노드의 CRI 객체와 연결한다.
아래는 `project-tiger/tigers-reunite`가 이미 실행 중인 경우다.

```bash
# kubeconfig가 있는 작업 호스트
kubectl -n project-tiger get pod tigers-reunite -o wide
kubectl -n project-tiger get pod tigers-reunite \
  -o jsonpath='{range .status.containerStatuses[*]}{.name}{" "}{.containerID}{"\n"}{end}'
```

확인한 NODE로 SSH한 뒤 노드에서 실행한다. `<sandbox-id>`와 `<container-id>`는 실제 조회값으로 바꾼다.

```bash
sudo crictl pods --namespace project-tiger --name tigers-reunite
sudo crictl ps -a --pod <sandbox-id>
sudo crictl inspect <container-id>
sudo crictl logs <container-id>
```

Pod sandbox ID와 앱 container ID는 다르다. 컨테이너가 여러 개면 이름과 실행 상태를 확인하고
API의 `containerd://` 접두사를 뺀 ID와 대조한다. `inspect`의 `status.id`는 전체 ID이고,
`info.runtimeType`은 런타임이 제공하는 세부 정보다. containerd 예시의 `io.containerd.runc.v2`를
모든 런타임의 고정값으로 쓰지 않는다. `crictl`과 `docker`의 옵션·출력도 동일하지 않다.
([공식 crictl 안내](https://kubernetes.io/docs/tasks/debug/debug-cluster/crictl/))

로그 파일을 worker가 아닌 작업 호스트에 제출하려면 **작업 호스트로 돌아와** 아래처럼 저장한다.
`worker-node`와 ID를 실제 값으로 바꾸며, 원격 sudo가 비대화형으로 허용되는 환경의 예다.

```bash
ssh worker-node 'sudo crictl logs <container-id> 2>&1' > /course/17/pod-container.log
```

`2>&1`은 컨테이너의 stderr 로그도 함께 받기 위한 것이다. 명령이 실패하면 SSH·sudo·crictl
오류가 섞일 수 있으므로 종료 코드와 파일 내용을 확인한다. 프롬프트·수동 복사 흔적·빈 파일이
없고 해당 컨테이너의 로그인지 대조한다. 권한상 이 방식이 안 되면 노드의 쓰기 가능한 임시 파일에
저장한 뒤 `scp`로 지정 호스트에 가져온다. 조회 작업이므로 컨테이너를 재시작할 필요는 없다.

## 완료 기준

- Metrics API가 응답하고 `kubectl top node`·`top pod -A`가 실제 값을 낸다.
- CPU `m`과 메모리 `Mi`를 구분하고, 필요하면 `--sort-by`로 문제의 대상을 찾는다.
- Pod이 실행 전이면 Events, 실행·재시작 뒤면 `logs -c`와 `--previous`, 노드 문제면 kubelet 로그를 선택한다.
- 로그에서 찾은 원인을 고친 뒤 원래 workload의 Ready와 기능을 다시 확인한다.
