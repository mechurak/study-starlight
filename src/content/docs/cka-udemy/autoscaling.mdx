<Thesis>HPA는 메트릭 종류에 맞는 목표를 선언하고, 설정 저장과 메트릭 수집·실제 replica 조정을 구분해 검증한다.</Thesis>

> 짝이 되는 개념 장: [CKA 오토스케일링](/cka/autoscaling/)

이 장의 과제는 제공된 HPA 파일을 요구한 CPU·메모리 또는 사용자 정의 메트릭 목표로 고치고, 실제로 replica를 계산할
수 있는 상태인지 확인하는 것이다. HPA는 Deployment 같은 대상의 복제본 수를 조정한다.

리소스 `Utilization`은 현재 사용량을 Pod의 request와 비교한 비율이다. 따라서 metrics API가
응답하고 대상 컨테이너에 해당 리소스 request가 있어야 한다. `kubectl apply` 성공과 HPA의
`TARGETS`가 숫자로 나오는 상태를 별도로 판정한다.

## 리소스 메트릭의 사전 조건 — metrics와 request

```bash
kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top pods
kubectl get deployment kkapp-deploy \
  -o jsonpath='{.spec.template.spec.containers[*].resources.requests}{"\n"}'
```

APIService가 `Available=True`이고 `kubectl top`이 값을 반환해야 resource metric을 읽을 수 있다.
CPU 목표에는 `requests.cpu`, 메모리 목표에는 `requests.memory`가 필요하다. 설치·수집이 아직
준비되지 않았다면 [metrics-server 실습](/cka-udemy/troubleshooting/#metrics-server--practice-test-monitor-cluster-components)에서
선행 조건을 해결한다.

## webapp-hpa — CPU 50%와 축소 안정화 300초

```bash
cat /root/webapp-hpa.yaml
vim /root/webapp-hpa.yaml
kubectl explain hpa.spec.behavior.scaleDown --api-version=autoscaling/v2
```

제공 파일부터 연다. 다음 완성본의 최소·최대값은 이 예제의 조건이다. 문제에서 따로 지정하지 않았다면
제공 파일의 값을 유지한다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: webapp-hpa
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: kkapp-deploy
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```

`stabilizationWindowSeconds: 300`은 최근 300초의 권장 replica 중 가장 큰 값을 고려해 급격한 축소를
억제한다. 모든 축소를 무조건 300초 뒤에 한 번 실행하는 타이머는 아니다.

```bash
kubectl apply --dry-run=server -f /root/webapp-hpa.yaml
kubectl apply -f /root/webapp-hpa.yaml
kubectl get hpa webapp-hpa
kubectl describe hpa webapp-hpa
```

## backend-hpa — memory utilization 65%로 바꾼다

CPU 예제를 메모리 문제에 재사용할 때는 `resource.name`과 목표값뿐 아니라 대상·namespace·최소·최대
replica를 모두 문제와 맞춘다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend-hpa
  namespace: backend
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend-deployment
  minReplicas: 3
  maxReplicas: 15
  metrics:
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 65
```

```bash
kubectl apply --dry-run=server -f /root/webapp-hpa.yaml
kubectl apply -f /root/webapp-hpa.yaml
kubectl get hpa backend-hpa -n backend
kubectl describe hpa backend-hpa -n backend
kubectl get deploy backend-deployment -n backend \
  -o jsonpath='{.spec.template.spec.containers[*].resources.requests.memory}{"\n"}'
```

`TARGETS`가 `<unknown>/65%`라면 객체는 생성됐지만 replica 계산은 아직 불가능하다. `describe hpa`의
Conditions·Events에서 `FailedGetResourceMetric` 같은 수집 오류와 request 누락을 구분한다. target
Deployment 이름이나 namespace가 틀렸다면 `AbleToScale` 조건에서도 드러난다.

## api-hpa — Pod별 requests_per_second 평균 목표

Mock Exam은 `api` namespace의 기존 `api-deployment`를 Pod당 평균 초당 요청 1000건에 맞춰
1~20개로 조정하도록 선언한다. CPU 사용률과 달리 `Pods` 메트릭의 절대 평균값이다.
[HorizontalPodAutoscaler Walkthrough의 다른 메트릭 예제](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/#autoscaling-on-multiple-metrics-and-custom-metrics)에서
`type: Pods` 블록을 가져와 메트릭 이름과 `AverageValue`를 바꾼다.

제공된 `/root/api-hpa.yaml`이 있으면 그 파일을 편집하고, 없으면 아래 완성본으로 만든다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
  namespace: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-deployment
  minReplicas: 1
  maxReplicas: 20
  metrics:
  - type: Pods
    pods:
      metric:
        name: requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"
```

```bash
kubectl get deploy api-deployment -n api
kubectl apply -f /root/api-hpa.yaml
kubectl get hpa api-hpa -n api -o yaml
kubectl describe hpa api-hpa -n api
```

이 사례는 문제에서 메트릭 미수집 오류를 무시하라고 명시했다. 따라서 대상·namespace·min/max·
메트릭·목표값이 정확히 저장된 것을 제출 기준으로 하고 실제 자동 확장은 미검증으로 남긴다.
`<unknown>`이나 `FailedGetPodsMetric`이 나왔다고 CPU 메트릭으로 바꾸지 않는다.

정확히는 metrics-server가 사용자 정의 RPS를 제공하는 구조가 아니다. 실동작에는
[`custom.metrics.k8s.io`를 제공하는 어댑터](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#support-for-metrics-apis)가
필요하다. 이 목표에 CPU·메모리 request는 계산 분모가 아니며, 일반 HPA 검증에서는 메트릭 API와
실제 replica 변화까지 확인한다. 연습을 되돌릴 때 HPA를 삭제해도 이미 바뀐 replicas는 자동 복원되지
않으므로 시작 전 Deployment 복제본 수를 기록한다.

## 완료 판정

```bash
kubectl get hpa webapp-hpa \
  -o custom-columns='NAME:.metadata.name,CURRENT:.status.currentReplicas,DESIRED:.status.desiredReplicas,MIN:.spec.minReplicas,MAX:.spec.maxReplicas'
kubectl get deployment kkapp-deploy
```

- HPA의 target, metric 종류·목표, min/max와 scaleDown 안정화 값이 문제와 같다.
- 실동작 검증에서는 `TARGETS`의 현재값이 `<unknown>`이 아니고 Conditions에서 `AbleToScale=True`다.
  `api-hpa`처럼 문제에서 수집 오류를 무시하라고 한 경우는 선언값 확인으로 한정한다.
- 부하가 주어진 문제라면 `desiredReplicas`와 Deployment replicas가 기대 범위로 변했다.

부하가 없는 랩에서는 임의의 큰 부하를 만들지 않고 위 조건과 현재·목표 replica를 제출 증거로 남긴다.
