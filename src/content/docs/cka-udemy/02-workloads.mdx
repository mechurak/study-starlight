<Thesis>Deployment의 Pod template을 바꾸고 rollout이 끝났는지 확인하며, 실패하면 새 ReplicaSet과 Pod 증거로 복구한다</Thesis>

Deployment는 Pod을 직접 고치는 대신 Pod template의 새 버전을 ReplicaSet으로 rollout한다.
이 페이지에서는 **생성 → template 변경 → rollout 관찰 → 실패 원인 확인과 rollback**을 한 흐름으로
연습한다. controller 관계와 전략은 [CKA 워크로드 컨트롤러](/cka/workloads/)에서 복습한다.

ReplicaSet은 개수를, Deployment는 그 ReplicaSet의 버전과 교체 과정까지 관리한다.
두 리소스 모두 selector와 Pod template 라벨이 맞아야 한다. 생성 성공과 새 Pod의 Ready,
rollout 완료는 서로 다른 판정이다.

## ReplicaSet — Practice Test: ReplicaSets

원본 풀이: [15-Practice-Tests-ReplicaSet.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/15-Practice-Tests-ReplicaSet.md)

| 과제 | 명령 |
|---|---|
| 조회 (단축명 `rs`) — *How many ReplicaSets exist on the system?* | `k get rs` / `k get rs -o wide` |
| 이미지 확인 — *What is the image used to create the pods in the new-replica-set?* | `k describe rs <name>` 또는 `-o wide`의 IMAGES 열 |
| 스케일 — *Scale the ReplicaSet to 5 PODs.* | `k scale rs new-replica-set --replicas 5` |
| 삭제 (여러 개 한 번에) — *Delete the two newly created ReplicaSets - replicaset-1 and replicaset-2* | `k delete rs replicaset-1 replicaset-2` |

깨진 정의 파일 두 유형 —

- **apiVersion 오류**: `kubectl explain replicaset | grep VERSION`으로 맞는 값(`apps/v1`)을 확인해 고친다
  — *Create a ReplicaSet using the replicaset-definition-1.yaml file located at /root/. There is an issue with the file, so try to fix it.*
- **셀렉터 불일치**: `spec.selector.matchLabels`와 `spec.template.metadata.labels`가 **같아야** 생성된다
  — *Fix the issue in the replicaset-definition-2.yaml file and create a ReplicaSet using it.*

:::caution[함정 — ReplicaSet은 이미지를 고쳐도 Pod을 안 갈아엎는다]
*Fix the original replica set new-replica-set to use the correct busybox image.* —
`kubectl edit rs`로 이미지를 고쳐도 **기존 Pod은 그대로 깨진 채**다.
ReplicaSet은 개수만 맞추는 루프라 템플릿 변경을 롤아웃하지 않는다. 고친 뒤 —

```bash
kubectl scale rs new-replica-set --replicas 0
kubectl scale rs new-replica-set --replicas 4
```

처럼 0으로 줄였다 되돌리거나, Pod을 직접 지워 재생성시킨다.
이게 Deployment가 존재하는 이유다 — [CKA 워크로드 컨트롤러](/cka/workloads/).
:::

## Deployment — Practice Test: Deployments

원본 풀이: [17-Practice-Tests-Deployments.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/17-Practice-Tests-Deployments.md)

Deployment를 만들면 ReplicaSet과 Pod이 딸려 나온다 — 조회 문제는
`get deploy` → `get rs` → `get pods` 세 층을 오가며 센다
— *How many Deployments exist on the system now? How many ReplicaSets exist on the system now?*

*Create a new Deployment using the deployment-definition-1.yaml file located at /root/. There is an issue with the file, so try to fix it.* —
깨진 파일 유형: **`kind: deployment`처럼 대소문자가 틀린 경우** — `Deployment`로 고친다.
kind는 대문자로 시작한다.

스펙이 주어지는 생성 문제는 명령형이 빠르다 —

```bash
# "Create a new Deployment with the below attributes using your own deployment definition file."
kubectl create deployment httpd-frontend --image=httpd:2.4-alpine --replicas=3
```

:::caution[함정 — 생성 뒤 selector는 바꿀 수 없다]
`apps/v1` Deployment의 `spec.selector`는 생성 뒤 불변이다. `kubectl edit`·`apply`·Helm 업그레이드로도
바꿀 수 없다. selector와 Pod 템플릿 라벨이 어긋난 파일은 생성 전에 함께 고치고, 이미 만든
Deployment의 selector를 바꿔야 한다면 기존 워크로드·Service 영향을 확인한 뒤 삭제·재생성하거나
새 이름으로 교체한다.
:::

### hr-web-app — 이미지와 복제본 수만 지정된 생성

```bash
kubectl create deployment --help
kubectl create deployment hr-web-app -n default \
  --image=kodekloud/webapp-color --replicas=2
kubectl rollout status deployment/hr-web-app -n default
kubectl get deployment hr-web-app -n default
```

[공식 create deployment 예제](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_deployment/)와
도움말의 Examples에 `--image`·`--replicas` 조합이 있다. 이 조건만 있으면 YAML을 따로 만들 필요가 없다.
`READY 2/2`를 확인하고, 준비되지 않으면 해당 Pod의 `describe`로 이미지 다운로드·스케줄링 실패를 구분한다.
뒤의 Service 문제에서는 이 Deployment를 `expose`의 대상으로 사용한다.

## 롤링 업데이트와 롤백 — Practice Test: Rolling Updates and Rollbacks

원본 풀이: [03-Practice-Test-RollingUpdates-Rollback.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/03-Practice-Test-RollingUpdates-Rollback.md)

| 과제 | 보는 곳 |
|---|---|
| 전략 확인 — *Run the command 'kubectl describe deployment' and look at 'StrategyType'* | `k describe deploy` → StrategyType |
| 몇 개씩 교체되나 — *Look at the Max Unavailable value under RollingUpdateStrategy in deployment details* | `k describe deploy` → RollingUpdateStrategy의 max unavailable |
| 이미지 변경 — *Run the command 'kubectl edit deployment frontend' and modify the required feild* | `k edit deploy frontend` 또는 `k set image deploy/frontend <컨테이너>=<이미지>` |

:::caution[함정 — 전략을 Recreate로 바꿀 때]
*Run the command 'kubectl edit deployment frontend' and modify the required field. Make sure to delete the properties of rollingUpdate as well, set at 'strategy.rollingUpdate'.* —
`strategy.type`을 `Recreate`로 바꾸라는 문제에서 `type`만 고치면 에러가 난다.
**`strategy.rollingUpdate` 블록(maxSurge/maxUnavailable)을 통째로 지워야** 한다 —
Recreate 전략에는 rollingUpdate 파라미터가 있을 수 없다.
:::

:::tip[관찰 명령]
롤아웃이 실제로 어떻게 진행되는지는 `kubectl rollout status deploy/frontend`,
되돌리기는 `kubectl rollout undo deploy/frontend`.
히스토리 관리와 원리는 [CKA 워크로드 컨트롤러](/cka/workloads/)에 있다.
시험 중 전략 필드가 헷갈리면 공식
[Deployments 문서](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)에서
`strategy` 예시를 복사해 온다.
:::

### nginx 이미지 변경과 변경 사유 기록

요구: `nginx-deploy`를 `nginx:1.16`, 복제본 1개로 만든 뒤 `1.17`로 rolling update하고
`Updated nginx image to 1.17`을 기록한다. 새 Deployment의 기본 전략은 `RollingUpdate`다.

```bash
kubectl create deployment nginx-deploy --image=nginx:1.16 --replicas=1
kubectl rollout status deployment/nginx-deploy
kubectl set image deployment/nginx-deploy nginx=nginx:1.17
kubectl annotate deployment/nginx-deploy \
  kubernetes.io/change-cause="Updated nginx image to 1.17"
kubectl rollout status deployment/nginx-deploy
kubectl rollout history deployment/nginx-deploy
kubectl get deployment nginx-deploy -o wide
```

`nginx=`는 Deployment 이름이 아니라 **컨테이너 이름**이다. 이 생성 명령에서는 `nginx`가 된다.
기존 annotation을 수정할 때는 `--overwrite`를 붙인다.

명령 이름만 기억하고 문법은 도움말의 Examples에서 찾는다: `kubectl --help` →
`kubectl set --help` → `kubectl set image --help`. 진행·이력·되돌리기는
`kubectl rollout --help`의 `status`·`history`·`undo`, 설명 추가는 `kubectl annotate --help`다.
`set image` 대신 `kubectl edit deployment nginx-deploy`로 템플릿의 image를 바꿔도 된다.

**change-cause = 변경 사유**다. 키가 기억나지 않으면 공식
[Deployments — Checking Rollout History](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#checking-rollout-history-of-a-deployment)에서
`annotate`를 검색해 예제를 복사한다. 이 annotation이 `rollout history`의 `CHANGE-CAUSE`에 표시된다.

### nginx-deploy — apply로 생성과 rolling update를 모두 수행

`nginx:1.16`, 복제본 1개로 생성한 뒤 `nginx:1.17`로 올리되 **생성과 변경 모두 `kubectl apply`를
사용하라**는 조건이다. 위 변경 사유 기록 문제와 이름이 같지만 이번에는 annotation이 요구되지 않는다.
새 Deployment의 [기본 전략은 `RollingUpdate`](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#strategy)이므로
이미지를 바꾸어 적용하면 롤아웃이 시작된다.

```bash
kubectl create deployment nginx-deploy --image=nginx:1.16 --replicas=1 \
  --dry-run=client -o yaml > nginx.yaml
kubectl apply -f nginx.yaml
kubectl rollout status deployment/nginx-deploy --timeout=120s
```

`create`는 YAML 생성에만 사용했고 실제 리소스는 `apply`로 만들었다. **1.16 배포가 완료된 뒤**
`vim nginx.yaml`에서 `image: nginx:1.16`을 `image: nginx:1.17`로 바꾸고 다시 적용한다.

```bash
kubectl apply -f nginx.yaml
kubectl rollout status deployment/nginx-deploy --timeout=120s
kubectl get deployment nginx-deploy -o wide
kubectl describe deployment nginx-deploy
kubectl get pods -l app=nginx-deploy \
  -o custom-columns='NAME:.metadata.name,IMAGE:.spec.containers[*].image,READY:.status.containerStatuses[*].ready'
```

완료 기준은 Deployment `READY 1/1`, 이미지 `nginx:1.17`, `StrategyType: RollingUpdate`,
새 Pod의 이미지·준비 상태다. 최초 생성 직후 곧바로 1.17을 적용하면 1.16 배포 완료를 확인하지 못한다.
복제본 1개여도 기본 전략은 업데이트 중 새 Pod를 추가할 수 있으므로 잠깐 Pod가 두 개 보이는 것은 정상이다.

실패하면 새 Pod의 Events부터 확인한다. 이미지 오타라면 파일을 고쳐 다시 `apply`하고,
1.16으로 복구할 때도 파일의 태그를 되돌려 `apply`한 뒤 `rollout status`를 확인한다.
작업 방식을 지정한 문제에서는 `set image`·`edit`·`rollout undo`로 대신 끝내지 않는다.

### 실패한 롤아웃은 새 ReplicaSet부터 내려간다

`set image`가 성공했다는 출력은 새 템플릿이 저장됐다는 뜻일 뿐, 새 Pod이 준비됐다는 뜻이 아니다.
완료를 기다리고, 실패하면 Deployment → 새 ReplicaSet → 새 Pod 순서로 원인을 좁힌다.

```bash
kubectl rollout status deploy/frontend --timeout=120s

kubectl describe deploy frontend
kubectl get rs --sort-by=.metadata.creationTimestamp
kubectl get pods -l app=frontend -o wide
kubectl describe pod <new-pod>
kubectl logs <new-pod> --all-containers
kubectl get events --sort-by=.lastTimestamp
```

`ProgressDeadlineExceeded`는 자동 롤백 신호가 아니다. Deployment 컨트롤러는 계속 재시도하므로,
시간이 부족하거나 새 템플릿 자체가 잘못됐다면 정상 리비전을 확인해 직접 되돌린다.

```bash
kubectl rollout history deploy/frontend
kubectl rollout history deploy/frontend --revision=2
kubectl rollout undo deploy/frontend --to-revision=2
kubectl rollout status deploy/frontend --timeout=120s

# 복구 완료는 컨트롤러와 실제 Pod 양쪽에서 확인한다
kubectl get deploy frontend
kubectl get pods -l app=frontend \
  -o custom-columns='NAME:.metadata.name,READY:.status.containerStatuses[*].ready,IMAGE:.spec.containers[*].image'
```

공식 근거: [Deployments](https://v1-35.docs.kubernetes.io/docs/concepts/workloads/controllers/deployment/).


## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| ReplicaSet | `ReplicaSet` | [ReplicaSet](https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/)의 **Writing a ReplicaSet manifest** 예시. `apps/v1`, `selector.matchLabels`, `template.metadata.labels`를 한 묶음으로 복사 |
| Deployment 생성 | `Deployments` | [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)의 첫 매니페스트. ReplicaSet과 같은 selector/label 짝에 `spec.replicas`를 더한다 |
| 롤링 업데이트·롤백 | `Deployments strategy rollingUpdate` | 같은 [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) 문서의 **Strategy**와 **Rolling Back a Deployment** 절에서 `type`, `maxUnavailable`, `maxSurge` 확인 |

문서 예시가 길면 먼저 `kubectl create deployment ... --dry-run=client -o yaml` 또는
`kubectl create job ... --dry-run=client -o yaml`로 골격을 만든 뒤, 문서에서 명령형 플래그로 만들 수 없는
`strategy` 같은 필드만 찾아 붙인다.


## 완료 판정

Deployment의 `AVAILABLE`만 보지 않고 `kubectl rollout status`가 성공한 뒤 새 Pod의
이미지와 Ready를 확인한다. 실패하면 Deployment condition → 가장 최근 ReplicaSet → 그 Pod의
Events·로그 순서로 내려간다. 정상 리비전으로 되돌린 뒤에도 같은 검증을 반복한다.

ReplicaSet의 template을 직접 바꾼 경우 기존 Pod은 자동 교체되지 않는다. 새 template으로 만든
Pod을 요구한다면 영향을 확인한 뒤 기존 Pod 재생성까지 수행하거나 Deployment로 관리한다.
