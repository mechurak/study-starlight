<Thesis>스토리지 실습은 공식 예제에서 PV·PVC 뼈대를 가져와 요구 필드만 남기고, 생성 뒤 바인딩 조건과 실제 마운트를 차례로 검증하는 문제다</Thesis>

> 짝이 되는 개념 장: [cka 13. 스토리지](/cka/13-storage/)

스토리지 실습의 핵심 질문은 하나다 — **"왜 Pending인가."**
PVC가 Pending인 이유가 랩마다 다르고, 그 차이가 곧 출제 포인트다.

:::tip[실습 전 확인]
PV(PersistentVolume)는 관리자가 준비한 저장 공간, PVC(PersistentVolumeClaim)는 앱의 요청,
StorageClass는 PVC가 사용할 **프로비저닝 방식과 바인딩 정책**을 묶은 규칙이다. 동적
프로비저너가 있으면 PV를 만들 수 있지만 `kubernetes.io/no-provisioner`는 만들지 않는다.
PVC가 `Pending`이면 **클래스 · access mode · 용량 · 셀렉터**가 맞는지 `describe pvc`의
Events에서 확인한다.
:::

## hostPath 로그 볼륨 — webapp

과제는 기존 `webapp` Pod의 로그를 **노드의 `/var/log/webapp` → 컨테이너의 `/log`**로
연결하는 것이다. Pod 수준의 `spec.volumes`가 저장소를 정의하고, 대상 컨테이너의
`volumeMounts`가 그 저장소를 어디에서 볼지 정한다. 두 블록의 `name: log-volume`이 연결 고리다 —
공식 [Volumes](https://kubernetes.io/docs/concepts/storage/volumes/#hostpath) 예시도 같은 구조다.

기존 Pod을 바탕으로 작업한다면 먼저 전체 스펙을 뽑는다.

```bash
kubectl get pod webapp -o yaml > webapp.yaml
```

처음부터 최소 골격을 만들고 싶다면 다음 명령으로 API 서버에 아무것도 생성하지 않은 채 YAML만
만든 뒤, 아래 완성본처럼 컨테이너 이름과 볼륨 두 블록을 고친다.

```bash
kubectl run webapp \
  --image=kodekloud/event-simulator \
  --env=LOG_HANDLERS=file \
  --dry-run=client -o yaml > webapp.yaml
```

완성된 `webapp.yaml`은 다음 네 값을 한 번에 만족해야 한다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webapp
spec:
  containers:
  - name: event-simulator
    image: kodekloud/event-simulator
    env:
    - name: LOG_HANDLERS
      value: file
    volumeMounts:
    - name: log-volume
      mountPath: /log
  volumes:
  - name: log-volume
    hostPath:
      path: /var/log/webapp
      type: Directory
```

[`LOG_HANDLERS=file`](https://github.com/kodekloudhub/event-simulator/blob/master/event-simulator.py)은
이 이미지가 로그를 `/log/app.log`에 쓰게 한다. 기존 Pod의 바꿀 수 없는 볼륨 스펙을 적용하려면
지운 뒤 다시 만드는 force replace를 사용한다. 공식
[`kubectl replace`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_replace/)에서
`--force`도 **delete 후 create**로 정의한다.

```bash
kubectl replace -f webapp.yaml --force
kubectl wait --for=condition=Ready pod/webapp --timeout=60s

# 저장소와 마운트 경로가 올바르게 연결됐는지
kubectl get pod webapp -o jsonpath='{.spec.volumes[?(@.name=="log-volume")].hostPath.path}{" -> "}{.spec.containers[0].volumeMounts[?(@.name=="log-volume")].mountPath}{"\n"}'

# 파일 로그가 실제로 기록되는지
kubectl exec webapp -- sh -c 'test -s /log/app.log && tail -n 3 /log/app.log'
```

:::caution[함정 — Directory는 경로를 만들지 않는다]
`hostPath.type: Directory`는 **스케줄된 노드에 그 디렉터리가 이미 있어야** 한다. Pod이
`ContainerCreating`에 머물면 `kubectl describe pod webapp`의 Events에서 `FailedMount`를 확인한다.
`DirectoryOrCreate`는 경로를 만들지만, 문제에서 `Directory`를 요구했다면 임의로 바꾸지 않는다.
또한 `LOG_HANDLERS=file`이면 표준 출력 로그가 없을 수 있으므로 `kubectl logs`만으로 실패라고
판정하지 말고 `/log/app.log`를 확인한다.
:::

## PV와 PVC — Practice Test: Persistent Volume Claims

원본 풀이: [10-Practice-Test-Persistent-Volume-Claims.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/08-Storage/10-Practice-Test-Persistent-Volume-Claims.md)

흐름: 바로 위의 Pod 직접 hostPath → PV(PersistentVolume) → PVC(PersistentVolumeClaim) → Pod 마운트.
PV와 PVC에는 `kubectl create deployment` 같은 전용 명령형 생성기가 없다. 공식
[`kubectl create`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/)도 파일이나
표준 입력으로 매니페스트를 받으므로 YAML로 푸는 편이 빠르고 검증하기 쉽다.

### 시험장에서 뼈대와 필드 찾기

공식 문서 검색창에서 `configure persistent volume storage`를 찾으면
[Configure a Pod to Use a PersistentVolume for Storage](https://kubernetes.io/docs/tutorials/configuration/configure-persistent-volume-storage/)의
**Create a PersistentVolume → Create a PersistentVolumeClaim → Create a Pod** 순서에 세 YAML이 모두
있다. 예제 전체를 그대로 남기지 말고 이름·용량·access mode·스토리지 구현처럼 **문제가 요구한
필드만 대입**한다. 예제의 `storageClassName: manual`도 문제에서 클래스를 지정할 때만 남긴다.

필드 철자가 기억나지 않으면 인터넷을 헤매기 전에 클러스터의 OpenAPI 스키마를 조회한다.

```bash
# 전체 필드에서 less의 /reclaim 검색으로 정확한 camelCase를 찾는다
kubectl explain pv.spec --recursive | less
kubectl explain pvc.spec --recursive | less

# 찾은 필드의 설명·허용 값을 좁혀 본다
kubectl explain pv.spec.persistentVolumeReclaimPolicy
kubectl explain pvc.spec.resources.requests
```

PV에서는 긴 이름 `spec.persistentVolumeReclaimPolicy`, StorageClass에서는 짧은 이름
`reclaimPolicy`를 쓴다. PV의 값은 `Retain`·`Delete`·deprecated된 `Recycle`이며, 정확한 enum과
기본값은 공식 [PersistentVolume API](https://kubernetes.io/docs/reference/kubernetes-api/core/persistent-volume-v1/)에서도
확인할 수 있다. 문제에서 `Retain`을 명시했다면 기본값에 기대지 말고 YAML에도 명시한다.

### 1. PV 생성 — 관리자 쪽 저장 공간

`pv-log`는 네임스페이스에 속하지 않는 클러스터 범위 리소스다. 따라서 `-n` 없이 만들고 조회한다.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-log
spec:
  capacity:
    storage: 100Mi
  accessModes:
  - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /pv/log
```

```bash
kubectl create --dry-run=server -f pv-log.yaml
kubectl create -f pv-log.yaml
kubectl get pv pv-log
```

깨끗한 랩이라면 아직 claim이 없으므로 `Available`이 정상이다. 이미 조건이 맞는 PVC가 있으면 곧바로
`Bound`가 될 수 있으므로 상태 이름 하나만 외우지 말고 `CLAIM` 열도 함께 본다.

### 2. PVC 생성 — 앱의 요청

PVC는 네임스페이스 범위 리소스다. 다음 첫 요청은 문제의 값 그대로 `50Mi`와 `ReadWriteOnce`를 쓴다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: claim-log-1
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 50Mi
```

```bash
kubectl create --dry-run=server -f claim-log-1.yaml
kubectl create -f claim-log-1.yaml
kubectl get pv,pvc
kubectl describe pvc claim-log-1
```

공식 PVC 예제에서 `storageClassName: manual`을 복사해 왔다면 앞의 class 없는 `pv-log`와 묶이지
않는다. 반대로 클러스터에 default StorageClass가 있으면 생략한 PVC에 클래스가 자동 지정될 수 있다.
예상과 다르면 먼저 실제 저장값과 기본 클래스를 확인한다.

```bash
kubectl get pvc claim-log-1 -o jsonpath='{.spec.storageClassName}{"\n"}'
kubectl get storageclass
```

명시적으로 class 없는 PV만 요청해야 하는 환경에서는 PVC에 `storageClassName: ""`를 둔다. 다만
이 랩처럼 제공된 요구사항과 정답이 필드를 생략한다면 불필요한 값을 먼저 추가하지 않는다.

:::tip[`volumeName`을 생략하라는 문제]
`spec.volumeName`은 특정 PV에 미리 바인딩할 때 쓰는 필드다. 공식
[Persistent Volumes — Volume Name](https://v1-35.docs.kubernetes.io/docs/concepts/storage/persistent-volumes/#volume-name)처럼
이를 생략하면 컨트롤 플레인이 class·access mode·용량에 맞는 PV를 고르거나 동적 프로비저닝을
요청한다. `Do not use the volumeName field`가 있으면 작성하는 PVC YAML에서 필드 자체를 빼고,
`Pending`을 없애려고 조회한 PV 이름을 임의로 넣지 않는다.
:::

:::caution[함정 1 — access mode는 크기 비교가 아니다]
`pv-log`는 `ReadWriteMany`, `claim-log-1`은 `ReadWriteOnce`만 선언했으므로 용량이 맞아도
**Pending**이다. `ReadWriteMany`가 `ReadWriteOnce`를 포함하는 상위 등급처럼 보이지만, 바인더는
PVC가 요청한 mode 문자열이 PV의 `accessModes` 목록에 실제로 있는지 확인한다. 원인은
`kubectl describe pvc claim-log-1`의 Events에서 좁힌다.
:::

### 3. mode를 맞춘 뒤 Pod에서 사용

이 랩 흐름에서 claim을 실제로 묶으려면 `claim-log-1.yaml`의 mode를 `ReadWriteMany`로 고친 뒤
Pending PVC를 다시 만든다.

```bash
kubectl delete pvc claim-log-1
# claim-log-1.yaml: ReadWriteOnce → ReadWriteMany
kubectl create -f claim-log-1.yaml
kubectl get pv,pvc
```

바인딩 뒤 Pod에는 PVC 이름만 연결한다. Pod은 `hostPath` 같은 실제 구현을 알 필요가 없다.

```yaml
  volumes:
  - name: log-volume
    persistentVolumeClaim:
      claimName: claim-log-1
```

:::caution[함정 2 — 바인딩되면 용량은 PV 것]
50Mi를 요청해도 100Mi PV에 묶이면 **PVC의 CAPACITY는 100Mi**다. PV는 쪼개지지 않는다.
:::

사용 중인 PVC를 지우면 — `Terminating`에 **멈춘 채 대기**한다 (Pod이 쓰고 있는 동안).
Pod을 지우면 그제야 삭제되고, PV는 reclaim 정책이 `Retain`이면 `Released`가 된다 —
**다시 쓸 수 있는 상태가 아니다** (Available로 안 돌아온다).

## StorageClass — Practice Test: Storage Class

원본 풀이: [13-Practice-Test-Storage-Class.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/08-Storage/13-Practice-Test-Storage-Class.md)

이 랩은 **기존 StorageClass를 요청하는 PVC → 그 PVC를 소비하는 Pod → 새 StorageClass** 순서다.
리소스 이름이 비슷해도 `local-path`가 어떤 프로비저너를 쓰는지는 이름만 보고 단정하지 않고 실제
오브젝트를 조회한다.

```bash
kubectl get storageclass
kubectl get storageclass local-path -o yaml
kubectl get pv
```

### 1. 기존 클래스 요청 — local-pvc

PVC에는 전용 명령형 생성기가 없으므로 요구한 네 값을 YAML에 직접 옮긴다. 특정 PV를 지목하는
`volumeName`은 넣지 않는다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-pvc
spec:
  storageClassName: local-path
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 500Mi
```

```bash
kubectl create -f local-pvc.yaml
kubectl get pvc local-pvc
kubectl describe pvc local-pvc
```

여기서 `Pending`을 곧바로 실패로 판정하지 않는다. 먼저 `local-path`의 `volumeBindingMode`와 PVC
Events를 확인한다. `WaitForFirstConsumer`라면 이 PVC를 쓰는 Pod이 아직 없어서 기다리는 중이다.

### 2. 소비 Pod 생성 — nginx

`kubectl run`에는 PVC와 마운트 경로를 받는 전용 플래그가 없다. 공식
[`kubectl run`](https://v1-35.docs.kubernetes.io/docs/reference/kubectl/generated/kubectl_run/)의
`--dry-run=client -o yaml`로 이름과 이미지를 먼저 만든 뒤 `volumeMounts`와 `volumes`를 추가한다.
`--overrides`에 JSON을 전부 넣을 수도 있지만 시험장에서는 YAML을 고치는 편이 읽고 검증하기 쉽다.

```bash
kubectl run nginx --image=nginx:alpine --dry-run=client -o yaml > nginx.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:alpine
    volumeMounts:
    - name: local-persistent-storage
      mountPath: /var/www/html
  volumes:
  - name: local-persistent-storage
    persistentVolumeClaim:
      claimName: local-pvc
```

`volumeMounts[].name`과 `volumes[].name`은 Pod 안의 연결 고리라 서로 같아야 한다. 실제 PVC를
고르는 값은 별도의 `persistentVolumeClaim.claimName: local-pvc`다. 뼈대가 만든 라벨이나
`restartPolicy`는 문제에서 다른 값을 요구하지 않는 한 그대로 둬도 된다.

```bash
kubectl create -f nginx.yaml
kubectl wait --for=condition=Ready pod/nginx --timeout=60s
kubectl get pvc local-pvc
kubectl describe pod nginx
```

Pod 생성 뒤 `local-pvc`가 `Bound`, Pod이 `Running`인지 함께 본다. `WaitForFirstConsumer`였다면
이때 스케줄러가 소비 노드를 고르면서 바인딩이 진행된다.

### 3. 로컬 PV용 클래스 생성 — delayed-volume-sc

공식 [Storage Classes — Local](https://v1-35.docs.kubernetes.io/docs/concepts/storage/storage-classes/#local)의
예제가 이 문제의 뼈대다. 이름만 문제의 값으로 바꾼다.

| 필드 | 여기서의 의미 |
|---|---|
| `provisioner: kubernetes.io/no-provisioner` | 컨트롤러가 PV를 자동 생성하지 않음 — 조건에 맞는 local PV를 관리자가 미리 준비 |
| `volumeBindingMode: WaitForFirstConsumer` | 소비 Pod의 스케줄 조건을 알 때까지 준비된 PV의 선택·바인딩을 미룸 |

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: delayed-volume-sc
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
```

:::caution[함정 — WaitForFirstConsumer의 Pending은 정상이다]
`volumeBindingMode: WaitForFirstConsumer`인 클래스의 PVC는 **그 PVC를 쓰는 Pod이
스케줄될 때까지 Pending이 정상**이다. "왜 Pending인가"에 대한 답이
7장 첫 랩(accessModes 불일치)과 다르다는 것 — 이 대비가 두 랩의 출제 의도다.
다만 `no-provisioner`는 PV를 만들지 않으므로 Pod을 만든 뒤에도 조건에 맞는 PV가 없으면 계속
Pending이다. 또한 Pod의 `spec.nodeName`은 스케줄러를 우회하므로 이 모드와 함께 쓰지 않는다.
노드를 제한해야 하면 `nodeSelector`나 affinity를 쓴다.
:::

## 정적·동적 프로비저닝 완료 판정

### 정적 PV — Bound 뒤에 실제 마운트까지

`PV=Bound`, `PVC=Bound`는 클래스·access mode·용량 같은 **API 바인딩 조건**을 통과했다는 뜻이다.
NFS 서버 주소·export 경로나 노드의 `/sbin/mount.nfs`까지 검증한 것은 아니다. 소비 Pod을 만들어
마운트하고 파일을 읽고 써야 정적 프로비저닝 완료를 증명한다.

```bash
# 1) 바인딩과 claim 연결
kubectl get pv,pvc
kubectl describe pvc <claim>

# 2) 실제 마운트 — 실패하면 Pod Events에서 서버·경로·mount helper를 확인
kubectl get pod <pod> -o wide
kubectl describe pod <pod>

# 3) 컨테이너가 마운트한 경로에 실제로 읽고 쓸 수 있는가
kubectl exec <pod> -- sh -c 'echo storage-ok > /data/probe && cat /data/probe'
```

NFS는 모든 소비 노드에서 서버 export에 닿아야 하고 NFS mount helper도 있어야 한다. `Bound`인데
Pod이 `ContainerCreating`이면 PVC를 다시 만들기 전에 Pod Events와 해당 노드의 kubelet 로그를 본다.
공식 [Persistent Volumes](https://v1-35.docs.kubernetes.io/docs/concepts/storage/persistent-volumes/#types-of-persistent-volumes)에도
NFS PV를 마운트하려면 `/sbin/mount.nfs` 같은 helper가 필요하다고 명시돼 있다.

### 동적 프로비저닝 — 생성 주체까지 추적

동적 프로비저닝은 **StorageClass 오브젝트 자체가 PV를 만드는 것이 아니다.** `provisioner` 필드와 같은
이름으로 동작하는 컨트롤러가 PVC를 보고 백엔드 볼륨과 PV를 만든다. 특히 NFS에는 Kubernetes 내장
프로비저너가 없으므로 외부 프로비저너나 CSI 드라이버가 실제로 실행 중이어야 한다.

```bash
# 1) 클래스 이름·provisioner·binding mode
kubectl get sc <class> -o yaml

# 2) PVC Events에서 누구를 기다리는지 확인
kubectl describe pvc <claim>

# 3) 동적으로 생긴 PV와 생성 주체 확인
kubectl get pv
kubectl get pv <pv> -o jsonpath='{.metadata.annotations.pv\.kubernetes\.io/provisioned-by}{"\n"}'

# 4) Bound 뒤에도 소비 Pod의 마운트와 읽기·쓰기를 확인
kubectl describe pod <pod>
kubectl exec <pod> -- sh -c 'echo dynamic-ok > /data/probe && cat /data/probe'
```

PVC가 계속 `Pending`이면 다음 순서로 범위를 줄인다.

1. `storageclass not found` — PVC의 `storageClassName` 오타 또는 클래스 없음
2. `waiting for first consumer` — `WaitForFirstConsumer`의 정상 대기. PVC를 쓰는 Pod을 만든다
3. `waiting for a volume to be created ... by external provisioner` — provisioner 이름이 맞는지,
   컨트롤러 Pod이 Running인지, 컨트롤러 로그에 백엔드·권한 오류가 있는지 확인
4. PVC는 `Bound`인데 Pod이 멈춤 — 프로비저닝이 아니라 노드 attach·mount 층의 문제다

세부 필드와 외부 프로비저너의 경계는 공식
[Storage Classes](https://v1-35.docs.kubernetes.io/docs/concepts/storage/storage-classes/)에서 확인한다.

## 스토리지 quota 검증

스토리지 quota는 네임스페이스의 PVC **개수와 요청 용량 합**을 admission에서 제한한다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
spec:
  hard:
    persistentvolumeclaims: "5"
    requests.storage: 20Gi
    fast.storageclass.storage.k8s.io/persistentvolumeclaims: "3"
    fast.storageclass.storage.k8s.io/requests.storage: 10Gi
```

```bash
kubectl describe quota storage-quota -n <namespace>   # Used / Hard
kubectl create -f pvc.yaml -n <namespace>             # 초과 시 즉시 Forbidden
```

`requests.storage`의 `Used`는 PVC의 `spec.resources.requests.storage` 합이다. 마운트 안에 큰 파일을
써도 이 값은 늘지 않는다. 즉 quota가 통과했다는 사실은 NFS 공유의 실제 용량 제한이나 여유 공간을
증명하지 않는다. 클래스별 키를 쓰면 비싼 클래스와 일반 클래스를 따로 제한할 수 있다. 정확한 키는
공식 [Resource Quotas](https://v1-35.docs.kubernetes.io/docs/concepts/policy/resource-quotas/#quota-for-storage)에서
확인한다.

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| Pod hostPath | `Volumes hostPath` | [Volumes — hostPath](https://kubernetes.io/docs/concepts/storage/volumes/#hostpath)에서 `spec.volumes`와 `containers[].volumeMounts`, `type`의 의미 |
| PV·PVC·Pod | `Configure PersistentVolume Storage` | [Configure a Pod to Use a PersistentVolume for Storage](https://kubernetes.io/docs/tutorials/configuration/configure-persistent-volume-storage/) 한 페이지에서 PV, PVC, `persistentVolumeClaim` 볼륨의 세 YAML |
| 바인딩·reclaim 진단 | `Persistent Volumes` | [Persistent Volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)에서 바인딩 조건과 claim 상태를 보고, [PersistentVolume API](https://kubernetes.io/docs/reference/kubernetes-api/core/persistent-volume-v1/)에서 `persistentVolumeReclaimPolicy`의 정확한 enum 확인 |
| StorageClass·동적 프로비저닝 | `Storage Classes` | [Storage Classes](https://v1-35.docs.kubernetes.io/docs/concepts/storage/storage-classes/)에서 필드 구조를, [Local](https://v1-35.docs.kubernetes.io/docs/concepts/storage/storage-classes/#local)에서 `no-provisioner`와 `WaitForFirstConsumer` 조합을 확인 |
| 스토리지 quota | `Resource Quotas storage` | [Resource Quotas — Storage Resource Quota](https://kubernetes.io/docs/concepts/policy/resource-quotas/#storage-resource-quota)의 전체·클래스별 `spec.hard` 키 |

PV/PVC 문제에서는 문서 예시를 통째로 복사한 뒤 **스토리지 구현 필드만** 문제에 맞게 바꾼다.
예를 들어 `hostPath`, `nfs`, `csi`는 같은 위치의 대안이므로 둘 이상을 함께 남기면 안 된다.

## 이 장에서 남길 것

- Pod 볼륨은 **`spec.volumes` 정의 ↔ `containers[].volumeMounts` 사용**을 같은 `name`으로 연결
- `hostPath.type: Directory`는 노드 경로를 만들지 않으며, 파일 로그는 마운트 안에서 직접 검증
- PV/PVC YAML은 공식 문서의 `Configure Persistent Volume Storage`, 필드 철자는 `kubectl explain`
- `volumeName`을 생략하면 특정 PV를 선점하지 않고 바인더의 선택·프로비저닝에 맡긴다
- PV는 `persistentVolumeReclaimPolicy`, StorageClass는 `reclaimPolicy` — `Recycle`은 deprecated
- PVC Pending의 원인은 둘 — **맞는 PV가 없다** vs **WaitForFirstConsumer 대기**
- 바인딩 조건: accessModes · 용량 · storageClassName — access mode는 상하 관계가 아닌 정확한 목록 값
- PVC를 쓰는 Pod은 `kubectl run`으로 뼈대를 만들고 `volumeMounts` ↔ `volumes`를 같은 이름으로 연결
- `Bound`는 바인딩 성공일 뿐 — 소비 Pod의 **mount와 읽기·쓰기**까지 확인
- 바인딩 후 용량은 PV 기준, PV는 Released여도 자동 재사용 안 됨
- `no-provisioner` = 동적 프로비저닝 불가 = PV를 손으로 만들어야 한다
- `WaitForFirstConsumer` = Pod 스케줄 때까지 바인딩 지연 — PV 생성 기능은 아니다
- 동적 Pending은 **StorageClass → provisioner 컨트롤러 → PVC Events → Pod mount** 순서로 좁힌다
- 스토리지 quota는 **PVC 요청 용량·개수**를 세며 실제 파일 사용량은 세지 않는다
