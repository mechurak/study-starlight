<Thesis>Pod 배치는 라벨로 고른 후보와 taint를 견디는 후보의 교집합을 만들고, 실제 nodeName과 Ready 상태로 증명하는 작업이다.</Thesis>

> 짝이 되는 개념 장: [CKA 스케줄링](/cka/scheduling/)

이 장의 과제는 Pod을 요구한 노드에 놓고 그 결과를 확인하는 것이다. `nodeName`은 스케줄러를
건너뛰는 직접 지정이고, `nodeSelector`·node affinity는 Pod 쪽 조건이며, taint는 노드 쪽 거부
조건이다. toleration은 거부를 견딜 뿐 그 노드를 선택하지는 않는다.

먼저 명령으로 현재 라벨과 taint를 읽고, 필요한 필드를 Pod 스펙에 넣는다. 마지막에는
`spec.nodeName`이 기대한 노드인지, Pod이 `Running`·`Ready`인지 확인한다. Pending이면 아직 실행된
컨테이너가 없을 수 있으므로 로그가 아니라 Events에서 탈락 조건을 찾는다.

## 수동 배치 — Practice Test: Manual Scheduling

원본 풀이: [03-Practice-Test-Manual-Scheduling.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/03-Practice-Test-Manual-Scheduling.md)

스케줄러가 없는 클러스터에서 Pod이 Pending에 머무르면 `spec.nodeName`을 직접 채워 배치한다.

```yaml
spec:
  nodeName: node01
  containers:
    - image: nginx
      name: nginx
```

`nodeName`이 있으면 스케줄러는 이 Pod을 처리하지 않고, 지정한 노드의 kubelet이 실행을 시도한다.
존재하지 않는 노드나 자원이 모자란 노드를 지정해도 다른 노드를 다시 고르지 않는다.

:::caution[기존 Pod은 재생성한다]
이미 생성된 Pod의 `nodeName`은 바꿀 수 없다. YAML을 수정한 뒤
`kubectl replace --force -f nginx.yaml`처럼 기존 Pod을 지우고 다시 만든다. Deployment 소유 Pod이라면
개별 Pod이 아니라 `spec.template.spec`을 수정해 새 Pod을 만들게 한다.
:::

## 라벨과 셀렉터 — Practice Test: Labels and Selectors

원본 풀이: [05-Practice-Test-Labels-and-Selectors.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/05-Practice-Test-Labels-and-Selectors.md)

```bash
kubectl get pods --selector env=dev
kubectl get all --selector env=prod,bu=finance,tier=frontend
kubectl get pods -l env=dev --no-headers | wc -l
```

`--selector`와 `-l`은 같다. 쉼표로 나열한 equality 조건은 모두 만족해야 한다. “Pod, ReplicaSet을
포함한 모든 오브젝트”를 세라는 문제라면 `get pods`가 아니라 `get all`을 사용한다.

## taint와 toleration — Practice Test: Taints and Tolerations

원본 풀이: [07-Practice-Test-Taints-and-Tolerations.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/07-Practice-Test-Taints-and-Tolerations.md)

```bash
kubectl describe node node01 | grep -i taints
kubectl taint nodes node01 spray=mortein:NoSchedule
kubectl taint nodes controlplane node-role.kubernetes.io/control-plane:NoSchedule-
```

taint 제거는 명령 끝에 `-`를 붙인다. 원본 풀이의 옛 `master` 키 대신 현재 컨트롤 플레인 키
`node-role.kubernetes.io/control-plane`을 먼저 조회해 사용한다.

toleration은 containers와 같은 Pod 스펙 수준에 넣는다.

```yaml
spec:
  tolerations:
    - key: spray
      operator: Equal
      value: mortein
      effect: NoSchedule
  containers:
    - image: nginx
      name: bee
```

:::caution[toleration은 유도가 아니다]
toleration은 taint가 있는 노드에도 갈 수 있게 할 뿐 그 노드로 배치를 보장하지 않는다. 특정 노드를
골라야 한다면 nodeSelector나 affinity 같은 선택 조건도 함께 둔다.
:::

### 라벨과 taint는 교집합으로 판정한다

다음 Pod은 `workload=batch` 라벨이 있고 `reserved=batch:NoSchedule` taint도 견디는 노드에만
배치될 수 있다.

```yaml
spec:
  nodeSelector:
    workload: batch
  tolerations:
    - key: reserved
      operator: Equal
      value: batch
      effect: NoSchedule
```

```bash
kubectl get pod placement-check \
  -o jsonpath='{.spec.nodeSelector}{"\n"}{.spec.tolerations}{"\n"}'
kubectl get nodes -l workload=batch --show-labels
kubectl describe node <candidate-node> | grep -A3 Taints
kubectl get pod placement-check \
  -o custom-columns='NAME:.metadata.name,NODE:.spec.nodeName,PHASE:.status.phase'
kubectl describe pod placement-check
kubectl get events --field-selector involvedObject.name=placement-check \
  --sort-by=.lastTimestamp
```

`nodeName`이 비고 Events에 `didn't match Pod's node affinity/selector`가 나오면 라벨 후보가 없고,
`had untolerated taint`면 후보에 견디지 못한 taint가 남은 것이다. 두 조건을 따로 고친 뒤 다시 확인한다.

:::tip[Pending에서는 로그보다 Events]
아직 노드가 정해지지 않은 Pod에는 실행된 컨테이너가 없다. `nodeName`이 채워진 뒤
`ContainerCreating`이나 `CrashLoopBackOff`로 실패하면
[로그 진단](/cka-udemy/troubleshooting/#증상에-맞는-로그-진입점을-고른다)으로 넘긴다.
:::

## nodeAffinity — Practice Test: Node Affinity

원본 풀이: [10-Practice-Test-Node-Affinity.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/03-Scheduling/10-Practice-Test-Node-Affinity.md)

```bash
kubectl get node node01 --show-labels
kubectl label node node01 color=blue
```

필수 조건은 `requiredDuringSchedulingIgnoredDuringExecution`, 선호 조건은
`preferredDuringSchedulingIgnoredDuringExecution`이다. Deployment라면 아래 블록을
`spec.template.spec` 아래에 둔다.

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: color
              operator: In
              values:
                - blue
```

값이 아니라 라벨 존재만 검사할 때는 `operator: Exists`를 쓴다. required와 preferred 모두 이름의
`IgnoredDuringExecution`대로 배치 뒤 노드 라벨이 바뀌어도 실행 중인 Pod을 자동 퇴거시키지는 않는다.

## 완료 판정

```bash
kubectl get pod placement-check -o wide
kubectl wait --for=condition=Ready pod/placement-check --timeout=90s
```

- `NODE`가 요구한 노드이고 Pod이 `Running`·`Ready`다.
- Pending이라면 Events의 라벨·affinity·taint 원인을 구분해 수정했다.
- Deployment 문제라면 개별 Pod이 아니라 Pod 템플릿에 조건이 남아 있다.
