<Thesis>Kustomize 실습은 resources로 대상을 모으고, 요구 범위에 맞는 설정에 변환을 적은 뒤 최종 YAML과 적용 결과를 검증한다</Thesis>

여러 폴더에 흩어진 리소스를 한 번에 적용하려면, 어떤 파일을 묶을지 적은 목록이 필요하다.
`kustomization.yaml`이 그 목록이고, Kustomize가 읽어 최종 리소스 YAML을 만든 다음
`kubectl`이 클러스터에 보낸다. 파일을 작성하는 것과 실제 적용하는 것은 별도 단계다.

이 장은 리소스를 한 목록으로 묶고 이름·라벨·이미지 등을 변환하거나 패치로 특정 항목을 삭제하는 실습과, 문법이 기억나지 않을 때 시험에서 확인할 수 있는
범위를 다룬다. base·overlay·patch의 원리는
[cka 16장 — Kustomize](/cka/16-helm-kustomize/#kustomize)에서 이어 본다.

## 여러 폴더의 리소스를 하나로 묶기

상황: `/root/code/k8s` 아래 `db`, `message-broker`, `nginx`에 있는 리소스를
루트의 **단일 `kustomization.yaml`로 묶고 적용**해야 한다.
기존 YAML을 복사해 합칠 필요는 없고, 파일 경로를 나열하면 된다.
공식 문서의 [Composing 예제](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#composing)도 이 방식을 사용한다.

<Steps>

1. **대상 파일 확인**

   ```bash
   cd /root/code/k8s
   find . -name '*.yaml'
   ```

   `*.yaml`을 따옴표로 감싸야 셸이 먼저 펼치지 않고 `find`가 검색 패턴으로 받는다.
   출력 경로를 복사해 아래 목록에 넣는다. `kustomization.yaml` 자체나 패치 전용 파일은 제외한다.

2. **루트에 설정 작성**

   `/root/code/k8s/kustomization.yaml`을 다음처럼 작성한다.

   ```yaml
   apiVersion: kustomize.config.k8s.io/v1beta1
   kind: Kustomization

   resources:
     - db/db-config.yaml
     - db/db-depl.yaml
     - db/db-service.yaml
     - message-broker/rabbitmq-config.yaml
     - message-broker/rabbitmq-depl.yaml
     - message-broker/rabbitmq-service.yaml
     - nginx/nginx-depl.yaml
     - nginx/nginx-service.yaml
   ```

   경로는 **이 설정 파일이 있는 디렉터리 기준**이다. `./db/db-config.yaml`도 같은 경로다.
   이 문제에는 이름·이미지 변경이나 overlay가 필요하지 않다.

3. **미리보기 후 적용**

   ```bash
   kubectl kustomize .
   kubectl apply -k .
   kubectl get -k .
   ```

   첫 명령에서 파일 누락·YAML 오류가 없고 의도한 리소스가 모두 나오는지 확인한다.
   적용 뒤에는 마지막 명령으로 해당 리소스가 실제로 존재하는지 확인한다.

</Steps>

## Transformer는 적용 범위부터 고른다

Transformer는 모아 둔 리소스의 이름·라벨·이미지 같은 필드를 일괄 변환하는 기능이다.
문제에서 먼저 찾을 것은 **무엇을 바꾸는가**와 **어디까지 바꾸는가**다.
전체 프로젝트이면 루트 설정, db만이면 db 설정, nginx와 monitoring만이면 두 설정을 고른다.

이후 실습은 앞의 단일 파일 실습과 달리 **하위 폴더에도 `kustomization.yaml`이 있는 구조**다.
루트가 다음처럼 각 하위 설정을 참조하고, db는 다시 sql·nosql의 리소스를 모은다고 가정한다.
실제 랩의 기존 `resources`를 먼저 읽고, 아래 예제로 통째로 덮어쓰지 않는다.

```yaml
# k8s/kustomization.yaml의 resources 예시
resources:
  - db
  - message-broker
  - nginx
  - monitoring
```

**범위는 파일시스템의 하위 폴더 전체가 아니라 `resources`를 따라 모인 리소스다.**
루트가 `db/db-depl.yaml` 같은 원본 파일을 직접 참조하면 `db/kustomization.yaml`에 적힌
변환은 거치지 않는다. db 설정을 적용하려면 루트에서 `db` 디렉터리를 참조해야 한다.
([공식 문서 — Bases and Overlays](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#bases-and-overlays))

| 문제의 대상 | 확인·수정할 파일 | 필드와 답 |
|---|---|---|
| 전체 리소스의 라벨 조회 | `k8s/kustomization.yaml` | `commonLabels` → `sandbox: dev` |
| sql·nosql을 포함한 db의 접두사 조회 | `k8s/db/kustomization.yaml` | `namePrefix` → `data-` |
| monitoring의 네임스페이스 조회 | `k8s/monitoring/kustomization.yaml` | `namespace` → `logging` |
| nginx·monitoring에만 annotation 추가 | 두 폴더의 `kustomization.yaml` | `commonAnnotations` → `owner: bob@gmail.com` |
| 프로젝트 전체 postgres 이미지 교체 | `k8s/kustomization.yaml` | `images`의 `newName: mysql` |
| nginx 폴더의 nginx 태그 변경 | `k8s/nginx/kustomization.yaml` | `images`의 `newTag: "1.23"` |

질문 2~4처럼 **현재 값을 묻는 문제에서는 수정하지 않는다**. 설정을 읽고 렌더된 결과로
확인한다. 질문 5~7처럼 변경을 요구하면 기존 키에 내용을 병합하고, 같은 YAML 키를 두 번
만들지 않는다. 아래 코드들은 각 파일의 최상위에 들어갈 **관련 필드만 발췌한 것**이다.

### 전체 라벨 — commonLabels 읽기

```yaml
# k8s/kustomization.yaml
commonLabels:
  sandbox: dev
```

답은 키와 값을 함께 읽은 **`sandbox: dev`**다. 이 변환은 리소스의 `metadata.labels`뿐 아니라
Deployment·Service의 selector와 Pod template 라벨 등에도 반영된다.
현행 문서의 [Setting cross-cutting fields](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#setting-cross-cutting-fields)는
다음 `labels` 형식을 사용한다. `commonLabels`는 deprecated이지만 기존 랩에서는 만날 수 있다.
([공식 소스의 deprecated 표시 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/api/types/kustomization.go))

```yaml
# 새로 작성할 때 commonLabels와 같은 selector 반영을 원하면
labels:
  - pairs:
      sandbox: dev
    includeSelectors: true
```

두 형식을 동시에 추가하지 않는다. `labels`는 기본으로 selector를 바꾸지 않으므로
`includeSelectors: true`를 빼면 같은 동작이 아니다.
실습이 기존 값을 묻거나 특정 필드 사용을 요구하면 그 형식을 따른다.

:::caution[함정 — 라벨 추가가 selector 변경이 될 수 있다]
이미 배포된 Deployment의 selector는 변경할 수 없다. `commonLabels` 또는
`includeSelectors: true`를 나중에 추가해 적용하면 immutable 오류가 날 수 있다.
`kubectl diff -k .`에서 selector까지 달라지는지 보고, 라벨만 필요한 요구라면 selector 변경을
피하는 `labels` 설정을 검토한다. 오류를 없애려고 Deployment부터 삭제하지 않는다.
:::

### db 이름의 접두사 — namePrefix

```yaml
# k8s/db/kustomization.yaml
namePrefix: data-
```

답은 **`data-`**다. db의 `resources`가 sql과 nosql을 모두 참조하면 양쪽에 적용된다.
예를 들어 `metadata.name: postgres`는 `data-postgres`가 된다.
루트에 쓰면 다른 서비스의 이름도 바뀌므로 db 범위를 벗어난다.
접두사는 컨테이너 이미지 이름을 바꾸는 설정이 아니다.

### monitoring 네임스페이스 — namespace

```yaml
# k8s/monitoring/kustomization.yaml
namespace: logging
```

답은 **`logging`**이다. monitoring에서 모은 Deployment·Service 같은 네임스페이스 소속
리소스에 적용된다. ClusterRole 같은 클러스터 범위 리소스를 네임스페이스 소속으로 바꾸지는 않는다.
또한 이 필드만으로 Namespace 오브젝트가 생성되지는 않는다.
적용을 요구받았다면 `kubectl get namespace logging`으로 존재 여부를 확인하고,
필요한 Namespace 생성은 문제의 요구에 맞춰 처리한다.

### 두 그룹에만 annotation — commonAnnotations

```yaml
# k8s/nginx/kustomization.yaml과
# k8s/monitoring/kustomization.yaml 각각에 추가
commonAnnotations:
  owner: bob@gmail.com
```

루트에 넣으면 db·message-broker까지 영향을 받는다.
두 하위 설정에 각각 추가하고, 전체 렌더 결과의 `metadata.annotations.owner`를 확인한다.
nginx·monitoring에 값이 생겼는지와 함께 다른 그룹에는 이번 변경이 들어가지 않았는지도 본다.

## 이미지 변환 — newName과 newTag 구분하기

`images`의 `name`은 **변경할 기존 이미지 이름을 찾는 키**다. Deployment 이름이나
`containers[].name`을 넣는 자리가 아니다.
`newName`은 이미지 이름 교체, `newTag`는 태그 교체다.
([공식 문서 — Customizing의 images 예제](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#customizing))

### 전체 postgres를 mysql로 교체

```yaml
# k8s/kustomization.yaml
images:
  - name: postgres
    newName: mysql
```

루트가 모은 리소스에서 `postgres` 이미지가 바뀐다. `postgres`는 `mysql`이 되며,
`postgres:15`처럼 태그가 있었다면 `mysql:15`로 **기존 태그가 유지**된다.
`newName`만으로 새 이미지에 적합한 태그를 골라 주지는 않는다.
`registry.example.com/postgres`처럼 경로가 붙은 이미지라면 실제 이미지 이름에 맞춰 `name`도 확인한다.

:::caution[함정 — 이미지 변환은 DB 마이그레이션이 아니다]
이 문제는 이미지 문자열 변환 연습이다. PostgreSQL의 데이터·환경변수·포트·볼륨 구성이
MySQL용으로 바뀌지는 않는다. 렌더 성공과 애플리케이션 기동 성공을 구분하고,
실제 적용까지 요구받았다면 변경된 이미지의 존재 여부와 워크로드 상태도 확인한다.
:::

### nginx 폴더의 nginx 태그만 변경

```yaml
# k8s/nginx/kustomization.yaml
images:
  - name: nginx
    newTag: "1.23"
```

이미지 이름은 유지하고 태그만 `1.23`으로 바꾼다. 태그는 문자열이므로 따옴표로 감싼다.
루트에 쓰면 다른 그룹에서 사용하는 nginx까지 바뀔 수 있다.

### 하위 결과와 전체 결과를 모두 확인

```bash
cd /root/code/k8s
kubectl kustomize db
kubectl kustomize nginx
kubectl kustomize monitoring
kubectl kustomize .
```

하위 렌더에서는 해당 그룹의 변경을, **마지막 루트 렌더에서는 부모 변환까지 반영된 결과**를 본다.
원본 YAML 파일이 그대로인 것은 정상이다. Kustomize는 원본을 덮어쓰지 않고 결과를 생성한다.
확인할 필드는 `metadata.labels`, `metadata.name`, `metadata.namespace`,
`metadata.annotations`, `spec.template.spec.containers[].image`다.

하위 결과는 맞고 루트 결과가 틀리면 루트의 `resources`가 하위 설정을 거치는지,
루트에 같은 필드를 바꾸는 변환이 있는지 확인한다.
적용까지 요구한 문제에서는 아래 순서로 이어 간다.

```bash
kubectl diff -k .
kubectl apply -k .
kubectl get -k .
```

이름·namespace 변환은 적용 대상의 식별자를 바꾼다. 이전 이름이나 namespace에 이미 있던
리소스가 자동 이동·삭제되는 것은 아니므로, 변경 전후 대상을 구분해 요구 범위만 처리한다.

## Patch로 특정 필드·항목 수정하기

패치는 원본 리소스 전체를 다시 쓰지 않고 필요한 변경만 적는 방법이다.
**대상 선택 → 변경 위치 확인 → 패치 작성 → 루트 렌더 검증 → 적용** 순서로 접근한다.
Kustomize의 `patches`는 strategic merge와 JSON6902를 지원한다.
([공식 문서 — Customizing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#customizing))

| 방식 | 변경을 적는 방법 | 이번 삭제 예제 |
|---|---|---|
| Strategic merge | 원본 YAML 구조를 따라 필요한 부분을 쓴다. `containers`는 `name` 기준으로 병합한다 | `name: memcached`에 `$patch: delete` |
| JSON6902 | `target`으로 리소스를 고르고 `op`·`path`로 작업과 위치를 지정한다 | `op: remove`로 Pod template의 `org` 삭제 |

JSON6902는 **RFC 6902에 정의된 JSON Patch**라는 뜻이며, 6902는 버전이 아니라 표준 문서 번호다.
Kustomize에서는 작업 목록을 YAML로 작성할 수 있다.
([RFC 6902 — 학습용](https://www.rfc-editor.org/rfc/rfc6902))
파일에 따로 쓰는지, inline으로 직접 쓰는지는 패치 방식과 별개다. 문제에서 방식과 위치를
지정하면 그대로 따른다.

### Strategic merge — memcached 컨테이너 삭제

요구: `api-patch.yaml`에 strategic merge patch를 작성해 `api-deployment`의
`memcached` 컨테이너를 제거한다. 원본에서 Deployment 이름과 **컨테이너의 `name`**을 먼저 확인한다.

```yaml
# api-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  template:
    spec:
      containers:
        - name: memcached
          $patch: delete
```

`metadata.name`은 대상 Deployment, 아래 `name`은 삭제할 컨테이너다.
`$patch: delete`는 그 리스트 항목을 삭제하는 지시자다.
다른 컨테이너는 패치에 쓰지 않아도 유지된다.
([공식 strategic merge 규약 — 학습용](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md#strategic-merge-patch))

이 파일을 해당 `kustomization.yaml`에 연결한다. 이미 랩에서 연결해 놓았다면 중복 추가하지 않는다.

```yaml
# 기존 resources는 유지한다
patches:
  - path: api-patch.yaml
```

`path`는 이 설정 파일 기준 상대 경로다. 패치 파일은 독립된 Deployment 정의가 아니므로
`resources`에 넣거나 `kubectl apply -f api-patch.yaml`로 적용하지 않는다.

:::caution[함정 — 남길 컨테이너만 적어도 삭제되지 않는다]
Strategic merge에서 `containers`는 `name` 기준으로 병합된다.
패치에서 memcached를 단순히 생략하면 기존 항목이 남는다. 삭제하려면 해당 항목에
`$patch: delete`를 명시한다. 이 병합 규칙을 모든 리스트에 일반화하지 않는다.
[공식 patch 설명](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/#notes-on-the-strategic-merge-patch)은
필드마다 병합·교체 방식이 달라짐을 보여 준다.
:::

### Inline JSON6902 — Pod template의 org 라벨 삭제

요구: `mongo-deployment`에서 `org: KodeKloud` 라벨을 inline JSON6902로 제거한다.
이 랩의 솔루션은 **Pod template의 라벨**을 대상으로 한다.
Deployment 자체의 라벨과 위치가 다르므로 원본을 먼저 읽는다.

| 원본의 위치 | JSON Patch의 경로 |
|---|---|
| Deployment의 `metadata.labels.org` | `/metadata/labels/org` |
| Pod template의 `spec.template.metadata.labels.org` | `/spec/template/metadata/labels/org` |

```yaml
# kustomization.yaml — 기존 patches가 있으면 목록에 이어 붙인다
patches:
  - target:
      kind: Deployment
      name: mongo-deployment
    patch: |-
      - op: remove
        path: /spec/template/metadata/labels/org
```

`target`은 수정할 리소스를 선택하고, `path`는 그 리소스 내부의 정확한 위치를 가리킨다.
`remove`는 **현재 값과 관계없이 해당 키를 삭제**하므로 `value: KodeKloud`를 적지 않는다.
이 문제에서는 작업 전에 현재 값이 요구한 라벨인지 확인한다.

| 자주 쓰는 `op` | 동작 | `value` |
|---|---|---|
| `add` | 필드·항목 추가. 기존 객체 키라면 값 교체 | 필요 |
| `replace` | 존재하는 대상의 값 교체 | 필요 |
| `remove` | 존재하는 대상 삭제 | 불필요 |

`path`는 JSON Pointer 표기다. 객체는 키 이름, 배열은 0부터 시작하는 인덱스로 접근한다.
예를 들어 `/spec/template/spec/containers/1`은 두 번째 컨테이너이며, 이름으로 고르는 방식이
아니므로 순서 확인이 필요하다. 라벨 키 자체에 `/`가 있으면 `~1`, `~`가 있으면 `~0`으로
표현한다. `example.com/org`의 경로 끝은 `example.com~1org`다.
([RFC 6901 — 학습용](https://www.rfc-editor.org/rfc/rfc6901))

### patch 뒤의 |-는 여러 줄 문자열

`patch: |-`의 `|`는 **아래 들여쓴 여러 줄을 줄바꿈이 유지되는 문자열로 읽으라**는 뜻이고,
`-`는 문자열 끝의 줄바꿈을 제거한다는 뜻이다.
바깥 YAML에서 `patch`의 값은 문자열 하나이며, Kustomize가 그 문자열을 다시 패치 작업 목록으로
해석한다. `patch: |`로 써도 끝에 줄바꿈이 남을 뿐 이 패치의 동작은 같다.
([YAML 명세 — Block Chomping Indicator](https://yaml.org/spec/1.2.2/#8112-block-chomping-indicator))

### 삭제 결과와 실패 지점 확인

```bash
cd /root/code/k8s
kubectl kustomize .
kubectl diff -k .
kubectl apply -k .
kubectl get -k .
```

첫 렌더에서 api-deployment의 memcached만 사라지고 다른 컨테이너는 남았는지,
mongo-deployment의 **Pod template에서만 org가 없어졌는지** 확인한다.
적용 후에는 해당 Deployment의 rollout 완료도 확인한다.

| 증상 | 확인·수정 |
|---|---|
| 패치를 썼는데 변화가 없음 | 대상 이름·kind, `patches` 연결, 루트 `resources`가 해당 하위 설정을 거치는지 확인 |
| JSON Patch에서 missing path 오류 | `remove` 대상이 원본에 존재하는지 확인. 이미 삭제했거나 라벨 위치를 잘못 골랐는지 확인 |
| selector와 template 라벨 불일치 | `spec.selector.matchLabels`가 `org`를 요구하면 template에서만 지울 수 없다. 문제의 대상 위치와 원본 selector를 다시 확인 |
| 렌더는 성공하지만 적용 실패 | 로컬 변환 성공은 API 검증 성공이 아니다. 오류 메시지와 `diff`로 변경 필드를 확인 |

selector 오류를 해결하려고 selector까지 무작정 지우지 않는다. 기존 Deployment의 selector는
불변이며, 문제에서 요구한 변경 범위를 먼저 확인해야 한다.
잘못된 패치는 파일 내용을 정상으로 고친 뒤 같은 검증 순서로 다시 적용한다.

## 미리보기와 완료 검증 구분하기

`kubectl kustomize .`가 성공해도 클러스터에는 아직 아무것도 적용하지 않았다.
공식 문서의 [적용·조회 방법](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#how-to-apply-view-delete-objects-using-kustomize)처럼
`-k`에는 설정 파일이 들어 있는 **디렉터리**를 준다.

| 명령 | 확인하는 것 |
|---|---|
| `kubectl kustomize .` | 로컬에서 최종 YAML을 만들 수 있는가 |
| `kubectl diff -k .` | 현재 클러스터와 적용할 내용이 어떻게 다른가 |
| `kubectl apply -k .` | 실제 리소스를 생성·갱신했는가 |
| `kubectl get -k .` | 이번 목록의 리소스가 존재하며 어떤 상태인가 |

`diff`의 종료 코드 1은 차이가 있다는 뜻이고, 1보다 큰 값은 오류다.
([kubectl diff 레퍼런스](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_diff/))
`get -k`에 Deployment가 보이면 READY도 확인한다. 준비되지 않았다면 실제 이름과
네임스페이스를 사용해 `kubectl rollout status deployment/<이름> -n <네임스페이스>`로
완료를 기다리고, 실패하면 해당 Pod의 `describe`와 Events로 내려간다.

별도 Kustomize CLI가 있을 때는 다음처럼 두 단계를 파이프로 연결할 수도 있다.

```bash
# /root/code에서 실행
kustomize build k8s/ | kubectl apply -f -
```

`build`는 YAML 생성, `apply -f -`의 마지막 `-`는 표준입력에서 YAML을 읽는다는 뜻이다.
이 실습에서는 `kubectl apply -k /root/code/k8s`만으로도 적용할 수 있다.

## 실패하면 경로와 입력 형식부터 확인하기

| 증상·시도 | 원인과 수정 |
|---|---|
| `no such file or directory` | `resources` 경로 오타·파일 누락을 확인한다. 기준은 `kustomization.yaml`의 위치다 |
| `resources: ["*.yaml"]` | 와일드카드를 펼치지 않고 문자 그대로의 파일을 찾는다. `find` 결과를 개별 경로로 넣는다 |
| `resources`에 `db/`만 지정 | 디렉터리를 참조하려면 그 안에도 `kustomization.yaml`이 필요하다. 루트에 하나만 만드는 문제에서는 개별 파일을 나열한다 |
| `apply -f kustomization.yaml`에서 kind를 찾지 못함 | Kustomize 설정을 클러스터 API에 직접 보냈다. `apply -k .`로 실행한다 |
| `get -k .`는 성공하지만 필요한 리소스가 빠짐 | `get -k`는 목록에 넣은 것만 조회한다. 원래 요구된 파일 목록과 `resources`를 다시 대조한다 |

:::caution[함정 — 전체 디렉터리 적용으로 우회하지 않는다]
`kubectl apply -f . -R`은 하위 YAML을 재귀적으로 적용하는 별도 방식이다.
Kustomize의 목록·변환을 처리하지 않으므로, 설정 파일을 만들고 적용하라는 요구를 대신하지 못한다.
:::

잘못 적용했다면 해당 설정이나 원본 YAML을 정상 내용으로 고친 뒤 `diff -k` → `apply -k` →
`get -k`로 다시 확인한다. Kustomize에는 Helm처럼 릴리스 이력을 고르는 rollback이 없다.
`delete -k`는 목록의 리소스를 삭제하므로 복구 명령으로 사용하지 않는다.
목록에서 경로를 빼는 것만으로 이미 적용된 리소스가 자동 삭제되는 것도 아니다.

## kind와 apiVersion이 기억나지 않을 때

### api-resources에 나오지 않는 이유

`kubectl api-resources`는 **클러스터 API가 제공하는 리소스 종류**를 조회한다.
여기서 쓰는 `Kustomization`은 로컬 도구의 설정 형식이므로 이 목록이나 `kubectl explain`에서
찾을 수 없다. 같은 이름의 CRD가 설치돼 있더라도 그것은 이 로컬 설정과 별개다.
([api-resources 레퍼런스](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_api-resources/))

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
```

`kind`는 파일명 `kustomization.yaml`에서 확장자를 빼고 첫 글자를 대문자로 바꾸면 된다.
`apiVersion`까지 명시해야 하는 실습에 대비해서는 위 두 줄을 한 쌍으로 익혀 둔다.

### 생략해도 실행되는 것과 채점 통과는 다르다

Kustomize는 이 두 필드를 생략하면 기본값으로 처리한다.
Kubernetes 공식 문서의 [Composing 예제](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#composing)에도
`resources:`만 있고, **위 두 줄은 그 페이지에서 찾을 수 없다**.
기본값 처리와 정확한 표기는 [Kustomize 공식 소스](https://github.com/kubernetes-sigs/kustomize/blob/master/api/types/kustomization.go)에서 확인할 수 있다.
이 소스 링크는 학습용이며 시험 중 열람 경로로 사용하지 않는다.

:::caution[함정 — 실행 성공을 채점 통과로 단정하지 않는다]
이번 KodeKloud 실습에서는 학습자가 `kind: Kustomization`의 명시 여부를 확인하는 채점을 관찰했다.
채점 구현 전체는 확인하지 않았으므로 다른 랩이나 실제 CKA도 같은 방식이라고 일반화하지 않는다.
이 랩에서는 힌트대로 `apiVersion`·`kind`를 모두 적는다.
Deployment·Service 같은 원본 리소스 YAML에서 두 필드를 생략해도 된다는 뜻은 아니다.
:::

### 별도 CLI가 있으면 기본 파일 생성하기

```bash
command -v kustomize
```

경로가 나오면 **설정 파일이 없는 빈 디렉터리**에서 다음 명령으로 기본 파일을 만들어 볼 수 있다.
문제를 풀고 있는 기존 파일을 지우고 실행하지 않는다.

```bash
kustomize create
cat kustomization.yaml
```

생성된 파일에 `apiVersion`과 `kind`가 들어간다.
([공식 create 구현 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/kustomize/commands/create/create.go))
`kubectl kustomize`에는 이 `create` 기능이 없고, 그 `--help`에도 위 두 줄은 나오지 않는다.

## 시험장에서 공식 문서와 도구 확인하기

2026-09-07 확인 기준,
[CKA 공식 환경 안내](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)는
지정 SSH 호스트에 `kubectl`·`yq`·`curl`·`wget`·`man`을 제공한다고 명시하지만
**별도 `kustomize` 실행 파일의 사전 설치는 명시하지 않는다**.
목록에 없다는 이유로 반드시 없다고 단정할 수도 없다. 따라서 `kustomize create`를 쓸 수 있다는
전제로 준비하지 않고, 기본 실행은 kubectl 내장 기능으로 연습한다.

문제가 지정한 호스트에 SSH로 들어간 뒤 `command -v kustomize`로 별도 CLI 유무를 확인한다.
`kubectl version --client`에 Kustomize 버전이 표시되는 것은 **내장 버전**이며,
별도 명령이 설치됐다는 증거가 아니다.

[시험 허용 자료 규정](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)에
따라 시험 VM의 브라우저에서 Kubernetes 문서를 열 수 있다. 문서 내 검색은 허용되지만 외부 검색
결과는 열면 안 된다. 문제의 Quick Reference에서 제공하는 전용 문서도 확인한다.
별도 Kustomize 사이트나 GitHub를 일반 허용 자료로 간주하지 않는다.

| 필요한 것 | 찾는 위치와 검색어 |
|---|---|
| 파일 목록 작성 | Kubernetes 문서에서 `kustomize` 검색 → [Composing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#composing)의 `resources` 예제 |
| 적용·조회 명령 | 같은 페이지의 [How to apply/view/delete objects using Kustomize](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#how-to-apply-view-delete-objects-using-kustomize) |
| 이미지·replicas·patch 변경 | 같은 페이지의 Customizing 절. 개념 복습은 [cka 16장](/cka/16-helm-kustomize/#kustomize) |
| Strategic merge·JSON6902 예제와 연결 | [Customizing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#customizing)에서 `patches`, `target`, `op`, `path` 확인 |
| 컨테이너 병합 기준 | [Notes on the strategic merge patch](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/#notes-on-the-strategic-merge-patch)의 `patchMergeKey: name` |
| `$patch: delete` 삭제 지시자 | 위 두 Kubernetes 문서에는 해당 예제가 없다. 컨테이너 이름과 함께 쓰는 형태를 별도로 익힌다 |
| label·이름·namespace·annotation | 같은 페이지의 [Setting cross-cutting fields](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#setting-cross-cutting-fields). 라벨 예제는 `commonLabels` 대신 `labels` 사용 |
| `apiVersion`·`kind` 두 줄 | 위 문서에 없다. 기본 표기를 익히고, 별도 CLI가 있을 때만 `kustomize create`로 생성 |

## 이 장에서 남길 것

- `find . -name '*.yaml'`로 경로를 확인하고, 필요한 파일만 `resources`에 나열한다.
- `resources`는 와일드카드를 지원하지 않는다. 디렉터리 참조에는 하위 설정 파일이 필요하다.
- 전체 변환은 루트, 일부 그룹 변환은 해당 하위 설정에 둔다. 적용 범위는 `resources`의 참조 관계로 결정된다.
- `commonLabels`는 selector도 바꾼다. `images.name`은 기존 이미지, `newName`은 이름 교체, `newTag`는 태그 교체다.
- 컨테이너 삭제는 strategic merge의 `name` + `$patch: delete`, 특정 라벨 삭제는 JSON6902의 `target` + `op: remove` + 정확한 `path`로 연습한다.
- `patch: |-`는 패치를 담은 여러 줄 문자열이다. Deployment 라벨과 Pod template 라벨의 경로를 구분한다.
- `kubectl kustomize .`는 미리보기, `apply -k .`는 적용, `get -k .`는 해당 목록의 실제 상태 조회다.
- 이 랩에서는 `apiVersion`·`kind`를 모두 적는다. 실행 가능 여부와 채점 조건을 구분한다.
- 별도 CLI 설치를 가정하지 않는다. 공식 문서에서 찾을 수 있는 예제와 외워 둘 두 줄을 구분한다.
