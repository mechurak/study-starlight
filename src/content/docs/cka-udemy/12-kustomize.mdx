<Thesis>resources로 배포 대상을 모으고, 적용할 환경의 디렉터리를 렌더한 뒤 실제 상태를 확인한다</Thesis>

여러 YAML을 환경마다 복사하면 공통 변경을 빠뜨리기 쉽다. Kustomize는 원본을 그대로 두고
공통 묶음(base)에 환경별 설정(overlay)을 얹어 최종 YAML을 만든다. 이 페이지에서는
**어떤 파일을 묶고 어느 환경을 적용할지** 결정한다.

원리는 [CKA Kustomize — YAML과 오버레이](/cka/kustomize/#kustomize)에서 본다.
이름·이미지를 일괄 변경할 때는 [범위별 변환](/cka-udemy/kustomize-transformers/),
특정 필드를 수정할 때는 [patch](/cka-udemy/kustomize-patches/),
선택 기능을 조합할 때는 [components 보충](/cka-udemy/kustomize-components/)으로 이어 간다.

## resources로 파일을 모으기

`kustomization.yaml`은 로컬 도구가 읽는 목록이다. Deployment처럼 클러스터에 생성하는 리소스가 아니다.
아래 명령은 기존 랩의 `/root/code/k8s`에서 실행한다.

```bash
cd /root/code/k8s
find . -name '*.yaml'
```

`'*.yaml'`을 따옴표로 감싸 셸이 먼저 펼치지 않게 한다. 출력에서 설정 파일 자체와 패치 파일을
제외하고 **요구된 배포 파일**을 고른다. 하위 폴더에 설정 파일이 없는 단일 목록 문제라면 다음처럼 적는다.

```yaml
# /root/code/k8s/kustomization.yaml — 이 랩의 파일 목록
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - db/db-config.yaml
  - db/db-depl.yaml
  - db/db-service.yaml
  - message-broker/rabbitmq-config.yaml
  - message-broker/rabbitmq-depl.yaml
  - message-broker/rabbitmq-service.yaml
  - nginx/nginx-depl.yaml
  - nginx/nginx-service.yaml
```

경로 기준은 **설정 파일이 있는 폴더**다. `./db/db-config.yaml`도 같은 경로다.
파일 경로를 일일이 적는 대신 디렉터리를 참조하려면 그 안에도 `kustomization.yaml`이 있어야 한다.
`resources: ["*.yaml"]`은 와일드카드를 펼치지 않는다.

문서에서는 Kubernetes 내부 검색으로 `kustomize` →
[Composing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#composing)을 연다.
`resources` 블록을 가져와 **실제 파일 경로**로 바꾼다. 파일이 있다는 이유만으로 전부 추가하지 않는다.

## 공통 base와 환경별 진입점

앞의 랩과 별개로, 이후 patch·선택 기능에서도 공유할 **재구성 예제**다.
새 연습 디렉터리 `k8s/`에 아래 파일을 만든다. 기존 랩 파일을 이 예제로 덮어쓰지 않는다.

```text
k8s/
  base/
    kustomization.yaml
    api-depl.yaml
  overlays/
    dev/kustomization.yaml
    staging/kustomization.yaml
    QA/kustomization.yaml
    prod/kustomization.yaml
```

`base/api-depl.yaml`은 완성된 Deployment다. API 역할의 컨테이너 이름은 `api`,
이미지는 렌더 연습용 nginx이고, 삭제 연습용 `memcached`가 함께 있다.
이 예제가 실제 API와 캐시의 연동을 구현한다는 뜻은 아니다.

```yaml
# base/api-depl.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: nginx:1.23
        - name: memcached
          image: memcached:1.6
```

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - api-depl.yaml
```

네 환경의 `kustomization.yaml`은 처음에 같은 내용이다. 이후 필요한 환경에만 변경을 추가한다.

```yaml
# overlays/staging/kustomization.yaml — dev·QA·prod도 처음에는 동일
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
```

base는 다른 환경을 알지 못한다. overlay가 base를 참조해야 공통 리소스가 포함된다.
환경 이름이 namespace를 정하지는 않는다. 이 예제는 namespace를 지정하지 않았으므로 실제 적용 시
문제에서 정한 namespace를 `-n`으로 명시한다. 같은 namespace에 네 환경을 번갈아 적용하면
같은 이름의 Deployment를 갱신하므로, 비교 실습은 먼저 로컬 렌더로 한다.

문서는 [Bases and Overlays](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#bases-and-overlays)의
`resources: - ../../base` 연결을 찾는다. generator·replicas 단축 설정은
[CKA Kustomize — YAML과 오버레이](/cka/kustomize/#오버레이--generator와-patch)에서 별도로 복습한다.

### staging에만 MySQL Deployment 추가

요구: staging에만 `mysql-deployment`를 추가한다. replicas 1, 컨테이너 이름·이미지 `mysql`,
환경변수 `MYSQL_ROOT_PASSWORD=mypassword`는 **원본 랩이 지정한 값**이다.

```bash
cd /root/code/k8s/overlays/staging
cat kustomization.yaml
ls
kubectl create deployment mysql-deployment \
  --image=mysql --replicas=1 --dry-run=client -o yaml > mysql-depl.yaml
```

파일이 이미 있으면 먼저 읽는다. 생성 명령은 파일을 덮어쓰므로 없는 경우에만 실행한다.
새 연습 디렉터리를 쓴다면 `cd` 경로를 그 위치로 바꾼다.
[create deployment 레퍼런스](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_deployment/)나
`kubectl create deployment --help`에서 골격 생성 옵션을 찾는다.
생성된 selector와 Pod label이 일치하면 문제에서 지정하지 않은 라벨을 해설의 `component: mysql`로 바꿀 필요는 없다.

다음은 **생성된 컨테이너 부분에 추가할 필드**다. 위치는
`kubectl explain deployment.spec.template.spec.containers.env`로 확인한다.

```yaml
      containers:
        - name: mysql
          image: mysql
          env:
            - name: MYSQL_ROOT_PASSWORD
              value: mypassword
```

기존 staging 설정의 `resources`만 다음처럼 확장한다. `apiVersion`·`kind`와 다른 설정은 유지한다.

```yaml
# overlays/staging/kustomization.yaml의 resources 전체
resources:
  - ../../base
  - mysql-depl.yaml
```

파일을 놓기만 해서는 포함되지 않는다. base에 등록하면 다른 환경에도 들어가므로 staging에 둔다.
`k8s/`에서 `kubectl kustomize overlays/staging`과 `kubectl kustomize overlays/prod`를 비교한다.
staging에는 API와 MySQL이 각각 한 번, prod에는 API만 있어야 한다.
MySQL의 replicas·이미지·환경변수도 확인한다. API가 사라졌다면 기존 base 참조를 지웠는지 본다.

## 미리보기와 완료 검증 구분하기

아래 명령은 `k8s/`에서 실행한다. 실제 적용·조회에서는 문제의 namespace를 함께 지정한다.
문서의 [How to apply/view/delete objects using Kustomize](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#how-to-apply-view-delete-objects-using-kustomize)에서
`-k` 명령을 찾고 경로를 **적용할 overlay 디렉터리**로 바꾼다.

| 명령 | 완료 판정 |
|---|---|
| `kubectl kustomize overlays/staging` | 경로·YAML 오류 없이 요구된 리소스와 필드가 출력됨. 클러스터 변경 없음 |
| `kubectl diff -k overlays/staging` | 현재 클러스터와 바뀔 내용이 요구 범위 안임 |
| `kubectl apply -k overlays/staging` | API가 생성을 받거나 갱신함. 앱 성공은 아직 별도 |
| `kubectl get -k overlays/staging` | 목록의 리소스가 존재하고 Deployment READY 확인 가능 |

`diff`의 exit 1은 차이가 있다는 뜻이고 1보다 크면 오류다.
([diff 레퍼런스](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_diff/))
Deployment의 실제 이름·namespace로 `kubectl rollout status deployment/mysql-deployment -n <namespace>`를
실행해 완료를 확인한다. 준비되지 않으면 `kubectl describe pod <Pod> -n <namespace>`의 Events에서
이미지 pull·설정·기동 실패를 좁힌다. `get -k`는 목록에 빠진 리소스를 찾아 주지 않으므로 요구 목록과도 대조한다.

### 현재 디렉터리와 overlay 경로 구분

`.`은 셸의 현재 디렉터리다. staging 안에서는 `kubectl kustomize .`를 쓰고,
다른 위치에서는 `kubectl kustomize /root/code/k8s/overlays/staging`처럼 경로를 지정한다.
apply·get도 같은 경로를 쓴다. QA 요구라면 세 명령 모두 `overlays/QA`를 대상으로 한다.
설정 안의 상대 경로는 셸 위치가 아니라 **그 설정 파일 위치** 기준이다.

별도 CLI가 설치됐다면 `/root/code`에서 다음 파이프도 가능하다.

```bash
kustomize build k8s/ | kubectl apply -f -
```

`build`는 YAML 생성, 마지막 `-`는 표준입력이다. 이는 `k8s/kustomization.yaml`이 있는
단일 목록·루트 구성용 명령이다. 공통 예제처럼 overlay가 진입점이면 `k8s/overlays/staging`으로 바꾼다.

### 경로·입력 형식과 복구

- 파일 없음: 설정 파일 기준의 `resources` 경로와 하위 설정 존재 여부를 확인한다.
- `apply -f kustomization.yaml`의 kind 오류: 로컬 설정을 API에 보냈다. `apply -k <디렉터리>`로 고친다.
- `apply -f . -R`: 하위 YAML을 직접 적용하므로 Kustomize의 목록·변환을 대신하지 못한다.

잘못 적용했다면 설정을 정상 내용으로 고치고 diff → apply → 상태 조회를 반복한다.
Helm 같은 릴리스 rollback은 없다. `delete -k`는 앱 전체를 삭제할 수 있어 복구 명령이 아니다.
목록에서 경로를 빼도 이미 적용한 리소스가 자동 삭제되지는 않는다.

## kind와 apiVersion이 기억나지 않을 때

기본 설정의 두 줄은 `apiVersion: kustomize.config.k8s.io/v1beta1`, `kind: Kustomization`이다.
파일명에서 첫 글자를 대문자로 만든 kind와 API 버전을 한 쌍으로 익힌다.
이 로컬 설정은 `kubectl api-resources`나 `kubectl explain`으로 찾을 수 없다.
같은 이름의 CRD가 있어도 별개다.
([api-resources 레퍼런스](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_api-resources/))

Kustomize는 두 필드를 생략하면 기본값으로 처리하지만, 원본 KodeKloud 랩에서는 학습자가
**kind 명시를 확인하는 채점**을 관찰했다. 다른 랩이나 실제 CKA의 일반 규칙으로 확대하지 않는다.
이 랩은 두 줄을 명시한다. 원본 Deployment·Service에서 생략해도 된다는 뜻은 아니다.
기본값 근거는 [공식 소스 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/api/types/kustomization.go)다.

Kubernetes의 위 Kustomize 문서 본문에는 이 두 줄이 없고 Composing 예제도 `resources`로 시작한다.
별도 CLI가 있다면 **설정 파일이 없는 빈 디렉터리**에서 `kustomize create` 후
`cat kustomization.yaml`로 볼 수 있다. 기존 파일을 지우고 생성하지 않는다.
([create 구현 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/kustomize/commands/create/create.go))
`kubectl kustomize`에는 create 기능이 없고 그 도움말에도 두 줄이 없다.

## 시험장에서 문서와 도구 확인하기

2026-09-12 [LF 시험 환경 안내](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)는
지정 SSH 호스트의 kubectl·yq·curl·wget·man을 안내하지만 별도 kustomize 설치는 명시하지 않는다.
반드시 없다는 뜻도 아니다. 기본 연습은 kubectl 내장 기능으로 하고, 별도 CLI는
`command -v kustomize`로 확인한다. `kubectl version --client`의 Kustomize 버전은 내장 버전이다.

[허용 자료 규정](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)에 따라
VM 브라우저의 Kubernetes 문서 내부 검색은 가능하지만 외부 검색 결과는 열지 않는다.
별도 Kustomize 사이트·GitHub는 일반 시험 열람 경로로 안내하지 않는다.
Quick Reference는 문제에서 제공할 때만 사용한다. patch·변환 문법의 찾을 위치는 해당 페이지에 둔다.
