<Thesis>패치는 리소스 대상을 먼저 고르고 변경할 필드나 컨테이너를 정확히 지정한다</Thesis>

공통 변환만으로는 한 Deployment의 컨테이너 삭제처럼 좁은 요구를 표현하기 어렵다.
Patch는 원본을 복사하지 않고 필요한 차이만 적는다. 이 페이지에서는 **대상 하나를 수정·삭제하고
다른 필드는 보존됐는지 확인한다**.

기본 구조는 [공유 base·overlay](/cka-udemy/kustomize/#공통-base와-환경별-진입점)를 사용한다.
`api-deployment`에는 첫 컨테이너 `api`와 두 번째 `memcached`가 있다.
원리는 [CKA Kustomize — YAML과 오버레이](/cka/kustomize/#오버레이--generator와-patch)에서 복습한다.

## Patch로 특정 필드·항목 수정하기

**대상 선택 → 변경 위치 확인 → 패치 작성 → 적용할 구성 렌더 검증 → 적용** 순서로 접근한다.
Kustomize의 `patches`는 strategic merge와 JSON6902를 지원한다.
([공식 문서 — Customizing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#customizing))

| 방식 | 변경을 적는 방법 | 이번 삭제 예제 |
|---|---|---|
| Strategic merge | 원본 YAML 구조를 따라 필요한 부분을 쓴다. `containers`는 `name` 기준으로 병합한다 | `name: memcached`에 `$patch: delete` |
| JSON6902 | `target`으로 리소스를 고르고 `op`·`path`로 작업과 위치를 지정한다 | `op: remove`로 Pod template의 `org` 삭제 |

JSON6902는 **RFC 6902에 정의된 JSON Patch**라는 뜻이며, 6902는 버전이 아니라 표준 문서 번호다.
Kustomize에서는 작업 목록을 YAML로 작성할 수 있다.
([RFC 6902 — 학습용](https://www.rfc-editor.org/rfc/rfc6902))
파일에 따로 쓰는지, inline으로 직접 쓰는지는 패치 방식과 별개다. 문제에서 방식과 위치를
지정하면 그대로 따른다.

### resources와 patches의 path는 파일 역할이 다르다

staging에서 새 MySQL과 API 이미지 패치 파일을 함께 추가한다면 파일 역할을 먼저 구분한다.
아래는 **기존 staging 설정에 병합할 필드**다. 실제 랩의 다른 resources·patches는 유지한다.

```yaml
resources:
  - ../../base
  - mysql-depl.yaml
patches:
  - target:
      kind: Deployment
      name: api-deployment
    path: api-image-patch.yaml
```

`mysql-depl.yaml`에는 완전한 Deployment, `api-image-patch.yaml`에는 아래 QA 예제의
`- op: replace`부터 `value: caddy`까지 **작업 목록만** 저장한다. 두 파일은 이 설정과 같은 폴더에 둔다.
바깥 `path`는 설정 파일 기준의 **파일 위치**, 작업의 `/spec/…/image`는 **리소스 내부 필드 위치**다.
패치 파일을 `resources`에 넣지 않는다. 파일 대신 같은 내용을 `patch: |-` 아래에 넣으면 inline이다.

## QA에서 inline JSON6902로 API 이미지 교체

요구: QA 환경의 `api-deployment`에서 API 컨테이너 이미지를 `caddy`로 바꾸되,
inline JSON6902 패치를 사용하고 QA 설정을 실제 적용한다.
먼저 QA 설정과 원본 Deployment를 읽고 컨테이너 순서를 확인한다.

```bash
cd /root/code/k8s/overlays/QA
cat kustomization.yaml
kubectl kustomize .
```

아래 패치는 API 컨테이너가 **첫 번째 컨테이너일 때** 사용한다.
`containers/0`은 이름이 아니라 배열 인덱스이며 두 번째 컨테이너라면 `containers/1`이다.
Deployment의 Pod template을 바꾸므로 경로는 `/spec/template/spec/containers/0/image`다.

```yaml
# overlays/QA/kustomization.yaml — 기존 resources 유지
# patches가 이미 있으면 그 목록에 항목을 추가한다
patches:
  - target:
      kind: Deployment
      name: api-deployment
    patch: |-
      - op: replace
        path: /spec/template/spec/containers/0/image
        value: caddy
```

`target`은 Deployment를, `replace`는 존재하는 이미지 필드를 고른다.
[공통 적용 순서](/cka-udemy/kustomize/#미리보기와-완료-검증-구분하기)를 QA 경로로 실행한다.

미리보기와 실제 Deployment의 `spec.template.spec.containers`에서 API 이미지가 `caddy`인지
확인하고 rollout 완료도 확인한다. 다른 컨테이너가 바뀌면 인덱스를, missing path 오류가 나면
`spec/template/spec` 경로와 해당 컨테이너의 `image` 존재 여부를 확인한다.
공통 base에 변경을 적었다면 이를 원래대로 고치고 QA overlay에 패치를 둔다.

## Strategic merge — memcached 컨테이너 삭제

공유 예제에서는 `overlays/QA/api-patch.yaml`을 만들고 QA 설정에 연결한다.
요구: `api-patch.yaml`에 strategic merge patch를 작성해 `api-deployment`의
`memcached` 컨테이너를 제거한다. 원본에서 Deployment 이름과 **컨테이너의 `name`**을 먼저 확인한다.

```yaml
# overlays/QA/api-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  template:
    spec:
      containers:
        - name: memcached
          $patch: delete
```

`metadata.name`은 대상 Deployment, 아래 `name`은 삭제할 컨테이너다.
`$patch: delete`는 그 리스트 항목을 삭제하는 지시자다.
다른 컨테이너는 패치에 쓰지 않아도 유지된다.
([공식 strategic merge 규약 — 학습용](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md#strategic-merge-patch))

이 파일을 해당 `kustomization.yaml`에 연결한다. 이미 랩에서 연결해 놓았다면 중복 추가하지 않는다.

```yaml
# 기존 resources는 유지한다
patches:
  - path: api-patch.yaml
```

`path`는 이 설정 파일 기준 상대 경로다. 패치 파일은 독립된 Deployment 정의가 아니므로
`resources`에 넣거나 `kubectl apply -f api-patch.yaml`로 적용하지 않는다.

:::caution[함정 — 남길 컨테이너만 적어도 삭제되지 않는다]
Strategic merge에서 `containers`는 `name` 기준으로 병합된다.
패치에서 memcached를 단순히 생략하면 기존 항목이 남는다. 삭제하려면 해당 항목에
`$patch: delete`를 명시한다. 이 병합 규칙을 모든 리스트에 일반화하지 않는다.
[공식 patch 설명](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/#notes-on-the-strategic-merge-patch)은
필드마다 병합·교체 방식이 달라짐을 보여 준다.
:::

## Inline JSON6902 — Pod template의 org 라벨 삭제

이 항목은 별도 원본 랩의 변형이다. 기존 `mongo-deployment`가 해당 overlay의 resources에
등록돼 있고 Pod template에 `org: KodeKloud`가 있는 상황을 전제로 한다.

요구: `mongo-deployment`에서 `org: KodeKloud` 라벨을 inline JSON6902로 제거한다.
이 랩의 솔루션은 **Pod template의 라벨**을 대상으로 한다.
Deployment 자체의 라벨과 위치가 다르므로 원본을 먼저 읽는다.

| 원본의 위치 | JSON Patch의 경로 |
|---|---|
| Deployment의 `metadata.labels.org` | `/metadata/labels/org` |
| Pod template의 `spec.template.metadata.labels.org` | `/spec/template/metadata/labels/org` |

```yaml
# kustomization.yaml — 기존 patches가 있으면 목록에 이어 붙인다
patches:
  - target:
      kind: Deployment
      name: mongo-deployment
    patch: |-
      - op: remove
        path: /spec/template/metadata/labels/org
```

`target`은 수정할 리소스를 선택하고, `path`는 그 리소스 내부의 정확한 위치를 가리킨다.
`remove`는 **현재 값과 관계없이 해당 키를 삭제**하므로 `value: KodeKloud`를 적지 않는다.
이 문제에서는 작업 전에 현재 값이 요구한 라벨인지 확인한다.

| 자주 쓰는 `op` | 동작 | `value` |
|---|---|---|
| `add` | 필드·항목 추가. 기존 객체 키라면 값 교체 | 필요 |
| `replace` | 존재하는 대상의 값 교체 | 필요 |
| `remove` | 존재하는 대상 삭제 | 불필요 |

`path`는 JSON Pointer 표기다. 객체는 키 이름, 배열은 0부터 시작하는 인덱스로 접근한다.
예를 들어 `/spec/template/spec/containers/1`은 두 번째 컨테이너이며, 이름으로 고르는 방식이
아니므로 순서 확인이 필요하다. 라벨 키 자체에 `/`가 있으면 `~1`, `~`가 있으면 `~0`으로
표현한다. `example.com/org`의 경로 끝은 `example.com~1org`다.
([RFC 6901 — 학습용](https://www.rfc-editor.org/rfc/rfc6901))

### patch 뒤의 |-는 여러 줄 문자열

`patch: |-`의 `|`는 **아래 들여쓴 여러 줄을 줄바꿈이 유지되는 문자열로 읽으라**는 뜻이고,
`-`는 문자열 끝의 줄바꿈을 제거한다는 뜻이다.
바깥 YAML에서 `patch`의 값은 문자열 하나이며, Kustomize가 그 문자열을 다시 패치 작업 목록으로
해석한다. `patch: |`로 써도 끝에 줄바꿈이 남을 뿐 이 패치의 동작은 같다.
([YAML 명세 — Block Chomping Indicator](https://yaml.org/spec/1.2.2/#8112-block-chomping-indicator))

### 삭제 결과와 실패 지점 확인

`k8s/`에서 `kubectl kustomize overlays/QA`로 검사한 뒤 같은 경로로 diff·apply·get을 진행한다.

첫 렌더에서 api-deployment의 memcached만 사라지고 다른 컨테이너는 남았는지,
라벨 삭제 랩에서는 해당 overlay를 지정해 mongo-deployment의 **Pod template에서만 org가 없어졌는지** 확인한다.
적용 후에는 해당 Deployment의 rollout 완료도 확인한다.

| 증상 | 확인·수정 |
|---|---|
| 패치를 썼는데 변화가 없음 | 대상 이름·kind, `patches` 연결, 루트 `resources`가 해당 하위 설정을 거치는지 확인 |
| JSON Patch에서 missing path 오류 | `remove` 대상이 원본에 존재하는지 확인. 이미 삭제했거나 라벨 위치를 잘못 골랐는지 확인 |
| selector와 template 라벨 불일치 | `spec.selector.matchLabels`가 `org`를 요구하면 template에서만 지울 수 없다. 문제의 대상 위치와 원본 selector를 다시 확인 |
| 렌더는 성공하지만 적용 실패 | 로컬 변환 성공은 API 검증 성공이 아니다. 오류 메시지와 `diff`로 변경 필드를 확인 |

selector 오류를 해결하려고 selector까지 무작정 지우지 않는다. 기존 Deployment의 selector는
불변이며, 문제에서 요구한 변경 범위를 먼저 확인해야 한다.
잘못된 패치는 파일 내용을 정상으로 고친 뒤 같은 검증 순서로 다시 적용한다.

## 공식 예제에서 가져올 것과 따로 익힐 것

Kubernetes 문서 내부에서 `kustomize` →
[Customizing](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#customizing)을 열고
`Json6902`를 찾는다. `/spec/replicas`를 교체하는 파일 예제의 `target`·`op`·`path`·`value`를 가져와
대상 이름·이미지 경로·새 이미지로 바꾼다. inline 요구라면 바깥 `path: patch.yaml`을
`patch: |-`와 작업 본문으로 바꾼다. 컨테이너 인덱스는 실제 원본에서 확인한다.

`$patch: delete`는 위 문서와
[Notes on the strategic merge patch](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/#notes-on-the-strategic-merge-patch)에
삭제 예제가 없다. `name`과 함께 쓰는 최소 문법을 따로 익힌다. 두 번째 문서는
`patchMergeKey: name`을 찾아 컨테이너 병합 규칙을 확인하는 데 사용한다.
