<Thesis>Gateway API는 CRD만으로 트래픽을 만들지 않으며, GatewayClass의 컨트롤러와 Gateway listener, HTTPRoute attachment를 조건으로 확인해야 한다.</Thesis>

> 짝이 되는 개념 장: [CKA Ingress와 Gateway API](/cka/ingress-gateway/#gateway-api--ingress의-후속)

이 장의 과제는 Gateway와 HTTPRoute를 만들거나 고쳐 Service로 요청을 전달하는 것이다. Gateway API는
add-on CRD이고, 그 리소스를 실제 데이터 플레인으로 바꾸는 구현체 컨트롤러도 별도로 필요하다.

먼저 API resource와 GatewayClass를 조회하고, Gateway의 listener가 어떤 namespace와 Route를
허용하는지 확인한다. HTTPRoute를 붙인 뒤 Accepted·ResolvedRefs 조건과 실제 HTTP 응답까지 본다.

## Gateway API — 만들기와 진단

Gateway API는 Ingress보다 오브젝트가 많지만, 층은 더 명확하다. **CRD는 API 서버가 리소스를
저장하게 하고, Gateway 컨트롤러는 그 선언을 실제 프록시 설정으로 만든다.** CRD만 설치해
`kubectl get gateway`가 동작하는 상태는 트래픽 준비 완료가 아니다.

### Gateway 만들기 — 명령형이 없으니 스키마와 가이드에서 뽑는다

최신 랩의 작성 유형이다 — 지정된 ns에 GatewayClass·listener·allowedRoutes를 갖춘 Gateway를
만들라는 식. Ingress와 갈리는 지점부터: **`kubectl create`의 서브커맨드에 `gateway`는 없다.**
Gateway는 CRD로 들어오는 리소스라 명령형 생성이 없고, YAML이 유일한 경로다. 출처는 세 곳이다.

```bash
# 1순위 — CRD는 스키마가 함께 설치되므로 explain이 그대로 동작한다
kubectl explain gateway.spec.listeners --recursive
kubectl explain gateway.spec.listeners.allowedRoutes.namespaces.from   # All | Same | Selector
```

- 샘플 YAML은 Gateway API 공식 가이드의 [Deploying a simple Gateway](https://gateway-api.sigs.k8s.io/guides/getting-started/simple-gateway/)다 —
  `gatewayClassName`, listener의 name/protocol/port, `allowedRoutes`까지 이 유형과 같은 모양이라
  이름·ns·클래스와 `from: Same → All`만 바꾸면 되고, Gateway에 붙는 HTTPRoute 예시도 같은 페이지에 있다.
  (사이트 개편으로 경로가 바뀐 적이 있으니 URL 대신 **Guides → Getting started** 위치로 기억한다.)
- 클러스터에 이미 Gateway가 있으면 `-o yaml`로 복사한다 — annotation 때와 같은 전략이다.

틀리기 쉬운 곳은 `allowedRoutes.namespaces.from`의 세 단계 중첩이다. 철자와 깊이는 explain으로
확인하고, 만든 뒤에는 아래 진단 사슬의 2단계(`describe gateway` → Accepted·Programmed)로 판정한다.
CRD면 explain이 동작하는 이유는 [CKA CRD — 새로운 API 리소스 정의](/cka/crd/#crd를-만들면-무슨-일이-생기나)에 있다.

### web-gateway — HTTP 80 리스너만 요구하는 생성

[공식 simple Gateway 예제](https://gateway-api.sigs.k8s.io/guides/getting-started/simple-gateway/)에서
`kind: Gateway`를 찾고 다음 요구 필드만 가져온다.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web-gateway
  namespace: nginx-gateway
spec:
  gatewayClassName: nginx
  listeners:
    - name: http
      protocol: HTTP
      port: 80
```

```bash
kubectl explain gateway.spec.listeners
kubectl create -f web-gateway.yaml
kubectl describe gateway web-gateway -n nginx-gateway
```

클래스·리스너 값과 `Accepted`·`Programmed` 조건을 확인한다. 조건이 False이면 아래 진단 절차로
GatewayClass·컨트롤러를 확인한다. 생성 요구만 있으면 HTTPRoute·백엔드를 추가하지 않는다.
경로가 기억나지 않으면 Gateway API 사이트의 **Guides → Getting started**에서 예제를 찾는다.

### 기존 Gateway를 HTTPS 443 리스너로 고친다

기존 리소스 수정 문제는 먼저 현재 listener와 Secret을 확인하고, `spec.listeners`의 해당 항목만
HTTP 80에서 HTTPS 443으로 바꾼다. Gateway와 Secret이 같은 `cka5673` 네임스페이스에 있으면
기본 `Secret` 참조에 별도 `ReferenceGrant`가 필요 없다.

```bash
kubectl get gateway web-gateway -n cka5673 -o yaml
kubectl get secret kodekloud-tls -n cka5673
kubectl edit gateway web-gateway -n cka5673
```

리스너의 완성 형태는 다음과 같다. `mode: Terminate`는 Gateway가 인증서로 TLS를 종료한다는 뜻이다.

```yaml
listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: kodekloud.com
    tls:
      mode: Terminate
      certificateRefs:
        - name: kodekloud-tls
```

```bash
kubectl describe gateway web-gateway -n cka5673
# Listeners의 Attached Routes와 status.conditions의 Accepted·Programmed를 확인
```

:::caution[함정 — HTTPS listener와 Route는 서로 다른 층이다]
Gateway를 443으로 바꿔도 Route가 자동으로 생기거나 hostname이 맞춰지지는 않는다. 기존 HTTPRoute가
이 listener에 계속 붙는지는 `kubectl describe httproute -n cka5673`의 `Accepted`와
`ResolvedRefs`로 별도 확인한다. Secret이 다른 네임스페이스에 있으면 단순 이름 참조로는 부족하다.
:::

### HTTPRoute의 parentRefs — 세 값을 클러스터에서 캐낸다

Gateway 다음 문제는 그 Gateway에 HTTPRoute를 붙이는 것이다. Route 자체는 **백엔드 Service와
같은 네임스페이스**에 만들고(`backendRefs`는 기본적으로 같은 ns만 참조한다 — "Ingress는 앱과
같은 ns"와 동일한 원칙), `parentRefs`에 채울 세 값은 전부 클러스터에서 캐낸다.

```bash
kubectl get gateway -A                       # parentRefs의 name과 namespace
kubectl get gateway nginx-gateway -n nginx-gateway \
  -o jsonpath='{.spec.listeners[*].name}'    # sectionName에 넣을 listener 이름
```

`sectionName`은 특정 listener에만 붙일 때 쓴다 — listener가 하나면 생략해도 붙지만, 문제가
listener 이름을 지정하면 명시한다. 그리고 이 Route가 실제로 붙을 수 있는지는 Route가 아니라
**Gateway의 `allowedRoutes`가 쥐고 있다** — 다른 ns에서 붙으려면 앞 절에서 만든 `from: All`이
전제다.

`rules` 쪽은 출처를 주의한다 — **simple-gateway 페이지의 HTTPRoute 예시에는 `matches`가 없다**
(경로 지정 없이 모든 트래픽을 매치하는 최소 예시다). `PathPrefix`를 명시하는 문제는
[HTTP routing 가이드](https://gateway-api.sigs.k8s.io/guides/user-guides/http-routing/)의 matches
블록을 복사하거나, `kubectl explain httproute.spec.rules.matches.path`로 철자와 허용값
(Exact | PathPrefix | RegularExpression)을 확인한다.

YAML 형태는 [CKA Ingress와 Gateway API](/cka/ingress-gateway/#httproute)에 있고, 만든 뒤에는
진단 사슬 3단계(`describe httproute` → `Accepted`·`ResolvedRefs`)로 판정한다 — `Accepted=False`면
parentRefs와 allowedRoutes, `ResolvedRefs=False`면 backendRefs의 Service 이름·포트를 본다.

### 배포를 진단하기 — API 설치와 구현체를 분리한다

```bash
# 1. API 종류와 구현체가 각각 존재하는가
kubectl api-resources --api-group=gateway.networking.k8s.io
kubectl get gatewayclass
kubectl describe gatewayclass <class>                 # Accepted condition
# 컨트롤러 Pod 위치와 라벨은 설치한 구현체 문서에서 확인한다
kubectl get pods -A | grep -i gateway

# 2. Gateway가 실제 데이터 플레인에 반영됐는가
kubectl describe gateway <gateway> -n <gateway-namespace>
# status.conditions의 Accepted=True, Programmed=True와 ADDRESS를 확인

# 3. HTTPRoute가 부모에 붙었고 백엔드 참조를 풀었는가
kubectl describe httproute <route> -n <route-namespace>
# status.parents[].conditions의 Accepted=True, ResolvedRefs=True를 확인

# 4. Route 아래의 Service에도 Ready 엔드포인트가 있는가
kubectl get svc <backend-service> -n <backend-namespace>
kubectl get endpointslices -n <backend-namespace> \
  -l kubernetes.io/service-name=<backend-service> -o wide

# 5. Gateway의 주소 또는 구현체 Service의 NodePort로 실제 요청한다
curl -fsS -H 'Host: <route-hostname>' http://<gateway-address>:<port>/<path>
```

`GatewayClass`가 `Accepted=False`면 `controllerName`을 처리할 구현체부터 확인한다.
Gateway가 `Programmed=False`면 선언은 받아들였지만 데이터 플레인 반영이 끝나지 않은 것이므로
컨트롤러 이벤트·로그로 내려간다. HTTPRoute가 `Accepted=False`면 `parentRefs`, listener와
`allowedRoutes`를, `ResolvedRefs=False`면 Service 이름·포트와 교차 네임스페이스 `ReferenceGrant`를 본다.
모든 condition이 참이어도 EndpointSlice와 마지막 HTTP 요청을 확인해야 실제 경로가 완성된다.

공식 기준은 Kubernetes v1.35의
[Ingress](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/ingress/),
[Gateway API](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/gateway/)와
Gateway API 프로젝트의 [시작 안내](https://gateway-api.sigs.k8s.io/guides/getting-started/introduction/)다.

## 완료 판정

- Gateway API 리소스와 GatewayClass의 구현체 컨트롤러가 존재한다.
- Gateway의 listener protocol·port·hostname과 HTTPRoute parentRefs·matches·backendRefs가 요구값이다.
- Gateway와 HTTPRoute의 Accepted·Programmed·ResolvedRefs 조건이 참이다.
- Gateway 주소에 host·path를 넣은 실제 요청이 대상 Service 응답을 반환한다.
