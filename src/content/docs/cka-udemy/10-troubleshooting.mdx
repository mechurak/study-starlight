## metrics-server — Practice Test: Monitor Cluster Components

원본 풀이: [03-Practice-Test-Monitor-Cluster-Components.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/04-Logging-and-Monitoring/03-Practice-Test-Monitor-Cluster-Components.md)

`kubectl top`은 **metrics-server가 있어야** 동작한다 — 기본 설치가 아니다.

```bash
# "Let us deploy metrics-server to monitor the PODs and Nodes. Pull the git repository for the deployment files."
git clone https://github.com/kodekloudhub/kubernetes-metrics-server.git
# "Deploy the metrics-server by creating all the components downloaded."
kubectl create -f kubernetes-metrics-server/
# "Identify the node that consumes the most CPU(cores)."
kubectl top node                  # CPU(cores) / MEMORY(bytes) 열
# "Identify the POD that consumes the most Memory(bytes)."
kubectl top pod
```

### `kubectl top` 출력 읽기

```text
NAME                           CPU(cores)   MEMORY(bytes)
flask-app-4-5cfb5d78c4-p9l2m  1m           19Mi
flask-app-4-5cfb5d78c4-t229n  1m           19Mi
```

헤더가 `CPU(cores)`와 `MEMORY(bytes)`여도 실제 값에는 읽기 쉬운 접미사가 붙는다.

| 출력 | 읽는 법 |
|---|---|
| CPU `1m` | 0.001 CPU = 코어 하나의 0.1%에 해당하는 사용량 |
| CPU `500m` | 0.5 CPU |
| CPU `1000m` | 1 CPU |
| 메모리 `19Mi` | 19 mebibytes = `19 × 1024²` bytes, 약 19.9 MB |

CPU의 `m`은 millisecond가 아니라 **millicpu**다. [공식 리소스 단위 설명](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#resource-units-in-kubernetes)처럼
`1000m = 1 CPU`로 읽는다. 메모리의 `Mi`는 mebibyte라서 `1Mi = 1,048,576 bytes`이고,
10진 단위인 `1M = 1,000,000 bytes`와 다르다.

CPU 값은 실행 후의 누적 CPU 시간이 아니라 **최근 측정 구간의 평균 CPU 사용 속도**다.
예를 들어 15초 구간에 CPU 시간 7.5초를 소비했다면 `7.5 / 15 = 0.5 CPU = 500m`이다.
여기서 15초는 설명용 예시이며 실제 구간은 클러스터에 따라 다를 수 있다. Metrics API는
그 구간을 `window`로 돌려준다.

```bash
kubectl get --raw \
  '/apis/metrics.k8s.io/v1beta1/namespaces/<namespace>/pods/<pod>'
# 응답의 timestamp와 window 확인
```

[Metrics API의 `timestamp`와 `window`](https://kubernetes.io/docs/reference/external-api/metrics.v1beta1/)는
`timestamp - window`부터 `timestamp`까지 수집한 값이라는 뜻이다. 요청이 없던 frontend Pod의
CPU가 `1m`처럼 작은 것은 자연스럽다. probe나 런타임의 백그라운드 작업 때문에 꼭 `0m`은 아니며,
메모리는 시간당 사용량이 아니므로 앱 프로세스가 떠 있는 동안 일정량을 계속 차지할 수 있다.

- `kubectl top pod`은 현재 namespace만 본다. 전체 namespace는 `kubectl top pods -A`
- 짧은 CPU 급증은 평균값에 희석돼 peak 그대로 보이지 않을 수 있다. `top`은 현황 점검과 오토스케일링용이지
  장기 이력이나 정밀 분석용 모니터링 도구가 아니다

- 설치 직후에는 수집이 안 돼 있다 — **몇 분 기다렸다가** top이 값을 낼 때까지 재시도
  — *It takes a few minutes for the metrics server to start gathering data.*
- "가장 CPU를 많이 쓰는 노드/Pod" 유형은 전부 top 출력의 열 읽기다
- 정렬까지 시키면 `kubectl top pod --sort-by=memory`

메트릭이 어디서 와서 어디로 가는지(kubelet → metrics-server → HPA)는
[cka 8장 메트릭 파이프라인](/cka/08-autoscaling/)에 있다.

## 오토스케일러 — 제공된 파일과 CRD 스키마 활용

HPA(Horizontal Pod Autoscaler)는 복제본 수를, VPA(Vertical Pod Autoscaler)는 컨테이너 리소스 요청량을
조정한다. 개념은 [CKA 오토스케일링 장](/cka/08-autoscaling/)에서 보고 여기서는 생성·검증 순서를 연습한다.

### webapp-hpa — CPU 50%와 축소 안정화 300초

```bash
cat /root/webapp-hpa.yaml
vim /root/webapp-hpa.yaml
kubectl explain hpa.spec.behavior.scaleDown --api-version=autoscaling/v2
```

제공 파일부터 연다. 다음은 예제 완성본이며 `minReplicas: 2`, `maxReplicas: 10`은 이 예제의 값이다.
본문에서 최소·최대를 따로 지정하지 않았다면 제공 파일의 값을 유지한다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: webapp-hpa
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: kkapp-deploy
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```

공식 [Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)에서
`stabilizationWindowSeconds`를 검색한다. CPU 비율은 **CPU request 대비 사용률**이고,
안정화 창은 최근 300초의 권장 복제본 수 중 큰 값을 고려해 급격한 축소를 억제한다.
단순히 모든 축소를 무조건 300초 지연하는 타이머로 읽지 않는다.

```bash
kubectl apply -f /root/webapp-hpa.yaml
kubectl get hpa webapp-hpa -n default
kubectl describe hpa webapp-hpa -n default
```

대상 Deployment, CPU 목표 50%, Scale Down 안정화 300초를 확인한다.
메트릭이 계속 `<unknown>`이면 Conditions·Events에서 CPU requests 누락과 metrics 수집 실패를 구분한다.
생성 성공과 실제 스케일링 가능 여부는 별도다.

### analytics-vpa — Recreate 모드로 요청량 조정

공식 [Vertical Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/vertical-pod-autoscale/)에서
`updateMode`를 검색해 골격을 가져온다. VPA는 별도 CRD·컨트롤러가 필요하며,
설치된 환경에서는 `kubectl explain vpa.spec`와 `kubectl explain vpa.spec.updatePolicy`도 활용한다.

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: analytics-vpa
  namespace: default
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: analytics-deployment
  updatePolicy:
    updateMode: Recreate
```

```bash
kubectl create -f analytics-vpa.yaml
kubectl describe vpa analytics-vpa -n default
```

`Target Ref`와 `Update Mode: Recreate`를 확인하고, 시간이 지난 뒤 권장값과 Conditions를 본다.
HPA는 `scaleTargetRef`, VPA는 `targetRef`다. Recreate는 필요 시 Pod를 축출하고 Deployment가
새 요청량을 가진 Pod를 다시 만들도록 한다. 생성 직후 즉시 축출되어야 하는 것은 아니다.
기본 구성은 CPU·메모리 요청량을 조정하며 limits도 비례 조정할 수 있다.
문제가 limits 유지를 명시하면 `resourcePolicy.containerPolicies`의
`controlledValues: RequestsOnly`를 공식 문서의 **Resource policies**에서 찾아 추가한다.

## 증상에 맞는 로그 진입점을 고른다

`Pending`이라는 글자만 보고 로그부터 열지 않는다. 먼저 `spec.nodeName`과 Events로 **스케줄링 전**인지,
노드에 배치된 뒤 **컨테이너 생성·실행 중** 실패했는지를 가른다.

```bash
kubectl get pod <pod> -o wide       # STATUS / NODE 확인
kubectl describe pod <pod>
```

| 확인 결과 | 다음 증거 | 진입점 |
|---|---|---|
| `NODE`가 비었고 `Pending` | 스케줄러가 후보 노드를 모두 거른 이유 | `describe pod`의 Events |
| `NODE`가 있고 컨테이너가 재시작 | 현재·이전 컨테이너 출력 | `kubectl logs -c …`, `--previous` |
| 노드가 `NotReady`이거나 컨테이너 생성 자체가 실패 | 해당 노드의 kubelet·런타임 | `journalctl -u kubelet`, `crictl` |
| control plane Pod이 실패하고 API는 응답함 | `kube-system`의 컴포넌트 로그 | `kubectl -n kube-system logs …` |
| API 서버가 응답하지 않음 | control plane 노드의 스태틱 Pod 컨테이너 | `crictl ps -a`, `crictl logs` |

```bash
# 실행된 컨테이너가 있다 — 애플리케이션 출력부터 본다
kubectl logs <pod> -c <container> --previous

# 노드 조건·kubelet 문제다 — Pod이 배치된 노드로 들어간다
kubectl get pod <pod> -o wide
ssh <node>
sudo journalctl -u kubelet -n 100 --no-pager
sudo ls -l /var/log/containers/                 # /var/log/pods 쪽 로그의 링크

# kubeadm control plane에서 API 서버가 죽었다 — kubectl 대신 런타임으로 내려간다
sudo crictl ps -a --name kube-apiserver
sudo crictl logs <container-id>
```

Linux의 systemd 기반 노드에서는 kubelet과 컨테이너 런타임 로그를 journald에서 읽는다. 반면 kubeadm의
API 서버·스케줄러·컨트롤러 매니저는 보통 스태틱 Pod이므로, API가 살아 있으면 `kubectl logs`, 죽었으면
노드의 `crictl logs`가 같은 컨테이너 로그로 가는 두 경로다. 컨테이너 표준 출력의 기본 실체는
`/var/log/pods` 아래이고 `/var/log/containers`는 이를 찾기 쉬운 링크로 제공한다.

:::caution[실패 층이 바뀌면 도구도 바뀐다]
라벨·taint·리소스 때문에 스케줄링되지 않은 Pod에는 읽을 컨테이너 로그가 없다. 반대로 `nodeName`이
채워졌는데도 `journalctl -u kubelet`만 뒤지면 애플리케이션의 종료 원인을 놓친다. 먼저 Events로
경계를 정하고, 배치 뒤에는 컨테이너 → kubelet → control plane 순으로 필요한 층만 내려간다.
:::

공식 근거: [로깅 아키텍처](https://v1-35.docs.kubernetes.io/docs/concepts/cluster-administration/logging/),
[Pod 디버깅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-application/debug-pods/),
[클러스터 트러블슈팅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-cluster/),
[`crictl`로 노드 디버깅](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-cluster/crictl/).

## 컨트롤 플레인 장애 — Control Plane Failure

배포가 동작하지 않거나 scale 뒤 Pod 수가 늘지 않을 때는 **Pod 생성과 노드 배정 중 어디서 멈췄는지**
먼저 가른다. 이 절은 실습에서 관찰한 scheduler 실행 명령 오타, controller-manager kubeconfig 경로
오타, 인증서 hostPath 오류를 다룬다. 명령의 `<namespace>`, `<deployment>`, `<app-pod>`는 실제 대상으로 바꾼다.

### Deployment에서 시작해 담당 컴포넌트를 좁힌다

```bash
kubectl get deployments -A
kubectl -n <namespace> get deployment <deployment> \
  -o jsonpath='{.spec.replicas}{"\n"}'
kubectl -n <namespace> get replicasets
kubectl -n <namespace> get pods -o wide
# 대상 Pod가 존재하면 Events 확인
kubectl -n <namespace> describe pod <app-pod>
kubectl -n kube-system get pods
```

Deployment controller는 Deployment의 원하는 상태를 ReplicaSet에 반영하고, ReplicaSet controller는
부족한 Pod를 생성한다. 이 두 controller는
[`kube-controller-manager`](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)에서
실행된다. scheduler는 생성된 Pod에 노드를 배정한다.

| 관찰 | 우선 조사할 단계 |
|---|---|
| `spec.replicas`가 요청한 값으로 바뀌지 않음 | scale 대상·namespace와 요청 결과 |
| 원하는 개수는 바뀌었지만 새 Pod 자체가 없음 | Deployment·ReplicaSet controller, 해당 객체의 Events |
| 새 Pod가 `Pending`이고 `NODE`가 `<none>` | scheduler 상태와 Pod의 스케줄링 Events |
| 노드는 배정됐지만 앱이 실행되지 않음 | 컨테이너 생성·실행 단계의 Events와 로그 |

이 표는 조사 방향이다. Pod 생성 실패는 quota, 미배정은 리소스 부족·taint 등으로도 발생하므로
**증상만으로 control plane 장애를 확정하지 않는다.** scheduler가 죽어 있으면 실패 이유를 기록할
프로세스도 없어 `FailedScheduling` 이벤트가 없을 수 있다.

### scheduler — 실행 파일 이름 오타는 Events에서 찾는다

```bash
kubectl -n kube-system describe pod kube-scheduler-controlplane
```

실습 Events의 결정적인 부분은 다음과 같다.

```text
exec: "kube-schedulerrrr": executable file not found in $PATH
```

`image ... already present`는 이미지가 있다는 뜻이고, `Container created`도 프로세스 실행 성공을
뜻하지 않는다. 긴 `containerd → shim → OCI → runc` 오류 끝의 `exec` 메시지가 실행 파일 이름을
가리킨다. `BackOff`는 반복 실패로 재시도 간격을 늘린 결과다. 프로세스가 시작되기 전 실패여서
`kubectl logs`에는 유용한 출력이 없을 수 있다.

controlplane 노드에서 다음 파일을 열고 `spec.containers[].command`의 첫 항목만 고친다.

```bash
vim /etc/kubernetes/manifests/kube-scheduler.yaml
```

```yaml
# command의 해당 항목 발췌 — 기존 플래그는 유지
command:
  - kube-scheduler # 잘못된 kube-schedulerrrr를 수정
```

### controller-manager — kubeconfig 경로 오타는 로그에서 찾는다

replicas를 2로 늘렸는데 새 Pod가 생기지 않고 controller-manager가 `CrashLoopBackOff`라면 로그를 읽는다.

```bash
kubectl -n kube-system logs kube-controller-manager-controlplane
# 현재 로그가 없거나 이전 실행의 원인이 필요할 때
kubectl -n kube-system logs kube-controller-manager-controlplane --previous
```

```text
stat /etc/kubernetes/controller-manager-XXXX.conf: no such file or directory
```

이번에는 프로세스가 시작한 뒤 지정된 파일을 찾지 못해 종료했다. 앞서 출력된
`Generated self-signed cert in-memory`는 실패 원인이 아니다.
[kubeadm의 기본 kubeconfig](https://kubernetes.io/docs/reference/setup-tools/kubeadm/implementation-details/)는
`/etc/kubernetes/controller-manager.conf`이며 API 서버 접속·인증 정보를 담는다.

```bash
# controlplane 노드에서 실제 파일 확인 후 manifest 수정
ls -l /etc/kubernetes/controller-manager.conf
vim /etc/kubernetes/manifests/kube-controller-manager.yaml
```

Vim에서 `/controller-manager-XXXX.conf`를 검색해 잘못된 참조를
`/etc/kubernetes/controller-manager.conf`로 바꾼다. 예를 들어 `--kubeconfig`가 틀렸다면 다음과 같다.

```yaml
- --kubeconfig=/etc/kubernetes/controller-manager.conf
```

로그만으로 어느 옵션이 틀렸는지까지 확정할 수는 없다. `--authentication-kubeconfig`,
`--authorization-kubeconfig` 등 실제 manifest에서 해당 경로를 쓰는 위치를 대조한다.

### controller-manager — 파일 없음에서 hostPath 오류까지 추적한다

replicas를 3으로 늘린 뒤 다시 멈췄고 로그가 다음과 같다면, 확인된 사실은
**컨테이너 안에서 CA 인증서 파일을 찾지 못했다는 것**이다. CA는 인증서를 검증하는 인증 기관이다.
아직 volume 오류로 단정할 수 없다.

```text
unable to load client CA provider: open /etc/kubernetes/pki/ca.crt: no such file or directory
```

manifest에서 `/ca.crt`를 검색해 실행 인자를 확인하고, `volumeMounts`의 이름으로 `volumes`를 따라간다.
아래는 잘못된 설정의 관련 부분만 발췌한 예시다. 이름은 실제 manifest를 따른다.

```yaml
spec:
  containers:
    - name: kube-controller-manager
      command:
        - kube-controller-manager
        - --client-ca-file=/etc/kubernetes/pki/ca.crt
      volumeMounts:
        - name: k8s-certs
          mountPath: /etc/kubernetes/pki
          readOnly: true
  volumes:
    - name: k8s-certs
      hostPath:
        path: /etc/kubernetes/WRONG-PKI-DIRECTORY
        type: DirectoryOrCreate
```

| 추적할 필드 | 이 예시에서 읽는 뜻 |
|---|---|
| `--client-ca-file` | 컨테이너가 `/etc/kubernetes/pki/ca.crt`를 열려고 함 |
| `volumeMounts.mountPath` | 컨테이너의 `/etc/kubernetes/pki`에 volume을 연결 |
| `volumeMounts.name` → `volumes.name` | `k8s-certs`라는 같은 이름으로 원본을 찾음 |
| `hostPath.path` | 노드의 `/etc/kubernetes/WRONG-PKI-DIRECTORY`가 실제 원본 |

[`hostPath`](https://kubernetes.io/docs/concepts/storage/volumes/#hostpath)는 노드의 파일·디렉터리를
컨테이너에 연결한다. 컨테이너와 노드의 경로 이름이 같아야 하는 것은 아니다. 이 예시에서는 컨테이너가
요청한 `ca.crt`가 **노드의 `/etc/kubernetes/WRONG-PKI-DIRECTORY/ca.crt`로 연결된다.**

controlplane 노드에서 실제 원본과 비교한다.

```bash
ls -l /etc/kubernetes/pki/ca.crt
ls -ld /etc/kubernetes/WRONG-PKI-DIRECTORY
ls -l /etc/kubernetes/WRONG-PKI-DIRECTORY/ca.crt
```

정상 경로에 파일이 있지만 연결된 경로에는 없다면 잘못된 `hostPath`라는 근거가 확보된다.
manifest에서 해당 volume의 원본만 수정한다.

```yaml
hostPath:
  path: /etc/kubernetes/pki
  type: DirectoryOrCreate
```

:::caution[마운트가 성공해도 필요한 파일은 없을 수 있다]
`DirectoryOrCreate`는 지정한 디렉터리가 없으면 빈 디렉터리를 만든다. 인증서를 채워 주지는 않는다.
따라서 잘못된 경로의 마운트 자체는 성공하고 controller-manager가 파일을 열 때 실패할 수 있다.
volume 설정 문제여도 `FailedMount` 이벤트가 반드시 나오는 것은 아니다.
:::

파일 없음은 **실행 인자 → 컨테이너 mountPath → 같은 name의 volume → 노드 원본 파일** 순으로
추적한다. 인자 오타, 마운트 누락, 잘못된 hostPath, 원본 파일 누락을 이 대조로 구분한다.

### static Pod 수정과 원래 워크로드 복구를 검증한다

이 실습의 scheduler와 controller-manager는 kubelet이 로컬 manifest를 읽어 관리하는 **static Pod**다.
[공식 static Pod 동작](https://kubernetes.io/docs/tasks/configure-pod-container/static-pod/)에 따라
controlplane 노드에서 `vim /etc/kubernetes/manifests/<component>.yaml`로 바로 수정하고 `:wq`로 저장하면
kubelet이 변경을 감지해 Pod를 재생성한다. 권한이 부족하면 `sudo vim`을 쓴다.
별도 `kubectl apply`나 kubelet 재시작은 필요하지 않으며, `kubectl edit pod` 대신 노드의 원본을 고친다.

백업은 선택 사항이다. 만들 경우 감시 디렉터리 밖에 둔다.

```bash
# 예: controller-manager를 편집하기 전에 실행
cp /etc/kubernetes/manifests/kube-controller-manager.yaml \
  /root/kube-controller-manager.yaml.bak
```

`manifests` 안의 `.bak`도 kubelet이 읽을 수 있다. 수정 실수로 상태가 악화되면 외부에 둔 백업을
원본 경로로 복원하고 다시 상태·Events·로그를 확인한다.

```bash
# 고친 컴포넌트만 선택 — READY 1/1, STATUS Running 확인 후 Ctrl+C
kubectl -n kube-system get pod kube-scheduler-controlplane -w
kubectl -n kube-system get pod kube-controller-manager-controlplane -w

# 원래 요청한 replica 수와 실제 상태 확인
kubectl -n <namespace> get deployment <deployment> \
  -o jsonpath='{.spec.replicas}{"\n"}'
kubectl -n <namespace> get deployment <deployment>
kubectl -n <namespace> get pods -o wide
kubectl -n <namespace> rollout status deployment/<deployment> --timeout=120s
```

:::tip[완료 기준은 원래 문제의 해결]
컴포넌트의 `Running`만 보고 끝내지 않는다. scheduler 복구 뒤에는 새 Pod의 노드 배정,
controller-manager 복구 뒤에는 부족한 Pod 생성, 최종적으로 Deployment의 `READY`가 요청한
`2/2` 또는 `3/3`인지 확인한다. 원하는 replica 수가 이미 저장됐다면 다시 scale할 필요가 없다.
Pod가 생성된 뒤 다른 이유로 실패하면 새 Events를 기준으로 다음 층을 조사한다.
:::

## 워커 노드 장애 — Worker Node Failure

“Fix the broken cluster”처럼 원인을 알려 주지 않는 문제는 **문제 노드 → 서비스 상태 → 최근 로그 →
최소 수정 → Ready 복구** 순으로 접근한다. 이 실습은 kubeadm·systemd 환경이며, node01에서는
root로 명령을 실행한다. 일반 사용자라면 서비스 제어·설정 수정 등에 `sudo`를 붙인다.

| 발견한 증거 | 수정 대상 | 첫 조치 |
|---|---|---|
| kubelet이 `inactive (dead)`이고 구체적인 시작 실패 원인은 아직 없음 | kubelet 서비스 | 시작한 뒤 유지되는지 확인 |
| `unable to load client CA file` + `no such file or directory` | `config.yaml`의 CA 파일 경로 | 실제 파일과 대조해 경로 수정 |
| `controlplane:6553` + `connection refused` | `kubelet.conf`의 API 서버 주소 | 정상 접속 주소와 대조해 포트 수정 |

### 공통 진입점 — 서비스 상태와 최근 로그를 함께 읽는다

```bash
# controlplane에서
kubectl get nodes
kubectl describe node node01
ssh node01

# node01에서
systemctl status containerd --no-pager
systemctl status kubelet --no-pager
journalctl -u kubelet -n 100 --no-pager
```

`describe node`의 Conditions·Events로 노드 상태를 확인한다. kubelet의 상태 보고가 끊기면
`Ready` 조건이 `Unknown`이고 `Kubelet stopped posting node status`가 나타날 수 있다.
`NotReady`만으로 서비스 중지를 확정하지 않는다.
[공식 클러스터 진단 예시](https://kubernetes.io/docs/tasks/debug/debug-cluster/)에서도 이 상태 보고를 확인한다.

containerd는 컨테이너 실행을, kubelet은 노드의 Pod 관리와 상태 보고를 담당한다.
`systemctl status`는 **현재 실행 상태**, `journalctl`은 **그 상태에 이른 과정**을 확인하는 도구다.
systemd 환경의 kubelet 로그는 [공식 로깅 문서](https://kubernetes.io/docs/concepts/cluster-administration/logging/)처럼
`journalctl -u kubelet`로 읽는다.

| 옵션 | 의미 |
|---|---|
| `-u kubelet` | kubelet 서비스의 로그만 선택 |
| `-n 100` | 최근 100줄 표시 |
| `-f` | 새 로그를 계속 표시. `Ctrl+C`로 종료 |
| `--no-pager` | 별도 뷰어 없이 터미널에 출력 |

`--no-pager`는 필수가 아니며 로그 내용을 바꾸지 않는다. 생략하면 보통 `less` 같은 뷰어가 열리고
`q`로 나간다. 최근 로그를 읽고 곧바로 다음 명령을 입력하기 편해서 붙인다.
`-f`를 붙였다면 `--no-pager`가 있어도 계속 관찰하므로 `Ctrl+C`로 종료한다.

### kubelet 중지 — inactive를 확인하고 시작한다

첫 문제에서는 containerd가 `active (running)`이고 kubelet은 다음 상태다.

```text
Loaded: ... enabled
Active: inactive (dead)
...
code=exited, status=0/SUCCESS
```

`enabled`는 부팅 시 자동 시작 설정이지 현재 실행 상태가 아니다. `inactive (dead)`가 현재 중지를 뜻한다.
`0/SUCCESS`는 이전 프로세스가 정상 종료 코드를 남겼다는 뜻이며, 노드 정상 여부나 중지 원인을 알려 주지는 않는다.

이때 “우선 start 해보자”는 판단은 중지 상태에서 나온다. 로그에 `Stopping…`, `Stopped…`만 있고
반복 오류가 없다면 시작 후 유지되는지 확인한다. 반면 파일 없음·설정 파싱 실패처럼 시작을 막는 오류가
있다면 해당 원인을 먼저 고친다. 종료 로그만으로 누가 왜 중지했는지까지 확정할 수는 없다.

```bash
# node01에서
systemctl start kubelet
systemctl status kubelet --no-pager
```

힌트의 `ssh node01 "service kubelet start"`는 controlplane에서 SSH로 node01의 서비스를 시작하는
축약형이다. 시작 직후 다시 종료되면 최근 로그로 원인을 조사하고, 실행이 유지되면 아래 공통 검증으로 넘어간다.

### 설정 경로 찾기 — config와 kubeconfig를 구분한다

기본 경로를 알아두되, 기억나지 않으면 node01에서 서비스 실행 설정을 확인한다.

```bash
systemctl cat kubelet
```

서비스 본체와 추가 설정에서 다음 인자를 찾는다. 실제 출력에는 환경 변수나 다른 인자가 함께 있다.

```text
--config=/var/lib/kubelet/config.yaml
--kubeconfig=/etc/kubernetes/kubelet.conf
```

| 인자와 기본 경로 | 역할 | 이 실습에서 수정하는 값 |
|---|---|---|
| `--config`: `/var/lib/kubelet/config.yaml` | kubelet 동작 설정 | `authentication.x509.clientCAFile` |
| `--kubeconfig`: `/etc/kubernetes/kubelet.conf` | kubelet의 API 서버 접속·인증 정보 | `clusters` 아래 `server` |

이는 [kubeadm의 기본 kubelet 실행 설정](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/kubelet-integration/)이다.
설치 방식이나 서비스 override에 따라 경로가 다를 수 있으므로 실제 실행 인자가 기준이다.

### CA 경로 오류 — 로그의 파일명과 실제 파일을 대조한다

두 번째 문제의 결정적인 오류는 다음과 같다.

```text
unable to load client CA file /etc/kubernetes/pki/WRONG-CA-FILE.crt:
open /etc/kubernetes/pki/WRONG-CA-FILE.crt: no such file or directory
```

**CA 파일을 읽으려 했으나 지정된 경로에 파일이 없다**는 뜻이다. 이 오류는 인증서 만료를 뜻하지 않는다.
같은 설정으로 시작을 반복하기 전에 파일 누락인지 경로 오타인지 확인한다.

```bash
# node01에서
cat /var/lib/kubelet/config.yaml
ls -l /etc/kubernetes/pki/ca.crt
vi /var/lib/kubelet/config.yaml
```

이번 실습의 올바른 파일은 `ca.crt`다. 기존 `authentication` 아래의 경로만 수정한다.
아래는 관련 부분 발췌이므로 파일 전체를 덮어쓰지 않는다.

```yaml
authentication:
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt
```

`clientCAFile`은 [kubelet에 접속하는 클라이언트의 인증서를 검증할 CA](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-authn-authz/)를
지정한다. 수정 뒤 `systemctl restart kubelet`으로 설정을 다시 읽게 하고 아래 공통 검증을 수행한다.

### API 서버 포트 오류 — kubelet.conf의 server를 고친다

세 번째 문제에서는 긴 로그의 접속 대상과 마지막 오류부터 읽는다.

```text
Get "https://controlplane:6553/api/v1/nodes?...":
dial tcp 192.24.132.5:6553: connect: connection refused
```

호스트 이름이 IP로 해석됐고 해당 IP의 `6553` 포트로 TCP 연결을 시도했으나 거부됐다.
인증서 검증이나 권한 검사까지 도달한 오류가 아니다. `connection refused`만으로 포트 오타를 확정할 수는
없지만, [API 서버 기본 포트가 6443](https://kubernetes.io/docs/reference/networking/ports-and-protocols/)이므로
`6553`을 의심하고 정상 설정과 대조한다. 서버가 해당 포트에서 실행되지 않는 경우에도 연결은 거부될 수 있다.

```bash
# kubectl이 정상 동작하는 controlplane에서
kubectl config view
```

출력의 `clusters` 아래 `server:`를 읽는다. 이 실습에서는 아래 주소가 정상이다.
context가 여러 개라면 `current-context`와 `contexts`의 cluster 이름으로 사용할 항목을 찾는다.
서버 주소를 읽는 데 복잡한 JSONPath 추출 명령은 필요 없다.

```yaml
# 정상 출력의 관련 항목 발췌
server: https://controlplane:6443
```

```bash
# node01에서
vi /etc/kubernetes/kubelet.conf
```

기존 `server: https://controlplane:6553`의 포트만 `6443`으로 바꾸고 인증서·사용자 정보는 유지한다.
다른 환경에서는 프록시나 로드 밸런서가 별도 포트를 쓸 수 있으므로 기본값만 보고 무조건 바꾸지는 않는다.
수정 뒤 `systemctl restart kubelet`을 실행한다.

:::caution[실행 중인 kubelet도 API 서버에 연결하지 못할 수 있다]
이 연결 실패 로그만으로 kubelet 프로세스가 종료됐다고 판단할 수 없다. `active (running)`이어도
API 서버에 상태를 보고하지 못하면 노드가 `NotReady`가 될 수 있다. 서비스 상태와 노드 상태를 모두 확인한다.
:::

### 공통 완료 검증 — 서비스 실행과 노드 Ready를 모두 확인한다

```bash
# node01에서 시작 또는 수정·재시작한 뒤
systemctl status kubelet --no-pager
journalctl -u kubelet --since "2 minutes ago" --no-pager

# SSH 접속을 끝내고 controlplane에서
exit
kubectl get nodes -w
```

기존 오류 로그는 수정 후에도 남는다. 최근 출력 중에서도 **시작·재시작 이후 시각**의 메시지를 확인한다.
kubelet이 실행 상태를 유지하고 `node01`이 `Ready`로 돌아오면 `Ctrl+C`로 관찰을 종료한다.
상태 반영에는 잠시 시간이 걸릴 수 있다. 노드의 워크로드도 확인하려면 다음 출력에서 `NODE`와 상태를 읽는다.

```bash
kubectl get pods -A -o wide
```

## 애플리케이션 연결 실패 — MySQL Service 진단

앱이 MySQL에 연결하지 못하는 두 실습 사례다. **증상 → 이름·selector·포트 대조 → 틀린 필드만
수정 → 실제 연결 검증** 순서로 접근한다. 아래의 `k`는 `alias k=kubectl`을 설정한 셸을 전제로 한다.

```bash
k -n beta get pod --show-labels -o wide
k -n beta get svc -o wide
k -n beta describe svc mysql-service
```

Pod 라벨과 Service selector를 비교한 뒤, `describe`의 `TargetPort`를 아키텍처와 대조한다.
`get svc -o wide`에는 `targetPort`가 나오지 않는다. 각 열의 의미와 `expose` 옵션은
[5장 Service 조회·생성](/cka-udemy/05-services-dns/#첫-조회--pod-라벨과-service-selector를-나란히-본다)에 있다.
네임스페이스는 아래 각 사례에 맞춰 바꾼다.

### 이름 오류 — alpha의 mysql을 mysql-service로 교체한다

앱이 `mysql-service`라는 이름으로 접속하는데 Service는 `mysql`로 만들어져 있다면, selector와
포트가 맞아도 앱이 기대한 이름을 찾지 못한다. 기존 객체의 이름은 `edit`으로 바꿀 수 없으므로
올바른 이름의 Service를 만든다. 다음은 **잘못된 `mysql` Service를 삭제·교체하는 이 실습**의 명령이다.

```bash
k -n alpha get pod --show-labels -o wide
k -n alpha get svc -o wide
k -n alpha describe svc mysql

# 조회한 실제 Pod 이름이 mysql인 경우
k -n alpha delete svc mysql
k -n alpha expose pod mysql \
  --name=mysql-service \
  --port=3306 \
  --target-port=3306 \
  --selector=name=mysql

k -n alpha describe svc mysql-service
```

`pod mysql`은 조회한 실제 Pod 이름으로 바꾼다. 새 Service의 selector가 `name=mysql`,
Port와 TargetPort가 `3306`인지 확인하고, 대상 Pod IP가 연결됐는지 본다. 이어서 문제의 앱·테스트로
MySQL 연결을 재시도한다. 실패하면 아래 포트 진단과 계층별 검증으로 이어간다.

### targetPort 오류 — beta의 기존 Service를 edit으로 수정한다

Service 이름과 selector는 맞지만 `TargetPort`가 아키텍처의 `3306`과 다르면 기존 Service를 수정한다.
[`kubectl edit`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_edit/)은 저장한 변경을
서버에 반영하므로 별도로 `apply`하거나 Service·Pod를 재생성할 필요가 없다.

```bash
k -n beta describe svc mysql-service
k -n beta edit svc mysql-service
```

에디터에서 **`spec.ports` 아래의 `targetPort`만** `3306`으로 바꾸고 저장한다. 아래는 수정할 부분이며,
객체 전체를 덮어쓸 YAML이 아니다.

```yaml
spec:
  ports:
    - port: 3306
      targetPort: 3306
```

저장 뒤 `k -n beta describe svc mysql-service`로 `TargetPort: 3306/TCP`와 대상 Pod IP를 확인한다.
EndpointSlice를 직접 보려면 다음 명령을 쓴다.

```bash
k -n beta get endpointslices \
  -l kubernetes.io/service-name=mysql-service -o wide
```

엔드포인트 주소가 없으면 selector와 Pod 라벨·Ready 상태를 확인한다. 반대로 **엔드포인트가 있어도
숫자 `targetPort`가 틀리면 접속에 실패할 수 있다.** 주소 등록은 MySQL이 그 포트에서 실제로
응답한다는 증거가 아니다. 마지막에는 문제에서 제공한 앱·테스트 또는 MySQL 클라이언트로 연결을
재검증한다. 일반 HTTP용 `curl`로 MySQL 응답을 검사하지 않는다.
더 넓은 연결 문제는 [5장의 계층별 검증 절](/cka-udemy/05-services-dns/#service--dns--외부-경로를-한-겹씩-검증하기)로 이어간다.

## 네트워크 장애 — Practice Test: Troubleshoot Network

원본 풀이: [10-Practice-Test-Troubleshoot-Network.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/12-Troubleshooting/10-Practice-Test-Troubleshoot-Network.md)

같은 `triton` 네임스페이스의 웹앱·MySQL이 실패해도 **앱 Pod의 상태와 시스템 Pod의 오류**에 따라
진단 경로가 달라진다. 아래는 Flannel을 설치하도록 안내하는 실습 버전 기준이다. 예전 원본 풀이와
플러그인·Pod 이름이 다를 수 있으므로 현재 문제의 아키텍처와 힌트를 따른다.

먼저 `kubectl get nodes`와 `kubectl get pods -A`를 본다. Test 1은 앱이 `Pending`이므로
Events → Node → CNI로, Test 2는 앱이 실행 중이고 kube-proxy가 `CrashLoopBackOff`이므로
kube-proxy 로그 → 실행 옵션 → ConfigMap으로 좁힌다. 앱 Pod가 `Running`이라는 사실만으로
Service 경유 통신이나 DB 연결 성공까지 보장되지는 않는다.

### Test 1 — Pending에서 CNI 초기화 실패까지 추적한다

```bash
kubectl -n triton get pods -o wide
kubectl -n triton describe pod mysql
```

`Pending`만으로 CNI 장애를 확정하지 않는다. 자원 부족·PVC 문제도 가능하므로 Events의
스케줄링 실패 이유를 읽는다. 이 실습의 결정적인 증거는 다음과 같다.

```text
0/1 nodes are available:
1 node(s) had untolerated taint {node.kubernetes.io/not-ready: }
```

배치 가능한 정상 노드가 없다는 뜻이다. 아직 실행되지 않은 MySQL의 로그 대신 노드를 확인한다.

```bash
kubectl get nodes
kubectl describe node controlplane
kubectl get pods -A
kubectl get daemonsets -A

# 문제가 있는 노드에서 실행 — 일반 사용자라면 sudo 사용
journalctl -u kubelet --since "15 minutes ago" --no-pager \
  | grep -iE 'cni|NetworkPluginNotReady'
ls -la /etc/cni/net.d/
```

`describe node`에서는 `Conditions`의 `Ready` 메시지를 읽는다. kubelet 로그에
`NetworkPluginNotReady`와 `cni plugin not initialized`가 있고, 네트워크 애드온이 보이지 않으며
`/etc/cni/net.d/`에 keep 파일만 있다면 CNI(Container Network Interface) 누락·초기화 실패를
뒷받침한다. 인과관계는 **CNI 초기화 실패 → Node NotReady → not-ready taint로 배치 차단 →
앱 Pending**이다. [Kubernetes 네트워크 플러그인 문서](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage/net/network-plugins/)에서
런타임과 CNI의 역할을 확인할 수 있다.

CoreDNS의 `ContainerCreating`은 보조 증거다. 그 상태나 `unable to allocate IP address`만으로
CNI 미설치를 확정하지 않는다. IP 할당 실패는 설치된 플러그인의 설정·주소 풀 문제일 수도 있다.
`flannel|calico|weave|cilium` 이름 검색에 결과가 없어도 다른 플러그인일 수 있으므로 전체 리소스와
노드 설정을 함께 본다. 기존 애드온이 있다면 그 Pod의 Events·로그로 초기화 실패 원인을 조사한다.

### CNI 누락 진단과 Flannel 선택은 별도의 판단이다

**CNI가 없다는 오류는 특정 제품을 지정하지 않는다.** 이번 실습에서는 힌트가 Flannel 설치를
명시했기 때문에 선택한다. 문제 본문과 오류 로그만으로 Flannel을 유일한 정답으로 도출할 수는 없다.

- 문제에 CNI 이름·매니페스트가 주어지면 지정된 것을 사용한다.
- 기존 클러스터 복구라면 DaemonSet·ConfigMap·노드의 CNI 설정·기존 매니페스트에서 원래 CNI를 찾는다.
- 새 클러스터이고 지정이 없다면 요구 기능과 환경 호환성에 따라 선택한다.

설치 방법은 [kubeadm 문서의 Installing a Pod network add-on](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/#pod-network)에서
공통 조건을 읽고, 선택한 제공자의 공식 문서로 이동한다. Flannel은
[공식 README의 Deploying flannel manually](https://github.com/flannel-io/flannel#deploying-flannel-manually)
→ **Deploying Flannel with kubectl**에서 설치 명령과 매니페스트 URL을 찾는다.
문제에서 버전·URL을 지정했다면 그 지시를 우선하며, 긴 최신 설치 URL을 암기하는 데 집중하지 않는다.

```bash
kubectl get nodes \
  -o custom-columns=NAME:.metadata.name,POD_CIDR:.spec.podCIDR
```

Flannel 기본 매니페스트의 네트워크는 `10.244.0.0/16`이다. 노드별 Pod CIDR은 그 안의 부분 범위로
할당되며, 클러스터의 네트워크 범위가 다르면 공식 안내에 따라 매니페스트를 맞춘다.
**CIDR이 기본값과 맞는다는 사실은 Flannel을 사용했다는 증거가 아니다.** 설치 문서의
CNI 바이너리·커널 모듈 등 전제 조건도 함께 확인한다.

설치 뒤에는 노드부터 앱까지 복구를 확인한다.

```bash
kubectl wait --for=condition=Ready node/controlplane --timeout=180s
kubectl -n kube-flannel get pods
kubectl -n kube-system get pods
kubectl -n triton get pods -w
```

웹앱·MySQL이 `1/1 Running`이면 `Ctrl+C`로 관찰을 끝내고 App 탭에서 초록색 페이지를 확인한다.
이 실습의 NodePort는 `30081`이며 실제 문제의 이름·포트는 유지한다.
`not-ready` taint를 제거하거나 toleration을 추가해 배치만 강제해도 CNI 초기화 실패는 해결되지 않는다.

### Test 2 — kube-proxy 로그에서 누락된 설정 파일을 찾는다

```bash
kubectl get pods -A
kubectl -n kube-system logs <kube-proxy-pod>
# 직전 종료된 컨테이너의 오류가 필요할 때
kubectl -n kube-system logs <kube-proxy-pod> --previous
```

앱은 실행 중이지만 kube-proxy가 반복 종료되고, 로그에 다음 경로가 나온다.

```text
open /var/lib/kube-proxy/configuration.conf: no such file or directory
```

이 클러스터에서 [kube-proxy](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-proxy/)는
Service IP·NodePort 트래픽을 백엔드로 전달하는 규칙을 관리한다. 시작 실패가 Service 연결 장애의
원인이 될 수 있다. 다만 기존 규칙이 남아 있을 수 있어 kube-proxy 종료가 모든 기존 연결의 즉시
단절을 뜻하지는 않는다. 먼저 로그로 확인된 설정 파일 오류를 고친다.

### 실행 옵션과 ConfigMap의 파일 경로를 대조한다

```bash
kubectl -n kube-system get ds kube-proxy -o yaml
kubectl -n kube-system get cm kube-proxy -o yaml
```

DaemonSet의 `spec.template.spec`에서 관련 부분을 읽는다. 다음은 잘못된 설정의 발췌다.

```yaml
containers:
  - name: kube-proxy
    command:
      - /usr/local/bin/kube-proxy
      - --config=/var/lib/kube-proxy/configuration.conf
    volumeMounts:
      - name: kube-proxy
        mountPath: /var/lib/kube-proxy
volumes:
  - name: kube-proxy
    configMap:
      name: kube-proxy
```

`--config`가 읽을 파일을 지정하고, `volumeMounts`가 그 디렉터리에 연결한 볼륨을 알려 준다.
같은 `name`으로 `volumes`를 따라가면 원본이 `kube-proxy` ConfigMap임을 알 수 있다.
그 ConfigMap의 주 설정 key는 다음과 같다.

```yaml
data:
  config.conf: |-
    apiVersion: kubeproxy.config.k8s.io/v1alpha1
    # 이하 설정 생략
```

[ConfigMap을 파일로 마운트](https://kubernetes.io/docs/concepts/configuration/configmap/#using-configmaps-as-files-from-a-pod)하면
기본적으로 key가 파일명, value가 파일 내용이다. `configMap.items`가 있으면 `key`와 `path`의
매핑도 읽는다. 별도 매핑이 없는 이 실습에서 실제 제공 경로는
`/var/lib/kube-proxy/config.conf`인데 실행 옵션은 `configuration.conf`를 요구한다.
**올바른 파일명을 외우는 대신 실행 인자 → mountPath → volume name → ConfigMap key/path를 대조한다.**

이 경로는 컨테이너 내부 경로다. 노드 셸에서 같은 이름의 디렉터리에 파일을 만들어도
ConfigMap 볼륨의 내용은 바뀌지 않는다. 앞선 control plane의 hostPath 사례와 원본 종류가 다르다.

### DaemonSet의 틀린 인자만 수정하고 앱까지 검증한다

```bash
kubectl -n kube-system edit ds kube-proxy
```

`spec.template.spec.containers`의 `command` 또는 `args`에서 해당 줄만 바꾼다.
기존 이미지·다른 인자·볼륨은 유지한다.

```diff
- - --config=/var/lib/kube-proxy/configuration.conf
+ - --config=/var/lib/kube-proxy/config.conf
```

Pod만 삭제하면 잘못된 템플릿으로 다시 생성되므로 관리 원본인 DaemonSet을 고친다.
`RollingUpdate`이면 변경 후 자동 교체된다. `OnDelete`이면 템플릿 수정 후 해당 Pod를 삭제해야
새 설정을 사용한다. 전략별 절차는 [4장 스케줄링](/cka-udemy/04-scheduling/)에서 확인한다.

```bash
kubectl -n kube-system rollout status ds/kube-proxy --timeout=180s
kubectl -n kube-system get pods -l k8s-app=kube-proxy
kubectl -n kube-system logs <새-kube-proxy-pod> --tail=30
kubectl -n triton get pods
```

새 kube-proxy가 `1/1 Running`을 유지하고 파일 오류가 사라졌는지 확인한 뒤 App 탭에서
초록색 페이지까지 검증한다. 여전히 실패하면 Service selector·port·targetPort, EndpointSlice,
앱 로그로 이어간다. 구체적인 명령은 [5장 계층별 연결 검증](/cka-udemy/05-services-dns/#service--dns--외부-경로를-한-겹씩-검증하기)에 있다.

## 이 장에서 남길 것

- `kubectl top`은 metrics-server 설치가 선행 조건이고, 값이 뜰 때까지 시간이 걸린다
- CPU `1000m` = 1코어, 메모리 `1Mi` = 1024² bytes. CPU 값은 측정 구간의 평균 사용 속도
- 로그는 `-c`(컨테이너 지정)와 `--previous`(재시작 전) 두 옵션이 점수를 가른다
- `nodeName`이 비어 있으면 Events, 배치 뒤에는 컨테이너 로그, NotReady면 kubelet 로그로 층을 바꾼다
- Pod 생성이 멈추면 controller-manager, 생성 후 노드 미배정이면 scheduler를 조사하되 증거로 확정한다
- 파일 없음은 실행 인자 → mountPath → volume name → hostPath 원본을 대조한다
- static Pod는 노드 manifest를 직접 수정하고, 컴포넌트 정상화 뒤 원래 Deployment의 Ready 개수까지 확인한다
- control plane 로그는 API가 살아 있으면 `kubectl logs`, 죽었으면 노드에서 `crictl logs`
- worker node는 서비스 상태·최근 로그로 단순 중지, CA 파일 경로 오류, API 서버 연결 실패를 구분한다
- `systemctl cat kubelet`에서 `--config`와 `--kubeconfig`를 찾고, API 서버 주소는 `kubectl config view`의 `server`와 대조한다
- kubelet이 실행 중이어도 노드는 NotReady일 수 있다. 수정 후 최근 로그와 노드 Ready까지 검증한다
- Service 이름 오류는 올바른 이름으로 생성하고, `targetPort` 오류는 `edit svc`로 수정한 뒤 실제 연결을 검증한다
- 엔드포인트가 있어도 숫자 `targetPort`가 틀리면 연결에 실패할 수 있다
- 앱 Pending이면 Events에서 not-ready taint를 확인하고, 노드 조건·kubelet 로그·CNI 설정으로 원인을 좁힌다
- CNI 누락만으로 Flannel을 선택하지 않는다. 문제의 지정 또는 기존 설치 근거를 확인한다
- kube-proxy 파일 오류는 실행 인자 → mountPath → volume name → ConfigMap key/path를 대조한다
- DaemonSet 템플릿을 수정하고 새 Pod 정상화 뒤 원래 앱의 성공 응답까지 확인한다
