> 짝이 되는 개념 장: [cka 14. 인증 · 인가 · RBAC](/cka/14-rbac/)

아홉 실습이 전부 **TLS로 API 서버를 확인한 뒤 요청이 통과하는 세 관문**
(인증 → 인가 → admission) 위에 있다. 어느 경계의 문제인지부터 가르면 절반은 푼 것이다.

:::tip[실습 전 확인]
인증은 **누구인지**, 인가는 **그 신원이 해도 되는지**, admission은 **요청 내용이 정책에
맞는지**를 본다. RBAC(Role-Based Access Control, 역할 기반 접근 제어)은 역할에 권한을
정의하고 사용자·그룹·ServiceAccount를 그 역할에 묶는 인가 방식이다.
:::

## 인증서와 kubeconfig

### 인증서 읽기 — Practice Test: View Certificate Details

원본 풀이: [10-Practice-Test-View-Certificate-Details.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/10-Practice-Test-View-Certificate-Details.md)

kubeadm 기본 배치에서는 인증서가 다음 경로에 있다 —

| 무엇 | 어디 |
|---|---|
| API 서버 인증서 — *Identify the certificate file used for the kube-api server* | `/etc/kubernetes/pki/apiserver.crt` |
| API 서버 → etcd 클라이언트 — *Identify the Certificate file used to authenticate kube-apiserver as a client to ETCD Server* | `/etc/kubernetes/pki/apiserver-etcd-client.crt` |
| API 서버 → kubelet 클라이언트 인증서 | `/etc/kubernetes/pki/apiserver-kubelet-client.crt` |
| API 서버 → kubelet 클라이언트 개인 키 — *Identify the key used to authenticate kubeapi-server to the kubelet server* | `/etc/kubernetes/pki/apiserver-kubelet-client.key` |
| etcd 서버 인증서 — *Look for cert file option in the file /etc/kubernetes/manifests/etcd.yaml* | `/etc/kubernetes/pki/etcd/server.crt` |
| etcd CA — *Look for CA Certificate in file /etc/kubernetes/manifests/etcd.yaml* | `/etc/kubernetes/pki/etcd/ca.crt` |

경로의 근거는 스태틱 Pod 매니페스트다 — `/etc/kubernetes/manifests/kube-apiserver.yaml`,
`etcd.yaml`의 커맨드라인 플래그에 다 적혀 있다.

같은 `kube-apiserver` 프로세스도 상대에 따라 서버나 클라이언트가 된다. 문제의 대상과
플래그의 역할을 연결해야 한다.

| 묻는 것 | 플래그 | 의미 |
|---|---|---|
| kube-api server가 사용하는 certificate | `--tls-cert-file` | API 서버가 `kubectl`·kubelet에게 제시하는 **서버 인증서** |
| 위 인증서의 private key | `--tls-private-key-file` | API 서버 인증서와 짝인 **개인 키** |
| kube-apiserver를 etcd client로 인증하는 certificate | `--etcd-certfile` | API 서버가 etcd에 제시하는 **클라이언트 인증서** |
| 위 인증서의 private key | `--etcd-keyfile` | etcd 클라이언트 인증서와 짝인 **개인 키** |
| etcd 서버를 검증할 CA | `--etcd-cafile` | API 서버가 etcd 서버 인증서를 검증할 **신뢰 기준** |
| kube-apiserver를 kubelet client로 인증하는 certificate | `--kubelet-client-certificate` | API 서버가 kubelet에 제시하는 **클라이언트 인증서** |
| 위 인증서의 private key | `--kubelet-client-key` | kubelet 클라이언트 인증서와 짝인 **개인 키** |

`--service-account-signing-key-file=sa.key`는 ServiceAccount JWT를 **서명하는 개인 키**고,
`--service-account-key-file=sa.pub`는 그 서명을 **검증하는 공개 키**다. 이 둘은 API 서버의
HTTPS 서버 인증서가 아니다.

:::tip[이 실습 문제의 판별법]
*Identify the certificate file used for the kube-api server* → `--tls-cert-file` →
`/etc/kubernetes/pki/apiserver.crt`다. `--etcd-certfile`은 파일명에 `apiserver`가 있어도,
API 서버가 **etcd에 접속하는 클라이언트**로서 쓰는 인증서라서 이 문제의 답이 아니다.

*Authenticate A to B*는 **A가 B에게 자기 신원을 증명한다**는 뜻이다. 따라서
*Identify the key used to authenticate kubeapi-server to the kubelet server* →
`--kubelet-client-key` → `/etc/kubernetes/pki/apiserver-kubelet-client.key`다.
:::

`.crt`는 공개 키·신원·유효기간·CA 서명이 든 **인증서**, `.key`는 보통 그 인증서와 짝인
**개인 키**다. `.pem`은 인증서나 키 모두를 담을 수 있는 텍스트 저장 형식이다.
확장자는 관례일 뿐이니 내용은 PEM의 `-----BEGIN ...-----` 헤더나 `openssl`로 확인한다.
인증할 때도 `.crt`는 상대에게 보내지만, `.key`는 로컬에 두고 TLS 핸드셰이크에 서명할 때만
쓴다. 상대는 인증서 안의 공개 키로 서명을 검증하며, **개인 키 자체는 네트워크로 보내지 않는다.**
인증서·키·CA의 관계와 PEM·DER의 차이는 [cka 14장의 인증서와 키를 구분하기](/cka/14-rbac/#인증서와-키를-구분하기)에서 이어진다.

시험 중 공식 문서에서 다시 찾을 때는 [Generate Certificates Manually](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/certificates/#openssl)의
**View the certificate** 단계에서 전체 출력 명령을, [Troubleshooting kubectl](https://v1-35.docs.kubernetes.io/docs/tasks/debug/debug-cluster/troubleshoot-kubectl/#tls-problems)의
**TLS problems**에서 `-dates`로 유효 시작·만료일만 보는 명령을 찾는다. 문서 검색어는
`Generate Certificates Manually openssl x509`, `Troubleshooting kubectl TLS problems`다.

```bash
# 명령 구조
# openssl: TLS·PKI 파일을 다루는 OpenSSL CLI
# x509: 입력을 X.509 인증서로 읽고 조회하는 하위 명령
# -in <file>: 읽을 인증서 파일. 이 실습에서는 kubeadm이 만든 PEM 인증서
# -text: Subject·Issuer·Validity·SAN·공개 키·서명 등을 사람이 읽는 형태로 출력
# -noout: -----BEGIN CERTIFICATE-----로 시작하는 PEM 인코딩 원문은 출력하지 않음
# 옵션 순서는 자유로워서 `x509 -in FILE -text -noout`과 `x509 -noout -text -in FILE`은 같다.

# "Run the command openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text and look for issuer"
# "Run the command openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text and look at Alternative Names"
# "Run the command openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text and check on the Expiry date."
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text -noout   # -text 사람이 읽게 풀기, -noout 인코딩된 원문은 생략
# 볼 곳: Subject CN / Issuer / X509v3 Subject Alternative Name / Validity(Not After)

# 다른 인증서는 -in 경로만 바꾼다.
openssl x509 -noout -text -in /etc/kubernetes/pki/etcd/server.crt
```

:::caution[함정 — etcd는 CA가 따로다]
etcd는 **자체 CA**(`pki/etcd/ca.crt`)를 쓴다. API 서버의 `--etcd-cafile`에
루트 CA를 넣으면 API 서버가 etcd에 못 붙는다 — 이 랩의 마지막 문제이자
[10장 트러블슈팅](/cka-udemy/10-troubleshooting/)의 단골 원인이다
— *ETCD has its own CA. The right CA must be used for the ETCD-CA file in /etc/kubernetes/manifests/kube-apiserver.yaml.*

API 서버 컨테이너 로그에 `127.0.0.1:2379`와
`failed to verify certificate: x509: certificate signed by unknown authority`가 같이 나오면,
로그를 낸 **kube-apiserver가 클라이언트**이고 etcd가 서버다. API 서버는 etcd가 낸
서버 인증서를 `--etcd-cafile`로 검증하므로 우선 다음 값을 확인한다.

```yaml
- --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
```

`--client-ca-file` 은 `kubectl`·kubelet 등 **API 서버로 들어오는 클라이언트**의 인증서를
검증할 때 쓰므로 etcd 접속 오류의 대상이 아니다. 다만 `unknown authority` 한 줄은
서버 인증서와 검증 CA가 서로 안 맞는다는 것까지만 알려 준다. 이 랩처럼
`kube-apiserver.yaml`의 CA가 바뀌었는지, etcd의 서버 인증서가 바뀌었는지는 문제의
변경 범위와 실제 플래그를 대조해 확정한다.
:::

### CSR 승인 — Practice Test: Certificates API

원본 풀이: [12-Practice-Test-Certificates-API.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/12-Practice-Test-Certificates-API.md)

새 사용자의 인증서 서명 요청(CSR, CertificateSigningRequest)을 만들 때는 공식 문서
[Issue a Certificate for a Kubernetes API Client Using a CertificateSigningRequest](https://kubernetes.io/docs/tasks/tls/certificate-issue-client-csr/#create-a-kubernetes-certificatesigningrequest)의
**Create a Kubernetes CertificateSigningRequest** 예시를 복사한다. 이 실습의 흐름은
CSR 파일 인코딩 → YAML의 `name`·`request` 수정 → 생성·확인 → 승인 또는 거부다.

```bash
# "A new member akshay joined our team. He requires access to our cluster. The Certificate Signing Request is at the /root location."
cat akshay.csr | base64 -w 0     # request 필드에 넣을 값. -w 0 = 줄바꿈 없이 한 줄로 — YAML에 그대로 붙이려면 필수
kubectl apply -f akshay-csr.yaml # kind: CertificateSigningRequest
# "Run the command kubectl get csr"
kubectl get csr
# "Run the command kubectl certificate approve akshay"
kubectl certificate approve akshay
# "Run the command kubectl certificate deny agent-smith"
kubectl certificate deny agent-smith    # 수상한 요청은 거부
# "Run the command kubectl delete csr agent-smith"
kubectl delete csr agent-smith
```

공식 예시에서 `apiVersion: certificates.k8s.io/v1`,
`signerName: kubernetes.io/kube-apiserver-client`, `usages: [client auth]`를 유지하고,
문제에서 준 이름과 CSR 내용만 바꾼다. 승인과 거부 명령은 공식 reference 문서의
[Approval or rejection using kubectl](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/#approval-or-rejection-using-kubectl)에서
확인한다 — [cka 14장](/cka/14-rbac/)에 전체 흐름이 있다.

:::tip[누가 요청했는지 의심하기]
`kubectl get csr <name> -o yaml`로 **groups와 usages**를 본다 — *Run the command kubectl get csr agent-smith -o yaml*.
`system:masters` 그룹을 요구하는 CSR은 승인하면 안 된다 — 거부 문제로 나온다.
:::

### kubeconfig — Practice Test: KubeConfig

원본 풀이: [14-Practice-Test-KubeConfig.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/14-Practice-Test-KubeConfig.md)

```bash
# "Run the kubectl config view command and count the number of clusters"
kubectl config view                                   # 기본 파일(~/.kube/config)
# "How many contexts are configured in the 'my-kube-config' file?"
# "What user is configured in the 'research' context?"
kubectl config view --kubeconfig my-kube-config       # 다른 파일 지정
# "Run the command kubectl config --kubeconfig=/root/my-kube-config use-context research"
kubectl config --kubeconfig=/root/my-kube-config use-context research
```

클러스터·유저·컨텍스트 개수, research 컨텍스트의 유저 같은 조회 문제는
전부 `config view` 출력 하나에서 읽는다.

:::caution[함정 — kubectl이 갑자기 안 될 때]
`kubectl get pods`가 인증서 에러를 뱉으면 kubeconfig의
**client-certificate 경로 오타**부터 확인한다. 이 랩의 마지막 문제이며,
실전에서도 "잘 되던 kubectl이 안 된다" 유형의 흔한 정답이다
— *The path to certificate is incorrect in the kubeconfig file. Fix it. All users certificates are stored at /etc/kubernetes/pki/users*.
:::

### kubeconfig 재료로 API 요청 검증

`kubectl`이 숨겨 주는 흐름은 **서버 주소 확인 → 서버 CA 검증 → 클라이언트 인증 → RBAC 판정 →
API 경로 처리**다. 먼저 현재 컨텍스트의 전송 설정을 그대로 쓰는 `--raw`로 경로를 확인하면,
REST 경로 문제와 인증서 추출 문제를 분리할 수 있다.

```bash
kubectl auth whoami
kubectl get --raw='/api'                                      # 코어 API 버전
kubectl get --raw='/apis'                                    # 이름 있는 API 그룹
kubectl get --raw='/api/v1/namespaces/default/pods'          # 코어 그룹
kubectl get --raw='/apis/apps/v1/namespaces/default/deployments'
```

`kubectl get --raw`도 kubeconfig의 전송 설정과 신원을 쓰므로 **kubectl 없는 요청은 아니다.**
직접 요청까지 확인하려면 현재 컨텍스트만 `--minify`하고, 내장된 인증 정보를 임시 파일로 풀어
같은 REST 경로를 `curl`로 호출한다.

```bash
umask 077
api_tls_dir=$(mktemp -d)
api_server=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')

kubectl config view --raw --minify \
  -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' \
  | base64 -d > "$api_tls_dir/ca.crt"
kubectl config view --raw --minify \
  -o jsonpath='{.users[0].user.client-certificate-data}' \
  | base64 -d > "$api_tls_dir/client.crt"
kubectl config view --raw --minify \
  -o jsonpath='{.users[0].user.client-key-data}' \
  | base64 -d > "$api_tls_dir/client.key"

curl --fail --silent --show-error \
  --cacert "$api_tls_dir/ca.crt" \
  --cert "$api_tls_dir/client.crt" \
  --key "$api_tls_dir/client.key" \
  "$api_server/api/v1/namespaces/default/pods"

rm -rf "$api_tls_dir"
```

위 예는 `*-data`에 인증서가 내장된 kubeconfig용이다. `certificate-authority`,
`client-certificate`, `client-key`가 파일 경로라면 디코딩하지 말고 그 파일을 각각 `curl`에 넘긴다.
`--raw`는 민감정보를 그대로 표시하므로 출력이나 임시 키를 남기지 않는다. `-k`로 TLS 검증을
생략하면 인증은 될 수 있어도 **서버 신원 확인을 검증한 것은 아니다.**

`kubectl proxy`는 다른 경계다. 현재 kubeconfig의 서버 주소·TLS·신원을 대신 사용하고,
기본적으로 로컬 루프백에서만 HTTP를 받는다.

```bash
# 첫 터미널 — 기본 127.0.0.1:8001
kubectl proxy

# 둘째 터미널 — curl에는 별도 자격증명이 없지만 proxy의 kubeconfig 신원으로 요청된다
curl --fail --silent --show-error http://127.0.0.1:8001/api/
curl --fail --silent --show-error http://127.0.0.1:8001/api/v1/namespaces
```

:::caution[함정 — proxy는 RBAC 우회가 아니다]
Bearer 토큰 직접 호출은 토큰의 ServiceAccount로, `kubectl proxy` 호출은 **proxy를 띄운
kubeconfig 사용자로** 인가된다. 두 결과가 다르면 proxy가 RBAC을 우회한 게 아니라 신원이 다른 것이다.
또한 로컬 프로세스는 proxy 신원을 빌려 API를 호출할 수 있다. `--address=0.0.0.0`이나
`--disable-filter`로 노출하지 말고, 확인이 끝나면 proxy를 종료한다.
:::

공식 근거: [Access Clusters Using the Kubernetes API](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/access-cluster-api/),
[`kubectl get --raw`](https://v1-35.docs.kubernetes.io/docs/reference/kubectl/generated/kubectl_get/),
[`kubectl proxy`](https://v1-35.docs.kubernetes.io/docs/reference/kubectl/generated/kubectl_proxy/).

## RBAC으로 권한 주기

### Role과 RoleBinding — Practice Test: RBAC

원본 풀이: [18-Practice-Test-RBAC.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/18-Practice-Test-RBAC.md)

```bash
# "Run the command kubectl describe pod kube-apiserver-controlplane -n kube-system and look for --authorization-mode"
kubectl describe pod kube-apiserver-controlplane -n kube-system | grep authorization-mode
# "Run the command kubectl get roles --all-namespaces"
kubectl get roles -A
# "Check the verbs associated to the kube-proxy role"
kubectl describe role kube-proxy -n kube-system       # 리소스·verbs 읽기
# "Run the command kubectl get pods --as dev-user"
kubectl get pods --as dev-user                        # 권한 시험해보기
kubectl create role developer --verb=list,create,delete --resource=pods -n default
kubectl create rolebinding dev-user-binding --role=developer --user=dev-user -n default
```

:::tip[--as로 확인까지가 한 세트]
만들라는 문제든 고치라는 문제든, 끝은 항상
`kubectl get pods --as dev-user`(또는 `kubectl auth can-i ... --as ...`)로 검증한다.
:::

:::caution[함정 — resourceNames]
"특정 이름의 리소스만" 허용하는 Role은 rules에 `resourceNames: ["blue-app"]`가 붙는다
— *New roles and role bindings are created in the blue namespace. Check it out. Check the resourceNames configured on the role*.
edit로 고칠 때 이 필드를 놓치면 계속 403이다.
:::

기존 Role을 고치는 문제는 `kubectl edit`가 기본이다 —
*Add a new rule in the existing role developer to grant the dev-user permissions to create
deployments in the blue namespace. Remember to add api group "apps"*.

```bash
kubectl edit role developer -n blue
```

```yaml
# rules 배열에 항목을 추가한다
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["create"]
```

:::caution[함정 — Deployment는 apps 그룹]
Pod는 core group이라 `apiGroups: [""]`지만 Deployment는 `apps`다. 빈 문자열로 두면
rule이 있어도 권한이 안 먹는다 — 문제가 "api group을 잊지 말라"고 강조하는 이유다.
:::

:::caution[함정 — RoleBinding의 roleRef는 immutable]
Role의 rules와 RoleBinding의 subjects는 edit로 자유롭게 고치지만, `roleRef`는 수정
불가라 저장이 거부된다. 연결된 Role 이름이 틀렸으면 RoleBinding을 지우고 다시 만든다.
정리하면 — **새로 만들 땐 `kubectl create role/rolebinding`, 고칠 땐 `kubectl edit`,
roleRef가 틀렸을 때만 삭제 후 재생성.**
:::

### ClusterRole — Practice Test: Cluster Roles

원본 풀이: [20-Practice-Test-Cluster-Roles.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/20-Practice-Test-Cluster-Roles.md)

- ClusterRole/ClusterRoleBinding은 **네임스페이스가 없다** — "어느 ns 소속인가"는 함정 질문 — *What namespace is the cluster-admin clusterrole part of?*
- 개수 세기: `kubectl get clusterroles --no-headers | wc -l` — *Run the command `kubectl get clusterroles --no-headers | wc -l` or `kubectl get clusterroles --no-headers -o json | jq '.items | length'`*

노드 관리자·스토리지 관리자를 만드는 문제 —

```bash
kubectl create clusterrole node-admin --verb=get,watch,list,create,delete --resource=nodes
kubectl create clusterrolebinding michelle-binding --clusterrole=node-admin --user=michelle

kubectl create clusterrole storage-admin \
  --verb=get,watch,list,create,delete --resource=persistentvolumes,storageclasses
kubectl create clusterrolebinding michelle-storage-admin \
  --clusterrole=storage-admin --user=michelle
```

storage-admin 문제가 *Get the API groups and resource names from command `kubectl api-resources`*
라고 안내하는 이유 — 두 리소스의 API 그룹이 다르다. `persistentvolumes`는 core group이고
`storageclasses`는 `storage.k8s.io`라서, rules YAML로 풀면 위 RBAC 절의 Deployment `apps`
그룹과 같은 계열의 함정이 된다. `kubectl create clusterrole`은 리소스 이름에서 그룹을 알아서
해석하므로 임퍼러티브가 특히 유리한 문제다.

```bash
kubectl api-resources | grep -E "persistentvolumes |storageclasses"
# persistentvolumes   pv   v1                  false   PersistentVolume
# storageclasses      sc   storage.k8s.io/v1   false   StorageClass
```

:::tip[verb 폭은 문제의 동사에서 읽는다]
*she will be focusing on the nodes*·*storage admin*처럼 관리 책임을 주는 문구면
`create,delete`까지, *view*·*list* 같은 조회 문구면 `get,list,watch`로 좁힌다. 애매하면
넓게 주는 쪽이 안전하다 — 채점은 보통 `kubectl auth can-i list nodes --as michelle` 수준만
보므로 verb가 남는 건 걸리지 않지만, 모자라면 바로 실패한다.

단 실전 CKA는 이 요령이 필요 없게 **오브젝트 이름·리소스·verb를 스펙으로 명시**하는 쪽이다 —
자동 채점이라 "storage 담당에게 알아서 권한을 구성하라"류의 열린 문제는 낼 수 없다.
스펙이 있으면 스펙 그대로가 우선이고, 넓게 주기는 문구만 있을 때의 폴백이다. 그래서 시험
대비는 "storage에 어떤 리소스가 필요한가"를 외우는 게 아니라, 문제에 적힌 리소스 이름을
`kubectl api-resources`로 API 그룹까지 변환하는 연습이다.
:::

표준 verb는 여덟 개다 — `get`·`list`·`watch`·`create`·`update`·`patch`·`delete`·`deletecollection`.
전체 목록은 공식 문서의 HTTP 메서드 대응표
[Determine the Request Verb](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authorization/#determine-the-request-verb)에
있지만, 시험장에서는 `kubectl api-resources -o wide`가 더 빠르다 — 리소스별로 쓸 수 있는
VERBS 컬럼이 그대로 나온다. `escalate`·`bind`(Role 권한 상승 제어)·`impersonate`(`--as`
권한)처럼 RBAC 전용 verb는 [RBAC 문서](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)에 있다.

:::caution[함정 — --user의 User는 리소스가 아니다]
`--user=michelle`의 User는 API 오브젝트가 아니다 — `kubectl get users` 같은 명령은 없고,
사용자를 "만드는" 단계도 없다. 인증 단계가 요청에서 꺼낸 신원(클라이언트 인증서의 CN,
토큰의 클레임)을 binding의 `subjects`(`kind: User`)의 `name` 문자열과 비교할 뿐이다.
사용자 생성에 해당하는 작업이 위의 [CSR 승인](#csr-승인--practice-test-certificates-api)이다.
Group도 같은 문자열이고(인증서의 O 필드 — `system:masters`가 이것), subject 세 종류 중
**ServiceAccount만 진짜 리소스**라 `--serviceaccount=네임스페이스:이름` 형식으로 지정한다.
:::

노드·PV·StorageClass처럼 **클러스터 범위 리소스에는 Role이 아니라 ClusterRole**이다 —
가르는 기준은 [cka 14장](/cka/14-rbac/). rule 여러 개처럼 `kubectl create` 플래그로 표현할 수
없는 걸 넣어야 해서 rules YAML을 직접 써야 하면 공식
[RBAC 문서](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)의 예시에서 복사하거나,
`kubectl create role ... --dry-run=client -o yaml`로 뼈대를 뽑아 고치는 쪽이 문서 검색보다 빠르다.

### ServiceAccount — Practice Test: Service Accounts

원본 풀이: [22-Practice-Test-Service-Accounts.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/22-Practice-Test-Service-Accounts.md)

```bash
# "How many service accounts exist in the default namespace?"
kubectl get sa
# "Create a new ServiceAccount named dashboard-sa."
kubectl create serviceaccount dashboard-sa
kubectl create token dashboard-sa            # 수명 있는 토큰 발급 (TokenRequest)
```

- Pod이 어떤 SA를 쓰는지: `kubectl get pod <name> -o jsonpath='{.spec.serviceAccountName}'` — *Which account does the Dashboard application use to query the Kubernetes API?*
- 토큰이 마운트되는 곳: `/var/run/secrets/kubernetes.io/serviceaccount` — *At what location is the ServiceAccount credentials available within the pod?*
- Deployment의 SA 교체: `kubectl set serviceaccount deploy web-dashboard dashboard-sa`
  (또는 edit로 `spec.template.spec.serviceAccountName`) — 템플릿 변경이라 롤아웃된다
  — *Edit the deployment to change ServiceAccount from default to dashboard-sa.*

:::caution[함정 — SA에는 더 이상 자동 Secret이 없다]
`describe sa`의 Tokens가 `<none>`인 게 정상이다 — *What is the secret token used by the default service account?* 무기한 Secret 자동 생성은 폐기됐고,
지금은 **`kubectl create token`으로 수명 있는 토큰을 발급**한다 — [cka 14장](/cka/14-rbac/).
:::

랩 후반부는 자동 마운트를 끄고 같은 토큰을 손으로 다시 주입한다 — *Modify the existing
ServiceAccount dashboard-sa … to disable automatic mounting of API credentials. …
Use a projected volume named token.* 1.22부터는 자동 마운트 자체가 내부적으로
serviceAccountToken projected volume 방식(TokenRequest 기반 수명 있는 토큰)이라,
자동으로 되던 걸 명시적으로 재구성해 보는 문제다.

```bash
# automountServiceAccountToken은 metadata 안이 아니라 오브젝트 최상위 필드다
kubectl patch sa dashboard-sa -p '{"automountServiceAccountToken": false}'
```

Deployment 쪽은 projected volume이라 대응하는 임퍼러티브 명령이 없다. 문제가 매니페스트
경로를 주는 게 신호다(*The Deployment manifest file can be found at:
~/web-dashboard/deployment.yaml*) — live만 `kubectl edit`로 고치면 디스크의 파일이 낡은 채
남아 다음 apply 때 수정이 되돌아가므로, **파일을 고쳐서 apply한다.** 도구 기준은 이렇다 —
한 필드 값은 `set`/`patch`, 기존 필드 수정은 `edit`, 여러 줄 중첩 구조 추가에 파일까지
주어졌으면 파일 수정 → `--dry-run=client` 검증 → `apply`.

```yaml
    spec:
      serviceAccountName: dashboard-sa
      volumes:
      - name: token
        projected:
          sources:
          - serviceAccountToken:
              path: token          # 볼륨 안에 만들어질 파일 이름
      containers:
      - name: web-dashboard
        volumeMounts:
        - name: token
          mountPath: /var/run/secrets/kubernetes.io/serviceaccount
          readOnly: true
```

```bash
kubectl apply --dry-run=client -f ~/web-dashboard/deployment.yaml   # 저장한 파일 사전 검증
kubectl apply -f ~/web-dashboard/deployment.yaml
kubectl rollout status deploy web-dashboard    # 채점 항목 "Deployment Ready"
```

:::caution[함정 — mountPath는 디렉터리까지만]
목표 경로가 `/var/run/secrets/kubernetes.io/serviceaccount/token`이면 `mountPath`는
디렉터리까지만 쓰고, 파일 이름 `token`은 projected source의 `path`가 맡는다.
mountPath에 `/token`까지 붙이면 실제 경로가 `…/token/token`이 되어 채점에 걸린다.
:::

:::tip[필드명은 외우지 말고 explain으로 꺼낸다]
`kubectl explain sa | grep -i mount`가 `automountServiceAccountToken`을 10초 안에 찾아준다.
이름 자체도 영어 구를 camelCase로 이어 쓴 것뿐이다 — "automount (the) ServiceAccount token".
같은 필드가 Pod spec에도 있고(`spec.automountServiceAccountToken`) **Pod 쪽이 SA 쪽보다
우선**하므로, "특정 Pod만 토큰을 안 받게" 하는 문제면 Pod spec에 쓴다.
:::

## Admission으로 요청 내용 검사

### admission 플러그인 켜고 끄기 — Lab: Admission Controllers (2025 신규)

소스: 강의 노트 [(2025 Updates) Admission Controllers](https://notes.kodekloud.com/docs/Certified-Kubernetes-Administrator-CKA/Scheduling/2025-Updates-Admission-Controllers/page)
— 원본 레포에는 이 랩의 풀이 문서가 없다 (2025년 추가 랩).
개념은 [cka 14장의 admission 절](/cka/14-rbac/#admission-컨트롤러)이 맡는다.

조회 문제부터 — "어떤 플러그인이 켜져 있나"는 **어디를 보느냐**가 곧 답이다.

```bash
# 기본으로 켜진 플러그인 목록 — 바이너리에 직접 물어본다
kubectl exec -n kube-system kube-apiserver-controlplane -- kube-apiserver -h | grep enable-admission-plugins
# 이 클러스터에 설정된 값 — 스태틱 Pod 매니페스트
grep admission-plugins /etc/kubernetes/manifests/kube-apiserver.yaml
# 실제 떠 있는 프로세스 기준 — 편집 직후의 검증은 이쪽이 확실하다
ps -ef | grep kube-apiserver | grep admission-plugins
```

수정 문제의 패턴은 둘 — **켜기**(`NamespaceAutoProvision` 등)와 **끄기**(`DefaultStorageClass` 등).
`/etc/kubernetes/manifests/kube-apiserver.yaml`의 `command`를 고친다.

```yaml
    - --enable-admission-plugins=NodeRestriction,NamespaceAutoProvision
    - --disable-admission-plugins=DefaultStorageClass
```

효과 확인까지가 한 문제다 — `kubectl run nginx --image nginx -n blue`처럼
**없는 네임스페이스에 만들어 본다**. `NamespaceAutoProvision`이 켜져 있으면
네임스페이스가 자동 생성되며 성공하고, 꺼져 있으면 거부된다.

:::caution[함정 — 저장하면 API 서버가 재시작된다]
스태틱 Pod라 매니페스트를 저장하는 순간 API 서버가 재시작된다 —
**몇십 초 kubectl이 안 먹는 게 정상**이다. 플래그에 오타가 있으면 아예 안 올라오는데,
그때는 kubectl이 아니라 `crictl ps -a`와 컨테이너 로그로 본다 ([10장](/cka-udemy/10-troubleshooting/)의 진단 순서).
검증은 매니페스트 grep이 아니라 `ps -ef` 쪽으로 — 매니페스트는 "설정한 값"이고
프로세스가 "실제 적용된 값"이다.
:::

:::tip[기본값을 묻는 문제]
`NamespaceAutoProvision`과 `NamespaceExists`는 **기본 비활성**이다.
"없는 네임스페이스 거부"라는 기본 동작은 요즘은 `NamespaceLifecycle`이 맡는다 —
"다음 중 기본으로 켜져 있지 않은 것은?" 유형의 답이 된다.
:::

### admission webhook 등록 — Lab: Validating and Mutating Admission Controllers (2025 신규)

소스: 강의 노트 [(2025 Updates) Validating and Mutating Admission Controllers](https://notes.kodekloud.com/docs/Certified-Kubernetes-Administrator-CKA/Scheduling/2025-Updates-Validating-and-Mutating-Admission-Controllers/page).
내장 플러그인이 아니라 **직접 만든 규칙**을 거는 쪽 — [cka 14장의 외부 webhook 절](/cka/14-rbac/#외부-webhook--직접-만드는-admission)이 개념 짝이다.

랩의 흐름은 세 단계다. webhook 서버 자체(코드)는 랩이 주고, **배포와 등록**이 문제다.

1. **webhook 서버 배포** — 랩이 주는 Deployment + Service를 적용한다.
   클러스터 안에서 돌면 API 서버가 Service 이름으로 호출한다
2. **TLS Secret** — API 서버 → webhook 통신은 HTTPS 의무라, 서버 인증서·키로
   `tls` 타입 Secret을 만든다 (파일 경로·이름은 문제가 준다)

   ```bash
   kubectl -n webhook-demo create secret tls webhook-server-tls \
     --cert=/root/keys/webhook-server-tls.crt --key=/root/keys/webhook-server-tls.key
   ```

3. **WebhookConfiguration 등록** — 이것이 API 서버에게 "이런 요청이 오면 저기 물어봐라"를
   알리는 리소스다. 강의 노트의 예시 —

   ```yaml
   apiVersion: admissionregistration.k8s.io/v1
   kind: MutatingWebhookConfiguration    # 검사만 하면 ValidatingWebhookConfiguration
   metadata:
     name: pod-policy.example.com
   webhooks:
   - name: pod-policy.example.com
     clientConfig:
       service:
         namespace: webhook-demo         # webhook 서버 Service의 위치
         name: webhook-server
       caBundle: "Ci0tLS0tQk...(서버 인증서를 검증할 CA를 base64로)"
     rules:
     - apiGroups: [""]
       apiVersions: ["v1"]
       operations: ["CREATE"]            # Pod 생성 때마다 호출
       resources: ["pods"]
       scope: "Namespaced"
   ```

검증도 Pod를 만들어 보는 것이다 — **mutating**이면 만든 Pod에 없던 필드
(예: securityContext 기본값)가 **주입되어** 나오고, **validating**이면
규칙 위반 Pod가 생성 자체를 거부당한다.

:::tip[개념 문제 — ImagePolicyWebhook]
webhook 계열의 내장판인 `ImagePolicyWebhook` 정의를 묻는 문제가 같이 나온다 —
*The ImagePolicyWebhook admission controller intercepts pod creation and update requests,
extracts the container images, and sends them to an external webhook for validation.
Based on the webhook's response, it either allows or denies the pod creation.
It does not perform authentication, post-deployment scanning, or image encryption.*
아닌 것 셋은 단계로 가른다 — 인증은 관문 ①의 일, 배포 후 스캔은 생성 시점 관문이 아니며,
mutating이 아니라 validating이라 내용을 바꾸지도 않는다. 그리고 이쪽 설정은
webhook 리소스가 아니라 `AdmissionConfiguration` **파일**이다 —
`kubectl api-resources`에 안 나온다 ([cka 14장](/cka/14-rbac/#세부-설정--admissionconfiguration-파일)).
:::

## TLS부터 저장까지 한 요청으로 검증하기

설정 파일의 경로를 외우기보다 **실제로 실행될 kube-apiserver 매니페스트에서 근거를 찾는다.**
kubeadm 기본 인증서는 `/etc/kubernetes/pki`에 있지만 인증서 디렉터리와 각 경로는 바꿀 수 있다.

```bash
api_manifest=/etc/kubernetes/manifests/kube-apiserver.yaml
sudo grep -E -- \
  '--(tls-cert-file|tls-private-key-file|client-ca-file|authorization-mode|enable-admission-plugins|disable-admission-plugins|admission-control-config-file)' \
  "$api_manifest"
```

출력은 한 요청이 지나갈 경계를 그대로 보여 준다.

| 경계 | 판정 증거 | 실패를 좁힐 곳 |
|---|---|---|
| TLS | 앞 절의 `curl --cacert`가 `-k` 없이 응답 | `--tls-cert-file`, CA, SAN, 유효기간 |
| 인증 | `kubectl auth whoami`의 사용자·그룹 | kubeconfig의 현재 context와 client cert·token |
| 인가 | `kubectl auth can-i <verb> <resource> -n <ns>`의 `yes` | `--authorization-mode`, Role·Binding |
| admission | 의도한 거부 또는 기본값 주입 | enable/disable 플래그, 설정 파일·webhook |
| 저장 | 다시 읽은 객체의 `uid`·`resourceVersion` | admission 이후 API 검증·etcd 경로 |

같은 context와 namespace를 끝까지 유지해야 단계별 결과를 비교할 수 있다. 아래 Pod는 예시이므로
실습에서 쓰는 context·namespace·이미지로 바꾼다.

```bash
flow_context=restricted-context
flow_namespace=sandbox

# 인증: API 서버가 최종적으로 본 신원
kubectl --context="$flow_context" auth whoami

# 인가: create pods 판정과 실제 요청은 같은 context로 실행
kubectl --context="$flow_context" auth can-i create pods -n "$flow_namespace"
kubectl --context="$flow_context" run flow-check \
  --image=nginx:1.27-alpine -n "$flow_namespace"

# admission을 통과해 저장됐는지, 어떤 기본값이 주입됐는지 확인
kubectl --context="$flow_context" get pod flow-check -n "$flow_namespace" \
  -o jsonpath='{.metadata.uid}{"\t"}{.metadata.resourceVersion}{"\t"}{.spec.serviceAccountName}{"\n"}'
```

`auth can-i=yes`는 **인가만** 증명한다. 이어지는 생성이 정책에 거부되면 admission까지 도달한 것이고,
객체를 다시 읽어 `uid`·`resourceVersion`과 주입된 필드를 확인해야 저장까지 통과한 것이다.
반대로 `401`과 `403`은 admission에 도달하기 전 실패라 정책 설정을 고칠 문제가 아니다.

admission 플래그를 바꾼 뒤에는 매니페스트 문자열만 확인하지 않는다. kube-apiserver 재기동,
준비 상태, 변경한 플러그인의 행동을 차례로 확인한다.

```bash
kubectl get pods -n kube-system -l component=kube-apiserver -w
kubectl get --raw='/readyz?verbose'
ps -ef | grep kube-apiserver | grep admission-plugins

# 마지막 판정은 위 flow-check처럼 실제 create 요청의 거부·변형·저장 결과다
```

공식 근거: [kubeadm PKI 인증서와 경로](https://v1-35.docs.kubernetes.io/docs/setup/best-practices/certificates/),
[인증 정보 확인](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authentication/#api-access-to-authentication-information-for-a-client),
[인가와 `auth can-i`](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/authorization/#checking-api-access),
[admission 컨트롤러](https://v1-35.docs.kubernetes.io/docs/reference/access-authn-authz/admission-controllers/).

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| 인증서 경로 | `PKI certificates requirements` | [PKI certificates and requirements](https://kubernetes.io/docs/setup/best-practices/certificates/)의 인증서 표. 실제 경로는 스태틱 Pod 플래그가 최종 근거이며 새 YAML 작성용 페이지는 아님 |
| CSR 생성 | `Issue Certificate Kubernetes API Client CSR` | [Issue a Certificate for a Kubernetes API Client Using a CertificateSigningRequest](https://kubernetes.io/docs/tasks/tls/certificate-issue-client-csr/#create-a-kubernetes-certificatesigningrequest)의 **Create a Kubernetes CertificateSigningRequest** 예시에서 `request`, `signerName`, `usages` |
| CSR 승인·거부 | `Certificate Signing Requests approval rejection kubectl` | [Certificates and Certificate Signing Requests](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/#approval-or-rejection-using-kubectl)의 **Approval or rejection using kubectl**에서 `certificate approve`·`certificate deny` 명령 |
| kubeconfig | `Organizing Cluster Access kubeconfig` | [Organizing Cluster Access Using kubeconfig Files](https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/)에서 clusters/users/contexts의 연결 구조 확인 |
| Role·ClusterRole·Binding | `RBAC` | [Using RBAC Authorization](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)의 Role, ClusterRole, RoleBinding, ClusterRoleBinding 예시. namespace와 `roleRef.kind`를 특히 확인 |
| ServiceAccount | `Service Accounts` | [Service Accounts](https://kubernetes.io/docs/concepts/security/service-accounts/)에서 Pod의 `serviceAccountName`과 토큰 방식 확인 |
| 프라이빗 레지스트리 | `Pull Image Private Registry` | [Pull an Image from a Private Registry](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/)에서 docker-registry Secret 생성과 Pod 수준 `imagePullSecrets` 예시 |
| admission 플러그인 | `Admission Controllers` | [Admission Control in Kubernetes](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/)에서 기본 활성 플러그인과 kube-apiserver 플래그 확인 |
| admission webhook | `Dynamic Admission Control` | [Dynamic Admission Control](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/)에서 `ValidatingWebhookConfiguration`·`MutatingWebhookConfiguration`, `clientConfig`, `rules` 예시 |

RBAC YAML은 이름이 비슷해도 범위가 다르다. 문서에서 예시를 고를 때 먼저 대상 리소스가
namespaced인지 `kubectl api-resources --namespaced=true/false`로 확인한 뒤 Role과 ClusterRole을 가른다.

## 이 장에서 남길 것

- 인증서 문제의 근거는 `/etc/kubernetes/manifests/`의 실제 플래그다. kubeadm 기본 경로를 외우지 말고
  TLS cert·client CA·etcd CA를 각각 찾아 확인한다
- CSR: 만들고 → `get csr`로 보고 → approve/deny. groups가 수상하면 거부
- RBAC는 만들기보다 **`--as`/`auth can-i`로 검증**까지가 한 문제
- 클러스터 범위 리소스(nodes·pv·sc)는 ClusterRole
- SA 토큰은 `create token`, 레지스트리 인증은 `docker-registry` 타입 Secret + imagePullSecrets
- admission 플러그인은 kube-apiserver **플래그**로 켜고 끄고, 검증은 `ps -ef`로.
  직접 만든 규칙은 WebhookConfiguration **리소스**, `ImagePolicyWebhook` 세부 설정은
  `AdmissionConfiguration` **파일**
- 한 요청은 **TLS → `auth whoami` → `auth can-i` → admission 행동 → `uid`·`resourceVersion`**
  순서로 증거를 남겨야 저장까지 통과했다고 판정한다
