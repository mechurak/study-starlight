<Thesis>
워커 복구는 kubelet 프로세스 실행 여부와 API 서버 연결 성공을 따로 확인한다. 서비스가 active여도
잘못된 CA나 서버 주소 때문에 Node는 계속 NotReady일 수 있다.
</Thesis>

문제 노드에 들어가 systemd가 실제로 넘긴 `--config`와 `--kubeconfig`를 찾는다. 로그의 파일명과
접속 주소를 실제 파일·정상 노드와 대조하고, 수정 뒤 최근 로그와 Node Ready를 함께 확인한다.

> 개념 연결: [CKA 트러블슈팅](/cka/troubleshooting/)

## 워커 노드 장애 — Worker Node Failure

“Fix the broken cluster”처럼 원인을 알려 주지 않는 문제는 **문제 노드 → 서비스 상태 → 최근 로그 →
최소 수정 → Ready 복구** 순으로 접근한다. 이 실습은 kubeadm·systemd 환경이며, node01에서는
root로 명령을 실행한다. 일반 사용자라면 서비스 제어·설정 수정 등에 `sudo`를 붙인다.

| 발견한 증거 | 수정 대상 | 첫 조치 |
|---|---|---|
| kubelet이 `inactive (dead)`이고 구체적인 시작 실패 원인은 아직 없음 | kubelet 서비스 | 시작한 뒤 유지되는지 확인 |
| `unable to load client CA file` + `no such file or directory` | `config.yaml`의 CA 파일 경로 | 실제 파일과 대조해 경로 수정 |
| `controlplane:6553` + `connection refused` | `kubelet.conf`의 API 서버 주소 | 정상 접속 주소와 대조해 포트 수정 |

### 공통 진입점 — 서비스 상태와 최근 로그를 함께 읽는다

```bash
# controlplane에서
kubectl get nodes
kubectl describe node node01
ssh node01

# node01에서
systemctl status containerd --no-pager
systemctl status kubelet --no-pager
journalctl -u kubelet -n 100 --no-pager
```

`describe node`의 Conditions·Events로 노드 상태를 확인한다. kubelet의 상태 보고가 끊기면
`Ready` 조건이 `Unknown`이고 `Kubelet stopped posting node status`가 나타날 수 있다.
`NotReady`만으로 서비스 중지를 확정하지 않는다.
[공식 클러스터 진단 예시](https://kubernetes.io/docs/tasks/debug/debug-cluster/)에서도 이 상태 보고를 확인한다.

containerd는 컨테이너 실행을, kubelet은 노드의 Pod 관리와 상태 보고를 담당한다.
`systemctl status`는 **현재 실행 상태**, `journalctl`은 **그 상태에 이른 과정**을 확인하는 도구다.
systemd 환경의 kubelet 로그는 [공식 로깅 문서](https://kubernetes.io/docs/concepts/cluster-administration/logging/)처럼
`journalctl -u kubelet`로 읽는다.

| 옵션 | 의미 |
|---|---|
| `-u kubelet` | kubelet 서비스의 로그만 선택 |
| `-n 100` | 최근 100줄 표시 |
| `-f` | 새 로그를 계속 표시. `Ctrl+C`로 종료 |
| `--no-pager` | 별도 뷰어 없이 터미널에 출력 |

`--no-pager`는 필수가 아니며 로그 내용을 바꾸지 않는다. 생략하면 보통 `less` 같은 뷰어가 열리고
`q`로 나간다. 최근 로그를 읽고 곧바로 다음 명령을 입력하기 편해서 붙인다.
`-f`를 붙였다면 `--no-pager`가 있어도 계속 관찰하므로 `Ctrl+C`로 종료한다.

### kubelet 중지 — inactive를 확인하고 시작한다

첫 문제에서는 containerd가 `active (running)`이고 kubelet은 다음 상태다.

```text
Loaded: ... enabled
Active: inactive (dead)
...
code=exited, status=0/SUCCESS
```

`enabled`는 부팅 시 자동 시작 설정이지 현재 실행 상태가 아니다. `inactive (dead)`가 현재 중지를 뜻한다.
`0/SUCCESS`는 이전 프로세스가 정상 종료 코드를 남겼다는 뜻이며, 노드 정상 여부나 중지 원인을 알려 주지는 않는다.

이때 “우선 start 해보자”는 판단은 중지 상태에서 나온다. 로그에 `Stopping…`, `Stopped…`만 있고
반복 오류가 없다면 시작 후 유지되는지 확인한다. 반면 파일 없음·설정 파싱 실패처럼 시작을 막는 오류가
있다면 해당 원인을 먼저 고친다. 종료 로그만으로 누가 왜 중지했는지까지 확정할 수는 없다.

```bash
# node01에서
systemctl start kubelet
systemctl status kubelet --no-pager
```

힌트의 `ssh node01 "service kubelet start"`는 controlplane에서 SSH로 node01의 서비스를 시작하는
축약형이다. 시작 직후 다시 종료되면 최근 로그로 원인을 조사하고, 실행이 유지되면 아래 공통 검증으로 넘어간다.

### 설정 경로 찾기 — config와 kubeconfig를 구분한다

기본 경로를 알아두되, 기억나지 않으면 node01에서 서비스 실행 설정을 확인한다.

```bash
systemctl cat kubelet
```

서비스 본체와 추가 설정에서 다음 인자를 찾는다. 실제 출력에는 환경 변수나 다른 인자가 함께 있다.

```text
--config=/var/lib/kubelet/config.yaml
--kubeconfig=/etc/kubernetes/kubelet.conf
```

| 인자와 기본 경로 | 역할 | 이 실습에서 수정하는 값 |
|---|---|---|
| `--config`: `/var/lib/kubelet/config.yaml` | kubelet 동작 설정 | `authentication.x509.clientCAFile` |
| `--kubeconfig`: `/etc/kubernetes/kubelet.conf` | kubelet의 API 서버 접속·인증 정보 | `clusters` 아래 `server` |

이는 [kubeadm의 기본 kubelet 실행 설정](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/kubelet-integration/)이다.
설치 방식이나 서비스 override에 따라 경로가 다를 수 있으므로 실제 실행 인자가 기준이다.

### CA 경로 오류 — 로그의 파일명과 실제 파일을 대조한다

두 번째 문제의 결정적인 오류는 다음과 같다.

```text
unable to load client CA file /etc/kubernetes/pki/WRONG-CA-FILE.crt:
open /etc/kubernetes/pki/WRONG-CA-FILE.crt: no such file or directory
```

**CA 파일을 읽으려 했으나 지정된 경로에 파일이 없다**는 뜻이다. 이 오류는 인증서 만료를 뜻하지 않는다.
같은 설정으로 시작을 반복하기 전에 파일 누락인지 경로 오타인지 확인한다.

```bash
# node01에서
cat /var/lib/kubelet/config.yaml
ls -l /etc/kubernetes/pki/ca.crt
vi /var/lib/kubelet/config.yaml
```

이번 실습의 올바른 파일은 `ca.crt`다. 기존 `authentication` 아래의 경로만 수정한다.
아래는 관련 부분 발췌이므로 파일 전체를 덮어쓰지 않는다.

```yaml
authentication:
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt
```

`clientCAFile`은 [kubelet에 접속하는 클라이언트의 인증서를 검증할 CA](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-authn-authz/)를
지정한다. 수정 뒤 `systemctl restart kubelet`으로 설정을 다시 읽게 하고 아래 공통 검증을 수행한다.

### API 서버 포트 오류 — kubelet.conf의 server를 고친다

세 번째 문제에서는 긴 로그의 접속 대상과 마지막 오류부터 읽는다.

```text
Get "https://controlplane:6553/api/v1/nodes?...":
dial tcp 192.24.132.5:6553: connect: connection refused
```

호스트 이름이 IP로 해석됐고 해당 IP의 `6553` 포트로 TCP 연결을 시도했으나 거부됐다.
인증서 검증이나 권한 검사까지 도달한 오류가 아니다. `connection refused`만으로 포트 오타를 확정할 수는
없지만, [API 서버 기본 포트가 6443](https://kubernetes.io/docs/reference/networking/ports-and-protocols/)이므로
`6553`을 의심하고 정상 설정과 대조한다. 서버가 해당 포트에서 실행되지 않는 경우에도 연결은 거부될 수 있다.

```bash
# kubectl이 정상 동작하는 controlplane에서
kubectl config view
```

출력의 `clusters` 아래 `server:`를 읽는다. 이 실습에서는 아래 주소가 정상이다.
context가 여러 개라면 `current-context`와 `contexts`의 cluster 이름으로 사용할 항목을 찾는다.
서버 주소를 읽는 데 복잡한 JSONPath 추출 명령은 필요 없다.

```yaml
# 정상 출력의 관련 항목 발췌
server: https://controlplane:6443
```

```bash
# node01에서
vi /etc/kubernetes/kubelet.conf
```

기존 `server: https://controlplane:6553`의 포트만 `6443`으로 바꾸고 인증서·사용자 정보는 유지한다.
다른 환경에서는 프록시나 로드 밸런서가 별도 포트를 쓸 수 있으므로 기본값만 보고 무조건 바꾸지는 않는다.
수정 뒤 `systemctl restart kubelet`을 실행한다.

:::caution[실행 중인 kubelet도 API 서버에 연결하지 못할 수 있다]
이 연결 실패 로그만으로 kubelet 프로세스가 종료됐다고 판단할 수 없다. `active (running)`이어도
API 서버에 상태를 보고하지 못하면 노드가 `NotReady`가 될 수 있다. 서비스 상태와 노드 상태를 모두 확인한다.
:::

### 공통 완료 검증 — 서비스 실행과 노드 Ready를 모두 확인한다

```bash
# node01에서 시작 또는 수정·재시작한 뒤
systemctl status kubelet --no-pager
journalctl -u kubelet --since "2 minutes ago" --no-pager

# SSH 접속을 끝내고 controlplane에서
exit
kubectl get nodes -w
```

기존 오류 로그는 수정 후에도 남는다. 최근 출력 중에서도 **시작·재시작 이후 시각**의 메시지를 확인한다.
kubelet이 실행 상태를 유지하고 `node01`이 `Ready`로 돌아오면 `Ctrl+C`로 관찰을 종료한다.
상태 반영에는 잠시 시간이 걸릴 수 있다. 노드의 워크로드도 확인하려면 다음 출력에서 `NODE`와 상태를 읽는다.

```bash
kubectl get pods -A -o wide
```

## 완료 기준

- 대상 노드와 kubelet의 active/inactive를 확인하고 최근 오류 로그를 확보한다.
- kubelet config와 kubeconfig를 구분해 CA 경로·API 서버 주소의 실제 원본만 수정한다.
- `systemctl restart kubelet` 뒤 새 로그에서 오류가 사라지고 Node가 `Ready`가 된다.
- 노드에 있던 원래 workload도 다시 Ready인지 확인한다.
