<Thesis>
ServiceAccount는 Pod가 API에 제시할 신원이고, imagePullSecret은 kubelet이 이미지를 받을 때
쓰는 레지스트리 자격증명이다. 둘을 같은 Secret 문제로 섞지 않는다.
</Thesis>

먼저 Pod가 쓰는 ServiceAccount와 토큰 마운트를 확인한다. 이미지 접근 문제는 별도로 Secret
타입·namespace·Pod 템플릿 연결을 확인하고 새 Pod가 실제로 이미지를 받는지까지 본다.

> 짝이 되는 개념 장: [CKA ServiceAccount — Pod의 신원](/cka/service-account/)

아래 명령은 `kubectl`이 설정된 실습 터미널에서 실행하며, 현재 namespace가 `default`라고
가정한다. 다른 namespace가 주어지면 명령에 `-n <namespace>`를 붙인다.
`<pod-name>`은 조회한 실제 Pod 이름으로 바꾼다.

## Pod가 사용하는 ServiceAccount 확인하기

학습용 원본 풀이: [Practice Test: Service Accounts](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/22-Practice-Test-Service-Accounts.md)

Dashboard가 Kubernetes API를 조회할 때 어떤 신원으로 요청하는지 먼저 확인한다.
ServiceAccount의 약어는 `sa`다. 계정 목록과 Pod의 YAML을 열어 `spec.serviceAccountName`을 찾는다.

```bash
kubectl get sa
kubectl get pods
kubectl get pod <pod-name> -o yaml
```

별도로 지정하지 않은 Pod는 같은 namespace의 `default` ServiceAccount를 사용한다.
토큰의 기본 마운트 디렉터리는 `/var/run/secrets/kubernetes.io/serviceaccount`다.
Pod YAML의 `volumes`와 컨테이너의 `volumeMounts`에서 연결을 확인한다.

## Dashboard에 전용 계정 연결하기

문제가 `dashboard-sa`를 만들고 Deployment에 연결하라고 하면 다음처럼 실행한다.
계정이 이미 있으면 생성은 건너뛴다.

```bash
kubectl create serviceaccount dashboard-sa
kubectl set serviceaccount deploy web-dashboard dashboard-sa
```

직접 편집하려면 `kubectl edit deploy web-dashboard`에서
`spec.template.spec.serviceAccountName`을 바꾼다. Pod 템플릿 변경이므로 새 Pod가 만들어진다.
계정 연결만으로 API 조회 권한이 생기지는 않는다. 권한은 [RBAC 실습](/cka-udemy/rbac/)에서 다룬다.

**문서 찾기:** Kubernetes 공식 사이트 내부에서 `Configure Service Accounts for Pods`를 검색한다.
[Use the default service account to access the API server](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#use-the-default-service-account-to-access-the-api-server)
절에서 `serviceAccountName`을 찾는다. 문서의 Pod `spec`은 Deployment에서는
`spec.template.spec`에 해당하며, 계정 이름을 `dashboard-sa`로 바꾼다.

## 화면에 입력할 토큰 발급하기

Dashboard 로그인 화면처럼 토큰 문자열을 요구하는 작업에서는 수명 있는 토큰을 발급한다.
이 명령은 Pod의 마운트 설정을 바꾸지 않는다.

```bash
kubectl create token dashboard-sa
```

**문서 찾기:** 같은 공식 페이지에서
[Manually create an API token for a ServiceAccount](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#manually-create-an-api-token-for-a-serviceaccount)
절을 연다. `kubectl create token` 예제의 계정 이름만 바꾼다.

:::caution[함정 — 자동 생성된 토큰 Secret을 찾지 않는다]
`kubectl describe sa dashboard-sa`의 Tokens가 `<none>`이어도 계정 생성 실패는 아니다.
현재 방식은 TokenRequest로 수명 있는 토큰을 발급한다. 예전 랩의 장기 토큰 Secret 자동 생성을
전제하지 않는다. 배경은 [CKA ServiceAccount — Pod의 신원](/cka/service-account/)에서 확인한다.
:::

## 토큰 자동 마운트 끄기

### 왜 끄는가

API를 호출하지 않는 앱에는 API 인증 토큰이 필요 없다. 자동 마운트를 끄면 컨테이너에
불필요한 자격증명을 넣지 않을 수 있다.

**이 랩의 목적은 직접 마운트를 구성하는 연습이다.** `dashboard-sa`의 자동 마운트를 끈 다음,
Deployment에 `token`이라는 projected volume을 직접 선언하라는 요구다.
다음 절에서 토큰을 다시 제공하므로, 최종 Pod에서 토큰을 없애는 작업은 아니다.
자동 마운트도 내부적으로 projected volume을 사용한다.

### 공식 예제를 찾아 ServiceAccount 편집하기

Kubernetes 공식 사이트 내부에서 **`Configure Service Accounts for Pods`**를 검색하고,
페이지 안에서 **`automount`**를 찾는다.
[Opt out of API credential automounting](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#opt-out-of-api-credential-automounting)
절에는 ServiceAccount 예제와 Pod 예제가 있다. 이번 요구는 **기존 ServiceAccount 수정**이므로
ServiceAccount 예제를 참고한다.

```bash
kubectl edit sa dashboard-sa
```

열린 YAML에 아래 필드를 추가하거나 기존 값을 바꾼 뒤 저장하고 종료한다.
아래는 **편집 위치를 보여주는 발췌**다. 기존 metadata 등은 유지한다.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: dashboard-sa
  namespace: default
automountServiceAccountToken: false
```

`automountServiceAccountToken`은 **`metadata`와 같은 들여쓰기**에 둔다.
ServiceAccount에는 이 값을 감싸는 `spec`이 없다.
필드 설명이 필요하면 `kubectl explain sa.automountServiceAccountToken`으로 확인한다.

:::caution[Pod 설정과 기존 Pod 확인]
Pod의 `spec.automountServiceAccountToken`이 지정되어 있으면 ServiceAccount 값보다 우선한다.
특정 Pod만 자동 마운트를 끄라는 요구라면 Pod spec에 설정한다.
또한 ServiceAccount를 편집해도 기존 Pod의 마운트가 제거되거나 Deployment가 자동으로
롤아웃되지는 않는다. 이 랩에서는 다음 절의 템플릿 변경으로 생성되는 새 Pod를 검증한다.
:::

## projected volume으로 토큰 직접 마운트하기

### 공식 예제에서 필요한 블록 가져오기

Kubernetes 공식 사이트 내부에서 **`ServiceAccount token volume projection`**을 검색한다.
[Configure Service Accounts for Pods의 같은 이름 절](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection)에서
Pod YAML의 `volumes`와 `volumeMounts`를 가져온다.

| 공식 예제에서 볼 필드 | 이 랩에 맞출 값 |
|---|---|
| `serviceAccountName` | `dashboard-sa` |
| 볼륨과 마운트의 `name` | 둘 다 `token` |
| `serviceAccountToken.path` | 파일 이름 `token` |
| `volumeMounts.mountPath` | `/var/run/secrets/kubernetes.io/serviceaccount` |

공식 예제의 `audience`는 그 예제의 수신 대상을 위한 값이다. 문제에 별도 요구가 없으면
그대로 복사하지 않고 생략한다. `expirationSeconds`도 문제에서 요구할 때 지정한다.
토큰 문자열을 YAML에 붙여 넣는 작업이 아니라, kubelet이 토큰 파일을 제공하도록 선언하는 작업이다.

### 제공된 Deployment 파일 수정하기

이 랩은 `~/web-dashboard/deployment.yaml`을 제공한다. 해당 파일을 편집한다.
live Deployment만 수정하면 파일이 낡은 채 남아 다음 `apply`에서 수정이 되돌아갈 수 있다.

아래는 **Deployment의 `spec.template` 아래 발췌**다. 기존 컨테이너의 image·ports 등은
유지하고 `volumeMounts`를 추가한다. `volumes`는 `containers`와 같은 수준에 둔다.

```yaml
    spec:
      serviceAccountName: dashboard-sa
      volumes:
      - name: token
        projected:
          sources:
          - serviceAccountToken:
              path: token
      containers:
      - name: web-dashboard
        volumeMounts:
        - name: token
          mountPath: /var/run/secrets/kubernetes.io/serviceaccount
          readOnly: true
```

:::caution[함정 — mountPath는 디렉터리까지만]
최종 파일 경로는 `mountPath`와 `path`를 합친
`/var/run/secrets/kubernetes.io/serviceaccount/token`이다.
`mountPath`에도 `/token`을 붙이면 `…/token/token`이 된다.
이 발췌는 토큰만 제공한다. 앱이 `ca.crt`나 `namespace` 파일도 사용한다면 별도 구성이 필요하다.
:::

### 적용 후 새 Pod 확인하기

```bash
kubectl apply --dry-run=client -f ~/web-dashboard/deployment.yaml
kubectl apply -f ~/web-dashboard/deployment.yaml
kubectl rollout status deploy web-dashboard
kubectl get sa dashboard-sa -o yaml
kubectl get pods
kubectl get pod <pod-name> -o yaml
```

dry-run은 파일의 사전 확인이고, rollout 성공은 Deployment의 준비 상태 확인이다.
새 Pod YAML에서 다음 연결까지 확인해야 마운트 구성 검증이 끝난다.

- ServiceAccount의 `automountServiceAccountToken`이 `false`다.
- 새 Pod의 `serviceAccountName`이 `dashboard-sa`다.
- `token` 볼륨의 source가 `serviceAccountToken`이고, 컨테이너가 같은 이름의 볼륨을 마운트한다.

컨테이너에 `test` 명령이 있으면 토큰 내용을 출력하지 않고 실제 파일도 확인한다.

```bash
kubectl exec <pod-name> -c web-dashboard -- test -s /var/run/secrets/kubernetes.io/serviceaccount/token
```

종료 코드 0이면 파일이 존재하고 비어 있지 않다. API 조회까지 요구한 문제라면 Dashboard에서
원래 조회 작업을 다시 수행한다. 파일 존재만으로 인증·권한 성공이 증명되지는 않는다.

## 프라이빗 레지스트리 자격증명 연결하기

학습용 원본 풀이: [Practice Test: Image Security](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/24-Practice-Test-Image-Security.md)

이 절은 앞의 Dashboard 토큰 작업과 별도인 Image Security 랩이다. 이미지 다운로드에는
kubelet이 레지스트리에 제시할 자격증명이 필요하다.

**문서 찾기:** Kubernetes 공식 사이트 내부에서 `Pull an Image from a Private Registry`를 검색한다.
[Create a Secret by providing credentials on the command line](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/#create-a-secret-by-providing-credentials-on-the-command-line)
절의 명령에서 Secret 이름·서버·사용자·비밀번호를 문제 값으로 바꾼다.

```bash
# "Run command kubectl create secret docker-registry private-reg-cred --docker-username=dock_user --docker-password=dock_password …"
kubectl create secret docker-registry private-reg-cred \
  --docker-server=myprivateregistry.com:5000 \
  --docker-username=dock_user \
  --docker-password=dock_password \
  --docker-email=dock_user@myprivateregistry.com
```

`kubectl edit deploy web`으로 Deployment를 연다. 같은 공식 페이지의
[Create a Pod that uses your Secret](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/#create-a-pod-that-uses-your-secret)
절에서 `imagePullSecrets` 블록을 가져와 `spec.template.spec` 아래에 넣는다.
아래는 발췌이며, Secret은 workload와 같은 namespace에 있어야 한다.

```yaml
      # "Edit deployment using kubectl edit deploy web command and add imagePullSecrets section. Use private-reg-cred"
      imagePullSecrets:
      - name: private-reg-cred
```

같은 편집에서 대상 컨테이너의 이미지를 `myprivateregistry.com:5000/nginx:alpine`으로 바꾼다.
`docker-registry`는 생성 명령의 종류이고, 만들어진 Secret의 실제 타입은
`kubernetes.io/dockerconfigjson`이다.

### 이미지 다운로드 완료 확인하기

```bash
kubectl rollout status deploy web
kubectl get secret private-reg-cred
kubectl describe pod <pod-name>
```

새 Pod가 이미지를 받아 준비 상태가 되는지 확인한다. `ImagePullBackOff`는 이미지 다운로드의
재시도를 늦추고 있다는 뜻이다. Secret 미존재만을 뜻하지 않으므로 Pod Events에서
레지스트리 인증 실패·이미지 이름 오류·연결 실패를 구분한다.
