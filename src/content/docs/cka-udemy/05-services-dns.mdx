> 짝이 되는 개념 장: [cka 9. Service](/cka/09-services/) · [cka 10. 클러스터 DNS](/cka/10-dns/)

이 장은 조회형 문제가 많다 — **어떤 명령의 어느 열을 보는가**가 곧 답이다.

:::tip[실습 전 확인]
Pod IP는 실행 중인 Pod의 주소, ClusterIP는 변하는 Pod들 앞에 둔 Service의 가상 주소다.
DNS(Domain Name System)는 Service 이름을 그 ClusterIP로 바꾼다.
FQDN(Fully Qualified Domain Name, 전체 도메인 이름)은
`<service>.<namespace>.svc.cluster.local`처럼 상위 도메인까지 모두 붙인 이름이다.
:::

## Service 기초 — Practice Test: Services

원본 풀이: [22-Practice-Test-Services.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/22-Practice-Test-Services.md)

| 과제 | 명령 |
|---|---|
| 타입·ClusterIP 확인 — *What is the type of the default kubernetes service?* | `k get svc` → TYPE 열 |
| targetPort 확인 — *What is the targetPort configured on the kubernetes service?* | `k describe svc <name>` → TargetPort |
| 라벨 확인 — *How many labels are configured on the kubernetes service?* | `k get svc --show-labels` |
| 엔드포인트 개수 — *How many Endpoints are attached on the kubernetes service?* | `k describe svc <name>` → Endpoints |

Service 생성 문제 — *Create a new service to access the web application using the
service-definition-1.yaml file.* — 는 정의 파일의 빈칸(셀렉터·포트)을 채워 `create -f` 하거나,
[1장의 `expose` 한 줄](/cka-udemy/01-basics/)로 끝낸다.

:::tip[엔드포인트가 답의 근거다]
"Service가 몇 개의 Pod으로 트래픽을 보내는가"는 전부 Endpoints 개수를 묻는 문제다.
셀렉터와 Pod 라벨이 맞아야 엔드포인트가 생긴다 — 0개면 셀렉터 불일치부터 의심.
실제 데이터 소스는 EndpointSlice다 ([cka 9장](/cka/09-services/)).
:::

## 환경 탐색 — Practice Test: Explore Environment

원본 풀이: [09-Practice-Test-Explore-Env.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/09-Practice-Test-Explore-Env.md)

노드의 네트워크 인터페이스를 읽는 연습 — 시험보다 [18장 트러블슈팅](/cka/18-troubleshooting/)의 재료다.

```bash
# "What is the Internal IP address of the controlplane node in this cluster?"
kubectl get nodes -o wide                 # INTERNAL-IP
# "What is the network interface configured for cluster connectivity on the controlplane node?"
# "What is the MAC address of the interface on the controlplane node?"
ip a | grep -B2 <그 IP>                   # -B2 = 매칭 앞 2줄까지 출력 — 인터페이스명과 MAC(link/ether)이 그 줄에 있다
# "If you were to ping google from the controlplane node, which route does it take?"
ip route show default                     # 기본 게이트웨이
# "What is the port the kube-scheduler is listening on in the controlplane node?"
netstat -nplt | grep kube-scheduler       # n(숫자 주소) p(프로세스명) l(리스닝만) t(TCP) — 듣는 포트 (스케줄러: 10259)
# "Notice that ETCD is listening on two ports. Which of these have more client connections established?"
netstat -anp | grep etcd                  # a = 리스닝뿐 아니라 맺힌 연결까지 전부 — 클라이언트 2379, 피어 2380
```

- 인터페이스 이름 규칙: `eth*`는 물리, `lo`는 루프백, `veth*`는 Pod 쪽 가상 인터페이스다.
  `cni0` 같은 브리지는 보통 **CNI(Container Network Interface) 플러그인**이 만든다.
  원본 문제는 containerd가 만든 브리지라고 표현하지만, 런타임 이름만 보고 답하지 말고
  `ip link`에서 실제 인터페이스를 확인한다
  — *We use Containerd as our container runtime. What is the interface/bridge created by
  Containerd on this host?*
- etcd의 두 포트 중 연결이 많은 쪽은 **2379**(API 서버가 붙는 클라이언트 포트),
  2380은 컨트롤 플레인이 여럿일 때의 피어 통신용이다

## 서비스 네트워킹 — Practice Test: Service Networking

원본 풀이: [18-Practice-Test-Service-Networking.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/18-Practice-Test-Service-Networking.md)

클러스터에는 서로 다른 세 IP 대역이 있다. **랩의 객관식 보기를 빠르게 푸는 법**과
**실제 설정값을 확인하는 법**은 구분한다. 현재 주소 몇 개만 보고 전체 CIDR을 단정할 수는 없다.

| 대역 | 랩 보기에서 빠르게 추론 | 설정 원본 확인 |
|---|---|---|
| 노드 — *What network range are the nodes in the cluster part of?* | `k get nodes -o wide` → INTERNAL-IP | 노드에서 `ip -brief address`, `ip route`로 주소의 prefix 확인 |
| Pod — *What is the range of IP addresses configured for PODs on this cluster?* | `k get pods -A -o wide` — 호스트 네트워크 Pod 제외 | `k get nodes -o custom-columns=NAME:.metadata.name,PODCIDR:.spec.podCIDR` 또는 CNI 설정 |
| Service — *What is the IP Range configured for the services within the cluster?* | `k get svc -A` → CLUSTER-IP | `k get servicecidr` 또는 kube-apiserver의 `--service-cluster-ip-range` |

현재 Kubernetes의 `ServiceCIDR` 확인 방법은
[Extend Service IP Ranges](https://kubernetes.io/docs/tasks/network/extend-service-ip-ranges/)에 있다.

kube-proxy 관련 —

```bash
# "How many kube-proxy pods are deployed in this cluster?"
kubectl get pods -n kube-system | grep kube-proxy   # 노드 수만큼 있다
# "What type of proxy is the kube-proxy configured to use?"
kubectl logs -n kube-system <kube-proxy-pod>        # 프록시 모드(iptables 등)가 로그에 찍힌다
# "How does this Kubernetes cluster ensure that a kube-proxy pod runs on all nodes in the cluster?"
kubectl get ds -n kube-system                       # 모든 노드에 하나씩 = DaemonSet
```

## CoreDNS — Practice Test: CoreDNS in Kubernetes

원본 풀이: [21-Practice-Test-CoreDNS-in-Kubernetes.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/21-Practice-Test-CoreDNS-in-Kubernetes.md)

| 과제 | 답의 위치 |
|---|---|
| DNS 서버 주소 | `kube-dns` Service의 ClusterIP (보통 `10.96.0.10`) |
| Corefile 경로 | CoreDNS Deployment의 Args → `/etc/coredns/Corefile` |
| Corefile은 어떻게 주입되나 | ConfigMap `coredns`로 마운트 |
| 루트 도메인 | Corefile의 `kubernetes cluster.local ...` |

이름 규칙의 공식 근거는
[DNS for Services and Pods 문서](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)다 —
시험 중 형식이 헷갈릴 때 여기를 연다.
이름 규칙 문제는 [1장에서 본 규칙](/cka-udemy/01-basics/)의 반복이다 —
같은 ns면 `web-service`, 다른 ns면 `web-service.payroll`,
풀 네임은 `web-service.payroll.svc.cluster.local`.

앱이 다른 ns의 DB를 못 찾는 문제의 정답은 대개 **환경 변수의 호스트명에
네임스페이스를 붙이는 것**이다 (`mysql` → `mysql.payroll`) —

```bash
kubectl exec -it hr -- nslookup mysql.payroll > /root/nslookup.out
```

:::caution[함정 — Pod의 DNS 이름]
Service와 달리 **Pod은 기본적으로 DNS 레코드가 없거나 IP 기반**(`10-244-1-5.<ns>.pod...`)이다.
"Pod을 이름으로 조회하라"는 보기가 나오면 의심부터 할 것 — 원리는 [cka 10장](/cka/10-dns/).
:::

## Service → DNS → 외부 경로를 한 겹씩 검증하기

Service를 만들었다는 사실만으로 트래픽 경로가 완성되지는 않는다. **백엔드 → Service → DNS →
외부 진입점** 순서로 통과 지점을 늘리면, 뒤 단계가 실패해도 이미 통과한 층은 원인에서 제외할 수 있다.

1. **셀렉터와 실제 백엔드가 연결됐는지 확인한다.**

   ```bash
   kubectl describe svc <service> -n <namespace>       # Selector / Port / TargetPort
   kubectl get pods -n <namespace> -l '<key>=<value>' --show-labels
   kubectl get endpointslices -n <namespace> \
     -l kubernetes.io/service-name=<service> -o wide
   ```

   `EndpointSlice`의 주소가 비었으면 아직 네트워크 경로를 시험할 단계가 아니다. Service 셀렉터와
   Pod 라벨, Pod `Ready`, `targetPort`를 먼저 맞춘다. 옛 `Endpoints` API는 v1.33부터 deprecated이므로,
   실습 판정의 단일 원본은 `EndpointSlice`로 잡는다.

2. **같은 디버그 Pod에서 Pod IP와 ClusterIP를 차례로 호출한다.**

   ```bash
   kubectl run netcheck -n <namespace> --image=busybox:1.36 \
     --restart=Never --rm -it -- sh

   # 컨테이너 안에서
   wget -qO- http://<pod-ip>:<target-port>
   wget -qO- http://<cluster-ip>:<service-port>
   ```

   Pod IP부터 실패하면 애플리케이션·컨테이너 포트 문제다. Pod IP는 되는데 ClusterIP가 실패하면
   Service 포트, EndpointSlice, kube-proxy 규칙을 본다.

3. **이름 해석과 실제 HTTP 연결을 분리한다.**

   ```bash
   nslookup kubernetes.default
   nslookup <service>.<namespace>.svc.cluster.local
   wget -qO- http://<service>.<namespace>.svc.cluster.local:<service-port>
   ```

   첫 조회는 클러스터 DNS 전체의 기준점이고, 둘째는 대상 레코드만 확인한다. `nslookup` 성공은
   IP를 얻었다는 뜻일 뿐 백엔드 응답까지 증명하지 않으므로 마지막 호출도 성공해야 한다.

4. **NodePort라면 클러스터 밖에서 마지막 한 겹을 확인한다.**

   ```bash
   kubectl get svc <service> -n <namespace> -o wide     # NODE-PORT 확인
   kubectl get nodes -o wide                           # 도달 가능한 노드 주소 확인

   # 클러스터 밖의 셸에서
   curl -fsS http://<reachable-node-ip>:<node-port>
   ```

   내부 FQDN 호출까지 되는데 외부 요청만 실패하면 앱·셀렉터·DNS를 다시 고치지 않는다. 도달 가능한
   노드 주소인지, NodePort 범위와 노드 방화벽·보안 그룹이 열렸는지 확인한다.
   `externalTrafficPolicy: Local`이면 요청을 받은 노드에 Ready 백엔드가 있는지도 함께 본다.

공식 기준은 Kubernetes v1.35의
[Service](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/service/),
[EndpointSlice](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/endpoint-slices/),
[DNS 진단](https://v1-35.docs.kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/) 문서다.

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| Service 기초 | `Service defining a Service` | [Service](https://kubernetes.io/docs/concepts/services-networking/service/)의 첫 YAML에서 `spec.selector`, `ports[].port`, `targetPort`, `type` 구조 |
| 환경·서비스 네트워킹 | `Service ClusterIP NodePort` | 같은 [Service](https://kubernetes.io/docs/concepts/services-networking/service/) 문서의 Service 타입과 가상 IP 설명. 인터페이스·라우팅 조회는 YAML 작성 없이 `ip`·`ss`로 확인 |
| CoreDNS와 이름 규칙 | `DNS for Services and Pods` | [DNS for Services and Pods](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)에서 Service FQDN 규칙 확인. Corefile을 고칠 때는 [Debugging DNS Resolution](https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/)의 `coredns` ConfigMap 예시 |
| Service 경로 진단 | `Debug Services` | [Debug Services](https://kubernetes.io/docs/tasks/debug/debug-application/debug-service/)의 Service → DNS → EndpointSlice → Pod 순서. 새 YAML보다 기존 Service의 selector/port를 대조할 때 사용 |

Service YAML은 `kubectl expose ... --dry-run=client -o yaml`로 뼈대를 얻는 편이 빠르다. 문서에서는
`port`와 `targetPort`의 의미, `NodePort`·`ExternalName`처럼 명령형 출력에 없는 필드만 확인한다.

## 이 장에서 남길 것

- 조회형 문제는 명령보다 **열 이름**(TYPE·Endpoints·INTERNAL-IP·CLUSTER-IP)을 기억한다
- 세 IP 대역(노드/Pod/Service)은 각각 다른 명령으로 찾는다 — 컨트롤 플레인 Pod은 호스트 IP라 제외
- 듣는 포트는 `netstat -nplt | grep <프로세스>`
- DNS 문제의 절반은 `<service>.<namespace>` 형식으로 끝난다
- 증명 순서는 **EndpointSlice → Pod IP → ClusterIP → FQDN → 외부 NodePort**다
