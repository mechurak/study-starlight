<Thesis>Service는 생성 출력이 아니라 selector와 Ready Pod이 만든 EndpointSlice, 그리고 실제 요청 성공으로 완성된다.</Thesis>

> 짝이 되는 개념 장: [cka 9. Service](/cka/09-services/)

이 장의 과제는 Pod 앞에 Service를 만들고 트래픽이 올바른 백엔드까지 가는지 확인하는 것이다.
`port`는 클라이언트가 접속하는 Service 포트이고, `targetPort`는 Pod가 실제로 듣는 포트다.

먼저 Pod 라벨과 Service selector를 나란히 보고, EndpointSlice의 Ready 주소를 확인한다. NodePort
문제라면 내부 연결이 된 뒤에만 도달 가능한 노드 IP와 nodePort로 외부 요청을 보낸다.

## Service 기초 — Practice Test: Services

원본 풀이: [22-Practice-Test-Services.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/02-Core-Concepts/22-Practice-Test-Services.md)

| 과제 | 명령 |
|---|---|
| 타입·ClusterIP 확인 — *What is the type of the default kubernetes service?* | `k get svc` → TYPE 열 |
| targetPort 확인 — *What is the targetPort configured on the kubernetes service?* | `k describe svc <name>` → TargetPort |
| 라벨 확인 — *How many labels are configured on the kubernetes service?* | `k get svc --show-labels` |
| 엔드포인트 개수 — *How many Endpoints are attached on the kubernetes service?* | `k describe svc <name>` → Endpoints |

Service 생성 문제 — *Create a new service to access the web application using the
service-definition-1.yaml file.* — 는 정의 파일의 빈칸(셀렉터·포트)을 채워 `create -f` 하거나,
[1장의 `expose` 한 줄](/cka-udemy/01-basics/)로 끝낸다.

:::tip[엔드포인트가 답의 근거다]
"Service가 몇 개의 Pod으로 트래픽을 보내는가"는 전부 Endpoints 개수를 묻는 문제다.
셀렉터와 Pod 라벨이 맞아야 엔드포인트가 생긴다 — 0개면 셀렉터 불일치부터 의심.
실제 데이터 소스는 EndpointSlice다 ([cka 9장](/cka/09-services/)).
:::

### 첫 조회 — Pod 라벨과 Service selector를 나란히 본다

애플리케이션이 MySQL에 연결하지 못하면, 먼저 문제의 아키텍처에 적힌 **Service 이름·포트·대상
Pod**와 현재 상태를 비교한다. 아래 예제의 `k`는 `alias k=kubectl`을 설정한 셸을 전제로 한다.

```bash
k -n beta get pod --show-labels -o wide
k -n beta get svc -o wide
```

첫 명령에서는 Pod의 `READY`, `STATUS`, `IP`, `NODE`, `LABELS`를 본다. 둘째에서는 Service의
`NAME`, `PORT(S)`, `SELECTOR`를 본다. Service selector가 `name=mysql`이면 같은 네임스페이스의
Pod에 그 라벨이 있어야 한다. **Pod 이름이나 Service 자체의 라벨과 비교하는 것이 아니다.**
옵션은 `--show-label`이 아니라 **`--show-labels`**다.

`get svc -o wide`의 `PORT(S)`는 Service가 받는 `port`를 보여 주며, NodePort 타입이면
`port:nodePort` 형태다. **Pod로 전달하는 `targetPort`는 표시하지 않는다.** 목록의 `3306/TCP`만
보고 포트 설정이 맞다고 결론 내리지 말고, 대상 Service를 상세 조회한다.

```bash
k -n beta describe svc mysql-service
# Selector / Port / TargetPort / Endpoints를 확인
```

`port`는 클라이언트가 접속하는 Service 포트이고, `targetPort`는 Service가 연결할 Pod 쪽 포트다.
두 값의 역할은 [Service 공식 문서](https://kubernetes.io/docs/concepts/services-networking/service/#defining-a-service)에서
확인할 수 있다. 전체 필드가 필요하면 `k -n beta get svc mysql-service -o yaml`로 본다.
이 유형은 `custom-columns`를 외우지 않아도 **목록은 `get`, 상세 진단은 `describe`**로 해결할 수 있다.

### 명령형 생성 — expose의 이름과 selector를 구분한다

기존 Pod를 Service로 노출할 때는 다음 명령을 쓴다. 아래는 `alpha`에 `name=mysql` 라벨을 가진
`mysql` Pod가 있고, 아직 `mysql-service`가 없는 경우다.

```bash
k -n alpha get pod -l name=mysql --show-labels
k -n alpha expose pod mysql \
  --name=mysql-service \
  --port=3306 \
  --target-port=3306 \
  --selector=name=mysql
```

`pod mysql`은 **기준으로 삼을 기존 Pod 이름**, `--name=mysql-service`는 **새 Service 이름**이다.
Pod 이름이 다르면 `pod mysql` 부분을 조회 결과로 바꾼다. `--selector=name=mysql`은 대상 라벨 조건을
요구사항과 정확히 맞춘다. 생략하면 Pod 라벨에서 추론하며, Service 타입의 기본값은 `ClusterIP`다.
옵션은 [`kubectl expose` 공식 문서](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_expose/)에서 확인한다.

단순 생성은 이처럼 명령형 커맨드로 끝내고, 추가 필드를 편집해야 하면 같은 명령 뒤에
`--dry-run=client -o yaml > service.yaml`을 붙여 초안을 만든 뒤 수정·적용한다.
문제에서 매니페스트 파일 작성을 요구하면 그 요구도 충족한다.

이름이 잘못된 Service 교체와 기존 `targetPort` 수정은
[10장 MySQL 연결 실패 사례](/cka-udemy/10-troubleshooting/#애플리케이션-연결-실패--mysql-service-진단)에서 다룬다.

### messaging — 클러스터 내부에 6379 공개

`within the cluster`는 ClusterIP, `imperative commands`는 명령으로 직접 생성하는 조건이다.
기본 타입은 ClusterIP이고 `targetPort`를 생략하면 `port` 값을 사용한다.

```bash
kubectl expose --help
kubectl expose pod messaging -n default --port=6379 --name=messaging-service
kubectl describe svc messaging-service -n default
kubectl get endpointslice -n default -l kubernetes.io/service-name=messaging-service
```

도움말 Examples의 `expose pod`에서 이름·포트를 바꾼다. Service의 Port·TargetPort가 6379이고,
EndpointSlice가 준비된 messaging Pod 주소를 가리키는지 확인한다. 비어 있으면 Pod 라벨과 selector부터 비교한다.

### hr-web-app — 골격에 nodePort 30082 추가

노드에서 받는 포트가 30082, 앱이 듣는 포트가 8080이면 `nodePort: 30082`, `targetPort: 8080`이다.
Service 자체의 `port`는 이 문제에서 8080으로 둔다. 기존 Deployment로부터 selector를 가져온다.

```bash
kubectl expose deployment hr-web-app -n default --name=hr-web-app-service \
  --type=NodePort --port=8080 --target-port=8080 \
  --dry-run=client -o yaml > hr-web-app-service.yaml
vim hr-web-app-service.yaml
```

생성된 `spec.ports`의 항목에 `nodePort`를 추가한다. 아래는 해당 부분만 발췌한 것이다.

```yaml
  ports:
    - port: 8080
      protocol: TCP
      targetPort: 8080
      nodePort: 30082
```

```bash
kubectl explain service.spec.ports
kubectl create -f hr-web-app-service.yaml
kubectl describe svc hr-web-app-service -n default
kubectl get endpointslice -n default -l kubernetes.io/service-name=hr-web-app-service
kubectl get nodes -o wide
# 접근 가능한 실제 노드 IP로 교체
curl http://NODE_IP:30082
```

`8080:30082/TCP` 표시만으로 백엔드 연결을 증명하지는 못한다. EndpointSlice와 실제 HTTP 응답까지 확인한다.
공식 [Service의 NodePort 절](https://kubernetes.io/docs/concepts/services-networking/service/#type-nodeport)에서
`nodePort`를 검색하거나 `explain`으로 필드 깊이를 확인한다. 기존 Deployment의 레이블을 유지해야 한다.

## 완료 판정

- Service selector와 대상 Pod 라벨이 일치하고 EndpointSlice에 Ready 백엔드 주소가 있다.
- Service의 port·targetPort·type과, 요구됐다면 nodePort가 문제 조건과 같다.
- ClusterIP 요청이 성공하며 NodePort 문제는 클러스터 밖의 실제 HTTP 응답까지 성공한다.
