<Thesis>Pod 설정은 생성 골격에 필요한 필드를 더하고, 변경 가능 여부와 소유자를 확인한 뒤 컨테이너별 실행 결과로 검증한다.</Thesis>

> 짝이 되는 개념 장: [cka 4. Pod](/cka/04-pods/) · [cka 6. 설정과 리소스](/cka/06-config/)

이 장 실습의 공통 뼈대는 하나다 — **Pod 스펙 대부분은 실행 중에 못 고친다.**

:::tip[실습 전 확인]
`command`는 이미지의 ENTRYPOINT, `args`는 CMD를 덮는다. ConfigMap은 일반 설정,
Secret은 민감한 값을 담지만 **base64일 뿐 암호화는 아니다**. 환경변수로 받은 값은 Secret이
바뀌어도 실행 중인 프로세스에 자동 반영되지 않는다.
:::

기존 Pod은 먼저 `describe`의 **Controlled By**를 확인한다. Deployment 등이 소유하면 그 컨트롤러의
Pod template을 고친다. 독립 Pod의 변경 불가 필드라면 원본을 보관하고 **수정본을 먼저 준비한 뒤**
대상 Pod만 재생성한다. 모든 문제에서 삭제가 필요한 것은 아니다.

```bash
kubectl get pod <name> -o yaml > pod.yaml
vim pod.yaml
# 재생성용 파일에서는 status와 metadata의 uid/resourceVersion/creationTimestamp/managedFields를 제거
kubectl delete pod <name>
kubectl create -f pod.yaml
```

`kubectl replace --force -f pod.yaml`도 삭제·재생성한다. 강제 삭제는 실행 중 프로세스의 종료 확인을
기다리지 않으므로 일반적인 시간 절약 방법으로 사용하지 않는다. 아래 orange 사례에서는 실패한 독립 Pod의
command를 바꾸기 위해 이 동작을 사용한다.

## command와 args — Practice Test: Commands and Arguments

원본 풀이: [06-Practice-Test-Commands-and-Arguments.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/06-Practice-Test-Commands-and-Arguments.md)

Dockerfile의 ENTRYPOINT/CMD와 Pod 스펙의 command/args가 어떻게 덮어쓰는지가 전부다 —

| Dockerfile | Pod 스펙 | 실제 실행 |
|---|---|---|
| `ENTRYPOINT` | `command` | command가 ENTRYPOINT를 **대체** |
| `CMD` | `args` | args가 CMD를 **대체** |

```yaml
spec:                       # — "Set the command option to ['sleep', '5000']."
  containers:
  - name: ubuntu-sleeper
    image: ubuntu-sleeper
    command: ["sleep"]
    args: ["5000"]
```

:::caution[함정 — 숫자도 문자열로]
`command: ["sleep", 1200]`은 생성이 거부된다 — *Both sleep and 1200 should be defined as a string.*
배열 원소는 **문자열**이어야 한다. 숫자로 해석되는 `1200`은 따옴표로 감싸지만,
`sleep`처럼 이미 문자열인 값은 따옴표를 생략해도 된다 — `[sleep, "1200"]`.
:::

### BusyBox — args 한 줄과 sh -c의 경계

공식 BusyBox 이미지에서 `command`를 생략했다면 아래처럼 `args`만 써도 된다.
[Logging Architecture의 예제](https://kubernetes.io/docs/concepts/cluster-administration/logging/#streaming-sidecar-container)도
이 형태를 사용한다. 시험에서는 긴 셸 명령을 마지막 문자열에 붙여 넣으면 편하다.

```yaml
# app-container: while·리다이렉션은 셸이 해석
args: [sh, -c, "while true; do echo 'Log entry' >> /var/log/app/app.log; sleep 5; done"]
```

```yaml
# log-agent: 단순 실행은 실행 파일과 인자를 나누면 충분
args: [tail, -f, /var/log/app/app.log]
```

`args: ["tail -f /var/log/app/app.log"]`는 공백을 포함한 전체 문자열을 실행 파일명으로 취급하므로
실패한다. 한 문자열로 쓰려면 `args: [sh, -c, "tail -f /var/log/app/app.log"]`로 감싼다.
따옴표는 YAML 값을 문자열로 묶을 뿐 셸을 실행하지 않는다. `sh`, `-c`, 경로는 그대로 문자열이므로
따옴표가 필수는 아니다. `;`, `while`, `>>`를 쓰는 명령은 `sh -c`로 실행한다.

이 단축형은 이미지의 기본 실행 설정에 의존한다. BusyBox는 ENTRYPOINT 없이 CMD로 `sh`를
지정하지만, ENTRYPOINT가 있는 다른 이미지에서는 `args`가 그 실행 파일에 전달된다.
기존 YAML에 `command`가 있다면 함께 확인한다.
[command·args 공식 문서](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)의
ENTRYPOINT/CMD 대체 규칙과 구분해 익힌다.

## 환경 변수와 ConfigMap — Practice Test: Env Variables

원본 풀이: [09-Practice-Test-Env-Variables.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/09-Practice-Test-Env-Variables.md)

```bash
# "Create a new ConfigMap for the 'webapp-color' POD. Use the spec given on the right."
kubectl create configmap webapp-config-map --from-literal=APP_COLOR=darkblue
```

주입 두 방식 — 개별 지정(`env`)과 통째로(`envFrom`) —

```yaml
    env:              # — "Set the environment option to APP_COLOR - green."
    - name: APP_COLOR
      value: green
    envFrom:          # — "Set the environment option to envFrom and use configMapRef webapp-config-map."
    - configMapRef:
        name: webapp-config-map
```

세 가지 주입 방식(env/envFrom/volume)의 전체 지도는 [cka 6장](/cka/06-config/)에 있다.
시험 중 YAML 뼈대는 공식 문서
[Configure a Pod to Use a ConfigMap](https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/)에서
복사하는 게 빠르다.

### ConfigMap 변경 반영을 판정하는 루프

ConfigMap을 고친 뒤 API 오브젝트만 보고 끝내면 안 된다. **같은 Pod의 환경 변수**, **마운트 파일**,
**교체된 Pod의 환경 변수**를 분리해 확인한다.

```bash
# 1) API 서버에는 새 값이 저장됐는가
kubectl get cm app-config -o jsonpath='{.data.APP_COLOR}{"\n"}'

# 2) 기존 Pod의 env는 옛 값, 디렉터리 마운트 파일은 동기화 뒤 새 값이어야 한다
kubectl exec <pod> -- printenv APP_COLOR
kubectl exec <pod> -- cat /etc/config/APP_COLOR

# 3) env를 바꾸려면 Pod을 교체하고 새 Pod에서 다시 읽는다
kubectl rollout restart deploy/<name>
kubectl rollout status deploy/<name>
kubectl exec deploy/<name> -- printenv APP_COLOR
```

볼륨 반영은 kubelet 동기화 때문에 즉시 보이지 않을 수 있다. 그래도 계속 옛 값이면 `subPath` 마운트인지
먼저 확인한다. `subPath`와 환경 변수는 자동 갱신되지 않는다. 단독 Pod은 재생성해야 하고,
Deployment도 rollout하지 않은 채 scale만 바꾸면 옛 값 Pod과 새 값 Pod이 섞일 수 있다. 공식
[Updating Configuration via a ConfigMap](https://v1-35.docs.kubernetes.io/docs/tutorials/configuration/updating-configuration-via-a-configmap/)이
이 차이를 실행 흐름으로 보여 준다.

## Secret — Practice Test: Secrets

원본 풀이: [11.Practice-Test-Secrets.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/11.Practice-Test-Secrets.md)

```bash
# "Run command kubectl create secret generic db-secret --from-literal=DB_Host=sql01 --from-literal=DBUser=root --from-literal=DB_Password=password123"
# generic = 임의 키-값 타입 — docker-registry·tls 타입과 구분하는 서브커맨드다
kubectl create secret generic db-secret \
  --from-literal=DB_Host=sql01 \
  --from-literal=DB_User=root \
  --from-literal=DB_Password=password123
```

Pod에 통째로 주입할 때는 ConfigMap과 대칭으로 공식 문서의
[`envFrom.secretRef`](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#configure-all-key-value-pairs-in-a-secret-as-container-environment-variables)를 쓴다 —

```yaml
    envFrom:
    - secretRef:
        name: db-secret
```

:::tip[조회 습관]
`k get secrets`의 **DATA 열**이 키 개수다 — *Run the command 'kubectl get secrets' and look at the DATA field*.
값 확인은 `k describe secret`이 아니라
`k get secret <name> -o jsonpath='{.data.<key>}' | base64 -d` — describe는 값을 안 보여준다.
:::

### 기존 Secret을 읽기 전용 파일로 마운트 — secret-1401

`admin1401`의 기존 `dotfile-secret`을 사용한다. 먼저 Pod 초안을 만들고 컨테이너 이름과
볼륨을 고친다. 공식 [Secret 볼륨 예제](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#create-a-pod-that-has-access-to-the-secret-data-through-a-volume)에서
`volumes`·`volumeMounts` 블록을 가져온다.

```bash
kubectl run secret-1401 -n admin1401 --image=busybox \
  --dry-run=client -o yaml --command -- sleep 4800 > admin.yaml
```

완성한 `admin.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-1401
  namespace: admin1401
spec:
  containers:
    - name: secret-admin
      image: busybox
      command: ["sleep", "4800"]
      volumeMounts:
        - name: secret-volume
          mountPath: /etc/secret-volume
          readOnly: true
  volumes:
    - name: secret-volume
      secret:
        secretName: dotfile-secret
```

`volumes.name`과 `volumeMounts.name`을 맞추고, `secretName`에는 **같은 네임스페이스의
기존 Secret 이름**을 넣는다. Pod 이름과 컨테이너 이름이 다르다는 조건도 놓치지 않는다.

```bash
kubectl apply -f admin.yaml
kubectl -n admin1401 wait --for=condition=Ready pod/secret-1401 --timeout=120s
kubectl -n admin1401 describe pod secret-1401
kubectl -n admin1401 exec secret-1401 -c secret-admin -- ls -la /etc/secret-volume
```

`describe`의 마운트가 `(ro)`인지 확인한다. 점으로 시작하는 숨김 파일도 보려면 `ls -la`를 쓴다.

## securityContext — Practice Test: Security Contexts

원본 풀이: [26-Practice-Test-Security-Context.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/26-Practice-Test-Security-Context.md)

| 과제 | 위치 |
|---|---|
| 실행 유저 확인 — *Run the command 'kubectl exec ubuntu-sleeper -- whoami'…* | `k exec ubuntu-sleeper -- whoami` |
| 유저 바꾸기 — *Set a security context to run as user 1010.* | `securityContext.runAsUser: 1010` |
| 커널 능력 추가 — *Add SYS_TIME capability to the container's securityContext* | 컨테이너 쪽 `securityContext.capabilities.add: ["SYS_TIME"]` |

필드 이름이 헷갈리면 공식 문서
[Configure a Security Context](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)에서
예시 YAML을 그대로 가져온다.

```yaml
spec:
  securityContext:        # Pod 수준 — 모든 컨테이너에 적용
    runAsUser: 1010
  containers:
  - name: ubuntu
    securityContext:      # 컨테이너 수준 — Pod 수준을 덮어쓴다
      capabilities:
        add: ["SYS_TIME"]
```

:::caution[함정 — capabilities는 컨테이너 수준에만]
`runAsUser`는 Pod·컨테이너 양쪽에 다 쓸 수 있고 컨테이너 쪽이 이기지만
(*The User ID defined in the securityContext of the container overrides the User ID in the POD.*),
**`capabilities`는 컨테이너 수준에만** 존재한다. Pod 수준에 넣으면 거부된다.
:::

## 멀티 컨테이너 — Practice Test: Multi-Container Pods

원본 풀이: [13-Practice-Test-Multi-Container-Pods.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/13-Practice-Test-Multi-Container-Pods.md)

- 컨테이너 수는 `k get pod red`의 READY 열(`x/y`의 y) — *Identify the number of containers running in the 'red' pod.*
- 이름은 `k describe pod blue` — *Identify the name of the containers running in the 'blue' pod.*
- 특정 컨테이너에 들어가기: `k exec -it <pod> -c <container> -- sh`
- 로그 확인: `k logs <pod> -c <container>` — 멀티 컨테이너에서 `-c`는 필수다

사이드카로 로그를 나르는 구성(앱 컨테이너 + 로그 에이전트)이 단골 문제다.
요즘 시험 기준의 **네이티브 사이드카**(initContainers + `restartPolicy: Always`, v1.33 GA)는
[cka 4장 컨테이너 여러 개 쓰기](/cka/04-pods/)를 볼 것.

### mc-pod — 노드 이름 주입과 파일 로그 공유

문제를 세 갈래로 옮긴다. 노드 정보는 **Downward API**로 주입하고, 두 busybox가 같은 `emptyDir`을
마운트하며, 기록자와 stdout 출력자의 명령을 나눈다. 같은 Pod라도 파일시스템은 자동 공유되지 않는다.
`emptyDir`은 컨테이너 재시작에는 유지되지만 Pod가 제거되면 사라지는 임시 볼륨이다.

```bash
# 네임스페이스가 없을 때만 생성
kubectl create namespace mc-namespace
kubectl run mc-pod -n mc-namespace --image=nginx:1-alpine \
  --dry-run=client -o yaml > mc-pod.yaml
vim mc-pod.yaml
```

첫 컨테이너 이름을 `mc-pod-1`로 바꾸고 `env`를 추가한다. busybox 두 개와 공유 볼륨을 넣은 완성본:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mc-pod
  namespace: mc-namespace
spec:
  containers:
    - name: mc-pod-1
      image: nginx:1-alpine
      env:
        - name: NODE_NAME
          valueFrom:
            fieldRef:
              fieldPath: spec.nodeName
    - name: mc-pod-2
      image: busybox:1
      command: ["/bin/sh", "-c"]
      args:
        - |
          while true; do
            date >> /var/log/shared/date.log
            sleep 1
          done
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/shared
    - name: mc-pod-3
      image: busybox:1
      args: ["/bin/sh", "-c", "tail -n+1 -F /var/log/shared/date.log"]
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/shared
  volumes:
    - name: shared-logs
      emptyDir: {}
```

공식 문서에서는 다음 세 위치를 찾는다.

- [환경 변수로 Pod 정보 노출](https://kubernetes.io/docs/tasks/inject-data-application/environment-variable-expose-pod-information/)에서
  `spec.nodeName`을 검색한다. 환경 변수 이름만 `NODE_NAME`으로 바꾸면 된다.
- [컨테이너 command·args](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)의
  **Run a command in a shell**에서 `/bin/sh -c` 구조를 가져온다. `while`·`>>`는 셸 문법이고,
  `args` 아래 `- |`는 여러 줄을 한 문자열로 전달한다. `>>`는 추가, `>`는 덮어쓰기다.
- [Logging Architecture의 Streaming sidecar container](https://kubernetes.io/docs/concepts/cluster-administration/logging/#streaming-sidecar-container)에서
  `tail -n+1 -F`와 공유 `emptyDir` 예제를 찾고 파일 경로를 바꾼다.

:::tip[파일 생성 대기는 대문자 -F로 해결]
공식 로깅 예제는 `touch` 없이 `tail -n+1 -F`를 사용한다. `-n+1`은 첫 줄부터 출력하고,
`-F`는 파일 이름을 추적하며 파일이 없어도 다시 열기를 시도한다. 읽는 컨테이너가 먼저 시작하면
초기 오류가 나올 수 있지만 파일 생성 뒤 읽기 시작하므로 별도의 `until`·`touch`는 필수가 아니다.
소문자 `-f`만 쓰면 처음부터 없는 파일을 같은 방식으로 재시도하지 않는다.
이 busybox 이미지에서는 위처럼 셸 실행 전체를 `args`에 넣어도 된다.
:::

```bash
kubectl apply -f mc-pod.yaml
kubectl wait -n mc-namespace --for=condition=Ready pod/mc-pod --timeout=120s
kubectl get pod mc-pod -n mc-namespace -o wide
kubectl exec -n mc-namespace mc-pod -c mc-pod-1 -- printenv NODE_NAME
kubectl logs -n mc-namespace mc-pod -c mc-pod-3 -f
```

`READY 3/3`, NODE 열과 환경 변수 값의 일치, 날짜 로그의 지속 추가를 각각 확인한다.
`Ctrl+C`는 로그 조회만 종료한다. 날짜가 안 나오면 기록 파일부터 확인한다.

```bash
kubectl exec -n mc-namespace mc-pod -c mc-pod-2 -- tail /var/log/shared/date.log
```

파일이 증가하는데 stdout이 비면 세 번째 컨테이너의 경로·마운트 이름·명령을 확인한다.
두 번째 컨테이너는 파일로 리다이렉션하므로 `kubectl logs -c mc-pod-2`가 비어 있어도 정상이다.

### logging-deployment — 네이티브 로그 사이드카

`logging-ns`에 복제본 1개의 Deployment를 만든다. `app-container`가 5초마다 파일에 기록하고,
`log-agent`가 그 파일을 읽어 표준 출력으로 보낸다. **같은 `emptyDir`을 마운트**해야 파일이 공유된다.
`kubectl logs -c log-agent`는 그 표준 출력을 보여 준다.

```bash
kubectl get ns logging-ns
# 없을 때만 생성
kubectl create ns logging-ns
kubectl create deployment logging-deployment -n logging-ns \
  --image=busybox --image=busybox --replicas=1 \
  --dry-run=client -o yaml > logging-deployment.yaml
```

생성된 컨테이너 이름을 고치고 `log-agent` 블록을 `initContainers`로 옮긴다.
아래가 수정한 파일이다. `args`를 사용해 실행 명령을 짧게 적었다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: logging-deployment
  namespace: logging-ns
spec:
  replicas: 1
  selector:
    matchLabels:
      app: logging-deployment
  template:
    metadata:
      labels:
        app: logging-deployment
    spec:
      volumes:
        - name: log-volume
          emptyDir: {}
      initContainers:
        - name: log-agent
          image: busybox
          restartPolicy: Always
          args: [sh, -c, "touch /var/log/app/app.log; tail -f /var/log/app/app.log"]
          volumeMounts:
            - name: log-volume
              mountPath: /var/log/app
      containers:
        - name: app-container
          image: busybox
          args: [sh, -c, "while true; do echo 'Log entry' >> /var/log/app/app.log; sleep 5; done"]
          volumeMounts:
            - name: log-volume
              mountPath: /var/log/app
```

[`initContainers` + 컨테이너 수준 `restartPolicy: Always`](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)
조합이 네이티브 사이드카다. 일반 init은 성공 종료를 기다리지만 이 사이드카는 시작 후 계속 실행되면서
앱도 시작할 수 있다. `restartPolicy`는 `image`·`args`와 같은 깊이에 둔다.

`touch`는 `tail` 실행 전에 빈 파일을 보장하며 기존 내용을 지우지 않는다. 로그 에이전트가 파일을
만들어야 하므로 이 마운트에 `readOnly: true`를 붙이지 않는다. 별도의 파일 생성용 init은 필요 없다.
두 컨테이너를 모두 `containers`에 두는 전통적인 공유 로그 구성도 가능하지만 네이티브 사이드카와
수명주기가 다르다. 이 실습에서는 제시된 솔루션에 맞춰 네이티브 구성을 연습한다.

```bash
kubectl apply -f logging-deployment.yaml
kubectl rollout status deployment/logging-deployment -n logging-ns --timeout=120s
kubectl logs -n logging-ns deployment/logging-deployment -c log-agent -f
```

`Log entry`가 약 5초마다 추가되는지 확인한다. 앱의 `kubectl logs -c app-container`가 비어 있어도
파일로 리다이렉션하므로 정상이다. 로그가 없으면 다음 순서로 원인을 좁힌다.

```bash
kubectl get pods -n logging-ns -l app=logging-deployment
kubectl describe pod -n logging-ns <pod-name>
kubectl logs -n logging-ns deployment/logging-deployment -c log-agent
kubectl exec -n logging-ns deployment/logging-deployment \
  -c app-container -- cat /var/log/app/app.log
```

앱이 시작되지 않으면 `log-agent`의 `restartPolicy: Always` 누락부터 확인한다. 이를 빼면 일반 init이
되어 끝나지 않는 `tail`을 기다린다. 파일 없음 오류는 `touch`·경로·마운트를, 파일은 증가하는데
로그가 비면 두 `volumeMounts.name`과 읽는 경로를 비교한다. Deployment YAML을 고쳐 다시
`apply`하고 검증한다. Pod를 직접 삭제하는 것으로 설정 오류를 해결하지 않는다.

## init 컨테이너 — Practice Test: Init-Containers

원본 풀이: [16-Practice-Test-Init-Containers.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/16-Practice-Test-Init-Containers.md)

| 과제 | 보는 곳 |
|---|---|
| init 컨테이너 있는 Pod 찾기 — *Identify the pod that has an initContainer configured.* | `k describe pods` → Init Containers 절 |
| init 상태·실패 이유 — *Run the command kubectl describe pod blue and check the state field of the initContainer.* | `k describe pod <name>` → State / Reason |
| init 추가·수정 — *Update the pod red to use an initContainer that uses the busybox image and sleeps for 20 seconds* | YAML 뽑아 고치고 재생성 (이 장 첫머리 3단계) |

```yaml
spec:
  initContainers:
  - name: warmup
    image: busybox
    command: ["sleep", "20"]
```

:::caution[함정 — Init:CrashLoopBackOff]
Pod STATUS가 `Init:...`으로 시작하면 범인은 본 컨테이너가 아니라 init이다.
원본 랩의 정답도 `sleeeep 2`라는 **오타 하나**였다 — *Check the command used by the initContainer.
Looks like there is a type in sleep command. Fix it, it should be `sleep 2` not `sleeeep 2`* —
init의 command부터 읽을 것.
init은 **순서대로, 성공해야** 다음으로 넘어간다.
:::

### orange — init command 오타의 진단·수정·복구

```bash
kubectl get pod orange
kubectl describe pod orange
# INIT_NAME을 describe의 실제 init 컨테이너 이름으로 교체
kubectl logs orange -c INIT_NAME
```

`Init:CrashLoopBackOff`, init의 Command `sleeeep 2`, 로그의 명령 없음 오류를 연결한다.
[Debug Init Containers](https://kubernetes.io/docs/tasks/debug/debug-application/debug-init-containers/)에서
`Accessing logs`를 찾으면 `-c` 예제가 있다. 컨트롤러가 없는 독립 Pod임을 확인한 뒤 수정한다.

```bash
kubectl edit pod orange
```

Vim에서 `/sleeeep`로 찾아 `sleep`으로 바꾸고 저장한다. init의 command 변경이 거절되면
kubectl이 수정본을 저장한 **실제 임시 파일 경로**를 오류 메시지에 출력한다.

```bash
# 아래 경로는 오류 메시지에 나온 파일로 교체
kubectl replace --force -f /tmp/kubectl-edit-실제파일명.yaml
kubectl get pod orange
kubectl describe pod orange
```

`replace --force`는 제자리 수정이 아니라 삭제·재생성이다. 실패한 대상 Pod 하나의 복구에 한정한다.
init이 `Completed`, Exit Code `0`으로 끝나고 본 컨테이너가 Ready인지 확인한다.
재생성이 실패하면 보관된 수정본을 고쳐 `kubectl create -f <파일>`로 복구한다.
명령 의미는 `kubectl replace --help`와 [공식 Quick Reference](https://kubernetes.io/docs/reference/kubectl/quick-reference/)에서 찾는다.

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| command와 args | `Define command arguments container` | [Define a Command and Arguments for a Container](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)의 `command`·`args` 배열과 셸 실행 패턴 |
| 환경 변수·ConfigMap | `Configure Pod ConfigMap` | [Configure a Pod to Use a ConfigMap](https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/)에서 `env.valueFrom`, `envFrom.configMapRef`, ConfigMap 볼륨 중 문제에 맞는 예시 |
| Secret | `Distribute credentials securely Secrets` | [Distribute Credentials Securely Using Secrets](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/)에서 `secretKeyRef`, `envFrom.secretRef`, Secret 볼륨 예시 |
| securityContext | `Configure Security Context` | [Configure a Security Context for a Pod or Container](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)에서 Pod/컨테이너 수준의 위치와 `capabilities` 구조 |
| 멀티 컨테이너·사이드카 | `Sidecar Containers` | [Sidecar Containers](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)에서 일반 앱 컨테이너와 네이티브 사이드카(`initContainers` + `restartPolicy: Always`) 구조 구분 |
| init 컨테이너 | `Init Containers` | [Init Containers](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/)의 `spec.initContainers` 예시. 일반 init에는 컨테이너 수준 `restartPolicy`를 붙이지 않는다 |

ConfigMap·Secret 페이지는 예시가 많다. 문제 문장에서 **한 키만 주입**이면 `env.valueFrom`,
**전체 키 주입**이면 `envFrom`, **파일로 제공**이면 `volumes`를 검색해 해당 블록만 가져온다.

## 이 장에서 남길 것

- 기존 Pod은 소유자와 변경 가능 필드를 확인하고, 독립 Pod 재생성은 수정본 준비 뒤 대상 하나에만 수행
- command↔ENTRYPOINT, args↔CMD — 각각 대체 관계
- 환경 주입은 `env`(개별) / `envFrom`(통째) 두 손잡이, ConfigMap과 Secret이 대칭
- ConfigMap 변경 뒤에는 **API 값 → 기존 Pod env·마운트 파일 → 교체된 Pod env** 순서로 판정
- securityContext는 Pod 수준과 컨테이너 수준의 우선순위(컨테이너 승)와 capabilities 위치
- `Init:` 접두사가 붙은 상태는 init 컨테이너부터 진단
