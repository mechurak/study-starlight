<Thesis>소유자를 먼저 확인하고 command·args를 올바른 위치에서 바꾼 뒤 새 컨테이너의 실제 실행 결과를 검증한다</Thesis>

`command`와 `args`는 컨테이너 이미지의 기본 실행 명령을 바꾼다. 이 페이지에서는
**누가 Pod을 관리하는지 확인 → 올바른 template 수정 → 새 컨테이너의 명령·상태 확인** 흐름을
연습한다. 기본 개념은 [CKA Pod — 배포의 최소 단위](/cka/pods/#command와-args--dockerfile과의-대응)에서 복습한다.

기존 Pod은 `kubectl describe pod <name>`의 **Controlled By**를 먼저 본다.
Deployment 등이 소유하면 그 workload의 `spec.template`을 고치고 rollout을 확인한다.
독립 Pod의 변경 불가 필드라면 수정본을 먼저 준비한 뒤 대상 Pod만 재생성한다.

```bash
kubectl get pod <name> -o yaml > pod.yaml
vim pod.yaml
# 재생성용 파일에서는 status와 서버가 채운 metadata 필드를 제거
kubectl delete pod <name>
kubectl create -f pod.yaml
```

`kubectl replace --force -f pod.yaml`도 삭제·재생성이다. API 서버가 노드의 프로세스 종료를
확인할 때까지 기다리지 않으므로 일반적인 시간 절약 방법으로 사용하지 않는다.

## command와 args — Practice Test: Commands and Arguments

원본 풀이: [06-Practice-Test-Commands-and-Arguments.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/05-Application-Lifecycle-Management/06-Practice-Test-Commands-and-Arguments.md)

Dockerfile의 ENTRYPOINT/CMD와 Pod 스펙의 command/args가 어떻게 덮어쓰는지가 전부다 —

| Dockerfile | Pod 스펙 | 실제 실행 |
|---|---|---|
| `ENTRYPOINT` | `command` | command가 ENTRYPOINT를 **대체** |
| `CMD` | `args` | args가 CMD를 **대체** |

```yaml
spec:                       # — "Set the command option to ['sleep', '5000']."
  containers:
  - name: ubuntu-sleeper
    image: ubuntu-sleeper
    command: ["sleep"]
    args: ["5000"]
```

:::caution[함정 — 숫자도 문자열로]
`command: ["sleep", 1200]`은 생성이 거부된다 — *Both sleep and 1200 should be defined as a string.*
배열 원소는 **문자열**이어야 한다. 숫자로 해석되는 `1200`은 따옴표로 감싸지만,
`sleep`처럼 이미 문자열인 값은 따옴표를 생략해도 된다 — `[sleep, "1200"]`.
:::

### BusyBox — args 한 줄과 sh -c의 경계

공식 BusyBox 이미지에서 `command`를 생략했다면 아래처럼 `args`만 써도 된다.
[Logging Architecture의 예제](https://kubernetes.io/docs/concepts/cluster-administration/logging/#streaming-sidecar-container)도
이 형태를 사용한다. 시험에서는 긴 셸 명령을 마지막 문자열에 붙여 넣으면 편하다.

```yaml
# app-container: while·리다이렉션은 셸이 해석
args: [sh, -c, "while true; do echo 'Log entry' >> /var/log/app/app.log; sleep 5; done"]
```

```yaml
# log-agent: 단순 실행은 실행 파일과 인자를 나누면 충분
args: [tail, -f, /var/log/app/app.log]
```

`args: ["tail -f /var/log/app/app.log"]`는 공백을 포함한 전체 문자열을 실행 파일명으로 취급하므로
실패한다. 한 문자열로 쓰려면 `args: [sh, -c, "tail -f /var/log/app/app.log"]`로 감싼다.
따옴표는 YAML 값을 문자열로 묶을 뿐 셸을 실행하지 않는다. `sh`, `-c`, 경로는 그대로 문자열이므로
따옴표가 필수는 아니다. `;`, `while`, `>>`를 쓰는 명령은 `sh -c`로 실행한다.

이 단축형은 이미지의 기본 실행 설정에 의존한다. BusyBox는 ENTRYPOINT 없이 CMD로 `sh`를
지정하지만, ENTRYPOINT가 있는 다른 이미지에서는 `args`가 그 실행 파일에 전달된다.
기존 YAML에 `command`가 있다면 함께 확인한다.
[command·args 공식 문서](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)의
ENTRYPOINT/CMD 대체 규칙과 구분해 익힌다.

## 공식 문서에서 찾을 것

Kubernetes 문서 내부 검색에서 `Define command arguments container`를 열고
[Define a Command and Arguments for a Container](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)의
`command`·`args` 배열과 **Run a command in a shell** 예제를 가져온다.
필드 위치는 `kubectl explain pod.spec.containers.command`와 `.args`로 확인한다.
문서의 ENTRYPOINT/CMD 대응을 보고, 현재 이미지에 이미 설정된 command도 함께 확인한다.

## 완료 판정

독립 Pod을 재생성했다면 새 UID의 Pod인지, workload를 고쳤다면 새 template으로 rollout됐는지
구분한다. `kubectl get pod -o wide`, `describe`, `logs`로 Ready와 실제 출력·종료 코드를
확인한다. `args` 배열 모양이 맞아도 셸 연산자(`;`, `while`, `>>`)를 쓴 명령에
`sh -c`가 없으면 실행 실패하므로 로그의 실행 파일 오류와 YAML을 대조한다.
