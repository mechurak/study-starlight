> 짝이 되는 개념 장: [cka 11. Ingress와 Gateway API](/cka/11-ingress-gateway/) · [cka 12. NetworkPolicy와 CNI](/cka/12-networkpolicy/)

Ingress 실습은 두 벌이다 — 첫 벌은 **리소스**(라우팅 규칙)만 다루고,
둘째 벌은 **컨트롤러**를 바닥부터 배포한다. 이 구분이 곧
"Ingress = 리소스 + 컨트롤러"라는 [cka 11장](/cka/11-ingress-gateway/)의 축이다.

:::tip[실습 전 확인]
Ingress 리소스만 만들어서는 트래픽이 흐르지 않는다. 그것을 읽어 실제 프록시를 설정하는
Ingress 컨트롤러가 필요하다. NetworkPolicy도 마찬가지로 **정책을 구현하는 CNI 플러그인**이
있어야 효력이 난다. 선택된 방향만 격리되며, 아무 정책도 없는 Pod은 기본적으로 모두 허용이다.
:::

## Ingress 리소스 — Practice Test: CKA Ingress 1

원본 풀이: [24-Practice-Test-CKA-Ingress-Net-1.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/24-Practice-Test-CKA-Ingress-Net-1.md)

| 과제 | 명령 |
|---|---|
| 컨트롤러가 어느 ns에 있나 | `k get all -A \| grep -i ingress` |
| 라우팅 규칙 읽기 | `k describe ingress -n app-space` → Host/Path → Backend |
| 경로 수정·추가 | `k edit ingress -n app-space` |

새 Ingress를 만드는 문제 — 현행 API(`networking.k8s.io/v1`)로 쓴다.
(원본 랩 답안 일부는 폐기된 `extensions/v1beta1`로 남아 있다 — 그대로 쓰면 안 된다.)
시험 중에는 공식 [Ingress 문서](https://kubernetes.io/docs/concepts/services-networking/ingress/)의
예시 YAML을 복사해 이름·경로·포트만 바꾸는 게 가장 빠르다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-pay
  namespace: critical-space
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
spec:
  rules:
  - http:
      paths:
      - path: /pay
        pathType: Prefix
        backend:
          service:
            name: pay-service
            port:
              number: 8282
```

:::caution[함정 — Ingress는 앱과 같은 네임스페이스]
Ingress 리소스는 **백엔드 Service가 있는 네임스페이스**에 만든다.
컨트롤러의 네임스페이스가 아니다. `-n`을 빼먹으면 default에 생기고 라우팅은 안 된다.
:::

:::tip[명령형 생성]
`kubectl create ingress ingress-pay -n critical-space --rule="/pay=pay-service:8282"`
한 줄로도 만들 수 있다 (`--rule`은 `경로=서비스:포트` 형식) —
뼈대를 뽑고 annotation만 edit로 붙이는 편이 빠르다.
:::

## Ingress 컨트롤러 배포 — Practice Test: CKA Ingress 2

원본 풀이: [25-Practice-Test-CKA-Ingress-Net-2.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/25-Practice-Test-CKA-Ingress-Net-2.md)

컨트롤러(nginx-ingress)를 구성 요소별로 직접 만든다 — 순서가 곧 답안이다:

```bash
kubectl create namespace ingress-nginx
kubectl create configmap ingress-nginx-controller -n ingress-nginx
kubectl create serviceaccount ingress-nginx -n ingress-nginx
kubectl create serviceaccount ingress-nginx-admission -n ingress-nginx
# Role/RoleBinding은 주어진 파일로, Deployment+Service는 /root/ingress-controller.yaml을 고쳐서
```

주어진 매니페스트에서 고치게 시키는 오류 네 가지 — **전부 실제 시험에서도 나오는 유형**이다:

- Deployment의 `namespace`가 다른 ns로 되어 있다
- 들여쓰기 오류 (vi에서 `:set nu`로 줄 번호 켜고 찾는다)
- Service `name` 오타
- `nodeport` 소문자 — `nodePort`가 맞다 (YAML 키는 대소문자 구분)

## Ingress — 컨트롤러부터 외부 요청까지 증명하기

Ingress의 성공 조건은 오브젝트 생성이 아니라 **컨트롤러 진입점으로 보낸 HTTP 요청이 규칙에 맞는
백엔드 응답을 받는 것**이다. 아래 순서로 리소스와 실제 트래픽을 연결한다.

```bash
# 1. 백엔드는 Ingress 없이도 준비됐는가
kubectl get svc <backend-service> -n <app-namespace>
kubectl get endpointslices -n <app-namespace> \
  -l kubernetes.io/service-name=<backend-service> -o wide

# 2. 이 Ingress를 맡을 클래스와 컨트롤러가 있는가
kubectl get ingressclass
kubectl get pods -n <controller-namespace>
kubectl logs -n <controller-namespace> <controller-pod> --tail=50

# 3. 규칙이 어느 클래스·호스트·경로·백엔드를 가리키는가
kubectl describe ingress <ingress> -n <app-namespace>

# 4. 컨트롤러의 LoadBalancer 주소나 NodePort를 찾는다
kubectl get svc -n <controller-namespace>

# 5. 클러스터 밖에서 Host 헤더와 경로를 포함해 호출한다
curl -fsS -H 'Host: <rule-host>' http://<entry-address>:<port>/<path>
```

백엔드 EndpointSlice가 비었으면 Ingress보다 아래 계층의 문제다. 백엔드와 컨트롤러는 정상인데
404가 나오면 요청의 `Host`·경로와 `pathType`을 규칙에 맞춰 본다. 연결 자체가 되지 않으면
컨트롤러 Service의 외부 주소·NodePort와 방화벽을 본다. Ingress만 생성하고 컨트롤러가 없으면
실제 데이터 플레인이 없으므로 이 검증의 2단계를 통과할 수 없다.

## Gateway API — API 설치와 구현체를 분리해 진단하기

Gateway API는 Ingress보다 오브젝트가 많지만, 층은 더 명확하다. **CRD는 API 서버가 리소스를
저장하게 하고, Gateway 컨트롤러는 그 선언을 실제 프록시 설정으로 만든다.** CRD만 설치해
`kubectl get gateway`가 동작하는 상태는 트래픽 준비 완료가 아니다.

```bash
# 1. API 종류와 구현체가 각각 존재하는가
kubectl api-resources --api-group=gateway.networking.k8s.io
kubectl get gatewayclass
kubectl describe gatewayclass <class>                 # Accepted condition
# 컨트롤러 Pod 위치와 라벨은 설치한 구현체 문서에서 확인한다
kubectl get pods -A | grep -i gateway

# 2. Gateway가 실제 데이터 플레인에 반영됐는가
kubectl describe gateway <gateway> -n <gateway-namespace>
# status.conditions의 Accepted=True, Programmed=True와 ADDRESS를 확인

# 3. HTTPRoute가 부모에 붙었고 백엔드 참조를 풀었는가
kubectl describe httproute <route> -n <route-namespace>
# status.parents[].conditions의 Accepted=True, ResolvedRefs=True를 확인

# 4. Route 아래의 Service에도 Ready 엔드포인트가 있는가
kubectl get svc <backend-service> -n <backend-namespace>
kubectl get endpointslices -n <backend-namespace> \
  -l kubernetes.io/service-name=<backend-service> -o wide

# 5. Gateway의 주소 또는 구현체 Service의 NodePort로 실제 요청한다
curl -fsS -H 'Host: <route-hostname>' http://<gateway-address>:<port>/<path>
```

`GatewayClass`가 `Accepted=False`면 `controllerName`을 처리할 구현체부터 확인한다.
Gateway가 `Programmed=False`면 선언은 받아들였지만 데이터 플레인 반영이 끝나지 않은 것이므로
컨트롤러 이벤트·로그로 내려간다. HTTPRoute가 `Accepted=False`면 `parentRefs`, listener와
`allowedRoutes`를, `ResolvedRefs=False`면 Service 이름·포트와 교차 네임스페이스 `ReferenceGrant`를 본다.
모든 condition이 참이어도 EndpointSlice와 마지막 HTTP 요청을 확인해야 실제 경로가 완성된다.

공식 기준은 Kubernetes v1.35의
[Ingress](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/ingress/),
[Gateway API](https://v1-35.docs.kubernetes.io/docs/concepts/services-networking/gateway/)와
Gateway API 프로젝트의 [시작 안내](https://gateway-api.sigs.k8s.io/guides/getting-started/introduction/)다.

## NetworkPolicy — Practice Test: Network Policies

원본 풀이: [28-Practice-Test-Network-Policies.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/07-Security/28-Practice-Test-Network-Policies.md)

| 과제 | 명령 |
|---|---|
| 정책 조회 | `k get netpol` |
| 어느 Pod에 적용되나 | `k describe netpol` → PodSelector |
| 무엇을 막나 — *What is the impact of the rule configured on this Network Policy?* | PolicyTypes + Ingress/Egress 규칙 읽기 |

### 문제를 셀렉터와 방향으로 번역하기

NetworkPolicy에는 `kubectl create ingress` 같은 전용 생성 서브커맨드가 없다. 작성 문제는 공식
[Network Policies 문서](https://kubernetes.io/docs/concepts/services-networking/network-policies/)의
전체 예시를 복사한 뒤 문제에 없는 필드를 덜어 내는 게 빠르다. YAML을 쓰기 전에 이름과 라벨부터
분리해 확인한다.

```bash
kubectl get pods -n default --show-labels
kubectl get svc payroll-service db-service -n default -o yaml
kubectl get svc kube-dns -n kube-system
```

문제에는 `payroll-service`와 `db-service`라는 **Service 이름**이 나오지만, NetworkPolicy의
`podSelector`가 고르는 것은 그 뒤의 **Pod 라벨**이다. 이 랩에서는 각각 `name: payroll`과
`name: mysql`이고, 정책을 적용할 출발지는 `name: internal`이다.

| 문제 문구 | 매니페스트에서 답할 자리 | 이 랩의 값 |
|---|---|---|
| 어느 Pod의 통신을 통제하나 | 최상위 `spec.podSelector` | `name: internal` |
| UI가 internal Pod에 들어올 수 있나 | `policyTypes`의 `Ingress` + `ingress` | `ingress`의 `- {}`로 모두 허용 |
| 어디로 나갈 수 있나 | `egress[].to.podSelector` | `name: mysql`, `name: payroll` |
| 어느 목적지 포트인가 | 각 `egress[].ports` | TCP 3306, TCP 8080 |
| 이름을 해석할 수 있나 | 목적지 없는 별도 egress 규칙 | UDP/TCP 53 |

### 랩 정답 — 업무 트래픽은 제한하고 UI ingress는 열기

문제의 핵심 정책 방향은 Egress지만, "UI에서 테스트하려면 ingress를 허용하라"는 문장까지 반영한
랩 솔루션은 `Ingress`도 정책 유형에 넣고 빈 허용 규칙 하나를 둔다. 따라서 internal Pod에서
나가는 업무 트래픽은 mysql(3306)과 payroll(8080)로 제한하면서, UI가 internal Pod로 들어오는
트래픽은 전부 허용한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: internal-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      name: internal
  policyTypes:
  - Egress
  - Ingress
  ingress:
  - {}
  egress:
  - to:
    - podSelector:
        matchLabels:
          name: mysql
    ports:
    - protocol: TCP
      port: 3306

  - to:
    - podSelector:
        matchLabels:
          name: payroll
    ports:
    - protocol: TCP
      port: 8080

  - ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

`policyTypes`의 `Egress`가 internal Pod의 출구를 격리하므로, 이제 위 세 egress 규칙에 걸리지 않는
목적지는 모두 막힌다. mysql과 payroll을 규칙 두 개로 나눠야 **mysql:3306**과
**payroll:8080** 조합만 허용된다. 두 Pod와 두 포트를 규칙 하나에 모으면 두 Pod 모두에 두 포트를
허용하는 교차 조합이 된다.

마지막 DNS 규칙에는 `to`가 없다. 즉 특정 DNS Pod만 고르는 대신 **어느 목적지든 UDP/TCP 53이면
허용**한다. 랩은 이 단순한 형태를 정답으로 삼는다. `kube-dns` Service에 함께 보이는 9153/TCP는
메트릭 포트라 이름 해석에 열 필요가 없다. 운영 정책에서는 클러스터의 CNI 동작과 CoreDNS 라벨을
확인한 뒤 `kube-system`의 DNS Pod로 목적지를 더 좁힌다 — 구체적인 형태는
[cka 12장](/cka/12-networkpolicy/#egress와-dns)에 있다.

:::caution[함정 — 빈 객체와 빈 목록은 정반대]
`ingress` 아래의 `- {}`는 출발지와 포트를 제한하지 않는 **allow all** 규칙이다. 반면 `policyTypes`에
`Ingress`를 넣고 `ingress: []`로 두거나 필드를 생략하면 허용 규칙이 하나도 없어 **deny all**이
된다. 이 랩의 빈 객체는 UI 테스트를 위한 의도적인 예외다. 운영에서는 신뢰할 수 있는 출발지만
허용한다.
:::

:::caution[함정 — 정책에 안 잡힌 Pod은 전부 허용]
NetworkPolicy가 있어도 **podSelector에 안 걸린 Pod은 여전히 전부 허용**이다.
"internal → payroll이 되는 이유"류의 보기 문제는 이 기본값을 묻는 것이다 —
랩의 정답 보기도 *Only internal applications can access payroll service* 다.
:::

### 적용 결과를 세 방향으로 증명하기

```bash
kubectl apply --dry-run=server -f internal-policy.yaml
kubectl apply -f internal-policy.yaml
kubectl describe networkpolicy internal-policy -n default
```

`describe`에서 선택 대상이 `name=internal`, 정책 유형에 `Ingress`와 `Egress`가 모두 있고 ingress가
모든 트래픽, egress가 mysql 3306·payroll 8080·DNS UDP/TCP 53으로 해석됐는지 먼저 확인한다.
그다음 Internal Application UI에서 다음 결과를 확인한다.

| 요청 | 기대 결과 | 증명하는 규칙 |
|---|---|---|
| UI → internal | 성공 | `ingress`의 `- {}` |
| internal → payroll-service:8080 | 성공 | payroll egress |
| internal → db-service:3306 | 성공 | mysql egress |
| internal → 그 밖의 서비스 | 실패 | Egress 격리 후 허용 목록에 없음 |
| internal → Service 이름 조회 | 성공 | DNS UDP/TCP 53 |

## 시험장에서 공식 문서 찾기

| 이 장의 섹션 | 검색어 | 공식 문서에서 가져올 것 |
|---|---|---|
| Ingress 리소스 | `Ingress` | [Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/)의 `networking.k8s.io/v1` 예시에서 `ingressClassName`, `rules`, `pathType`, Service backend 구조 |
| Ingress 컨트롤러 | `Ingress Controllers` | [Ingress Controllers](https://kubernetes.io/docs/concepts/services-networking/ingress-controllers/)에서 **지원되는 구현체를 고른 뒤 그 구현체 문서**로 이동. Kubernetes 공통 컨트롤러 Deployment YAML은 없으므로 문제에서 준 매니페스트가 우선 |
| Gateway API | `Gateway API` | [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/)에서 `GatewayClass` → `Gateway` → `HTTPRoute` 역할과 API 설치 필요 여부 확인 |
| NetworkPolicy | `Network Policies` | [Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)의 전체 ingress/egress 예시를 복사한 뒤 `podSelector`, `namespaceSelector`, `ports`를 문제에 맞게 줄이기 |

:::caution[구현체 전용 필드는 공식 Kubernetes 문서에 없다]
`nginx.ingress.kubernetes.io/rewrite-target` 같은 annotation과 컨트롤러 Deployment 인자는
Ingress API 필드가 아니라 구현체 설정이다. Kubernetes 문서에서 추측해 쓰지 말고, 시험이 제공한
매니페스트 또는 지정된 컨트롤러 문서에서 확인한다.
:::

## 이 장에서 남길 것

- Ingress 문제는 먼저 **리소스 문제인지 컨트롤러 문제인지** 가른다
- Ingress 리소스는 앱과 같은 ns, API는 `networking.k8s.io/v1`
- Ingress의 마지막 판정은 컨트롤러 진입점에 **Host 헤더·경로를 넣은 외부 요청**이다
- Gateway API는 **CRD와 컨트롤러**가 모두 필요하고, 조건을 Class → Gateway → Route 순서로 읽는다
- 남이 만든 매니페스트 디버깅: ns → 들여쓰기 → 이름 오타 → 키 대소문자 순으로 훑는다
- NetworkPolicy는 PolicyTypes에 적은 방향만 잠긴다 — 선택 안 된 Pod은 전부 허용
- `ingress`의 `- {}`는 모두 허용, 빈 목록은 모두 차단이며 Egress를 잠그면 DNS UDP/TCP 53도 따로 연다
