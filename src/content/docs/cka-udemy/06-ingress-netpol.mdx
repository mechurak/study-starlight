<Thesis>Ingress는 라우팅 리소스와 그것을 구현하는 컨트롤러가 모두 있어야 하며, 마지막 판정은 Host·path·TLS를 넣은 외부 요청이다.</Thesis>

> 짝이 되는 개념 장: [cka 11. Ingress와 Gateway API](/cka/11-ingress-gateway/)

이 장의 과제는 기존 Ingress 규칙을 읽거나 만들고, 요구한 host·path·Service backend·TLS가 실제
컨트롤러 진입점에 반영됐는지 확인하는 것이다. Ingress 객체만 생성해도 컨트롤러가 없으면 트래픽은 흐르지 않는다.

먼저 IngressClass와 컨트롤러 상태를 확인한 뒤 규칙을 수정한다. 내부 Service와 EndpointSlice를
확인하고, 마지막에 클러스터 밖에서 Host 헤더를 넣은 HTTP 또는 HTTPS 요청을 보낸다.

## Ingress 리소스 — Practice Test: CKA Ingress 1

원본 풀이: [24-Practice-Test-CKA-Ingress-Net-1.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/24-Practice-Test-CKA-Ingress-Net-1.md)

| 과제 | 명령 |
|---|---|
| 컨트롤러가 어느 ns에 있나 | `k get all -A \| grep -i ingress` |
| 라우팅 규칙 읽기 | `k describe ingress -n app-space` → Host/Path → Backend |
| 규칙 밖 요청은 어디로 | `k describe ingress -n app-space` → Default backend (`<default>`면 컨트롤러 인자로) |
| 경로 수정·추가 | `k edit ingress -n app-space` |

새 Ingress를 만드는 문제 — 현행 API(`networking.k8s.io/v1`)로 쓴다.
(원본 랩 답안 일부는 폐기된 `extensions/v1beta1`로 남아 있다 — 그대로 쓰면 안 된다.)
시험 중에는 공식 [Ingress 문서](https://kubernetes.io/docs/concepts/services-networking/ingress/)의
예시 YAML을 복사해 이름·경로·포트만 바꾸는 게 가장 빠르다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-pay
  namespace: critical-space
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
spec:
  rules:
  - http:
      paths:
      - path: /pay
        pathType: Prefix
        backend:
          service:
            name: pay-service
            port:
              number: 8282
```

:::caution[함정 — Ingress는 앱과 같은 네임스페이스]
Ingress 리소스는 **백엔드 Service가 있는 네임스페이스**에 만든다.
컨트롤러의 네임스페이스가 아니다. `-n`을 빼먹으면 default에 생기고 라우팅은 안 된다.
:::

:::tip[명령형 생성 — 문법은 외우지 않고 -h로 조립한다]
`kubectl create ingress ingress-pay -n critical-space --rule="/pay*=pay-service:8282"`
한 줄로도 만들 수 있고, `--annotation key=value`로 annotation까지 같이 붙는다.
`--rule`·`--annotation` 문법은 외울 대상이 아니다 — `kubectl create ingress -h`의
Examples에 그대로 나오므로, 기억할 것은 이 서브커맨드가 있다는 사실뿐이다.
함정 하나: 경로 끝의 `*`가 `pathType: Prefix`를 지정한다. `/pay*`는 `path: /pay`,
`/*`는 `path: /`를 만든다. `*`를 빼면 `Exact`가 된다.
`--dry-run=client -o yaml`로 뽑아 `path`·`pathType`을 확인하고 apply한다.
:::

:::tip[annotation은 클러스터의 기존 Ingress에서 복사한다]
`nginx.ingress.kubernetes.io/rewrite-target` 같은 annotation은 Ingress API가 아니라
nginx 구현체 설정이라 **kubernetes.io 공식 문서에 없다.** 가장 빠른 출처는 문서 검색이
아니라 클러스터에 이미 있는 Ingress다.

```bash
kubectl get ingress -A                          # 이 랩이라면 app-space에 이미 하나 있다
kubectl get ingress <이름> -n app-space -o yaml # annotation 블록을 통째로 복사
```

정리하면 — **뼈대는 공식 문서(또는 `create ingress -h`)에서, annotation은 기존 Ingress에서**
가져온다. rewrite-target이 필요한 이유: Ingress는 `/pay`로 노출하지만 앱은 `/`에서 응답하므로,
경로를 벗겨 주지 않으면 백엔드가 `/pay`를 받아 404를 낸다.

문제가 annotation **이름을 직접 준다면** 복사할 것도 없다 — 기존 리소스에는
`kubectl annotate ingress <이름> -n <ns> <key>="<value>"` 한 줄이 edit보다 빠르다.
:::

### webapp-ingress — host·Prefix·IngressClass를 한 명령으로

`ingress-ns`의 기존 Service `webapp-svc:80`으로 `kodekloud-ingress.app/` 요청을 보낸다.
Deployment `webapp-deploy`는 이미 있으므로 Ingress가 참조할 **Service 이름과 Service 포트**를 확인한다.
이 실습에서는 `nginx` 클래스 지정까지 해야 컨트롤러가 처리했다.

```bash
kubectl get svc webapp-svc -n ingress-ns
kubectl get ingressclass
kubectl create ingress -h
kubectl create ingress webapp-ingress -n ingress-ns \
  --class=nginx \
  --rule="kodekloud-ingress.app/*=webapp-svc:80" \
  --dry-run=client -o yaml > ingress.yaml
```

[`create ingress`의 Examples](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_ingress/)에서
`--rule=host/path=service:port` 형식을 찾는다. `*`가 셸에 해석되지 않도록 rule 값은 따옴표로 감싼다.
`--class=nginx`는 다음 YAML의 `spec.ingressClassName`으로 들어간다.

```yaml
spec:
  ingressClassName: nginx
  rules:
    - host: kodekloud-ingress.app
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: webapp-svc
                port:
                  number: 80
```

`nginx`는 이 환경의 클래스 이름이지 모든 클러스터의 고정값이 아니다. 다른 실습에서는
`kubectl get ingressclass`와 기존 Ingress를 확인한다. YAML을 직접 편집할 때도
`ingressClassName`은 `rules`와 같은 깊이다.

```bash
kubectl apply -f ingress.yaml
kubectl describe ingress webapp-ingress -n ingress-ns
curl -s http://kodekloud-ingress.app/
```

완료는 앱 응답까지 확인한다. `curl -s`가 아무것도 보이지 않으면 `curl -v`로 DNS·접속·HTTP 응답을
구분한다. 클래스 누락은 파일에 `ingressClassName: nginx`를 추가해 다시 `apply`한다.
백엔드가 연결되지 않으면 아래 EndpointSlice의 주소·준비 상태와 Service selector를 확인한다.

```bash
kubectl get endpointslice -n ingress-ns -l kubernetes.io/service-name=webapp-svc -o yaml
```

### 규칙에 안 맞는 요청 — 기본 백엔드는 두 층에서 정해진다

*If the requirement does not match any of the configured paths in the Ingress, to which service
are the requests forwarded?* — 어느 규칙에도 안 걸린 요청의 목적지를 묻는 문제다.
답은 한 곳에 있지 않고, **리소스 → 컨트롤러** 순서로 내려가며 찾는다.

```bash
# 1층 — Ingress 리소스가 직접 정했는가
kubectl describe ingress --namespace app-space      # Default backend: 필드

# 2층 — <default>면 컨트롤러의 기동 인자가 정한다
kubectl get deploy ingress-nginx-controller -n ingress-nginx -o yaml
#   args에서 --default-backend-service=<namespace>/<service> 를 찾는다
```

`Default backend: <default>`는 "기본 백엔드가 없다"가 아니라 **리소스가 비워 둔 결정을
컨트롤러 층이 채운다**는 뜻이다. 이 랩에서는 컨트롤러 인자가 가리키는
`app-space/default-backend-service`가 답이고, 이 인자마저 없으면 nginx 컨트롤러의
내장 404 백엔드로 간다. 우선순위로 쓰면
**리소스 `spec.defaultBackend` → 컨트롤러 `--default-backend-service` → 내장 404**다.

리소스에 직접 두는 `spec.defaultBackend`의 형태는
[cka 11장의 기본 백엔드](/cka/11-ingress-gateway/#기본-백엔드와-애노테이션)에 있다.
`--default-backend-service`는 Ingress API 필드가 아니라 nginx 구현체의 Deployment 인자라는
점까지, "리소스 문제인지 컨트롤러 문제인지 먼저 가른다"는 이 장의 축과 같은 문제다.

## Ingress 컨트롤러 배포 — Practice Test: CKA Ingress 2

원본 풀이: [25-Practice-Test-CKA-Ingress-Net-2.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/25-Practice-Test-CKA-Ingress-Net-2.md)

컨트롤러(nginx-ingress)를 구성 요소별로 직접 만든다 — 순서가 곧 답안이다:

```bash
kubectl create namespace ingress-nginx
kubectl create configmap ingress-nginx-controller -n ingress-nginx
kubectl create serviceaccount ingress-nginx -n ingress-nginx
kubectl create serviceaccount ingress-nginx-admission -n ingress-nginx
# Role/RoleBinding은 주어진 파일로, Deployment+Service는 /root/ingress-controller.yaml을 고쳐서
```

주어진 매니페스트에서 고치게 시키는 오류 네 가지 — **전부 실제 시험에서도 나오는 유형**이다:

- Deployment의 `namespace`가 다른 ns로 되어 있다
- 들여쓰기 오류 (vi에서 `:set nu`로 줄 번호 켜고 찾는다)
- Service `name` 오타
- `nodeport` 소문자 — `nodePort`가 맞다 (YAML 키는 대소문자 구분)

## Ingress TLS — 기존 리소스에 얹기

최신 랩에서 추가된 유형이다 — 이미 동작하는 Ingress에 `spec.tls`만 더해 TLS 종료를 켠다.
개념(같은 ns의 `kubernetes.io/tls` 타입 Secret, 컨트롤러에서 종료 후 백엔드는 평문)은
[cka 11장 Ingress TLS](/cka/11-ingress-gateway/#ingress-tls)가 정본이고, 여기서는 확인 사슬만 남긴다.

```bash
# 1. 참조할 Secret이 조건을 갖췄는가 — 타입과 네임스페이스
kubectl get secret app-tls -n webapp        # TYPE: kubernetes.io/tls, Ingress와 같은 ns

# 2. tls 블록을 얹는다 — 리소스가 이미 있으므로 edit
kubectl edit ingress web-app-ingress -n webapp
```

```yaml
spec:
  tls:                      # rules와 형제 레벨 — rules 안에 들여 넣지 않는다
  - hosts:
    - app.kodekloud.local   # rules의 host와 정확히 일치해야 한다
    secretName: app-tls
```

```bash
# 3. 판정은 컨트롤러 진입점의 443 — TLS는 거기서 종료된다
curl -k --resolve app.kodekloud.local:443:<컨트롤러IP> https://app.kodekloud.local/
```

`-k`는 랩의 자체 서명 인증서 때문이고, 백엔드로는 평문 HTTP로 넘어가므로 앱 쪽은 손대지 않는다.
YAML은 외울 필요 없다 — 이미 열어 둔 공식 [Ingress 문서의 TLS 절](https://kubernetes.io/docs/concepts/services-networking/ingress/#tls)에서
`tls:` 블록을 복사해 host·secretName만 바꾼다.

:::tip[처음부터 만든다면 한 줄]
생성 시점이라면 `--rule`에 `,tls=시크릿`을 붙여 라우팅과 TLS를 같이 만든다:
`kubectl create ingress web-app-ingress -n webapp --class=nginx --rule="app.kodekloud.local/*=web-app:80,tls=app-tls"`
다만 이미 있는 리소스를 지우고 다시 만드는 지름길로는 쓰지 않는다.
:::

### HTTP→HTTPS 리다이렉트 — 기본값의 방향을 안다

nginx 컨트롤러는 **TLS가 설정된 Ingress에 리다이렉트를 기본으로 켠다**
(전역 `ssl-redirect` 기본값이 true). 그래서 TLS 없이 HTTP로 테스트하는 rewrite 랩들이
`ssl-redirect: "false"`를 붙여 **끄는** 쪽이었고, "HTTP를 HTTPS로 리다이렉트하라"는 문제는
같은 키의 값을 `"true"`로 명시하는 반대 방향이다. 이름이 문제에 주어지므로 annotate 한 줄로 끝난다.

```bash
kubectl annotate ingress web-app-ingress -n webapp \
  nginx.ingress.kubernetes.io/ssl-redirect="true"

# 판정 — HTTP 요청이 308과 Location: https://… 를 받는가
curl -I -H 'Host: app.kodekloud.local' http://<컨트롤러IP>/
```

## Ingress — 컨트롤러부터 외부 요청까지 증명하기

Ingress의 성공 조건은 오브젝트 생성이 아니라 **컨트롤러 진입점으로 보낸 HTTP 요청이 규칙에 맞는
백엔드 응답을 받는 것**이다. 아래 순서로 리소스와 실제 트래픽을 연결한다.

```bash
# 1. 백엔드는 Ingress 없이도 준비됐는가
kubectl get svc <backend-service> -n <app-namespace>
kubectl get endpointslices -n <app-namespace> \
  -l kubernetes.io/service-name=<backend-service> -o wide

# 2. 이 Ingress를 맡을 클래스와 컨트롤러가 있는가
kubectl get ingressclass
kubectl get pods -n <controller-namespace>
kubectl logs -n <controller-namespace> <controller-pod> --tail=50

# 3. 규칙이 어느 클래스·호스트·경로·백엔드를 가리키는가
kubectl describe ingress <ingress> -n <app-namespace>

# 4. 컨트롤러의 LoadBalancer 주소나 NodePort를 찾는다
kubectl get svc -n <controller-namespace>

# 5. 클러스터 밖에서 Host 헤더와 경로를 포함해 호출한다
curl -fsS -H 'Host: <rule-host>' http://<entry-address>:<port>/<path>
```

백엔드 EndpointSlice가 비었으면 Ingress보다 아래 계층의 문제다. 백엔드와 컨트롤러는 정상인데
404가 나오면 요청의 `Host`·경로와 `pathType`을 규칙에 맞춰 본다. 연결 자체가 되지 않으면
컨트롤러 Service의 외부 주소·NodePort와 방화벽을 본다. Ingress만 생성하고 컨트롤러가 없으면
실제 데이터 플레인이 없으므로 이 검증의 2단계를 통과할 수 없다.

## 공식 문서에서 찾을 것

| 검색어 | 가져올 필드·판정 |
|---|---|
| `Ingress` | [`networking.k8s.io/v1`, `ingressClassName`, rules/pathType/backend](https://kubernetes.io/docs/concepts/services-networking/ingress/) |
| `Ingress TLS` | [`spec.tls[].hosts`와 `secretName`](https://kubernetes.io/docs/concepts/services-networking/ingress/#tls) |
| `Ingress Controllers` | [지원 구현체를 찾은 뒤 문제 지정 문서로 이동](https://kubernetes.io/docs/concepts/services-networking/ingress-controllers/) |

:::caution[구현체 전용 필드는 지정 문서에서 찾는다]
`nginx.ingress.kubernetes.io/rewrite-target` 같은 annotation과 컨트롤러 인자는 공통 Ingress API
필드가 아니다. 문제에서 준 매니페스트·구현체 문서·클러스터의 기존 Ingress에서 복사한다.
:::

## 완료 판정

- IngressClass와 컨트롤러가 존재하고 컨트롤러 Pod이 Ready다.
- host·pathType·Service 이름·Service port와 TLS Secret이 요구사항과 같다.
- Service EndpointSlice가 Ready 백엔드를 가리킨다.
- 컨트롤러의 실제 진입점에 Host·path를 넣은 HTTP/HTTPS 요청이 기대 응답을 반환한다.
