# CKA 실습 덱의 기준

`cka-udemy` 덱을 고치기 전에 읽는다.

## 이 덱의 역할

개념 설명을 다시 늘리는 덱이 아니라, CKA 실습에서 반복되는 **실패 진단 → 수정 → 완료 검증 → 복구** 패턴을 모은다.
기본 개념과 시험 환경은 [CKA 덱](/cka/)이 정본이다. 이 덱은 실습의 상황·관찰 지점·검증 명령에 집중한다.

## 서술 규칙

- 정답 YAML만 보여 주지 않고, 왜 실패했는지와 어떤 상태를 확인했는지를 남긴다.
- 요청한 대상만 수정하고 광범위한 삭제·재생성을 지름길로 권하지 않는다.
- 시험 배점·허용 자료·Kubernetes 버전은 `cka/_baseline.md`를 다시 확인한다.
- 실습 중심 덱이므로 `<TermIntro>`는 의무가 아니다. 새 용어는 쓰는 절 바로 앞에서 풀어 설명한다.

## 개편 페이지의 작성 계약

- 한 페이지는 하나의 작업 목표를 맡는다. 첫머리에 `<Thesis>` 한 문장과 큰 그림·할 일,
  관련 `cka` 개념 링크를 둔다. 수행에 필요한 배경은 이 덱에서도 2~4문장으로 설명한다.
- 작업 요구 → 관찰 → 최소 수정 → 완료 판정을 연결한다. 손으로 익힐 주 명령은 3~6개를
  목표로 하며, 실행 위치·namespace·리소스명·경로의 전제를 명시한다.
- 문서 안내는 작업 옆에 검색 위치·영문 검색어·공식 페이지의 절·가져올 블록과 바꿀 필드를 적는다.
  단순 조회에 불필요한 YAML이나 복구 절을 만들지 않는다. 발췌 YAML은 완성 파일과 구별한다.
- 시험용 검색은 허용 사이트 내부 검색과 본문 예제를 사용한다. KodeKloud·GitHub·제품 문서는
  학습용으로 구분한다. Quick Reference는 문제에서 제공할 때만 가능하다고 쓴다.
  문서에 없는 문법은 찾을 수 있다고 쓰지 않고 기억할 최소 표기나 실제 도구 도움말을 안내한다.
- Kustomize의 내장 기능과 별도 CLI, 로컬 렌더·실제 적용·앱 기능 성공을 구분한다.
  랩의 kind 채점 관찰을 일반 CKA 채점 규칙으로 확대하지 않는다.

## 분할·축약·정보 보존 판단

1. **분할**: 수정 대상·입력 형식·완료 판정이 달라지면 별도 작업으로 나눈다. Kustomize의
   묶기·범위 변환·특정 대상 patch·선택 기능이 기준 예다. 분량은 대략 150~300줄을 목표로 하되
   350줄 초과 시 두 번째 목표가 섞였는지 검토한다. 줄 수를 맞추기 위해 조건을 삭제하지 않는다.
2. **축약**: 같은 원리·명령·성공 조건을 반복하는 랩은 대표 사례와 차이 표로 합친다.
   질문 번호·반복 서론·말미의 재요약을 줄인다. 공통 절차는 한 번 설명하고 다른 페이지에서 링크한다.
3. **보존**: 다른 실패 원인, 요구된 패치 방식, selector 불변성, 경로 기준, 적용 범위 밖의 비변경 확인,
   삭제 후 잔존 리소스, 복구 조건은 짧아져도 남긴다. 출처와 유효한 사실을 함께 이동한다.
4. **보충**: 특정 랩 환경·선택 기능·설치된 CRD의 사례는 학습 보충으로 표시한다.
   커리큘럼에 상위 개념이 있다고 세부 문법의 필수 출제나 제공 도구를 단정하지 않는다.
5. **예제 공유**: 가능하면 같은 base·overlay·리소스명을 사용한다. 범위 판단이 달라 별도 구조가
   필요하면 차이를 먼저 설명한다. 원본 랩의 정답 값은 해당 사례에만 두고 일반 규칙으로 만들지 않는다.
6. **검증 기록**: 저장소 검사·브라우저·공식 문서 대조·로컬 렌더·클러스터 실행을 별도로 기록한다.
   지정 랩이 없으면 클러스터 실행 미검증으로 남긴다. 빌드 성공을 실습 성공으로 쓰지 않는다.

## 완료 판정의 공통 경계

- API 작업은 TLS·인증·인가·admission·저장을 구분한다. `auth can-i --as`는 인가 결정을
  검사할 뿐 실제 인증서 로그인을 증명하지 않으므로, 필요하면 지정 kubeconfig의 `auth whoami`로 확인한다.
- 리소스가 존재하는 것과 기능 성공을 분리한다. Service는 EndpointSlice와 실제 요청,
  storage는 Bound와 mount 읽기/쓰기, Helm은 release와 workload, 설치는 Node Ready와 통신을 함께 본다.
- 장애는 증상 → 첫 관찰 → 원본 설정 → 최소 수정 → 처음 실패한 요청의 재검증 순서로 쓴다.
  컴포넌트가 Running인 것만으로 앱 복구를 대신하지 않는다.
- 버전·노드·namespace·context가 결과를 바꾸는 절차는 명령 가까이에 전제를 쓴다.
  설치·업그레이드 문서는 시험 버전을 선택하고 패키지 목록의 실제 문자열을 확인한다.

## 최종 구조를 유지하는 법

- 제목·파일명·URL에 새 페이지 번호를 붙이지 않는다. 학습 순서는 `deckGroup`·`sidebar.order`로
  관리하며, 중간 삽입 때 주변 페이지를 다시 번호 매기지 않는다. 기존 표시 번호 1~39와
  `sidebar.order` 1010~1390은 이전 개편 결과이며 새 페이지의 번호 규칙이 아니다.
  기존 번호 제거는 별도 개편에서 처리하고, 페이지 추가·삭제 시 관련 `_deck.mjs`·LinkCard·작업 색인을 갱신한다.
- `exam-search.mdx`는 상세 풀이를 복제하지 않는다. 작업·첫 관찰 명령·공식 검색어·목적
  페이지만 연결하고, 성공 조건과 실패 분기는 각 실습 페이지를 정본으로 둔다.
- 커리큘럼 상위 개념만 있고 독립 실습이 없는 HA·CSI 설치·operator 종합 설치 등의 공백은
  index와 이관 계약에 계속 표시한다. 부분 사례를 전체 커버리지로 확대하지 않는다.

이전 이관의 파일·번호 예약과 원본 절 처리 기록은 `docs/plans/01-cka-udemy-migration.md`에 있다.
새 작업의 명명·검증 기준은 공통 작성·검증 지침을 따른다. 과거의 번호 예약이나 브라우저 실행 기록을
현재 작업의 필수 절차로 적용하지 않는다.


## 완성된 기준 예제

Kustomize의 `12-kustomize.mdx` → `kustomize-transformers.mdx` → `kustomize-patches.mdx`를
필수 흐름의 기준으로, `kustomize-components.mdx`를 선택 기능 보충의 기준으로 삼는다.
기본 적용은 실행 위치·완전한 공통 입력·완료 판정의 예이고, patch는 방식 차이·삭제 조건을
축약하면서 보존한 예다. Components는 선택하지 않은 환경과 기능 해제까지 확인하는 예다.

본문의 공통 예제와 원본 랩 변형은 섞어 연속 실행하지 않는다. 기존 파일이 필요하면 그 전제를 먼저
쓰고, 예제 값을 일반 규칙으로 확대하지 않는다. 축약량은 새로 추가한 재현용 입력까지 포함해 비교한다.
