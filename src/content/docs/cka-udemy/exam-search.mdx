<Thesis>
문제의 명사를 리소스로, 동사를 첫 명령으로 바꾼 뒤 이 표의 영문 검색어로 공식 문서 예제를 찾고,
연결된 실습 페이지의 완료 기준으로 결과를 판정한다.
</Thesis>

이 페이지는 정답 모음이 아니라 **출발점 색인**이다. 먼저 context·namespace·대상 노드를 확인하고,
표의 첫 명령으로 현재 상태를 관찰한다. 작성법이 필요하면 공식 문서에서 표시된 검색어를 찾고,
링크된 실습에서 바꿀 필드와 실제 성공 조건을 확인한다.

시험 브라우저에서는 허용된 공식 사이트 내부 검색을 사용한다. 설치·업그레이드 문서는 문제의
Kubernetes 버전으로 바꾸고, KodeKloud·GitHub 예제와 학습 보충은 Quick Reference가 제공한 경우에만 연다.

## Mock Exam 복습 경로

사용자가 제공한 KodeKloud Mock Exam 14개 문제를 작업별 정본으로 연결한다.
각 절의 이름·namespace·요구값은 해당 사례에만 적용한다. 공식 자료는 풀이 옆에 연결했으며,
아래 검색어로 예제 블록을 다시 찾을 수 있다. 명령은 랩에서 실행할 절차이고 이 문서 업데이트에서
클러스터 실행을 검증한 기록은 아니다.

| 제공 문제 | 풀이 위치 | 첫 관찰·도움말 | 공식 검색어 |
|---|---|---|---|
| 1 · 네트워크 파라미터 영구 설정 | [sysctl 저장과 적용](/cka-udemy/cluster-lifecycle/#네트워크-파라미터-영구-적용) | `sysctl net.ipv4.ip_forward net.bridge.bridge-nf-call-iptables` | `Container Runtimes ip_forward` |
| 2 · PV 목록을 읽는 계정과 Pod | [pvviewer](/cka-udemy/service-account/#pvviewer--클러스터-pv-목록-권한과-pod-연결) | `kubectl create clusterrole --help` | `RBAC ClusterRole ServiceAccount` |
| 3 · StorageClass 생성 | [rancher-sc](/cka-udemy/storage-class/#rancher-sc--provisioner와-지연-바인딩-지정) | `kubectl get sc` | `Storage Classes volumeBindingMode` |
| 4 · ConfigMap 환경 변수 | [app-config와 cm-webapp](/cka-udemy/configmap-secret/#app-config--기존-deployment에-두-환경-변수-연결) | `kubectl get deploy cm-webapp -n cm-namespace -o yaml` | `kubectl set env --from` |

| 9 · kubeconfig 포트 | [super.kubeconfig](/cka-udemy/security/#superkubeconfig--mock-exam의-잘못된-포트) | `kubectl --kubeconfig=/root/CKA/super.kubeconfig cluster-info` | `Troubleshooting kubectl` |
| 10 · scale 미반영 복구 | [nginx-deploy](/cka-udemy/control-plane-failure/#nginx-deploy--scale-후-실행-파일-오타-복구) | `kubectl get deploy,rs,pods -n default` | `Create static Pods` |
| 11 · 사용자 정의 메트릭 HPA | [api-hpa](/cka-udemy/autoscaling/#api-hpa--pod별-requests_per_second-평균-목표) | `kubectl get deploy api-deployment -n api` | `HPA walkthrough custom metrics` |

## 색인을 쓰고 끝내는 조건

1. 첫 명령으로 현재 상태를 저장하고, 증상만으로 원인을 단정하지 않는다.
2. 공식 예제의 API 버전·kind·필드 위치를 확인해 문제의 이름·namespace·값만 바꾼다.
3. 생성·수정된 오브젝트와 실제 동작을 나눠 확인한다. 장애 복구는 처음 실패한 요청까지 반복한다.
4. 기대한 허용뿐 아니라 거부·비변경·다른 namespace처럼 범위 밖 조건도 필요한 만큼 확인한다.
