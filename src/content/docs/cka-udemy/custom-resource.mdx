<Thesis>이미 설치된 CRD를 쓰는 문제는 API discovery로 리소스의 이름과 범위를 찾고, `kubectl explain`으로 스키마를 읽은 뒤 요구값만 넣은 CR을 만든다.</Thesis>

> 개념 연결: [CKA CRD — 새로운 API 리소스 정의](/cka/crd/)

:::note[학습 보충]
이 페이지는 랩에 미리 설치된 CRD를 사용하는 사례다. CRD 자체를 새로 정의하거나 컨트롤러를
구현하는 과제가 아니며, `traffic.controller` API가 모든 Kubernetes 클러스터에 있다고 가정하지 않는다.
:::

문제에서 `apiVersion: traffic.controller/v1`, `kind: Global`, 인스턴스 이름 `datacenter`와
`spec` 값을 주었다면 새 API의 **정의**가 아니라 그 API에 저장할 **Custom Resource(CR) 인스턴스**를
만들라는 뜻이다. CRD가 종류와 스키마를 등록하고, CR은 그 종류로 만든 실제 오브젝트다.

## 문제의 값을 YAML 자리로 옮긴다

| 문제·조회 결과 | CR YAML의 자리 |
|---|---|
| `APIVERSION traffic.controller/v1` | `apiVersion: traffic.controller/v1` |
| `KIND Global` | `kind: Global` |
| 인스턴스 이름 `datacenter` | `metadata.name: datacenter` |
| `access <boolean>` | `spec.access: true` |
| `dataField <integer>` | `spec.dataField: 2` |
| `NAMESPACED true` | 문제의 namespace 또는 현재 namespace |

`globals`는 kubectl에서 조회할 resource name, `gb`는 short name, `Global`은 YAML에 쓰는 kind다.
필드명은 대소문자까지 스키마와 같아야 한다. `2`와 `true`에 따옴표를 붙이면 각각 string이 되어
CRD가 요구하는 integer·boolean 타입과 달라진다.

## discovery → schema → CR 생성

<Steps>

1. API group의 리소스와 범위를 확인한다

   ```bash
   kubectl api-resources --api-group=traffic.controller
   ```

   ```text
   NAME      SHORTNAMES   APIVERSION              NAMESPACED   KIND
   globals   gb           traffic.controller/v1   true         Global
   ```

   이 결과가 비어 있으면 현재 context의 API 서버가 해당 group을 제공하지 않는 것이다. manifest부터
   쓰지 말고 context와 CRD 설치 여부를 확인한다. `NAMESPACED=true`인데 문제에 namespace가 있다면
   이후 모든 명령에 `-n <namespace>`를 붙이거나 `metadata.namespace`에 넣는다.

2. 현재 클러스터가 공개한 스키마를 읽는다

   ```bash
   kubectl explain global \
     --api-version=traffic.controller/v1
   kubectl explain global.spec \
     --api-version=traffic.controller/v1 \
     --recursive
   ```

   ```text
   GROUP:      traffic.controller
   KIND:       Global
   VERSION:    v1

   FIELD: spec <Object>

   FIELDS:
     access        <boolean>
     dataField     <integer>
   ```

   `--api-version`을 함께 쓰면 다른 group에 같은 resource 이름이 있어도 문제에 지정된 스키마를
   읽는다. 공식 문서는 CR의 전체 모양을 찾는 곳이고, `explain`은 설치된 CRD 버전의 정확한 필드명·깊이·타입을
   확인하는 곳이다.

3. 최소 manifest를 만들어 서버 검증 후 생성한다

   ```yaml title="datacenter.yaml"
   apiVersion: traffic.controller/v1
   kind: Global
   metadata:
     name: datacenter
   spec:
     dataField: 2
     access: true
   ```

   ```bash
   kubectl create --dry-run=server -f datacenter.yaml
   kubectl create -f datacenter.yaml
   ```

   arbitrary CR에는 `kubectl create global ...` 같은 전용 생성기가 없으므로 YAML과
   `kubectl create -f`를 쓴다. server dry-run은 실제 저장 없이 현재 API 서버의 CRD 스키마와
   admission을 통과하는지 확인한다. 이미 같은 객체가 있고 수정이 허용된 문제라면 기존 값을 먼저
   확인한 뒤 `kubectl apply -f`를 사용한다. 생성 문제를 풀기 위해 기존 객체를 무조건 삭제하지 않는다.

</Steps>

## 저장된 객체로 완료를 판정한다

생성 명령의 성공 메시지만 보지 말고 같은 namespace에서 kind·이름·값을 다시 읽는다.

```bash
kubectl get globals datacenter -o yaml
kubectl get globals datacenter \
  -o jsonpath='{.apiVersion}{"\t"}{.kind}{"\t"}{.metadata.name}{"\n"}'
kubectl get globals datacenter \
  -o jsonpath='{.spec.dataField}{"\t"}{.spec.access}{"\n"}'
```

```text
traffic.controller/v1	Global	datacenter
2	true
```

namespace가 지정된 문제라면 위 세 명령에도 같은 `-n <namespace>`를 붙인다. CR이 저장됐다는 것은
API 서버가 객체를 받아들였다는 뜻이다. 컨트롤러가 수행할 실제 동작까지 요구하는 문제라면
`status`, 컨트롤러가 만든 하위 리소스, 실제 기능을 별도로 확인해야 한다.

## 실패를 읽는 기준

| 증상 | 먼저 확인할 것 |
|---|---|
| `no matches for kind` | `apiVersion`·`kind`, 현재 context, CRD의 served version |
| `the server doesn't have a resource type` | `api-resources --api-group=...`의 실제 `NAME` |
| 타입·필수 필드 validation 오류 | `explain <resource>.spec --recursive`의 타입·필드 깊이 |
| 생성됐지만 조회되지 않음 | `NAMESPACED`와 생성·조회 양쪽의 namespace |
| 필드가 저장 결과에서 사라짐 | 필드명 대소문자·경로와 CRD의 pruning 규칙 |
| `AlreadyExists` | 기존 객체를 조회하고, 수정이 과제일 때만 `apply` 또는 `edit` |

:::caution[CRD를 삭제하지 않는다]
CR 생성 문제에서 CRD를 다시 만들거나 삭제할 이유가 없다. CRD를 삭제하면 그 CRD로 저장된 CR도
함께 삭제된다. discovery가 기대와 다르면 먼저 context·group·served version을 확인한다.
:::

## 공식 문서에서 찾기

| 검색어 | 공식 문서에서 확인할 것 |
|---|---|
| `CustomResourceDefinition create custom objects` | [Extend the Kubernetes API with CustomResourceDefinitions](https://v1-35.docs.kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#create-custom-objects)의 CR manifest 구조 |
| `kubectl api-resources` | [`kubectl api-resources`](https://v1-35.docs.kubernetes.io/docs/reference/kubectl/generated/kubectl_api-resources/)의 API group 필터와 서버 지원 리소스 조회 |
| `kubectl explain` | [`kubectl explain`](https://v1-35.docs.kubernetes.io/docs/reference/kubectl/generated/kubectl_explain/)의 필드 경로·`--api-version`·`--recursive` 사용법 |

시험에서는 공식 예제에서 `apiVersion`과 `kind`를 추측하기보다 문제의 값과 현재 클러스터의
discovery·OpenAPI 스키마를 우선한다. 문서 예제는 구조를 찾는 출발점이고 설치된 CRD가 실제 계약이다.

## 완료 기준

- API group에서 `Global`의 resource name·served version·namespace 범위를 확인했다.
- `explain`에서 `dataField`가 integer, `access`가 boolean임을 확인했다.
- 같은 namespace의 `datacenter`에 요구한 group/version/kind와 `spec` 값이 저장됐다.
- 실제 동작이 요구됐다면 객체 존재와 컨트롤러의 조정 결과를 구분해 추가 검증했다.
