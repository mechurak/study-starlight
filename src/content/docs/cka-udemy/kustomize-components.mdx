<Thesis>Component는 선택 기능을 묶고, 필요한 overlay만 불러와 기능의 포함 범위를 결정한다</Thesis>

환경마다 디버그 설정을 복사하면 ConfigMap과 패치를 함께 고쳐야 한다. Component는 이 둘을
한 묶음으로 두어 필요한 환경만 선택하게 한다. 이 페이지에서는 **dev·staging에만 debug 설정을
추가하고 prod에는 들어가지 않았는지 확인한다**.

공통 구조는 [기본 페이지의 base·overlay](/cka-udemy/12-kustomize/#공통-base와-환경별-진입점),
패치 원리는 [특정 대상 수정](/cka-udemy/kustomize-patches/),
base·overlay 개념은 [cka 16장](/cka/16-helm-kustomize/#kustomize)을 참조한다.
이 내용은 **학습 보충**이며 components 문법의 필수 시험 출제를 뜻하지 않는다.

## 기능 묶음 만들기

공유 예제의 `base`가 `api-deployment`를 등록하고 컨테이너 이름이 `api`인지 먼저 확인한다.
아래 재구성 예제는 환경변수 연결을 검증한다. **앱이 LOG_LEVEL을 지원해야 실제 로그가 바뀐다**.
공유 base의 nginx는 이 설정만으로 로그 레벨이 바뀌는 앱이 아니다.
[KodeKloud Components 노트 — 학습용](https://notes.kodekloud.com/docs/Kustomize/Kustomize-Basics/Components/page)의
DB·캐시 선택 패턴을 작은 debug 기능으로 바꿨으며 랩의 정답·채점 조건을 옮긴 것이 아니다.

```text
k8s/
  base/
    kustomization.yaml
    api-depl.yaml
  components/
    debug/
      kustomization.yaml
      debug-config.yaml
      api-patch.yaml
  overlays/
    dev/kustomization.yaml
    staging/kustomization.yaml
    prod/kustomization.yaml
```

Component도 파일명은 `kustomization.yaml`이다. 일반 base·overlay의
`v1beta1` / `Kustomization`과 달리 아래 두 줄로 선언한다.
([Kustomize 공식 Components 예제 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/examples/components.md#components-example))

```yaml
# components/debug/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
resources:
  - debug-config.yaml
patches:
  - path: api-patch.yaml
```

새로 추가할 ConfigMap은 `resources`에, 기존 Deployment의 수정 내용은 `patches`에 둔다.
Component 안에서 `../../base`를 다시 불러오지 않는다. base는 아래에서 overlay가 가져온다.

```yaml
# components/debug/debug-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: debug-config
data:
  LOG_LEVEL: debug
```

```yaml
# components/debug/api-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  template:
    spec:
      containers:
        - name: api
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: debug-config
                  key: LOG_LEVEL
```

이 strategic merge patch는 `api` 컨테이너에 환경변수를 연결한다. 예제의 base에는
`LOG_LEVEL`이 없다고 가정한다. 기존에 같은 이름의 환경변수가 있다면 `value`인지
`valueFrom`인지 먼저 확인하고, 병합 결과에 두 필드가 함께 남지 않도록 패치를 조정한다.

## 필요한 환경에서만 선택하기

dev와 staging의 `kustomization.yaml`에 각각 다음 구성을 둔다.
기존 설정이 있다면 `resources`와 다른 변경을 유지하며 `components` 항목을 추가한다.

```yaml
# overlays/dev/kustomization.yaml
# overlays/staging/kustomization.yaml도 같은 구성
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
components:
  - ../../components/debug
```

prod는 base만 참조한다.

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
```

`components:`에는 **Component 디렉터리 경로**를 적는다. 기준은 이 overlay의 설정 파일 위치다.
여러 기능을 쓰려면 이 목록에 Component 경로를 추가한다. 같은 리소스·필드를 여러 Component가
수정한다면 조합한 최종 결과도 확인해야 한다.

## 선택·미선택 결과 비교하기

```bash
# k8s/에서 실행 — 클러스터에 적용하지 않는 미리보기
kubectl kustomize overlays/dev
kubectl kustomize overlays/staging
kubectl kustomize overlays/prod
```

dev·staging에는 `debug-config`와 `api` 컨테이너의 `LOG_LEVEL` 참조가 모두 있어야 한다.
prod에는 둘 다 없어야 하며, 모든 환경에서 기존 Deployment가 한 번씩만 나와야 한다.
`Component` 자체는 결과 YAML의 Kubernetes 리소스로 출력되지 않는다.

실제 적용 요구가 dev라면 [공통 적용·완료 검증](/cka-udemy/12-kustomize/#미리보기와-완료-검증-구분하기)의
경로를 `overlays/dev`로 바꾼다. 최종 YAML의 namespace와 이름을 사용해 ConfigMap의 값,
Deployment의 `configMapKeyRef`, rollout 완료를 함께 확인한다. 기본 예제에서는
`kubectl rollout status deployment/api-deployment -n <namespace>`다.

## 실패와 기능 해제

- **Component 종류를 기대한다는 오류**: 참조 대상의 `kind: Component`와 `v1alpha1`을 확인한다.
  일반 Kustomization의 두 줄을 그대로 복사하지 않는다.
- **resources로 불러오다 종류 오류**: overlay의 `resources`에는 base를, `components`에는
  Component를 둔다. `components/debug`를 `resources` 목록으로 옮겨 해결하지 않는다.
- **패치 대상을 찾지 못함**: overlay가 base를 불러오는지, Deployment 이름·kind·namespace가
  맞는지 확인한다. 이 예제의 Component는 부모가 제공할 Deployment에 의존하므로,
  `kubectl kustomize components/debug`만 실행하면 대상이 없다. overlay를 빌드한다.
- **리소스 중복 오류**: Component가 base를 다시 불러오거나 같은 리소스를 여러 경로에서
  추가했는지 확인한다.
- **prod에도 기능이 들어감**: 공통 base에 참조나 패치를 넣었는지 확인하고, 필요한 overlay로 옮긴다.

잘못 연결했다면 해당 overlay의 참조를 고친 뒤 세 환경을 다시 렌더한다. `components`에서
항목을 빼면 이후 생성 YAML에서 기능이 빠지지만, 이미 적용한 ConfigMap이 자동 삭제되지는 않는다.
복구 시 Deployment 설정을 먼저 확인·적용하고, 남은 리소스는 사용 여부와 문제의 삭제 요구를
확인해 처리한다. `delete -k overlays/dev`는 앱 전체도 삭제할 수 있어 기능 해제용으로 쓰지 않는다.


## 시험 문서와 학습 자료 구분

[공식 Components 예제 — 학습용](https://github.com/kubernetes-sigs/kustomize/blob/master/examples/components.md#components-example)의
`Components example`에서 `kind: Component`·`components:`를 찾는다. 예제의 DB 설정 대신
이 페이지의 debug ConfigMap·패치를 넣고, overlay의 상대 경로를 맞춘다.
Kubernetes의 [Kustomize 본문](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/)에는
이 Component 선언·선택 예제가 없다. `v1alpha1`·`kind: Component`·overlay의 `components`를 함께 익힌다.
GitHub를 일반 시험 열람 자료로 간주하지 않으며 문제의 Quick Reference가 제공되면 그 경로를 확인한다.
