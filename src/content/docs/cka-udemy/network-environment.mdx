> 개념 연결: [CKA kubeadm — 클러스터 설치와 노드 조인](/cka/cluster-setup/#cni-설치--이걸-안-하면-노드가-notready), [CKA 확장 인터페이스 — CRI·CNI·CSI](/cka/extensions/#cni--pod-네트워크)

이 장의 과제는 노드의 인터페이스와 포트, 컨테이너 런타임 소켓, CNI 설정·바이너리 위치를 찾는
것이다. 보이는 IP 몇 개만 보고 전체 CIDR을 추측하지 않고 kubeadm과 컴포넌트 설정 원본을 확인한다.

Calico 설치 사례는 문제에서 제공한 Quick Reference를 따라가는 기존 부분 랩이다. 버전과 Pod CIDR을
문제 지정값으로 바꾸고, operator 상태·노드 Ready까지 확인한다. 독립적인 CNI 설계 실습으로 확대하지 않는다.

## 환경 탐색 — Practice Test: Explore Environment

원본 풀이: [09-Practice-Test-Explore-Env.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/09-Practice-Test-Explore-Env.md)

노드의 네트워크 인터페이스를 읽는 연습 — 시험보다 [18장 트러블슈팅](/cka/troubleshooting/)의 재료다.
이 랩은 원문대로 `netstat`을 쓰지만, 현재 Ubuntu에서는 같은 확인을 `ss`로 한다.
두 도구의 일반적인 읽기법은 [server 7장](/server/07-network/)에 있다.

```bash
# "What is the Internal IP address of the controlplane node in this cluster?"
kubectl get nodes -o wide                 # INTERNAL-IP
# "What is the network interface configured for cluster connectivity on the controlplane node?"
# "What is the MAC address of the interface on the controlplane node?"
ip a | grep -B2 <그 IP>                   # -B2 = 매칭 앞 2줄까지 출력 — 인터페이스명과 MAC(link/ether)이 그 줄에 있다
# "If you were to ping google from the controlplane node, which route does it take?"
ip route show default                     # 기본 게이트웨이
# "What is the port the kube-scheduler is listening on in the controlplane node?"
netstat -nplt | grep kube-scheduler       # n(숫자 주소) p(프로세스명) l(리스닝만) t(TCP) — 듣는 포트 (스케줄러: 10259)
# "Notice that ETCD is listening on two ports. Which of these have more client connections established?"
netstat -anp | grep etcd                  # a = 리스닝뿐 아니라 맺힌 연결까지 전부 — 클라이언트 2379, 피어 2380
```

이 실습에서 필요한 현대 명령 대응은 두 개다. `p`로 다른 프로세스 정보를 보려면 보통 root 권한이
필요하므로 `sudo`를 붙였다.

| 확인 목적 | 랩의 `netstat` | 현재의 `ss` |
|---|---|---|
| 리스닝 TCP 포트와 프로세스 | `netstat -nplt` | `sudo ss -lntp` |
| 리스닝·연결된 TCP 소켓과 프로세스 | `netstat -anp` | `sudo ss -antp` |

- 인터페이스 이름만으로 물리·가상 여부나 만든 주체를 단정하지 않는다. `lo`는 루프백이고,
  `veth*`는 가상 Ethernet pair의 한쪽이다. Kubernetes에서는 호스트 쪽이 `veth*`, Pod 안쪽이
  `eth0`로 보이는 경우가 흔하다. `cni0` 같은 브리지는 보통
  **CNI(Container Network Interface) 플러그인**이 만든다.
  원본 문제는 containerd가 만든 브리지라고 표현하지만, 런타임 이름만 보고 답하지 말고
  `ip -d link`에서 인터페이스 종류를 확인한다
  — *We use Containerd as our container runtime. What is the interface/bridge created by
  Containerd on this host?*
- etcd의 두 포트 중 연결이 많은 쪽은 **2379**(API 서버가 붙는 클라이언트 포트),
  2380은 컨트롤 플레인이 여럿일 때의 피어 통신용이다

## 런타임과 CNI 확인 — Practice Test: Explore CNI

원본 풀이: [13-Practice-Test-CNI-weave.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/13-Practice-Test-CNI-weave.md)

원본 랩은 Weave 기준이라 [index의 제외 목록](/cka-udemy/)에 있지만, **런타임 엔드포인트와 CNI
디렉터리를 확인하는 문항들은 지금도 그대로 쓸 수 있다.** Weave 설치에 의존하는 문항만 뺐다.

```bash
# "Inspect the kubelet service and identify the container runtime endpoint value is set for Kubernetes."
grep containerRuntimeEndpoint /var/lib/kubelet/config.yaml   # unix:///var/run/containerd/containerd.sock
# "What is the path configured with all binaries of CNI supported plugins?"
ls /opt/cni/bin                                              # 이 호스트에 깔린 플러그인 바이너리
# "What is the CNI plugin configured to be used on this kubernetes cluster?"
ls /etc/cni/net.d/                                           # 실제로 선택된 플러그인의 설정
# "What binary executable file will be invoked by the container runtime …?"
cat /etc/cni/net.d/10-flannel.conflist                       # plugins[].type
```

:::caution[함정 — 원본 풀이의 경로와 플래그가 낡았다]
원본은 `systemctl cat kubelet` → `/var/lib/kubelet/kubeadm-flags.env`에서 `--container-runtime`을
보라고 한다. 그 플래그는 **v1.27에서 제거돼 지금은 값 자체가 없다.**

지금 값이 들어 있는 곳은 kubelet 설정 파일 `/var/lib/kubelet/config.yaml`의
[`containerRuntimeEndpoint`](https://kubernetes.io/docs/reference/node/kubelet-files/) 필드다.
kubeadm은 노드에서 감지한 CRI 소켓을
[`/var/lib/kubelet/instance-config.yaml`](https://kubernetes.io/docs/tasks/administer-cluster/migrating-from-dockershim/change-runtime-containerd/)에
기록하고, 그 값이 `config.yaml`에 반영된다.

같은 이름의 [`--container-runtime-endpoint` 플래그](https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/)도
아직 있고 **설정 파일보다 우선**하지만, 공식 문서는 deprecated로 표시하고 설정 파일 쪽을 권한다.
그래서 확인은 `config.yaml`부터 하고, 값이 예상과 다르면 그때 `kubeadm-flags.env`와
`systemctl cat kubelet`으로 플래그 재정의를 찾는다.
:::

`/var/run`은 `/run`의 심링크라 `unix:///var/run/containerd/containerd.sock`과
`unix:///run/containerd/containerd.sock`은 **같은 소켓이다.** 랩 답과 표기가 달라도 틀린 게 아니다.
kubelet 플래그의 기본값은 `unix:///run/containerd/containerd.sock` 쪽이다.

노드가 실제로 무슨 런타임을 쓰는지는 API로도 보이므로, 노드에 들어가기 전에 이쪽을 먼저 본다.

```bash
kubectl get nodes -o wide     # CONTAINER-RUNTIME 열 — containerd://<버전>
```

### 경로 두 개로 환원한다

CNI 조회 문제는 외울 커맨드가 없다. 런타임이 Pod 네트워크를 만들려면 **무엇을 실행할지(설정)** 와
**실행할 것 자체(바이너리)** 가 있어야 하고, 각각의 자리가 하나씩 정해져 있을 뿐이다.
[Network Plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/)가
두 기본 경로를 모두 명시한다.

| 필요한 것 | 경로 | 답하는 질문 |
|---|---|---|
| 설정 — 무엇을 어떤 값으로 실행할지 | `/etc/cni/net.d/` | 이 클러스터가 **선택한** CNI는 무엇인가 |
| 바이너리 — 실행될 실체 | `/opt/cni/bin/` | 이 호스트에 **깔려 있는** 플러그인은 무엇인가 |

둘을 잇는 것이 설정 파일의 `type` 필드다. 런타임은 설정에서 `"type": "flannel"`을 읽고
`/opt/cni/bin/flannel`을 실행한다 — **`type` 값이 곧 바이너리 파일명이다.** 그래서 "무엇이
실행되는가"를 묻는 문제의 답은 설정 파일 안에 있다.

경로를 알면 남는 건 `ls`와 `cat`뿐이다. 문제를 읽고 **어느 디렉터리 이야기인지**만 판정하면 된다.

:::caution[함정 — "있다"와 "쓴다"는 다르다]
`/opt/cni/bin`에 있으면 **쓸 수 있다**는 뜻이고, `/etc/cni/net.d`에 있어야 **실제로 쓰고 있다**는
뜻이다. bin 디렉터리에는 `bridge`·`host-local`·`portmap`처럼 표준 플러그인이 여럿 깔려 있는데
전부 설치돼 있을 뿐 선택된 게 아니다.

*Identify which of the below plugins is not available…* 은 bin 디렉터리를,
*What is the CNI plugin configured to be used…* 는 설정 디렉터리를 묻는다. 문장이 비슷해도
읽는 곳이 다르다. 전자의 오답 보기는 보통 CNI 플러그인이 아예 아닌 이름이다.
:::

conflist의 `plugins`는 **배열이라 여러 개**가 들어 있다. flannel 설정을 열면 `flannel` 뒤에
`portmap` 같은 항목이 더 붙는다. 네트워크를 실제로 구성하는 체인의 첫 번째가 답이다.
파일 구조는 [Troubleshooting CNI plugin-related errors](https://kubernetes.io/docs/tasks/administer-cluster/migrating-from-dockershim/troubleshooting-cni-plugin-related-errors/)의
`10-containerd-net.conflist` 예제에서 `cniVersion`·`plugins[].type`을 그대로 볼 수 있다.

파일명 앞 숫자(`10-`)는 설정이 여러 개일 때 런타임이 **사전순 첫 번째**를 고르기 때문이다.
CNI를 갈아끼우고 옛 설정을 지우지 않아 엉뚱한 쪽이 이기는 사고가 여기서 난다. 이건 런타임의 동작이라
kubernetes.io에는 적혀 있지 않다.

## Calico 설치 — Lab: Install Calico CNI (2025 신규)

원본 레포에는 이 랩의 풀이 문서가 없다 — 2025년 시험 개편 뒤 추가된 랩이다. 절차의 정본은
[Calico 공식 문서의 operator 설치 가이드](https://docs.tigera.io/calico/3.31/getting-started/kubernetes/self-managed-onprem/onpremises)다.
CNI가 없으면 노드가 왜 NotReady로 남는지는
[CKA kubeadm — 클러스터 설치와 노드 조인](/cka/cluster-setup/#cni-설치--이걸-안-하면-노드가-notready),
NetworkPolicy가 CNI 구현에 달려 있다는 배경은 [CKA NetworkPolicy와 CNI](/cka/networkpolicy/)이 맡는다.

이 유형은 암기 문제가 아니라 **오픈북 문제**다. Calico 문서는
[열람 허용 목록](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)에
없지만, 같은 문서가 허용 목록 밖 도구가 필요한 태스크에는 **문제 화면의 Quick Reference 상자로
전용 문서 링크를 제공한다**고 명시한다. 랩이 "터미널 우상단의 링크"를 주는 게 이 형식의 재현이다.
그래서 채점 포인트는 절차 암기가 아니라, **주어진 문서를 따라가며 문제 지정값(버전·CIDR)으로
바꿔 넣는 것**이다.

절차는 문서 그대로 세 단계다. 랩은 v3.31.6을 지정한다 — 문서 커맨드에 박힌 버전이 문제 지정
버전과 다르면 전부 치환한다.

```bash
# 1. CRD 먼저 — 최신 Calico는 CRD가 별도 manifest로 분리돼 있어 이걸 건너뛰면 operator가 못 뜬다
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.31.6/manifests/operator-crds.yaml
# 2. Tigera Operator — Calico 컴포넌트들을 대신 설치·관리하는 오퍼레이터
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.31.6/manifests/tigera-operator.yaml
# 3. Installation 커스텀 리소스 — 받아서 cidr를 고친 뒤 적용
curl -O https://raw.githubusercontent.com/projectcalico/calico/v3.31.6/manifests/custom-resources.yaml
vi custom-resources.yaml     # ipPools[0].cidr: 192.168.0.0/16 → 문제 지정값(랩은 172.17.0.0/16)
kubectl create -f custom-resources.yaml
```

:::caution[함정 — `apply`가 아니라 `create`인 이유]
1·2단계는 공식 문서도 `kubectl create`를 쓴다. manifest가 워낙 커서 `apply`가 남기는
last-applied-configuration 어노테이션이 크기 제한(262144바이트)을 넘겨 실패하기 때문이다.
`apply`로 시도했다가 `metadata.annotations: Too long` 에러를 만나면 이 얘기다.
:::

:::caution[함정 — 문서 기본 CIDR를 그대로 붙여넣지 않는다]
`Installation`의 `ipPools[].cidr`는 클러스터 생성 때의 `--pod-network-cidr`와 일치해야 한다.
문서 기본값(`192.168.0.0/16`)을 그대로 두면 **Pod은 뜨는데 통신이 깨진다.** 랩도 시험도 CIDR를
문제에서 지정한다. eBPF dataplane 절로 빠지지 않는 것도 같은 결이다 — 기본
`custom-resources.yaml`이 이미 표준(iptables) dataplane이고, 랩 환경은 eBPF와 호환되지 않는다.
:::

맞춰야 할 `--pod-network-cidr` 값 자체는 클러스터 안에 남아 있다. kubeadm은 `init` 때 받은
설정을 `kubeadm-config` ConfigMap에 기록한다 — `podSubnet`이 정본이고, 나머지 둘은 교차 확인이다.

```bash
kubectl get cm kubeadm-config -n kube-system -o yaml | grep -i podSubnet         # 정본 — init 때 받은 값
grep cluster-cidr /etc/kubernetes/manifests/kube-controller-manager.yaml         # 대역을 실제로 나눠주는 주체
kubectl describe node controlplane | grep -i podcidr                             # 노드별 할당 결과
```

노드의 `podCIDR`는 전체 대역이 아니라 **노드별로 잘라 받은 조각**(보통 `/24`)이다 —
`172.17.0.0/24`만 보고 전체 CIDR을 `/24`로 답하지 않는다. `init` 때 `--pod-network-cidr`를
안 준 클러스터라면 `podSubnet`도 `--cluster-cidr`도 없을 수 있다. 그때는 노드 CIDR 할당 없이
Calico가 자체 IPAM(IP 주소 할당 관리)으로 동작하므로, 문제 지정값을 그대로 쓰면 된다.

완료 판정은 세 겹으로 본다 —

```bash
watch kubectl get pods -n calico-system                 # calico-node DaemonSet 등 Running까지
kubectl get tigerastatus                                # 오퍼레이터가 보는 컴포넌트별 AVAILABLE
kubectl get installation default -o yaml | grep cidr    # 문제 지정 CIDR 반영 확인
kubectl get nodes                                       # NotReady였다면 Ready로 돌아온다
```

`calico-system`의 `csi-node-driver` Pod 에러는 랩 안내대로 무시한다 — NetworkPolicy 동작과
무관하다. 오퍼레이터 방식은 Pod이 `kube-system`이 아니라 `calico-system`에 뜬다는 것도
기억해 둔다 — 설치 후 `kube-system`만 보고 "안 깔렸다"고 판단하는 실수가 잦다.

## 서비스 네트워킹 — Practice Test: Service Networking

원본 풀이: [18-Practice-Test-Service-Networking.md](https://github.com/kodekloudhub/certified-kubernetes-administrator-course/blob/master/docs/09-Networking/18-Practice-Test-Service-Networking.md)

클러스터에는 서로 다른 세 IP 대역이 있다. **랩의 객관식 보기를 빠르게 푸는 법**과
**실제 설정값을 확인하는 법**은 구분한다. 현재 주소 몇 개만 보고 전체 CIDR을 단정할 수는 없다.

| 대역 | 랩 보기에서 빠르게 추론 | 설정 원본 확인 |
|---|---|---|
| 노드 — *What network range are the nodes in the cluster part of?* | `k get nodes -o wide` → INTERNAL-IP | 노드에서 `ip a`로 그 주소의 prefix 확인 |
| Pod — *What is the range of IP addresses configured for PODs on this cluster?* | `k get pods -A -o wide` — 호스트 네트워크 Pod 제외 | controller-manager 매니페스트의 `--cluster-cidr` |
| Service — *What is the IP Range configured for the services within the cluster?* | `k get svc -A` → CLUSTER-IP | apiserver 매니페스트의 `--service-cluster-ip-range` |

:::tip[시험 — grep 한 번으로 Pod·Service 대역을 같이 뽑는다]
kubeadm 클러스터에서는 controller-manager 매니페스트에 두 플래그가 다 있다.

```bash
grep -E 'cluster-cidr|cluster-ip-range' /etc/kubernetes/manifests/kube-controller-manager.yaml
```

단, Service 대역의 정본은 ClusterIP를 실제로 할당하는 **kube-apiserver** 쪽
`--service-cluster-ip-range`다. controller-manager의 같은 플래그는 노드 CIDR을 나눌 때
Service 대역과 겹치지 않게 하려는 참고값이라, 서술형으로 "어느 설정이냐"를 물으면
apiserver라고 답한다.
:::

controller-manager에 `--cluster-cidr`가 없는 클러스터(`init` 때 `--pod-network-cidr` 생략)면
CNI가 자체 IPAM으로 대역을 관리한다 — 위 [Calico 설치 절](/cka-udemy/network-environment/#calico-설치--lab-install-calico-cni-2025-신규)처럼
CNI 설정(`kubectl get installation default -o yaml | grep cidr`)이나 CNI Pod 로그의
default IPv4 pool에서 확인한다.

Service 대역은 SSH 없이 `k get servicecidr`로도 보인다(1.33부터 stable인 `ServiceCIDR` API).
자세한 건 [Extend Service IP Ranges](https://kubernetes.io/docs/tasks/network/extend-service-ip-ranges/)에 있다.

kube-proxy 관련 —

```bash
# "How many kube-proxy pods are deployed in this cluster?"
kubectl get pods -n kube-system | grep kube-proxy   # 노드 수만큼 있다
# "What type of proxy is the kube-proxy configured to use?"
kubectl logs -n kube-system <kube-proxy-pod>        # 기동 로그에 "Using iptables Proxier" 같은 줄
# "How does this Kubernetes cluster ensure that a kube-proxy pod runs on all nodes in the cluster?"
kubectl get ds -n kube-system                       # 모든 노드에 하나씩 = DaemonSet
```

:::tip[왜 프록시 모드만 설정이 아니라 로그를 보는가]
kube-proxy 설정은 `kube-system`의 `kube-proxy` ConfigMap에 있지만, `mode:` 필드는 보통
**빈 값**이다. 빈 값이면 kube-proxy가 기동할 때 스스로 기본값(iptables)을 고르므로, 실제로
무엇을 쓰는지의 정본은 그 결정이 찍힌 **기동 로그**다. 앞의 CIDR 문제들과 구분하는 기준 —

- 플래그로 **반드시 명시되는 값**(Pod·Service CIDR) → 매니페스트 grep
- 설정이 비어 있으면 **런타임에 결정되는 값**(프록시 모드) → 로그

실전 순서는 `k describe cm kube-proxy -n kube-system | grep mode`를 먼저 쳐보고,
빈 값이면 로그로 간다. mode에 값이 박혀 있는 클러스터라면 ConfigMap만으로 끝난다.
:::

## 완료 판정

- 노드·Pod·Service CIDR은 각각의 설정 원본에서 확인했고 현재 주소와 모순되지 않는다.
- 런타임 endpoint와 실제 사용 중인 CNI conflist, 그 `type`에 대응하는 바이너리를 확인했다.
- Calico 설치 문제라면 Installation CIDR이 요구값이고 tigerastatus가 Available이며 노드가 Ready다.
- 지정 랩이 없다면 설치 명령을 임의 실행하지 않고 현재 환경 조회까지만 수행한다.
