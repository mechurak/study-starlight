Compose나 kind 실습이 `https://<이름>.<실습>.test:<port>` 같은 주소를 쓰면 브라우저는 세 가지를 통과해야
한다. 이름을 loopback으로 해석하고, 그 요청을 회사 프록시로 보내지 않고, 실습이 만든 인증서를
받아들이는 것이다. 이 장은 세 준비를 운영체제별로 모은다. 실습별 hostname·port·CA 파일 경로는 각 실습
덱이 정한다.

## 큰 그림

| 준비 | 없으면 생기는 일 | 필수 여부 |
|---|---|---|
| hosts 항목 | 이름을 못 찾아 페이지가 열리지 않음 | 필수 |
| 브라우저 프록시 예외 | 요청이 회사 프록시로 나가 loopback에 닿지 못함 | 회사 프록시·PAC 환경에서 필수 |
| 로컬 CA 등록 | host별로 한 번씩 인증서 경고를 넘겨야 함 | 선택 |

## 이 장에서 답할 질문

- 실습 hostname을 브라우저가 로컬로 해석하게 하려면 무엇을 고치는가?
- 회사 프록시 환경에서 예외는 어디에 넣는가?
- 인증서 경고 없이 보려면 CA를 어디에 등록하고, 실습을 초기화하면 어떻게 지우는가?

## 이름을 loopback으로 연결하기

`/etc/hosts`에 실습이 쓰는 이름을 모두 `127.0.0.1`로 적는다. 한 줄에 여러 이름을 둘 수 있다.

```text
127.0.0.1 app.example.test api.example.test
```

macOS와 Ubuntu 모두 같은 파일이며 편집에는 `sudo`가 필요하다. 확인은 브라우저 대신 터미널에서 한다.

```bash
getent hosts app.example.test   # Ubuntu
dscacheutil -q host -a name app.example.test   # macOS
```

## 회사 프록시 예외 넣기

브라우저가 회사 프록시나 PAC를 쓰면 실습 이름도 프록시로 보낸다. 프록시는 loopback을 모르므로 연결이
실패하거나 회사 오류 페이지가 뜬다. 실습 도메인 접미사를 예외에 넣는다.

<Tabs syncKey="operating-system">
<TabItem label="macOS">

시스템 설정 → 네트워크 → 현재 연결 → 세부사항 → 프록시의 **프록시 설정을 무시할 호스트 및 도메인**에
`*.example.test`를 추가한다. Chrome·Safari는 이 설정을 따르고, Firefox는 자체 네트워크 설정에서 같은
값을 **프록시 없음**에 넣는다.

</TabItem>
<TabItem label="Ubuntu">

GNOME은 설정 → 네트워크 → 프록시의 **Ignored Hosts**에 `*.example.test`를 추가한다. Chrome·Chromium은 이
설정을 따르고, Firefox는 자체 네트워크 설정의 **프록시 없음**에 같은 값을 넣는다.

</TabItem>
</Tabs>

터미널의 `curl`은 브라우저 설정이 아니라 `NO_PROXY`를 본다. 같은 접미사를 `.example.test` 형태로 넣는다.
daemon과 build 쪽 프록시 설정은 [Docker Compose 실습 환경](/lab-environment/docker-compose/#회사-프록시-뒤에서-pull과-build-구분하기)에 있다.

## 로컬 CA를 브라우저에 등록하기

실습이 만든 CA를 등록하지 않아도 host마다 한 번씩 인증서 경고를 넘기면 동작한다. 경고 없이 보고 싶을 때만
등록하고, 등록 뒤에는 브라우저를 다시 시작한다. 아래 `ca.crt`와 nickname은 실습 덱이 정한 값으로 바꾼다.

<Tabs syncKey="operating-system">
<TabItem label="macOS">

login keychain에 SSL trust root로 등록한다. 실행하면 암호 확인 창이 뜬다. Chrome·Safari는 keychain을 보고,
Firefox는 설정의 인증서 관리자에서 같은 파일을 가져온다.

```bash
security add-trusted-cert -r trustRoot -p ssl \
  -k ~/Library/Keychains/login.keychain-db path/to/ca.crt
```

</TabItem>
<TabItem label="Ubuntu">

Chrome·Chromium은 OS 인증서 저장소가 아니라 사용자별 NSS DB를 본다. `certutil`은 `libnss3-tools`에 들어 있다.
Firefox는 설정의 인증서 관리자에서 같은 파일을 가져온다.

```bash
sudo apt-get install --yes libnss3-tools
certutil -d sql:$HOME/.pki/nssdb -A -t 'C,,' -n example-lab-ca -i path/to/ca.crt
certutil -d sql:$HOME/.pki/nssdb -L
```

</TabItem>
</Tabs>

:::caution[함정]
실습을 초기화하면 CA가 새로 만들어진다. 옛 CA가 등록된 채로 새 인증서를 열면 다시 경고가 뜨므로,
초기화할 때는 아래 절차로 옛 항목을 지우고 새 파일을 다시 등록한다.
:::

## 등록한 CA 지우기

nickname으로 지운다. 등록할 때 쓴 이름을 그대로 넣는다.

<Tabs syncKey="operating-system">
<TabItem label="macOS">

```bash
security delete-certificate -c example-lab-ca ~/Library/Keychains/login.keychain-db
```

</TabItem>
<TabItem label="Ubuntu">

```bash
certutil -d sql:$HOME/.pki/nssdb -D -n example-lab-ca
```

</TabItem>
</Tabs>

Firefox에 가져온 CA는 인증서 관리자에서 같은 이름을 찾아 삭제한다.

## 안 될 때 어디를 보나

<Steps>
1. 이름 해석부터 본다. `getent hosts` 또는 `dscacheutil`이 `127.0.0.1`을 돌려주지 않으면 hosts 항목 문제다.

2. 프록시를 본다. 터미널의 `curl --noproxy '*' -k https://app.example.test:<port>/`가 되는데 브라우저만 안 되면 브라우저 프록시 예외 문제다.

3. 인증서를 본다. 경고 화면이 뜨는 것은 정상이며 넘기면 된다. 등록했는데도 경고가 뜨면 옛 CA가 남아 있거나 브라우저를 다시 시작하지 않은 것이다.
</Steps>

## 요약

- hosts 항목과 프록시 예외는 필수이고, CA 등록은 경고를 없애는 선택이다.
- 브라우저와 `curl`은 프록시 예외를 다른 곳에서 읽는다. 브라우저는 OS 또는 Firefox 설정, `curl`은 `NO_PROXY`다.
- Ubuntu Chrome은 OS 저장소가 아니라 NSS DB에 CA를 넣는다.
- 실습을 초기화하면 옛 CA를 지우고 새 CA를 다시 등록한다.
